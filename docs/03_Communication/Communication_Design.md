# 通信模块设计

## 概述

Communication Layer 负责与嵌入式设备之间的物理/链路层数据收发，向上（Protocol Layer）提供统一的字节流读写接口。本平台计划支持以下四种通信方式，均需遵循统一的接口设计原则，以保证可互换、可扩展。

## 支持的通信方式

### UART（串口）

- **典型场景**：STM32 / MSPM0 等 MCU 的调试口、日志输出、点对点通信
- **特点**：连接简单，速率有限，需处理波特率、校验位等参数配置
- **职责**：串口的打开/关闭、参数配置、字节收发、断线检测

### USB

- **典型场景**：设备通过 USB 转串口芯片或 USB CDC 方式与上位机通信
- **特点**：即插即用，需处理设备枚举、VID/PID 识别
- **职责**：USB 设备发现、连接建立、数据收发，可能复用 UART 通信逻辑（USB CDC 场景）

### TCP/IP

- **典型场景**：ESP32 等具备网络能力的设备，通过 WiFi 进行数据传输
- **特点**：支持远程/局域网通信，需处理连接超时、断线重连
- **职责**：Socket 连接管理、心跳保活、数据收发

### Bluetooth（蓝牙）

- **典型场景**：低功耗、短距离无线通信场景
- **特点**：需处理设备扫描、配对、连接状态管理
- **职责**：蓝牙设备发现、连接管理、数据收发（经典蓝牙或 BLE）

## 通信模块职责

- 管理与设备的连接生命周期：连接、断开、重连、超时处理
- 提供**统一的字节流收发接口**，屏蔽具体通信介质差异
- 上报连接状态变化（已连接/已断开/异常）供上层感知
- 不负责数据内容的解析，仅保证字节的可靠传输
- 记录通信层面的日志（连接事件、异常事件），便于调试

## 数据流

```
Protocol Layer                Communication Layer              Hardware Device
      │                              │                                │
      │── 待发送字节流 ──────────────>│                                │
      │                              │── 物理层发送 ─────────────────>│
      │                              │                                │
      │                              │<──────── 物理层接收 ───────────│
      │<───── 接收字节流（回调/队列）──│                                │
```

- 下行：Protocol Layer 将编码后的字节流交给 Communication Layer 发送
- 上行：Communication Layer 接收到字节流后，通过回调或数据队列的方式交给 Protocol Layer 解析
- Communication Layer 内部不对字节流内容做任何业务判断

## 接口设计原则

1. **统一抽象接口**：所有通信方式需实现同一套抽象接口（如 `connect` / `disconnect` / `send` / `receive` / `on_data_received` / `on_state_changed` 等概念，具体签名在开发阶段定义），Protocol Layer 与 Application Layer 只依赖该抽象接口，不感知具体通信方式。
2. **异步非阻塞**：数据收发应支持异步/事件驱动方式，避免阻塞 UI 或业务逻辑。
3. **状态可观测**：连接状态变化必须能够被上层监听，便于 UI 展示与异常处理。
4. **错误隔离**：单个通信实例的异常不应影响其他模块或整体程序运行。
5. **可替换性**：新增一种通信方式时，只需实现统一接口，不需修改 Protocol Layer 或 Application Layer 代码。
6. **参数可配置**：波特率、超时时间、重连策略等参数应可配置，不硬编码。

> 本文档仅规划通信模块的设计原则，具体实现将在编码阶段进行，且需遵循 `04_Development/Development_Rules.md` 中的开发约束。
