# 通用通信协议设计规范

## 概述

本协议用于定义上位机与嵌入式设备之间数据帧的统一格式，目的是在支持多种设备（STM32、MSPM0、ESP32 等）和多种通信方式（UART、USB、TCP/IP、蓝牙）的前提下，保持协议解析逻辑的一致性。

> 本文档**仅定义协议设计规范**，不包含具体编解码实现代码。实现应在 `src/protocol/` 模块中依据本规范完成，并在实现文档中注明所依据的协议版本。

## 帧结构总览

```
┌──────────┬───────────┬───────────┬────────────┬─────────────┬──────────┐
│  帧头     │  设备ID    │  命令类型  │  数据长度   │   Payload    │  CRC校验  │
│ (Header) │(Device ID)│  (Cmd)    │ (Length)   │   (Data)     │  (CRC)   │
└──────────┴───────────┴───────────┴────────────┴─────────────┴──────────┘
```

## 字段设计

### 帧头（Header）

- **作用**：标识一帧数据的起始，便于接收方在字节流中进行帧同步
- **设计要求**：使用固定的、不易与正常数据混淆的特征字节（具体取值在实现阶段确定）
- **说明**：接收方在解析时应先定位帧头，再按后续字段长度依次解析

### 设备ID（Device ID）

- **作用**：标识数据帧所属的目标/源设备，用于多设备场景下的路由与区分
- **设计要求**：长度固定，取值范围需保证同一系统内设备 ID 不重复
- **说明**：上位机侧可维护设备 ID 与设备实例的映射关系

### 命令类型（Command Type）

- **作用**：标识本帧数据的功能含义（如读取状态、下发配置、上报数据等）
- **设计要求**：采用分类编码方式，预留扩展区间，便于后续新增命令而不与已有命令冲突
- **说明**：命令类型与 Payload 的具体格式一一对应，需在协议实现文档中维护"命令类型表"

### 数据长度（Length）

- **作用**：标识 Payload 字段的字节长度，便于接收方确定帧的完整边界
- **设计要求**：长度字段本身的位宽需能覆盖预期最大 Payload 长度
- **说明**：接收方应根据该字段判断数据是否接收完整，不完整时应等待后续字节或触发超时处理

### Payload（数据域）

- **作用**：承载具体的业务数据，内容格式由 Command Type 决定
- **设计要求**：格式应与具体命令解耦，允许不同命令定义不同的 Payload 结构（在协议实现文档中单独说明）
- **说明**：Payload 为空时，Length 字段应为 0，帧结构仍然完整

### CRC校验

- **作用**：校验数据帧在传输过程中的完整性，防止因干扰、丢字节等导致的数据错误被上层误用
- **设计要求**：校验范围需在实现阶段明确定义（如是否包含帧头、设备ID等字段），校验算法需统一版本
- **说明**：接收方校验失败时应丢弃该帧并记录日志，不应尝试"修复"或部分使用数据

## 协议设计原则

1. **通用性优先**：协议结构不与具体设备/业务耦合，Command Type 和 Payload 的具体含义由各设备的协议扩展文档定义。
2. **可扩展性**：命令类型编码需预留扩展空间，新增功能不应破坏已有命令的解析逻辑。
3. **健壮性**：必须包含帧同步（帧头）与完整性校验（CRC）机制，能够应对通信过程中的丢字节、干扰等异常情况。
4. **前后兼容考虑**：协议版本变化时，应有明确的版本标识或兼容策略（具体机制在协议成熟后补充设计）。
5. **文档先行**：任何协议字段含义、命令类型的新增或变更，必须先更新本文档或对应的协议实现文档，再进行编码实现。

## 命令类型（Command Type）phase-1 内部约定

> **本表是同步副本，不是权威定义。** 权威在 `src/application/manager.py` 的
> `RESERVED_COMMAND_CODES`（PC 侧）与 `protocol_frame.h` 的 `PROTOCOL_CMD_*`（固件侧），
> 两者的一致性由 `tests/application/test_command_code_contract.py` 自动守护；
> 本表与代码不一致时**一律以代码为准**。放在这里是为了让读协议规范的人不必翻源码，
> 而不是为了多维护一份定义。

| Command Type 取值 | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| `0x01` | `DATA_REPORT_CODE` | 设备 → 上位机 | 设备上报一条数据点，Payload 为 UTF-8 JSON `{"channel": ..., "value": ...}`（phase-1 内部约定，见下方 Payload 说明） |
| `0x02` | `COMMAND_ACK_CODE` | 设备 → 上位机 | 设备对收到的业务命令的应答，Payload 为 UTF-8 JSON `{"status": "success"｜"failed"}` |
| `0x10` | `FAN_ON` | 上位机 → 设备 | **固定编码**（2026-09-07 新增）：启动通风风扇 |
| `0x11` | `FAN_OFF` | 上位机 → 设备 | **固定编码**（2026-09-07 新增）：停止通风风扇 |
| `0x12` | `ALERT_TEMPERATURE` | 上位机 → 设备 | **固定编码**（2026-09-07 新增）：播报"温度超限"语音 |
| `0x13` | `ALERT_HUMIDITY` | 上位机 → 设备 | **固定编码**（2026-09-07 新增）：播报"湿度超限"语音 |
| `0x14` | `ALERT_NOISE` | 上位机 → 设备 | **固定编码**（2026-09-07 新增）：播报"噪声超限"语音 |
| `0x15` | `ALERT_STATE` | 上位机 → 设备 | **固定编码**（2026-09-07 新增）：下发各通道当前是否处于报警的位图，供板载 LCD 显示"正常/报警"。Payload 为 UTF-8 JSON `{"bits": N}`，位序见下表 |
| `0x16` | `ANSWER_SHOW` | 上位机 → 设备 | **固定编码**（2026-09-09 新增）：下发最近一条问答的结果，供板载 LCD 第二页显示。Payload 为六个无符号整数，见下表 |
| `0x17`~`0x1F` | （保留） | — | 预留给后续同样需要被设备**解释**的命令 |
| `0x20` 起 | 业务命令（动态分配） | 上位机 → 设备 | 每个设备首次使用某个 `Command.command_type` 字符串时，由 `DeviceManager.code_for()` 从 `0x20` 起顺序分配一个数值编码；同一设备内同一命令类型始终对应同一编码，编码分配关系不跨设备共享 |

> **为什么要引入"固定编码"这一档（2026-09-07）**：原先所有业务命令都是从 `0x10` 起**按首次使用顺序动态分配**的。
> 在固件只需回 ACK、不解释命令内容的阶段这没有问题；但通风功能要求 MCU 区分"开风扇"和"关风扇"，
> 而一个**取决于本次会话里谁先被发送**的编号无法承载这个含义——同一条命令在两次运行中可能拿到不同的码。
>
> 因此规则调整为：**凡是设备需要解释的命令，必须在两端固定编码**；不需要解释的（如 `PING`，设备只回 ACK）
> 继续动态分配，动态区间上移到 `0x20` 起，与固定区间 `0x10~0x1F` 永不冲突。
>
> 两端的权威定义分别是 `src/application/manager.py` 的 `RESERVED_COMMAND_CODES` 与
> `firmware/stm32f407/Drivers/BSP/PROTOCOL/protocol_frame.h` 的 `PROTOCOL_CMD_*` 宏。
> **这是两个独立编译的程序之间的线上契约，编译器发现不了不一致。**
>
> **不一致不会崩** —— 采集端对不认识的命令照样回 ACK，表现只是某项功能安静地不工作，
> 因此这类错误比崩溃更难发现。2026-09-09 新增第六个码时补了一项自动检查：
> `tests/application/test_command_code_contract.py` 直接读固件头文件、逐条比对两侧数值，
> 并顺带守住"无重复码"与"保留码不越出 0x10~0x1F"。**新增此类命令时仍需人工同步两处，
> 但漏同步现在会被测试挡住。**

#### `ALERT_STATE`（0x15）的 Payload 位图

| 位 | 通道 | PC 侧常量 | 固件侧常量 |
| --- | --- | --- | --- |
| bit0 (`0x01`) | `temperature` | `CHANNEL_BITS` in `src/application/alarm_state_dispatcher.py` | `UI_ALERT_BIT_TEMPERATURE` in `Drivers/BSP/UI_SCREEN/ui_screen.h` |
| bit1 (`0x02`) | `humidity` | 同上 | `UI_ALERT_BIT_HUMIDITY` |
| bit2 (`0x04`) | `noise` | 同上 | `UI_ALERT_BIT_NOISE` |

位为 1 表示该通道当前**处于报警**。多个设备同时上报同一通道时按"或"合并——只要有一路超限，屏幕上那一行就应显示报警。

#### `ANSWER_SHOW`（0x16）的 Payload

Payload 为 UTF-8 JSON，六个无符号整数：

| 键 | 含义 |
| --- | --- |
| `kind` | 答案种类 1~7（当前值/最高/最低/平均/是否越限/阈值/风扇）。PC 侧 `AnswerKind`，固件侧 `UI_ANSWER_KIND_*` |
| `channel` | `0`=温度 `1`=湿度 `2`=噪声 `255`=与通道无关（风扇） |
| `value` | 数值 **×10**（本链路无浮点解析，24.7 传 247） |
| `limit` | 阈值 ×10 |
| `flags` | bit0 越限 / bit1 风扇运行 / bit2 自动模式 / bit3 阈值是上限 |
| `source` | `0`=PC 提问 `1`=移动端提问 |

**为什么下发的不是文本。** 采集端的中文字库是从界面文案自动提取的子集（完整 GBK 需外挂串行 Flash，其总线占用调试接口引脚），画不出任意语句。但这一受限方案带来了一处并非被迫的收益：**上位机侧语言模型对措辞的改写不会影响屏幕**，屏上出现的始终是事实——与问答功能"模型负责表达、系统负责数字"的分工出于同一判断。

负值不予下发：该字段在固件侧为无符号，`-2.0 ℃` 会变成一个很大的正数被满有把握地画出来，因此上位机侧直接拒发，屏幕保留上一页。

PC 侧 `src/application/answer_dispatcher.py`，固件侧 `ui_screen_set_answer()`。

> **为什么位图由 PC 下发，而不是固件自己判定**：阈值只有一份，在 `src/service/sensor_data_processor.py`，
> 论文第 4 章围绕 GB 37488-2019 展开的那套论证也只对应这一份。若固件再实现一套阈值，就会出现第二份
> 数值，两边任何一次调整都可能悄悄分叉，而这种分叉在演示现场表现为"PC 报警了、屏幕还是正常"，
> 极难当场解释。让固件只做显示，是把"唯一事实来源"这条原则贯彻到跨程序边界上。
>
> **为什么 Payload 仍是 JSON**："命令 Payload 一律是 UTF-8 JSON"是本链路已经成文的约定
> （见 `src/application/manager.py` 模块注释）。为一条命令破例改成裸字节，会让协议文档多出一条特例，
> 收益只是省下十几字节。固件侧因此没有引入 JSON 解析器，而是用
> `protocol_payload_get_uint()` 做一次键名扫描取出整数——该函数的局限（不理解嵌套、转义与字符串值）
> 已在其函数注释中如实写明。

**Payload 格式说明**：当前 Simulator/Hardware 两种模式共用的 Payload 是 UTF-8 JSON 文本。

> **2026-09-07 更正**：本段原写作"仅为 phase-1 内部实现约定，不是本文档规范的一部分——真实 STM32 上
> JSON 解析开销较大，预计后续会重新设计更紧凑的二进制格式"。两处均已被实际落地情况推翻：
>
> 1. **STM32 固件沿用了同一套 JSON 约定**（`firmware/stm32f407/User/main.c` 的 `report_channel()`
>    以 `snprintf` 拼出 `{"channel":"...","value":...}`，通道字符串与 `src/device/sensors/channels.py`
>    完全一致），因此它**已经是 PC 与 MCU 之间事实上的双端契约**，不再只是 PC 侧内部约定。
> 2. **二进制格式改造已结案不做**：实机 1 小时连续运行 3489 帧、零丢帧零校验失败，JSON 未构成瓶颈；
>    且按用户 2026-09-07 的指示不再作为后续方向（见 `docs/05_Test/status/论文与交付物记录.md`，2026-09-09 前为 `Project_Status_Context.md` 5.8 节）。
>
> 若将来确需更换 Payload 格式，影响范围的判断依然成立：只涉及
> `src/application/manager.py`/`hardware_runtime.py`、`scripts/virtual_stm32.py` 与固件的
> `report_channel()`，本文档定义的帧结构（帧头/长度/CRC）不受影响。

**设备侧应答义务**：真实设备收到一条业务命令帧后，必须回复一条 `COMMAND_ACK_CODE` 帧（`device_id` 与收到的命令一致），否则上位机侧 `DeviceManager.deliver()` 会在超时（phase-1 实现为 2 秒）后判定本次命令投递失败——这是 Hardware 模式下"指令下发"链路已验证可用的前提，验证过程见 `docs/05_Test/Virtual_STM32_Test.md`。

### 字段位宽与字节序

所有多字节整数一律采用**大端序（网络字节序）**：

```
+--------+-----------+--------------+--------+-----------+-----+
| Header | Device ID | Command Type | Length | Payload   | CRC |
| 2B     | 1B        | 1B           | 2B     | Length B  | 4B  |
+--------+-----------+--------------+--------+-----------+-----+
```

| 字段 | 宽度 | 取值范围 | 说明 |
| --- | --- | --- | --- |
| 帧头 Header | 2 字节 | 固定 `0xAA 0x55` | 固定同步标记，接收方据此定位帧起点 |
| 设备ID Device ID | 1 字节 | `0x00`~`0xFF` | 数值型 wire id；与 Service 层字符串 `DeviceId` 的映射在应用层完成 |
| 命令类型 Command Type | 1 字节 | `0x00`~`0xFF` | 取值约定见上一节"命令类型 phase-1 内部约定" |
| 数据长度 Length | 2 字节 | `0`~`65535` | Payload 字节数；为 0 时帧结构仍完整 |
| Payload | Length 字节 | — | UTF-8 JSON 文本，见上一节 Payload 格式说明 |
| CRC 校验 | 4 字节 | — | 见下 |

### CRC 算法与校验范围

- **算法**：**CRC-32**，采用 Python 标准库 `zlib.crc32`（不引入第三方依赖）；MCU 侧为等价实现，位于 `firmware/stm32f407/Drivers/BSP/PROTOCOL/crc32.c`，两端已逐字节比对一致
- **校验范围**：**设备ID + 命令类型 + 数据长度 + Payload**，即**不含帧头**——帧头是固定同步标记，恒定不变、不携带需要保护的信息
- **存放**：4 字节大端，置于帧尾

### 异常帧处理规范

| 异常 | 处理 |
| --- | --- |
| 帧头不匹配 | 抛 `FrameSyncError`；字节流场景下由 `FrameStreamBuffer` 逐字节重同步，丢弃的前导字节计入错误计数 |
| 长度与实际数据不符 | 抛 `FrameLengthError`；字节流场景下若数据尚未收全则**继续缓冲等待**，不判为错误 |
| CRC 校验失败 | 抛 `ChecksumError`，**丢弃整帧**，不尝试"修复"或部分使用数据 |
| 设备未在超时内应答 | `DeviceManager.deliver()` 等待 `COMMAND_ACK_CODE` 超时（2 秒）后判定本次投递失败，优雅返回失败结果，不影响后续数据流 |
| 收到非期望帧 | wire id 不匹配或命令类型不是 `DATA_REPORT` 的帧被忽略并计入 `ignored_frame_count`，不中断接收循环 |

> **字节流拼帧**：`decode()` 只负责解析"恰好一帧"的字节，**定位帧边界不属于它的职责**。
> 粘包（一次读到多帧）、半包（一帧跨多次读取）与脏字节重同步由
> `src/application/frame_stream.py` 的 `FrameStreamBuffer` 统一处理，
> 这是本项目论文第 6 章的核心内容，实测中该机制暴露并修复过真实缺陷。
