## B. 现有项目源码架构梳理（迁移前提）

当前 `src/` 分为 `core/device/protocol/communication/service/application/api/ui/gateway/llm` 十包，Simulator 与 Hardware 两种模式在 Protocol Layer 及以上完全共用代码，差异仅在 Hardware Device Layer 与 Communication Layer：

```
Simulator 模式：SimulatorDevice + LoopbackChannel
Hardware  模式：RemoteDevice    + SerialChannel
```

与本次硬件落地直接相关的既有实现：

- `src/protocol/frame.py`/`encoder.py`/`decoder.py`：帧头 `0xAA 0x55` + 设备ID(1B) + 命令类型(1B) + 长度(2B大端) + Payload + CRC-32(4B)，**STM32 固件必须按此格式收发**，这是 PC↔STM32 这条链路唯一需要 STM32 侧遵循的协议——本方案不改动这一格式（见 D.5）。
- `src/communication/serial.py`：`SerialChannel`，基于 pyserial，PC 侧已就绪，**无需改动**。
- `src/application/hardware_runtime.py`/`frame_stream.py`：`HardwareDeviceReceiver` + `FrameStreamBuffer`，处理真实字节流的粘包/半包，**已在 WSL+socat 虚拟串口环境验证通过**，PC 侧无需改动。
- `src/application/manager.py`：`DeviceManager.deliver()` 对 `RemoteDevice` 走 `_await_device_ack()`，等待 STM32 回复 `COMMAND_ACK_CODE(0x02)` 帧，2 秒超时——**STM32 固件必须实现"收到业务命令后回复 ACK 帧"这一义务**，否则命令下发会超时失败（这是 `scripts/virtual_stm32.py` 已经验证过的行为约定）。
- `src/device/sensors/{temperature,humidity,noise}.py`：三个 `SimulatorDevice` 预设，**仿真阶段的数据源，硬件迁移后不删除**，继续作为无硬件条件下的回归测试与演示手段。
- `src/service/sensor_data_processor.py`：阈值报警（温度>35℃/湿度 30~75%RH 双向/噪声>80dB，论文第 2 章 2.1 节已论证，依据 GB 37488—2019）、统计（当前/最大/最小/平均），**这套逻辑对数据来源无感知**（Simulator 还是真实 STM32 对它完全一样），硬件迁移不需要改动。
- `scripts/virtual_stm32.py`：当前"虚拟 STM32"角色，字面量硬编码 `DATA_REPORT_CODE=0x01`/`COMMAND_ACK_CODE=0x02`，真实固件需要实现同样的行为约定（见 D.5、D.6）。

**结论**：仿真阶段已验证的软件架构（Protocol Layer 及以上）**完全不需要因为接入真实硬件而改动**——这正是分层架构设计的目的。硬件落地的全部工作量集中在"用真实 STM32 固件代码替换 `scripts/virtual_stm32.py` 这个角色"，PC 侧唯一可能需要的改动是把 `scripts/run_gui.py --mode hardware --port <真实COM口>` 指向真实串口号，属于命令行参数层面，不改代码。

## C. 仿真版本 → STM32 硬件版本 迁移方案（总览）

```
仿真版本（当前已验证）                        STM32 硬件版本（本方案目标）
──────────────────────                        ──────────────────────
TemperatureSensorSimulator  ──┐                真实 AHT20 温湿度传感器（I2C）──┐
HumiditySensorSimulator     ──┼─ SimulatorDevice   真实 HH_07.06 噪声传感器（UART）─┼─ STM32F407 固件
NoiseSensorSimulator        ──┘                （通过软件 I2C + 专用 USART 采集）──┘
        │                                              │
   LoopbackChannel                                SerialChannel
   （内存回环）                                    （USART1，经板载 CH340 USB 转串口）
        │                                              │
        └──────────────── Protocol Layer（帧编解码，双方完全一致）────────────────┘
                                    │
                    Application / Service / API / UI（PC 端，零改动）
```

**迁移原则**（呼应用户"不是重新开发，而是逐步迁移"的要求）：

1. STM32 固件是**新增的独立代码**（C 语言，MDK/HAL 工程），不修改 `src/` 下任何 Python 代码的对外接口。
2. PC 端从 Simulator 模式切到 Hardware 模式，只需换一个启动参数（`--mode hardware --port COMx`），不需要改代码——这是仿真阶段就已经验证过的既有能力。
3. 迁移分阶段进行，每个阶段独立可验证，不要求一次性把三个传感器全部接上才能看到效果（见 J 节"后续开发顺序"）。
4. `scripts/virtual_stm32.py` 在真实固件就绪前继续保留，作为固件行为的"验收基准"（固件的帧格式、ACK 行为应该和这个脚本已验证过的行为完全兼容）。

## D. 关键技术问题确认（依据官方资料，非推测）

### D.1 STM32F407 可使用哪些 UART

STM32F407ZGT6 共有 **6 个串口**（USART1/2/3、UART4/5、USART6，据《探索者V3硬件参考手册》2.1.29 节芯片资源汇总）。开发板上已明确接线关系的三个是：

| 串口 | 引脚 | 板载去向 | 是否可作原始 TTL 使用 |
| --- | --- | --- | --- |
| USART1 | PA9(TX)/PA10(RX) | 经 P10 跳线默认接板载 CH340C（USB_UART Type-C 口），也是一键下载电路所在 | **是**——这正是它默认的用法，PC 通过 USB 线接 USB_UART 口即可，无需额外硬件 |
| USART2 | PA2(TX)/PA3(RX) | 经 P4 跳线在 RS232(COM2) 电平 / RS485 电平之间切换（TP3232/TP8485 电平转换芯片） | 否，默认经过电平转换芯片，**不是原始 TTL**；且 PA2 与网口 ETH_MDIO 共用（本项目不用网口，无冲突，但需记住这一共用关系） |
| USART3 | PB10(TX)/PB11(RX) | 经 P2 跳线在 RS232(COM3) 电平 / ATK-MODULE接口(U17，TTL) 之间切换 | 视跳线位置而定——若不接 P2 任何一侧，PB10/PB11 应仍在 `P7/P8/P9` 主 IO 排针上可用，**具体需拿到实物后核对原理图确认（【待确认】）** |

**结论与建议**：

- **USART1（PA9/PA10）→ STM32 与 PC 的通信**（详见 D.6）：直接复用板载 USB_UART，是最省事、最可靠的选择，且完全匹配本项目现有 `SerialChannel`/`--port COMx` 的使用方式，波特率与 `scripts/run_gui.py` 现有默认值 115200 一致。
- **USART3（PB10/PB11）→ 噪声传感器（UART TTL）**：候选首选，但需要拿到实物后核对"不使用 P2 跳线时，PB10/PB11 是否仍在主排针上以原始 TTL 形式可用"这一点【待确认】。若确认不可用，退回使用 UART4/UART5/USART6 中的任意一个空闲串口（探索者V3 主排针 P7/P8/P9 引出了 102 个 IO，据资料这些串口的引脚大概率也在其中，具体引脚号需要对照完整原理图逐一核实，本方案不猜测）。

### D.2 哪些 GPIO 可以使用

板卡"P7、P8、P9"三组 2×22 排针为"MCU 主 IO 引出口"，共引出 102 个 IO（STM32F407ZGT6 共 112 个 IO，除去 RTC 晶振占用的 2 个，还剩 110 个，主排针引出 102 个，其余 8 个通过 P2/P4/P5/P10 引出）。**已确认被板载其它外设占用、不应视为"空闲"的引脚**（依据手册原文逐条核实）：

- PF9/PF10：LED0/LED1（板载 LED，若需要状态指示灯可直接复用，不需要额外接线）
- PB8/PB9：硬件 I2C1（板载 24C02 EEPROM + ST480MC 磁力计 + ES8388 音频编解码器共享总线，**手册明确不建议再用于其它 I2C 外设**，见 D.4）
- PA2/PA3：USART2（见 D.1，含以太网 MDIO 共用关系）
- PB10/PB11：USART3（见 D.1）
- PA9/PA10：USART1（本方案计划占用，见 D.1/D.6）
- PA11/PA12：USB 与 CAN 共用（本方案不使用 USB Device/CAN，暂不占用）
- PC6：I2S_MCLK 与 OLED/摄像头接口 D0 共用（本方案不用 OLED/摄像头/音频，理论空闲，但存在复用关系需留意）
- SD 卡、TFTLCD、以太网、CAN、RS232/485、SPI FLASH 相关引脚（PC1/PC4/PC5/PA1/PA7/PD3/PG11/PG13/PG14 等以太网引脚，PB12/PB13/PC2/PC3 音频 I2S 引脚等）：本方案均不使用对应外设，理论空闲，但**具体哪些引脚可安全复用为温湿度传感器软件 I2C，需要在拿到实物、对照完整原理图确认后再最终选定**（【待确认】，本方案不在未核实前指定具体引脚号，避免"凭型号猜测引脚"）。

**结论**：GPIO 资源明显充足（102 个主排针 IO，本方案只需额外占用 2 个软件 I2C 引脚），不存在资源紧张的问题，但**具体选用哪两个 GPIO 做软件 I2C，将在拿到开发板实物、核对完整原理图后确定**，届时会更新本文档。

### D.3 I2C/SPI/ADC 等外设如何分配

- **I2C**：AHT20 温湿度传感器需要 I2C（详见 D.5）。**不使用 STM32 硬件 I2C 外设**——原因有二：其一，板载硬件 I2C1（PB8/PB9）已经被 EEPROM/磁力计/音频编解码器占用，手册明确建议避免复用；其二，ATK-MB016 官方驱动本身就是用软件模拟 I2C（`myiic.c`，非 HAL 库 I2C 外设）实现的，本方案沿用同样的技术路线（软件 I2C，GPIO 位翻转实现），既符合官方参考实现，又避免了 STM32 硬件 I2C 外设已知的稳定性问题（手册原话"STM32 的 IIC 是鸡肋"）。
- **SPI**：本方案当前不需要任何 SPI 外设（不使用 SPI FLASH、不使用 TFTLCD 触摸屏等 SPI 设备）。
- **ADC**：本方案当前不需要 ADC——三个传感器（AHT20 温湿度、HH_07.06 噪声）均为数字接口输出（I2C / UART），不是模拟电压输出，STM32 不需要做模数转换。

### D.4 噪声传感器采用什么通信方式

**串行 TTL-3.3V（UART）**，非 RS-485、非 I2C（依据《噪声检测模块(HH_07.06)应用手册V1.2》1.1/1.3/1.4 节）：

- 4 芯接口：1=电源正(5-24VDC)、2=电源负(GND)、3=串行数据发送端(TXD)、4=串行数据接收端(RXD)
- 默认波特率 115200，可配置为 9600/19200/38400/57600/115200，8 位数据位、1 位停止位、无校验（8N1）
- 支持三种协议模式（需通过配套配置工具预先设置好模式与波特率，之后固件按对应协议解析）：
  1. **主动模式**：上电即持续主动上报，帧格式 `起始符(BB AA) + 命令(1B) + 数据(2B，声压级×0.1dB，低位在前) + 校验(1B，算术和校验)`，无地址概念，无需 STM32 主动发起读取。
  2. **被动模式**：STM32 主动发起、模块应答，帧格式 `地址(1B) + 命令(1B) + 数据(4B) + CRC16(2B，CRC16_MODBUS 算法)`，固定 8 字节，支持读设备信息(命令1)/读噪声值(命令2)/设置地址(命令3)/设置波特率(命令4)；地址范围手册中两处表述不一致（技术参数表写"1-247"，3.2.1 节正文写"1-47"）；**2026-08-19 用户确认以后出版本为准，取 1-247**（该值亦与 Modbus RTU 规范的从站地址范围一致，"1-47"应为旧版手册的笔误）。
  3. **ModbusRTU 模式**：符合标准 Modbus RTU，用 03H 功能码读保持寄存器（协议地址 `0x0000`，寄存器数量 1），返回 2 字节声压级数据。
- 每次测量响应时间约 400ms（模块内部运算周期，不是通信延迟）。

**本方案建议**：采用**被动模式**（STM32 主动发起读取），理由：（1）与本项目 PC↔STM32 链路"命令下发必须等待 ACK"的既有设计哲学一致——被动模式的"发送命令→等待应答"结构，STM32 侧的实现经验可以直接复用到 PC↔STM32 那一层积累的经验；（2）CRC16_MODBUS 校验、地址、错误代码机制均已就绪，比主动模式的简单算术和校验更符合"验证通信协议稳定性"这一论文核心目标（第 4 章 CRC 校验一节可以同时覆盖 PC↔STM32 的 CRC-32 与 STM32↔噪声传感器的 CRC16，形成对照）。**ModbusRTU 模式作为备选**——若后续希望论文额外体现"遵循工业标准协议"这一点，可改用该模式，两种模式对 STM32 侧代码的影响仅限于噪声传感器驱动这一个文件，不影响其余架构。**最终选用哪种模式，建议在确认本方案时一并决定**。

### D.5 温湿度传感器采用什么通信方式

**I2C（标准 I2C 协议）**，非 UART（依据《AHT20说明书》与 ATK-MB016 官方驱动源码）：

- ATK-MB016 模块接口：VCC、GND、SDA、SCL 四线
- 传感器芯片为 AHT20，I2C 地址（8 位写地址）为 **0x70**（对应 7 位地址 0x38），已从官方驱动源码 `atk_aht20.h` 的宏定义 `#define ATK_AHT20_IIC_ADDR 0x70` 直接确认，非猜测
- 官方驱动读取流程：上电等待 5ms → 发送初始化命令 `0x08 0x00` → 延时 500ms → 发送测量命令 `0xAC 0x33 0x00` → 延时 80ms → 读取 7 字节原始数据（状态字 1B + 湿度 20bit + 温度 20bit + CRC8 1B）→ 按公式换算为浮点温度/湿度值
- I2C 时序：标准模式最高 100kHz、快速模式最高 400kHz；官方建议"采集数据周期应大于 1 秒/1 次"以避免自身温升影响测量精度
- 电源：2.2~5.5V（探索者V3 板载 3.3V 电源可直接供电）

**本方案建议**：采用软件模拟 I2C（沿用官方驱动 `atk_aht20.c`/`myiic.c` 的实现思路，仅需将 F103 例程中的引脚定义改为 F407 板上实际选定的空闲 GPIO，见 D.2），采样周期建议 ≥1 秒。

### D.6 后续与 PC 通信采用什么接口

**USART1（PA9/PA10），经开发板板载 CH340C 芯片转为 USB，PC 侧看到一个标准 COM 口**（详见 D.1）。这条链路**完全复用本项目已实现、已验证的 `src/protocol/`（帧编解码）+ `src/communication/serial.py`（`SerialChannel`）+ `src/application/hardware_runtime.py`（`HardwareDeviceReceiver`+`FrameStreamBuffer`）**，STM32 侧固件只需要按 `docs/03_Communication/Protocol_Design.md` 定义的帧格式（帧头 `0xAA 0x55` + 设备ID(1B) + 命令类型(1B) + 长度(2B大端) + Payload + CRC-32(4B)）收发数据，不需要了解 PC 侧 Python 代码的任何实现细节——这正是 `docs/05_Test/Hardware_Simulation_Mode.md`"未来 MCU 只需实现的最小集合"一节早已规划好的边界。波特率建议与 PC 侧默认值保持一致（115200）。

### D.7 是否需要 FreeRTOS

**当前阶段不需要**。理由：

- 本方案的固件工作内容——周期性读取两个数字传感器（I2C/UART）、维护一路 UART 与 PC 通信、按协议组帧收发——是典型的"轮询 + 简单状态机"即可胜任的规模，不存在需要抢占式多任务调度、任务间同步（信号量/消息队列）的复杂度
- 遵循用户明确要求（第 E 条："不要为了看起来完整而引入 FreeRTOS 等复杂组件，只有在项目实际需要时才使用"）
- 若未来功能显著增加（如同时驱动多个高频外设、需要精确的多任务时间片调度），可以再引入，当前不做超前设计

### D.8 是否需要 DMA

**建议按需使用，非强制**：

- USART1（PC 通信）：若后续观察到高频率数据收发导致 CPU 中断负担明显，可以给 USART1 接收配置 DMA + 空闲中断（这是 HAL 库串口通信的常见成熟方案，`探索者开发指南` 有配套章节）；**第一版实现建议先用中断方式跑通功能，验证稳定后再视需要引入 DMA 优化**，避免过早引入复杂度
- 温湿度/噪声传感器：数据量极小（每次几字节到十几字节），完全不需要 DMA

### D.9 是否需要中断

**需要，且是必需的**（不是可选项）：

- USART1 接收中断（或 DMA+空闲中断）：PC 主动下发命令是异步事件，STM32 必须能够在命令到达时及时响应并回复 ACK，不能靠轮询等待
- 噪声传感器若采用主动模式，同样需要 UART 接收中断持续接收模块主动上报的数据帧
- 定时器中断（可选但建议）：用于产生"周期性采集温湿度/上报数据"的时基，比 `HAL_Delay()` 阻塞式延时更可靠

### D.10 哪些功能应该由 STM32 完成，哪些继续由 PC 完成

严格延续现有分层架构的职责边界（不因硬件落地而改变）：

| 职责 | 归属 | 说明 |
| --- | --- | --- |
| 传感器原始数据读取（I2C/UART 时序） | **STM32** | 只有 STM32 能直接访问物理传感器 |
| 按协议帧格式组帧/解帧、CRC-32 计算 | **STM32（组帧发送侧）+ PC（解帧接收侧，已实现）** | 帧格式定义权威来源是 `docs/03_Communication/Protocol_Design.md`，双方各自独立实现编解码，不共享代码（与 `scripts/virtual_stm32.py` 的既有设计哲学一致） |
| 命令 ACK 应答 | **STM32** | 收到业务命令后必须回复 `COMMAND_ACK_CODE(0x02)` 帧，否则 PC 侧 2 秒超时判定失败 |
| 数据统计（当前/最大/最小/平均） | **PC（`SensorDataProcessor`，已实现）** | 不在 STM32 重复实现，STM32 只负责"如实上报原始读数" |
| 阈值报警判定 | **PC（`SensorDataProcessor`，已实现）** | 阈值规则、报警状态机均在 PC 侧，STM32 不做业务判断，只做数据采集与传输 |
| 实时曲线/历史记录/UI 展示 | **PC（`ui/`，已实现）**，后续 **Android（只读展示）** | STM32 不做任何展示 |
| 设备管理指令（PING/RESET/CONFIG_GET/CONFIG_SET/FW_UPDATE） | **STM32 接收并执行对应动作，PC 发起** | 现有 `ControlPanelWidget` 已支持这六种命令类型的下发，STM32 固件需要针对每种命令实现相应的响应逻辑（例如 RESET 触发软复位、PING 只需回 ACK 即可） |
| 环境执行器控制（如自动调节通风/除湿） | **均不实现** | 呼应此前"项目定位收敛"结论：系统边界是"监测+预警+设备管理"，不包含环境自动干预，STM32 不需要驱动任何执行器 |

## E. 数据帧格式（复用现有协议，STM32 侧新增内容仅限固件实现）

不新增、不修改协议规范本身，STM32 固件需要实现的完整取值集合：

```
帧头(0xAA 0x55, 2B) + 设备ID(1B) + 命令类型(1B) + 数据长度(2B大端) + Payload(变长) + CRC-32(4B, 覆盖 设备ID+命令类型+长度+Payload)
```

- **命令类型**：`0x01`=数据上报(STM32→PC)，`0x02`=命令应答(STM32→PC)，`0x10` 起=业务命令(PC→STM32，由 PC 侧 `DeviceManager.code_for()` 动态分配，STM32 侧只需识别收到的数值并按需响应，不需要预先知道分配规则)
- **Payload**（当前 phase-1 沿用 PC 侧既有的 JSON 文本约定，**是否要为真实固件改成更紧凑的二进制格式，留到 D.7~D.9 验证完基本链路稳定后再评估，不在本次方案中预先决定**）：
  - 数据上报：`{"channel": "temperature"|"humidity"|"noise", "value": <数值>}`
  - 命令应答：`{"status": "success"|"failed"}`
- **设备 ID**：STM32 固件侧对自身 wire id（0-255）需有固定认知，与 PC 侧启动参数 `--device-id` 约定一致（当前 `scripts/run_gui.py` 的 Hardware 模式固定分配为 `1`，见 `docs/05_Test/Virtual_STM32_Test.md`）

## I. 电源与电平注意事项

依据官方资料明确列出的电气约束：

1. **噪声传感器 HH_07.06**：供电 5-24VDC（宽电压），但**通信接口是 TTL-3.3V**——供电和通信电平是两回事，接线时电源可以用板载 5V 排针（VOUT2），通信线必须直接接 STM32 的 3.3V TTL 电平 GPIO，不需要电平转换。
2. **AHT20（ATK-MB016）**：供电 2.2~5.5V，可用板载 3.3V 或 5V 均可；**通信是标准 I2C 电平（3.3V 系统下即 3.3V TTL）**，需要外部上拉电阻（若模块板上已集成上拉则不需要额外加，需拿到实物核实模块板上是否已有上拉电阻，【待确认】）。AHT20 说明书明确要求"VDD 需加 RC 滤波电路"，模块化产品(ATK-MB016)通常已在模块板上处理好，仅需确认。
3. **STM32 侧 GPIO 输入电平**：STM32F407 GPIO 为 3.3V 系统，两个传感器通信电平均为 3.3V TTL，**不存在电平不匹配问题**，不需要额外电平转换芯片——这是本方案选择这两款传感器模块（而非 RS-485/RS-232 电平的模块）的天然优势。
4. **USART1/CH340 链路**：无需关心，板载电路已处理好 USB 5V 到板卡 3.3V 系统的转换。
5. **共地**：两个传感器模块与 STM32 板必须共地（GND 相连），这是所有非隔离通信接口的基本要求，接线时需注意。

## J. 后续开发顺序（建议）

严格遵循用户第十条"从现在开始，优先保证：真实STM32接入→三种传感器→数据稳定采集→PC实时监测→异常报警→历史数据→Android远程查看→实验验证→论文材料"的顺序，细化为可验证的阶段：

4. **噪声传感器接入**：接入 HH_07.06（按 D.4 选定的协议模式实现驱动），验证真实读数正确上报
5. **命令下发验证**：验证 PC 侧"发送命令"能收到 STM32 的真实 ACK 应答，覆盖 PING 等既有命令类型

7. **PC 实时监测确认**：确认现有 UI（实时数据表、曲线、统计信息面板）在真实数据下正常工作，预期不需要改代码
8. **异常报警验证与阈值重新论证**：结合真实环境数据，评估温度 35℃/湿度 30%/噪声 80dB 三个阈值是否需要调整（呼应"项目定位审查"第 6 条）
9. **历史数据/长时间运行验证**：收集通信稳定性数据（丢包率、CRC 错误率等），作为论文第 5 章实验数据的主要来源
10. **Android 远程查看端开发**：待 PC 端与 STM32 链路稳定后再启动，届时再评估是否需要引入 ATK-MB026 WiFi/BLE 模块

- `Drivers/BSP/AHT20/aht20.c`：**字节级通信序列完整比对了官方驱动 `atk_aht20.c`**（`atk_aht20_write_nbytes`/`read_nbytes`/`init`/`check` 四个函数的地址、命令字节 0xBE/0xAC、参数字节 {0x08,0x00}/{0x33,0x00}、状态位判定逻辑均逐行核对一致），并在官方驱动基础上**新增了 CRC8 校验**（官方 Demo 本身没做这一步）——多项式 0x31、初始值 0xFF，取自 AHT20 说明书 5.2 节给出的参考代码，温湿度换算公式已用说明书自带的"ST=0x2FFAB → -12.5℃"这个 worked example 核对通过
- `Drivers/BSP/DEBUG_LOG/debug_log.c`：USART2（PA2/PA3，对应板载 RS232 COM2 接口）调试日志输出，与 USART1（PC 协议）、USART3（Modbus）完全独立，不接调试线也不影响固件运行
- `Drivers/BSP/SENSOR_DATA/sensor_data.h`：统一的传感器读数结构体
- `main.c` 重写为完整的采集周期状态机：每 3 秒一轮，异步等待噪声传感器 Modbus 应答（不阻塞 PC 链路响应）→ 应答落定后阻塞式读取 AHT20（约 80~100ms）→ 三个通道（`temperature`/`humidity`/`noise`，与 PC 端 `src/device/sensors/channels.py` 的 channel 字符串完全一致）分别上报给 PC；AHT20/噪声传感器初始化或读取失败不会让固件卡死或影响另一路传感器与 PC 链路，只是该周期跳过上报该通道（`valid=0`）

**软件验证情况（如实说明，不夸大）**：CRC-32、协议帧编码、Modbus CRC16、Modbus 请求/响应解析、AHT20 数据换算与 CRC8 五处纯逻辑，均已用 Python 等价实现或手册/官方驱动给出的真实数据核对，可信度较高。但 `noise_usart.c`（寄存器级 IDLE 中断处理）、`soft_i2c.c`（GPIO 位翻转时序）、`board_uart_msp.c`（三路 UART 复用）这三处强依赖 STM32 硬件寄存器行为的代码，**在真实电气环境下的正确性尚未验证**——真实 UART/I2C 时序、真实传感器返回数据必须等硬件到货后实测，如遇问题需据此针对性修改，这是当前阶段无法绕过的限制，不代表代码已知有缺陷。

## 扩展外设：通风风扇 ATK-MB023（2026-09-07 新增；2026-09-08 实机验证通过，并改为 PWM 调速）

| 项 | 内容 |
| --- | --- |
| 模块 | 正点原子 ATK-MB023 小风扇模块，驱动芯片 SS6285L |
| 接口 | 1*4 排针：`VCC(3.3~5V)` / `GND` / `FI`(前进输入) / `BI`(后退输入) |
| 接线 | `VCC → 5V`、`GND → GND`、`FI → PE5`、`BI → PE6` |
| 驱动方式 | **FI 由 TIM9_CH1 输出 20kHz PWM 调速（60% 占空比 + 150ms 启动脉冲），BI 恒为低**。2026-09-08 由“两个普通 GPIO 全速开关”改来——实机发现转速过快且有过热保护风险，详见下方“实机调试记录”第三节。PE5 的 AF3 正是 TIM9_CH1，改动不涉及任何接线 |
| 固件 | `Drivers/BSP/FAN/fan.c` / `fan.h`；`main.c` 中 `fan_init()` 初始化、`handle_incoming_pc_frame()` 处理 `PROTOCOL_CMD_FAN_ON`/`FAN_OFF` |

**为什么不照抄厂商例程**：官方例程（M48Z-M3 最小系统板 F103 版）用 `TIM1_CH1(PA8)` + `CH1N(PB13)` 输出互补 PWM，目的是支持正反转与调速。放到探索者V3 上这两个脚都不干净——PA8 是摄像头 XCLK + 红外接收头，PB13 是 ES8388 的 SCLK。而本项目不需要反转和调速，改用两个普通 GPIO 后既省掉一路定时器通道，选脚也自由得多。

**PE5/PE6 的选择依据**：《探索者V3 硬件参考手册》表 1.2.2.1 中两者均标注为"可做独立 IO"（Y），仅连接到 OLED/CAMERA 接口的 D6/D7，而本项目不接摄像头；且与 LCD 占用的 PE7~PE15 不重叠，与 AHT20 软件 I2C 占用的 PE0/PE1 也不重叠。

> ⚠ **安全约束**：SS6285L 的 FI 与 BI **绝不能同时为高**（刹车/直通状态）。驱动通过"BI 恒低、只切换 FI"从结构上排除这种情况。
>
> ✅ **已确认（2026-09-07，用户对照实物）**：**PE5/PE6 未被占用**，插上 2.8 寸 LCD 后也不会被屏幕遮挡，**不需要改选引脚**。原列的前两项待确认（排针位置、是否被屏幕遮挡）就此闭环，风扇引脚方案定稿为 FI=PE5 / BI=PE6。
>
> ☆ **仍待实机确认**：电机启动电流下的供电是否充足（建议改用板载 DC6~15V 适配器供电，不要靠 USB 取电）。

### 引脚冲突核查结论

| 与之比对的既有外设 | 占用 | 是否冲突 |
| --- | --- | --- |
| AHT20 软件 I2C | PE0 / PE1 | **否**（见下） |
| 通风风扇 | PE5 / PE6 | 否（FSMC 只用 PE7~PE15） |
| 噪声传感器 USART3 | PB10 / PB11 | 否 |
| PC 链路 USART1 | PA9 / PA10 | 否 |
| 调试日志 USART2 | PA2 / PA3 | 否 |
| ES8388 + I2S2 | PB8/PB9(IIC)、PB12/PB13、PC2、PC6 | 否 |

> **PE0/PE1 与 LCD 的共存（重新论证）**：本项目最初把 AHT20 的软件 I2C 放在 PE0/PE1，理由是
> "本项目不引入 FSMC 外设"。引入 LCD 后这个前提**已经不成立**，因此重新核查，改用不依赖该前提的依据：
>
> 1. 厂商 LCD 驱动的 `HAL_SRAM_MspInit()`（`Drivers/BSP/LCD/lcd.c`）**逐个引脚列举**要配成 FSMC 复用的脚——
>    GPIOD 的 0/1/8/9/10/14/15 与 GPIOE 的 7~15，**不含 PE0/PE1**；`lcd_init()` 另行配置的 CS/WR/RD/RS/BL 也不在这两个脚上。
> 2. PE0/PE1 的 FSMC 功能是 `NBL0/NBL1`（字节通道选通），只有按**字节**访问外部 SRAM 时才需要；
>    LCD 走 16 位 NOR/PSRAM 时序、整字读写，用不到字节选通。
>
> 结论没变（PE0/PE1 在本项目中始终是普通 GPIO），但依据从"我们不用 FSMC"换成了"用了 FSMC 也不碰这两个脚"——
> 后者不会再被下一次功能扩展推翻。**该结论是源码级静态核查，尚未实测**：接屏后第一次上电应先确认 AHT20 仍能正常读数。

### 屏幕内容与职责边界

横屏 320x240，**分两页**（2026-09-09 起），由标题栏右侧的「数据」「问答」页签切换；标题栏与底栏两页共用：

- 标题栏：站点名 + 链路状态 + 两个页签
- 正文区（y 26..193）：第一页是三行数据行（标签 / 2 倍放大的数值 / 单位 / 正常·报警·无效）；第二页是最近一条问答（种类 + 数值 + 是否越限 + 阈值 + 来自本机还是手机）
- 底栏：风扇状态 + 「语音自检」按钮

**屏幕上显示的每一项都是固件确实知道的状态**，没有一项是屏幕自己推断的：

| 显示项 | 来源 |
| --- | --- |
| 三个数值 | 本机采集结果，与上报给 PC 的是同一份 |
| 正常 / 报警 | 上位机经 `ALERT_STATE`(0x15) 下发，阈值只有 PC 一份 |
| 无效 | 本周期该通道 `valid == 0`（如噪声消隐、AHT20 读失败） |
| 风扇 运行 / 停止 | `fan_is_running()`，是本机执行的结果 |
| 播报 | `audio_alert_is_playing()` |
| 已连接 / 未连接 | 是否曾收到过上位机的帧 |

> ⚠ **"已连接"的准确含义是"已与上位机握手"，不是"此刻链路仍然通畅"**。本链路的上位机只在状态变化时才下发命令，
> 长时间没有下行帧是正常稳态而非掉线，用超时判断会误报，所以刻意不做超时回落。要做成真正的实时链路指示，
> 需要 PC 周期性发心跳，代价是每个采集周期多一次命令往返，会挤占留给 Modbus 应答的等待窗口——暂不引入。

### 「语音自检」按钮

现场噪声很难自然超过 80dB，温湿度也不便临时改造，演示时需要一个能确定性地让喇叭出声的入口。按一次播一句，三句轮换。

**它不经过 PC，也不上报 PC**：自检不是告警，不进告警日志、不计入论文第 5 章统计的告警次数、不消耗 PC 端 30 秒冷却窗口——
统计口径要干净，这与噪声消隐时"跳过 Modbus 请求"而不是"请求了再丢掉"是同一个原则。
但它照样触发噪声消隐，因为消隐的判据是 `audio_alert_is_playing()`，与这段声音是谁请求的无关。

### 中文字库：内嵌子集，不外挂 SPI Flash

屏幕文案共 **59 个**汉字/全角符号，24x24 点阵，**4484 字节**，直接编进内部 Flash。（2026-09-09 加入第二页后由 34 字 2584 字节增至此数；`python scripts/hz_font_to_c.py` 会扫描 `UI_TXT` 字面量自动重新生成。）

生成方式：`scripts/hz_font_to_c.py` 扫描 `Drivers/BSP/UI_SCREEN` 下所有 `UI_TXT("...")` 字符串字面量，
提取其中的非 ASCII 字符，用 SimHei 渲染成点阵。字符集**不是手工维护的清单**——改了屏幕文案重新运行一次脚本即可，
不会出现"加了字忘了加字库"。中文注释不会被扫进来，因为扫描器只认 `UI_TXT(...)` 里的字面量。

改文案后重新生成：

```bash
python scripts/hz_font_to_c.py            # 重新生成 hzfont.c
python scripts/hz_font_to_c.py --dry-run  # 只看字符集与体积
```

> **为什么不用完整 GBK 字库**：完整字库 250KB 以上，只能外挂 W25Q128 SPI Flash，而那条 SPI 会占用
> `PB3/PB4`（JTDO/NJTRST），要禁 JTAG 才能用。**在答辩前把自己的调试通道砍掉，风险和收益完全不成比例**——
> 一旦固件跑飞就只剩 BOOT0 串口下载一条路。将来 AI 问答需要显示任意中文时，方案是由 PC 把渲染好的点阵下发
> （PC 有完整字体，MCU 只负责贴图），依然不需要外部字库。

### 顺带修复：printf 半主机依赖

厂商 `lcd.c` 在 `lcd_init()` 末尾有一句 `printf("LCD ID:%x\r\n", lcddev.id)`。本工程没有启用 MicroLIB
（`.uvprojx` 里 `useUlib=0`），ARM Compiler 5 的完整 C 库在没有重定向时会用**半主机**实现 printf——
半主机靠调试器接管 SVC 指令完成 I/O，**脱机运行（烧录后拔掉调试器直接上电）时那条 SVC 无人应答，程序当场停住**。
`lcd.c` 里那句"会卡死在 printf"的注释说的正是这件事。

因此在 `Drivers/BSP/DEBUG_LOG/debug_log.c` 中补了标准输出重定向：声明 `__use_no_semihosting` 断掉半主机依赖，
把 `fputc` 接到 USART2 调试串口。顺带的好处是厂商那句 `LCD ID:9341` 会真的打印出来，屏幕不显示时可据此
判断到底是没检出屏、还是检出了但没画上去。

### 一、编译期的三个坑（都与"引入厂商驱动"有关）

#### 1. UTF-8 中文字符串在 armcc 下被拆散 → 必须加 `--no_multibyte_chars`

**现象**：`ui_screen.c` 报 13 个错，主要是 `#8: missing closing quote`，指向含中文的 `UI_TXT("...")` 行，同时伴随 `#870-D: invalid multibyte character sequence`。

**根因**：armcc 默认按**系统 locale**（中文 Windows = GBK）解析多字节字符。把 UTF-8 的"地铁站环境监测"按 GBK 读，最后一个字节 `0x8B` 被当成 GBK 前导字节，而紧跟其后的结束引号 `"`(0x22) 不是合法的 GBK 尾字节——于是编译器把**引号本身吃掉了**，报"缺少结束引号"。

报错信息完全指不到真正原因，这是它难查的地方。

**验证过程**（本机装有 armcc，直接做了对照实验，不是推断）：

| 编译选项 | `ui_screen.c` | 全工程 46 个 `.c` |
| --- | --- | --- |
| 无（默认） | 13 errors | 失败 1 个 |
| `--locale=C` | 0 error，**123 warnings** | — |
| **`--no_multibyte_chars`** | **0 error 0 warning** | **失败 0 个** |

最后一列是关键：该选项是全局的，需确认它不会反过来搞坏 GBK 编码的厂商文件（GBK 尾字节可能是反斜杠，关掉多字节处理理论上可能导致行拼接）。**实测 46 个文件全过**，包括全部 GBK 厂商驱动。

已写入 `.uvprojx` 的 C 编译器 Misc Controls（只改 `<Cads>` 段，汇编器不动）。

> 这条对任何"在中文 Windows 上用 Keil + UTF-8 源码写带中文界面"的项目都适用。

#### 2. `lcd_ex.c` 不能加进工程

**现象**：链接期 `L6200E: Symbol lcd_ex_*_reginit multiply defined (by lcd_ex.o and lcd.o)`，七个符号。

**根因**：厂商 `lcd.c` 第 39 行有 `#include "./BSP/LCD/lcd_ex.c"`——**把 .c 当头文件包进来了**。再把它作为独立编译单元列入工程，就有两份定义。

佐证：**厂商自己的工程文件里 `lcd_ex.c` 出现次数为 0**，他们知道不能加。

已全工程扫描确认只此一例（`grep '#include ".*\.c"'`）。

#### 3. 厂商驱动 include 了本项目没有的 `SYSTEM/usart/usart.h`

`lcd.c` / `gt9xxx.c` / `ft5206.c` 都 include 它，但**真正需要的只是 `printf` 的声明**。

本项目未沿用厂商 usart 模块（USART1 归 `BSP/PC_LINK`，USART2 归 `BSP/DEBUG_LOG`）。为守住"厂商文件一字不改"的纪律，没有删它们的 include，而是新增 `Drivers/SYSTEM/usart/usart.h` 垫片，只 `#include <stdio.h>`。

垫片**刻意不提供** `USART_UX` / `g_uart1_handle` / `g_usart_rx_buf` 等符号：谁真用到就应该编译期报错并改用 PC_LINK/DEBUG_LOG，而不是悄悄链到一份平行的串口实现上。

### 二、触摸完全无响应——两个原因叠加

这是本轮最费时的问题，表现是"屏幕正常显示，但怎么点都没反应"。实际有**两个独立原因**，症状完全一样。

#### 原因 A：`tp_scan()` 的返回值恒为 0

厂商实现：

```c
static uint8_t tp_scan(uint8_t mode)   /* 返回 uint8_t */
{
    ...
    return tp_dev.sta & TP_PRES_DOWN;  /* TP_PRES_DOWN = 0x8000 */
}
```

按下时 `0x8000` 截断成 `uint8_t` 就是 **0**——这个返回值永远为假。

厂商自己的例程从不看它，一律是「先 `tp_dev.scan(0)`，再单独判 `tp_dev.sta & TP_PRES_DOWN`」（见实验28 `main.c` 第 129/131 行）。本项目最初写的是 `if (tp_dev.scan(0))`，照抄了函数名却没照抄用法。

**教训**：引入厂商驱动时，不能只看函数签名，必须核对**厂商自己是怎么调用它的**。

#### 原因 B：出厂遗留的竖屏校准数据

`tp_init()` 只在 24C02 中**没有**校准标记（偏移 52 处不等于 `0x0A`）时才执行校准。而开发板出厂测试程序很可能已经写过一份校准值——**那份是在竖屏下做的**，本项目跑横屏（`lcd_display_dir(1)`），坐标换算方向不同。

结果是：校准数据"存在且合法"，于是永远不会重新校准；但换算出的坐标落在别处，表现同样是"点了没反应"。**厂商代码没有任何机制能察觉这种情况。**

**解决**：`ui_screen_poll()` 中检测板载 **KEY0（PE4，低电平有效）**，按下即调 `tp_adjust()` 强制重新做五点校准，完成后整屏重绘。

两个设计选择值得记：

- **放在 poll 而不是 init**。最初只在 `ui_screen_init()` 里查一次，要求上电那一瞬间正好按住，运行中按毫无反应——用户无从判断是"固件没这功能"还是"没按对时机"。厂商例程也是在主循环里查 KEY0，改为随时可触发。
- **不做自动强制校准**。`tp_adjust()` 是阻塞的，要点满五个点才返回；若触摸硬件本身有问题，自动强制会让整机卡死在校准界面，而本机主职责是采集上报，不能因为一块屏幕停摆。做成显式人工触发。

> PE4 在本项目中空闲：PE0/PE1 给 AHT20，PE5/PE6 给风扇，PE7~PE15 给 FSMC。

### 三、风扇全速过快 → 改 TIM9 PWM 调速

**现象**：`fan_set(1)` 把 FI 直接拉高 = 100% 全速，实测转速过高，持续运行一段时间后驱动可能进入过热保护。

本项目要的是**持续换气**而不是最大风量，全速既没必要也不可持续。

**解决**：改用 PWM。关键发现是 **PE5 在 STM32F407 上的 AF3 正是 TIM9_CH1**，而 TIM9 全项目未被占用（此前唯一提及是 `fan.h` 里"为什么不用 TIM1"那段注释）——所以**接线一根都不用动**。

| 项 | 值 |
| --- | --- |
| 定时器 | TIM9_CH1（PE5，AF3） |
| PWM 频率 | 20 kHz（`PSC=0, ARR=8399`，APB2 定时器时钟 168MHz），高于人耳上限，无啸叫 |
| 默认占空比 | **60%**（`FAN_DEFAULT_DUTY_PERCENT`） |
| 启动脉冲 | 150 ms 满占空比后落到设定值（`FAN_KICKSTART_MS`） |

启动脉冲的必要性：直流电机启动转矩需求高于运行时，直接给 60% 可能通电不转。这里阻塞 150 ms 可以接受——风扇启停只在阈值穿越时发生，远低于每个采集周期都要阻塞 80~100 ms 的 AHT20 读取，为它单开非阻塞状态机得不偿失。

BI(PE6) 仍是恒低的普通 GPIO，从结构上保证 FI/BI 不会同时为高（SS6285L 的刹车态）。

需在工程中加入 `stm32f4xx_hal_tim.c` 与 `stm32f4xx_hal_tim_ex.c`。

### 四、Keil 会覆盖 `.uvprojx` —— 已加自动校验

Keil 把工程模型读进内存，退出/保存时整体写回。**在 Keil 打开着的时候用编辑器改 `.uvprojx`，改动会被静默覆盖**。本项目已因此被坑两次：

- 2026-09-07：漏掉 `stm32f4xx_hal_i2s.c`，链接期报 undefined symbol
- 2026-09-08：漏掉 `stm32f4xx_hal_tim.c`，同样表现

两次都是编译报错之后才发现，而报错信息指向的是 HAL 内部符号，与真正原因（工程文件被回写）毫无关联。

**已把"工程该长什么样"写成可执行断言**：

```bash
python scripts/check_keil_project.py
```

校验 6 个必需 HAL 源文件、9 个必需分组、9 个驱动文件、1 个必须**排除**的文件（`lcd_ex.c`）、1 个必需编译选项。只读不改，返回码 0 = 一致。**建议每次从 Keil 退出后执行一次。**

### 五之二、LCD 第二页：最近一条问答（2026-09-09）

标题栏右侧加了「数据」「问答」两个页签，正文区（y 26..193）按页签切换，
标题栏与底栏两页共用——「语音自检」在哪一页都按得到。

**为什么是分页而不是下拉滚动。** 这块是**电阻屏**：单点、需按压、没有惯性滚动，
而拖动恰恰是最吃触摸校准误差的操作——校准误差在本项目里已经是踩过的坑（见第五节 KEY0 那段）。
离散页签按偏几个像素照样命中；滚动还要维护偏移量与局部重绘，代价和风险都更高。

**下发的不是文本，是「哪一类答案 + 数值」。** 新增命令码 `0x16 PROTOCOL_CMD_ANSWER_SHOW`，
payload 六个无符号整数：

| 字段 | 含义 |
| --- | --- |
| `kind` | 答案种类 1~7，见 `ui_screen.h` 的 `UI_ANSWER_KIND_*` |
| `channel` | 0=温度 1=湿度 2=噪声 255=与通道无关（风扇） |
| `value` | 数值 ×10（本链路无浮点，24.7 传 247） |
| `limit` | 阈值 ×10 |
| `flags` | 位 0 越限 / 位 1 风扇运行 / 位 2 自动 / 位 3 阈值是上限 |
| `source` | 0=PC 提问 1=移动端提问 |

直接原因是**字库画不出任意中文句子**：本板字库是从 `ui_screen.c` 的 `UI_TXT` 字面量生成的子集
（完整 GBK 要外挂 SPI Flash，其总线占 JTAG 引脚）。但真正的好处在别处——
**上位机那边模型改写措辞不会影响屏幕**，屏上出现的永远是事实，这与整套问答
"模型管措辞、系统管数字"的分工是同一条原则。

字库随之从 35 字扩到 **59 字、4484 字节**（`python scripts/hz_font_to_c.py` 自动重新生成）。

**不显示的东西**：帮助文案、反问澄清、以及**所有指令**。指令的结果本来就在屏上——
风扇那一行和报警位图都是活的，再摆一句"已把风扇打开"只会随时间变成一句过期的话。

PC 侧对应 `src/application/answer_dispatcher.py`；负数读数**拒发而不是回绕**
（字段在固件侧是无符号的，-2.0 ℃ 会变成一个很大的正数，被满有把握地画在屏幕上）。

> ⚠️ **源码已改，板子尚未重新烧录。** 与"噪声首帧丢弃"攒在一起烧。

### 六、链路指示的已知局限

**现象**：PC 端启动后屏幕仍显示"未连接"，要手动触发一次风扇才变成"已连接"。

**这是符合设计的**：链路指示的判据是"收到过上位机的帧"，而本链路的上位机**只在状态变化时才下发命令**，开机后长时间没有下行帧属于正常稳态。刻意没做超时回落——用超时判断会把正常稳态误报成掉线。

因此该指示的准确含义是「**已与上位机握手**」，不是「此刻链路仍然通畅」。要做成真正的实时链路指示，需要 PC 周期性发心跳，代价是每周期多一次命令往返、挤占留给 Modbus 应答的等待窗口。

**可选的小改进**：PC 端在硬件设备注册后主动发一次 `PING`，即可让指示开机就亮。尚未实施。

## 待确认事项清单（本方案不擅自决定，需实物到手或用户拍板后确认）
