## 第二阶段：上电前检查清单

> **本阶段全程不通电**。目的是在通电前排除接线错误，因为部分接线错误（尤其是电源接反、5V 接入 3.3V 逻辑口）可能在通电瞬间就造成硬件损坏，通电后再检查为时已晚。

### 检查项（逐条打勾）

| 序号 | 检查内容 | 检查方法 | 风险等级 |
| --- | --- | --- | --- |
| 1 | **电源线**：开发板供电方式确认——USB_UART 口供电，还是 DC005 直流电源口供电，二选一即可，不需要同时用两种方式供电 | 目视确认只接了一种供电方式 | 中（同时供电一般不会立刻损坏，但不建议） |
| 2 | **GND 共地**：STM32 开发板、AHT20 模块、HH_07.06 模块三者的 GND 必须全部连在一起 | 目视核对每个模块的 GND 引脚都接到了开发板的 GND（VOUT1/VOUT2 排针或其它 GND 测试点均可） | **高——不共地会导致通信完全失败，甚至因电位差损坏芯片** |
| 3 | **3.3V 供电**：AHT20 模块的 VCC 是否接到开发板 **VOUT1（3.3V 排针）**，不是 5V | 目视 + 万用表测量 VOUT1 排针在断电状态下对地阻值正常（无短路迹象） | **高——接到 5V 可能超出模块/I2C 逻辑电平上限** |
| 4 | **5V 供电**：HH_07.06 模块的电源正极（接线序号1）是否接到开发板 **VOUT2（5V 排针）**或独立 5-24V 电源的正极，模块电源负极（序号2）接 GND | 目视核对 | 中（模块本身支持 5-24V 宽电压，接错到 3.3V 只会导致不工作，不会立刻损坏；但正负极接反有风险，见下） |
| 5 | **UART TX/RX 交叉**：HH_07.06 的 TXD（序号3）接 STM32 **PB11（USART3_RX）**，RXD（序号4）接 STM32 **PB10（USART3_TX）**——注意是交叉接，不是 TX 接 TX | 目视核对杜邦线两端 | **高——接反会导致完全无通信（不会损坏硬件，但会一直收不到数据、排查耗时）** |
| 6 | **I2C SDA/SCL**：AHT20 的 SDA 接 STM32 **PE0**，SCL 接 STM32 **PE1**——这两根线不需要交叉，各自对应 | 目视核对 | 中（接反通常表现为无 ACK/读取失败，一般不会损坏硬件） |
| 7 | RS485 A/B | **本方案不使用 RS485，跳过此项** | — |
| 8 | **STM32 与传感器之间的电平**：确认 AHT20、HH_07.06 两个模块的数据手册/说明书均标注为 3.3V TTL 逻辑电平，与 STM32F407 的 GPIO（3.3V 系统）电平一致，**不需要**额外电平转换芯片 | 已在硬件落地方案 I 节确认，无需重复测量，但**如果发现你实际购买的模块型号与本手册假设的 ATK-MB016/HH_07.06 不一致，必须重新核实电平，不能凭本手册结论** | 高（如果实际型号不同） |
| 9 | **开发板跳线**：**【待实物确认】**——需要现场核对以下几处跳线帽的默认位置，本手册假设的是"出厂默认状态"，但不能排除之前被人为改动过： | | |
| 9a | P10 跳线（USART1 与 CH340 之间）应处于**接通**状态（即 PA9/PA10 默认连接到板载 CH340C），这样 USB_UART 口才能直接用于 PC 通信；若之前被人为断开过（比如做过其它实验），需要重新接上跳线帽 | 目视核对 P10 位置的跳线帽是否安装，具体位置需对照《探索者V3硬件参考手册》2.1.3 节图示 | 高（未接通会导致 USART1 完全联系不到 PC） |
| 9b | P2 跳线（USART3 与 RS232/ATK-MODULE 之间）：本方案要求 PB10/PB11 以**原始 TTL** 方式直接接到噪声传感器，**不安装** P2 的任何跳线帽（既不选 RS232 侧，也不选 ATK-MODULE 侧），直接用杜邦线从 P2 排针的 MCU 侧引脚接出 | **这是整份方案里置信度最低的一处推断**（详见 `STM32F407_硬件落地方案.md`"待确认事项清单"第 1 条），必须在本阶段用万用表测量：断电状态下测 P2 排针上标注为 MCU 侧（而非 RS232 侧/ATK-MODULE 侧）的两个引脚，对 GND 的阻值应符合普通 GPIO 特征（不是被内部强下拉/上拉到某个固定电平的样子）；更可靠的确认方法是通电后在第三阶段用万用表测这两个点在 STM32 空闲状态下是否呈现 UART 空闲电平（TTL 空闲时 TX 应为高电平，约 3.3V） | **高——这是本次上板测试最大的不确定项，务必先确认再接线，避免误接到 RS232 电平转换芯片的输出端** |
| 10 | USART1 跳线：与第 9a 条为同一处（P10），无需重复检查 | — | — |
| 11 | **ST-LINK/USB 下载接口**：若使用外接调试器，确认调试器排线方向正确（20 针 JTAG/SWD 座通常有防呆缺口，不易插反，但仍建议目视核对第 1 脚方向） | 目视核对 | 中（插反一般插不进去或调试器报错，不易造成硬件损坏，但保险起见先检查） |

### 特别标注

- **接反可能导致通信失败（不损坏硬件）**：第 5 条（UART TX/RX）、第 6 条（I2C SDA/SCL）
- **接反可能损坏硬件**：第 3 条（AHT20 供电接到 5V 而非 3.3V，长期或极端情况下有风险）、第 4 条（HH_07.06 电源正负极接反）——**这两条务必在通电前用万用表复核一遍**
- **不能同时使用的接口**：USART1 的 P10 跳线只能选"接 CH340"或"接外部 TTL 串口"二选一（本方案选前者）；USART3 的 P2 跳线只能选"RS232"或"ATK-MODULE"或"不接任何一侧、直接用 MCU 侧原始引脚"三选一（本方案选第三种，见第 9b 条）
- **必须检查的跳线**：P10（第 9a 条）、P2（第 9b 条）

## 第三阶段：STM32 单独上电（不接任何传感器）

```
STM32F407 V3  →  USB_UART (CH340C)  →  电脑
```

### 操作步骤

1. **不要连接 AHT20、HH_07.06 任何一个传感器**，此阶段只测试开发板本身
2. **USB 插在哪里**：使用 USB 数据线连接开发板的 **USB_UART**（板载 Type-C 口，即 CH340C 对应的那个口），另一端接电脑
3. **开发板电源从哪里来**：本阶段直接用 USB_UART 口的 USB 供电即可，不需要额外接 DC005 电源
4. **是否需要拨动跳线**：第二阶段已确认 P10 跳线处于"接通 CH340"位置，本阶段不需要再动

### 若使用外接调试器（正点原子 DAP / ST-Link 等）下载固件

5. 调试器一端接电脑 USB 口，另一端排线接开发板的 20 针 JTAG/SWD 座（板载标准 JTAG 接口）
6. 打开 Keil，打开 `firmware/stm32f407/Projects/MDK-ARM/atk_f407.uvprojx` 工程
7. 确认 Keil 的 Debug 设置里 "Use" 选中了实际连接的调试器型号（正点原子 DAP 通常识别为 CMSIS-DAP；ST-Link 识别为 ST-Link）——**这一步需要 Keil 能检测到调试器，检测不到说明驱动未装或连接有问题，先解决这个再继续**
8. 点击 Keil 的 Download（下载）按钮（不是 Build/Rebuild，那两个只编译不下载）
9. **成功标准**：Keil 输出窗口显示下载成功（类似 "Application running ..." 或 Flash 编程完成的提示），无报错

### 若没有外接调试器，改用串口下载（备选方案，前提是 P10 跳线已确认接通 CH340）

5b. 使用 STMicroelectronics 官方的 **STM32CubeProgrammer** 软件（免费，需要单独下载安装，不在 `docs/08_YINGJIAN` 资料中——这是【待实物确认】项：需要你确认是否已安装此软件，或改用外接调试器方案）
6b. 打开 STM32CubeProgrammer，连接方式选择 "UART"，串口选开发板对应的 COM 口（见第四阶段如何查看 COM 口），波特率可选默认值
7b. 由于开发板具备"一键下载"电路（DTR/RTS 自动控制 BOOT0/RESET），理论上点击"Connect"时会自动进入 ISP 下载模式，不需要手动拨动 BOOT0 跳线——**若自动进入失败，需要手动将 BOOT0 跳线拨到"1"、按一次复位键，再点击 Connect，进入后再选择本工程编译好的 `Output/atk_f407.hex` 文件下载，下载完成后需要把 BOOT0 跳线拨回默认位置（一般是"0"，即从 Flash 启动）**——BOOT0 跳线的具体位置见"启动模式设置接口"（《探索者V3硬件参考手册》2.1.8 节），当前手册未在本文档中重复摘录具体跳线编号，**建议现场对照原手册插图确认**
8b. **成功标准**：STM32CubeProgrammer 显示 "Download verified successfully" 或等效成功提示

### 观察最小运行标志

10. 无论用哪种方式下载完成后，观察开发板：
    - **LED0（红色，PF9）**：应该以约 300ms 的节奏持续闪烁（对应固件 `main.c` 里"每 30 个 10ms 节拍翻转一次"的心跳逻辑）——这是"系统在跑"的最直接标志
    - **LED1（绿色，PF10）**：由于此时还没有传感器数据，只有噪声传感器请求超时/AHT20 初始化失败后固件仍会走到"完成一轮采集"逻辑并翻转 LED1，所以 LED1 大约每 3 秒左右也会翻转一次（哪怕传感器都没接，因为固件设计上传感器失败不会阻塞这个流程，只是上报的数据会被跳过）

### 第三阶段成功标准

- [ ] 开发板正常上电（板上电源指示灯亮，若板载有专门的电源 LED；若没有，以能被电脑识别为准）
- [ ] 调试器能被电脑识别（外接调试器方案）或 STM32CubeProgrammer 能连接上（串口下载方案）
- [ ] 固件下载成功，无报错
- [ ] LED0 以约 0.3 秒节奏持续闪烁
- [ ] LED1 大约每 3 秒翻转一次

全部达标后才进入第四阶段。

## 第四阶段：USART1 → PC 测试

### 确认 COM 口

1. Windows 下打开**设备管理器**（右键"此电脑"→"管理"→"设备管理器"，或开始菜单搜索"设备管理器"）
2. 展开"端口 (COM 和 LPT)"，插上 USB_UART 数据线后应该会出现一个新的 **"USB-SERIAL CH340 (COMx)"** 设备（x 为具体数字，因电脑而异）
3. 记下这个 COM 口编号

### 串口参数

| 参数 | 值 |
| --- | --- |
| 波特率 | 115200 |
| 数据位 | 8 |
| 停止位 | 1 |
| 校验位 | 无 |
| 流控 | 无 |

### 用串口终端做最小通信测试（不启动 PC 项目，先用通用串口工具）

4. 打开任意串口调试助手（如 `docs/08_YINGJIAN` 的 WiFi 模块资料自带的"串口调试助手.zip"，或 XCOM 等同类工具均可）
5. 选中上一步记下的 COM 口，按上表参数打开串口，**接收区显示模式选"HEX"（十六进制）而不是文本/ASCII**——因为 STM32↔PC 走的是二进制协议帧，不是可读文本
6. **应该看到什么数据**：每隔 **3 秒**（固件里 `SENSOR_CYCLE_INTERVAL_TICKS = 300`，主循环 10 ms 一拍）会看到一串以 `AA 55` 开头的十六进制字节——这是协议帧头，出现即说明 USART1 链路通了。帧内容包含 `74656d70657261747572...`（"temperature" 的 ASCII 十六进制）等字样。

   > **2026-09-09 订正**：本步骤原先写的是"每隔约 1 秒，看到心跳帧（payload 含 `stm32_heartbeat`）"。
   > 早期固件确实有独立心跳帧，后来采集周期状态机成型后**心跳被数据上报取代**，
   > 现在固件只在两种时刻发帧：每个采集周期上报一次数据、收到命令后回一次 ACK。
   > 按旧描述去找 `stm32_heartbeat` 会一无所获，从而误判成"链路不通"。
   >
   > **因此这一步必须接好传感器才做得了。** `finish_cycle_and_report()` 对三个通道
   > 都是 `if (valid) report_channel(...)`——读失败的通道**不发帧**，
   > 所以一个传感器都没接时 USART1 上会完全没有数据，与"链路不通"表现一致、无法区分。
   > 没接传感器时改用调试串口（USART2）看 `[aht20] read failed` 这类日志判断固件是否在跑。

### 如果没有数据，按以下顺序排查

1. 确认 COM 口选对了（可以拔插一次 USB 线，观察设备管理器里 COM 口是否消失/重新出现，确认这就是目标端口）
2. 确认串口参数（尤其波特率）填的是 115200，不是其它值
3. 确认第三阶段的 LED0 仍在闪烁（说明固件仍在正常运行，不是死机了）
4. 确认 P10 跳线仍处于"接通 CH340"位置（第二阶段第 9a 条）
5. 换一根 USB 数据线（部分线材只有供电线芯、没有数据线芯，容易被忽略）
6. 换一个 USB 口（部分老旧 USB Hub 供电不稳可能影响 CH340 工作）

### 第四阶段成功标准

- [ ] 设备管理器能看到 CH340 对应的 COM 口
- [ ] 串口工具以 115200 8N1 打开后，能持续看到以 `AA 55` 开头的十六进制数据，间隔约 1 秒

| --- | --- |
| 波特率 | 115200（出厂默认） |
| 数据位 | 8 |

### 协议细节（复述自 `docs/09_STM32Hardware/STM32F407_硬件落地方案.md` D.4 节，已用手册真实报文核对）

- **读取寄存器**：功能码 `03H`（读保持寄存器），协议地址 `0x0000`，寄存器数量 `1`
- **请求帧**（从机地址=1 时）：`01 03 00 00 00 01 84 0A`（最后两字节为 CRC16，低字节在前）
- **正常响应帧**：`01 03 02 [数据高字节] [数据低字节] [CRC低] [CRC高]`，例如 `01 03 02 01 9E 38 7C`
- **CRC16**：标准 Modbus CRC16（多项式 0xA001，初始值 0xFFFF）
- **dB 数据换算**：`声压级(dB) = (数据高字节<<8 | 数据低字节) × 0.1`，如 `0x019E`=414 → 41.4dB

### 第一次测试只验证："STM32 能否稳定读取一个噪声值"

## 第八阶段：PC 端验证

本阶段验证的是"PC 项目能不能正确接收并解析 STM32 发来的真实数据"，而不是重新验证硬件。

### 操作步骤

1. **COM 口确认**：与第四阶段相同的方法，在设备管理器确认 CH340 对应的 COM 口编号
2. **串口参数**：PC 端由 `src/communication/serial.py` 的 `SerialChannel` 自动按 `--baudrate` 参数配置，默认 115200，与固件一致，不需要手动设置
3. **原始数据查看**：可选，先用第四阶段的串口工具确认 USART1 持续有 `AA 55` 开头的数据（复用第四/七阶段已验证过的结果即可，不需要重复）
4. **当前 PC 项目如何启动**：

   ```bash
   python scripts/run_gui.py --mode hardware --port COMx --baudrate 115200 --device-id mcu-1
   ```

   其中 `COMx` 替换为第 1 步确认的实际 COM 口
5. **数据帧解析**：由 `src/application/hardware_runtime.py` 的 `HardwareDeviceReceiver` 自动完成，不需要人工干预，GUI 界面会自动显示解析结果
6. **如何确认温度/湿度/噪声**：GUI 界面的"实时数据"表格中应出现 `temperature`/`humidity`/`noise` 三行，数值应与第七阶段串口工具里看到的原始十六进制数据解码后的值一致（可以用第七阶段记的某一时刻的原始十六进制数据，手动核对一次，作为"PC 解析没有出错"的交叉验证）
7. **如何确认时间戳/状态字段**：GUI 的"历史记录"表格"接收时间"列显示的是 PC 本地接收到该数据点的时间（不是设备时间戳，因为协议里没有设备时间戳字段，这是已知的设计——见 `docs/07_Thesis/毕业论文初稿.md` 第 5.7 节的说明）；"状态"列在数值超出阈值（温度>35℃/湿度 30~75%RH 之外/噪声>80dB）时会显示"报警"，正常时显示"正常"

### 特别设计："证明 Simulator 已经关闭"的验证步骤

这是本阶段最关键的一步，防止误以为看到的是模拟数据：

1. **看启动参数**：确认启动命令里带的是 `--mode hardware`，不是默认的 `--mode simulator`（不带 `--mode` 参数时默认走 Simulator 模式）
2. **看界面顶部信息栏**：`TopBarWidget` 会显示当前"运行模式"标签，`scripts/run_gui.py` 在 Hardware 模式下会传入 `mode_label="硬件模式"`——**若界面上显示的是"硬件模式"而不是"模拟模式"，说明确实走的是 Hardware 链路**
3. **看设备 ID**：Hardware 模式下设备 ID 由 `--device-id` 参数决定（本手册示例为 `mcu-1`）；Simulator 模式固定是 `sim-1`——**界面设备列表里显示的是你自己指定的设备 ID，而不是 `sim-1`，也是一个佐证**
4. **决定性验证——断开真实传感器，观察数据是否停止变化**：临时拔掉 AHT20 或 HH_07.06 中的一个（不用整个断电，现场拔线即可），观察 GUI 对应通道的数值是否**停止更新**（因为固件那一路会持续报 `read failed`、不再上报该 channel）——**如果是 Simulator 模式，拔线不会有任何影响，因为数据根本不是真实传感器产生的；只有 Hardware 模式下，拔线才会导致对应通道数据停止变化，这是最直接、最不会出错的证明方式**
5. 验证完成后重新接回传感器

| E | USART3（噪声传感器链路）没数据 | ①噪声传感器未切换到ModbusRTU模式②TX/RX接反③P2跳线状态不对（可能被接到了RS232或ATK-MODULE侧，而不是原始TTL）④供电不足⑤地址/波特率与固件假设不一致 | 1. 先用USB转TTL+配置工具单独确认模块已在ModbusRTU模式（第五阶段前置步骤）2. 检查TX/RX是否交叉接（第二阶段第5条）3. 用万用表复核P2跳线状态（第二阶段第9b条，本手册置信度最低项）4. 检查5V供电 | 这是最需要耐心排查的一项，建议先用USB转TTL模块直接对HH_07.06做Modbus读取测试（用配置工具自带的"读取声压级"功能），确认模块本身工作正常后，再排查STM32这一侧 |
| F | Modbus CRC错误 | ①波特率不匹配导致收到的字节本身就是错的②接线不稳定（杜邦线接触不良）③模块与固件的地址/波特率假设不一致④总线上有干扰 | 1. 检查杜邦线连接是否牢固 2. 核对波特率 3. 缩短接线长度、远离强干扰源（如开关电源） | 优先排除接触不良；若持续出现，考虑降低波特率测试（模块支持9600~115200） |
| G | 噪声数据异常（数值超出30-130dB范围或明显不合理） | ①CRC校验通过但解析字节顺序搞反了②模块本身故障③环境确实异常吵闹 | 1. 先确认环境本身声音水平（用手机分贝App粗略对照）2. 检查代码里数据高低字节顺序是否与手册一致（已交叉核对过，正常不应该有问题）3. 用配置工具直接读一次模块数据，与STM32读到的对比 | 若配置工具读到的和STM32读到的一致，说明是模块本身特性或环境问题，不是代码问题 |
| H | I2C无ACK | ①SDA/SCL接反或未接②未共地③模块未上电④PE0/PE1实际被占用（万一之前的高危假设不成立）⑤模块本身需要外部上拉电阻而模块板上没有 | 1. 核对接线（第二阶段第6条）2. 核对供电 3. 万用表测SDA/SCL在空闲时是否能被上拉到3.3V附近 4. 尝试外加4.7kΩ上拉电阻 | 若加上拉电阻后恢复正常，说明模块板上未自带上拉，属于"待实物确认"项的实际结论，请更新硬件方案文档记录这一发现 |
| I | 温湿度读取失败（I2C有ACK但数据不对/CRC8失败） | ①测量延时不够被打断②供电不稳③CRC8计算逻辑问题（已交叉核对，可能性较低） | 1. 确认没有在80ms测量等待期间做其它耗时操作打断时序 2. 检查供电纹波 3. 多次重试排除偶发干扰 | 偶发一两次失败属正常（固件设计上会在下个周期自动重试），持续失败才需要深入排查 |
| J | PC端COM口找不到 | ①USB线未插好②CH340驱动未安装③USB线是纯供电线 | 1. 换线 2. 设备管理器看"未知设备"提示，据此安装CH340驱动 | 从厂商官网下载CH340驱动安装 |
| K | PC收到乱码 | ①波特率不匹配②接收模式选了文本而不是HEX③线材质量问题导致误码 | 1. 核对波特率一致 2. 串口工具切到HEX显示模式 3. 换线/缩短线长 | 波特率不一致是最常见原因，优先核对 |
| L | GUI没有真实数据 | ①还在Simulator模式（忘记加--mode hardware）②COM口/波特率参数错③STM32那边链路本身没通（应先用串口工具确认原始字节有没有，见D/E项） | 1. 检查启动命令 2. 按第八阶段"证明Simulator已关闭"的步骤逐条核实 3. 回退到第四/五/六阶段用串口工具单独确认硬件链路 | 优先分清楚是"PC没收到"还是"STM32没发出"，用串口工具能直接看到原始字节流，是最有效的分界点 |
| M | 传感器工作但STM32读取不到 | ①传感器本身工作正常（如配置工具能读到），但STM32这一侧接线/时序有问题②STM32的软件I2C/Modbus驱动存在尚未暴露的逻辑问题 | 1. 先用配置工具/USB转TTL确认传感器本身工作正常（排除传感器本身故障）2. 回到STM32侧核对接线 3. 若接线确认无误仍读取失败，可能是软件时序问题，需要反馈给开发者（我）进一步排查代码 | 这种情况下请把现象详细描述给我（哪个传感器、什么现象、接线截图/描述），我会针对性检查驱动代码 |
