### 1.1 各模块引脚

- **小风扇（4 脚）**：`VCC` / `GND` / `FI` / `BI` ★
- **LCD（2×17 排针，或 32Pin FPC）**：`CS`/`RS`/`WR`/`RD`/`RST`/`D0~D15`/`BL`/`VDD(3.3V)`/`V5(背光5V)`/`GND`，触摸 `MI`/`MO`/`PEN`/`TCS`/`CLK` ★
  - 对正点原子 STM32 开发板，**该模块可直接插在板载 TFTLCD 排座上**，无需飞线 ★
- **WiFi（6 脚）**：`VCC(5V)` / `GND` / `TXD` / `RXD` / `RST(低有效)` / `IO_9(低=固件烧写模式，高=运行)` ★
- **TW-TTS（6 脚）**：`G` / `V` / `R`(输入) / `T`(输出) / `SPK+` / `SPK-` ★
  - 仅接 `G/V/R` 三线即可完成播报；加上 `T` 才能查询播报状态（空闲/播放中）★

### 1.2 TW-TTS 的串口协议（与本项目协议的对照）

TW-TTS 自带一套帧协议，结构与本项目自定义协议**思路一致但更简单**（无校验）★：

```
0xFD | 数据长度(2B) | 命令字(1B) | 编码参数(1B) | 文本(N B)
```

| 项 | 取值 ★ |
| --- | --- |
| 帧头 | 固定 `0xFD` |
| 数据长度 | 文本字节数 + 2（大端 2 字节） |
| 命令字 | `0x01` 开始合成 / `0x02` 停止 / `0x03` 暂停 / `0x04` 继续 / `0x21` 查询状态 |
| 编码参数 | `0x00` = GB2312，`0x04` = UTF-8 |
| 音量/语速/语调 | 用文本标记 `[v0]~[v9]` / `[s0]~[s9]` 等，各 10 级 |

> 例（手册原文给出的 worked example）：UTF-8 播报"天问五幺，你好" =
> `FD 00 17 01 04 E5 A4 A9 E9 97 AE E4 BA 94 E5 B9 BA EF BC 8C E4 BD A0 E5 A5 BD` ★
>
> 对本项目的意义：**固件侧可以复用已有的"拼帧—发送"写法**，且因为 TTS 只收不校验、
> 我们只需单向发送，实现成本很低。但它**没有 CRC**，可靠性讨论时不要与本项目主协议混为一谈。

## 三、可行性预判：三个好消息，两个真问题

### ✅ 结论 1：LCD 与 AHT20 **不冲突**（这是最需要先确认的一条，已确认安全）

**为什么值得专门查**：AHT20 的软件 I2C 当初选 PE0/PE1，理由正是"它们在硬件手册里标注为
FSMC_NBL0/NBL1、**SRAM 专用**，而本项目从不初始化 FSMC"。现在 LCD 恰恰要用 FSMC，
这条理由是否被推翻，直接决定 AHT20 要不要改引脚。

**核对结果：不冲突。** 两处独立证据：

1. **硬件手册原文** ★：PE0 = `FSMC_NBL0`、PE1 = `FSMC_NBL1`，连接关系栏均注明
   **"(SRAM 专用)"**；而 LCD 用到的信号在表中一律注明 "(LCD/SRAM 共用)"。
   即 NBL0/NBL1 是外部 SRAM 的字节使能，LCD 通路不经过它们。
2. **官方 探索者 F407 LCD 例程源码** ★（`ATK-MD0280模块测试实验（FMC&FSMC）/探索者STM32F407开发板.zip`
   → `Drivers/BSP/ATK_MD0280/atk_md0280_fsmc.h`）的实际引脚定义里
   **完全没有出现 PE0/PE1**，数据线用的是 PE7~PE15 + PD 口：

| 信号 | 引脚 ★ | 信号 | 引脚 ★ |
| --- | --- | --- | --- |
| D0~D1 | PD14, PD15 | D10~D12 | PE13, PE14, PE15 |
| D2~D3 | PD0, PD1 | D13~D15 | PD8, PD9, PD10 |
| D4~D9 | PE7, PE8, PE9, PE10, PE11, PE12 | RD / WR | PD4 / PD5 |
| RS | PF12（FSMC_A6） | CS | PG12（FSMC_NE4） |
| 背光 BL | PB15 | | |

触摸（SPI）★：`SCK=PB0`、`PEN=PB1`、`MISO=PB2`、`MOSI=PF11`、`CS=PC13`——
这些都是板载 TFTLCD 排座的专用脚，与本项目现有引脚无一重叠。

> **前提条件**：不得启用板载外部 SRAM（片选 FSMC_NE3 = PG10）。本项目本来就不用 SRAM，
> 继续不用即可。☆ 需注意的是，PE0/PE1 物理上仍连着 SRAM 芯片的字节使能引脚，
> 我们把它们当 GPIO 翻转时 SRAM 片选始终无效、不会驱动总线——这一点当前固件已实测工作正常
> （2026-08-16 AHT20 实机验证通过），加入 LCD 后**逻辑上不变，但仍建议实测复核一次**。

### ⛔ 结论 2：WiFi 模块与噪声传感器**抢同一组引脚**（硬冲突，必须先决策）

硬件手册对 PB10/PB11 的连接关系写得很明确 ★：

| 引脚 | 连接关系（手册原文）|
| --- | --- |
| PB10 | 1，RS232 串口3(COM3) RX 脚(P2 设置)　2，**ATK-MODULE 接口的 RXD 脚**(P2 设置) |
| PB11 | 1，RS232 串口3(COM3) TX 脚(P2 设置)　2，**ATK-MODULE 接口的 TXD 脚**(P2 设置) |

也就是说，板载那个**给正点原子无线模块用的 ATK-MODULE 接口，走的就是 USART3 = PB10/PB11**——
而本项目的 **HH_07.06 噪声传感器现在正占着这两个脚**（当原始 TTL 用，2026-08-18 实测接通）。

**后果**：ATK-MB026 **不能插板载 ATK-MODULE 座**，否则与噪声传感器二选一。

**可行的出路**（讨论时定）：WiFi 模块本身只是个 6 脚模块，**用杜邦线接到任意空闲 UART 即可**，
不必使用那个专用座。所以这不是死结，但它把问题推到了结论 3。

### ⚠️ 结论 3：串口数量够，但**没有"干净"的空闲串口**了

STM32F407ZGT6 共 6 路串口（USART1/2/3/6 + UART4/5），**已用 3 路**，新增 WiFi + TTS 需要**再开 2 路**。
剩下的三路，其默认引脚在探索者V3 上都已挂了板载外设 ★：

| 串口 | 可选引脚 | 板上占用情况 ★ | 代价 |
| --- | --- | --- | --- |
| **USART6** | PC6 / PC7 | PC6 = ES8388 音频 MCLK + 摄像头 D0（手册标 N）<br>PC7 = 摄像头 D1（标 Y） | 放弃板载音频编解码 + 摄像头接口 |
| **UART5** | PC12 / PD2 | PC12 = SDIO_SCK（标 Y）<br>PD2 = SDIO_CMD（标 N） | 放弃 SD 卡 |
| **UART4** | PC10 / PC11 | SD 卡 D2 / D3（均标 N） | 放弃 SD 卡 |

> 手册对 Y/N 的定义 ★：Y = 可作完全独立 IO；N = 已接其他外设，不可作独立 IO。
> 这里的 N **不等于不能用**，而是"用了就等于占用/放弃那个板载外设"。
> ☆ 具体到电气层面能否稳定工作（例如 PC6 上挂着 ES8388 的 MCLK 输入负载），**需实测确认**。

**初步倾向**：本项目不用 SD 卡、不用摄像头、不用板载音频，因此 **USART6 + UART5（或 UART4）** 两路可用。
TTS 固定 9600、WiFi 默认 115200，两者互不影响。

### ⚠️ 结论 4：风扇的引脚要另选，官方例程的引脚在本板上被占

官方例程（M48Z-M3 最小系统板 F103 版）用 `TIM1_CH1 = PA8` + `TIM1_CH1N = PB13` 输出互补 PWM ★。
放到探索者V3 上 ★：PA8 = 摄像头 XCLK + 红外接收头（N），PB13 = ES8388 的 SCLK（N）——都不干净。

**但这里有个简化空间**：官方例程用互补通道是为了支持**正反转**。
本项目若只需要"按温度调速的单向送风"，则 ☆ **只需 1 路 PWM 驱动 FI、BI 常拉低**即可，
不必占用互补通道，选脚自由度大得多。手册标 Y 且只挂摄像头/ADC 的候选脚有：
`PA5`、`PA6`、`PB6`、`PB7`、`PE5`、`PE6`、`PC7`、`PG15`（注意 PE5/PE6 与 LCD 用的 PE7~PE15 不重叠）。

> ☆ 需确认：是否真的需要反转？若需要，就得找一组可用的互补通道，难度明显上升。

### ⚠️ 结论 5：供电要重新算

三个新增负载都不小 ★：LCD 背光最大 113mA、WiFi（ESP32-C3 发射瞬时电流可达数百 mA）、
风扇电机（启动/堵转电流远高于稳态）。
☆ 仅靠开发板 USB 取电很可能不足，建议讨论时把**独立 5V 电源**列入方案。

## 四、对项目结构形态的影响（供讨论，未做任何决定）

用户已说明新增内容属于"后端"部分且**会影响整个项目的结构形态**。就这批模块看，影响主要来自 WiFi：

**WiFi 让 STM32 第一次具备了脱离串口、直接进网络的能力。** 这会引出一个必须先回答的问题：

> **WiFi 是要"替代"串口成为主链路，还是与串口"并列"成为第二条链路？**

两者对现有架构的影响完全不同：

| 方案 | 对现有代码的影响 | 备注 |
| --- | --- | --- |
| **并列**（串口继续在，WiFi 另开一路上报到后端） | 影响小。现有 `CommunicationChannel` 抽象本就与介质无关，PC 侧若要收 TCP，只需新增一个 `TcpChannel` 实现，`protocol`/`service`/`api`/`ui` 理论上不动 | 与现有"两模式共用上层代码"的设计一脉相承 |
| **替代**（STM32 直接连后端，PC 上位机不再是数据必经之路） | 影响大。PC 上位机从"数据链路的中枢"退化为"后端的一个客户端"，`gateway` 与 `ui` 的定位、乃至 `api` 之下的分层都要重新论证 | 这才是真正意义上的"结构形态改变" |

另外三个模块（LCD / TTS / 风扇）在架构上是**另一类变化**：它们让 STM32 从"纯采集端"变成了
**"采集 + 本地显示 + 本地告警播报 + 执行器控制"**的自治节点。这会引出第二个问题：

> **控制决策放在哪一端？** 是 STM32 本地闭环（测到温度高就自己开风扇），
> 还是由上位机/后端下发指令？前者 STM32 要有自己的阈值逻辑，后者会用到现有的命令下发通道
> （`DeviceManager.deliver()` + `COMMAND_ACK`，这条链路已实测可用）。

> ⚠️ 按 `CLAUDE.md` 的修改规则，若最终方案要动 `docs/02_Architecture/` 已定义的分层结构，
> **必须先说明修改原因（动机、影响范围、替代方案取舍）并更新架构文档，之后才能实施**。
