# 问答基线归档

本目录存放**换模型/调训练之前**的问答能力快照。存在的理由只有一条：

> 训练之后要回答"变好了还是变差了"，而这个问题**只能靠训练之前留下的数字**回答。
> 补不回来——换掉模型的那一刻，旧模型在旧题库上的表现就永远不可复现了。

## 归档规则

- **每次换模型、改训练、调采样参数之前，先跑一次并存档**，文件名带日期与模型标识
- 存的是 `scripts/assistant_benchmark.py` 的完整输出，不做摘要——
  摘要会丢掉逐题明细，而回归往往只体现在个别题上
- 同时记下**配置**（见下），否则两次分数不可比：同一个模型换个温度就是另一组数

## 怎么比

```bash
python scripts/assistant_benchmark.py > docs/05_Test/baseline/问答基线_<日期>_<模型>.txt
diff docs/05_Test/baseline/问答基线_20260910_qwen3.5-4b.txt <新文件>
```

三个数要**分开读**，不要合成一个总分（脚本 docstring 里讲了原因）：

| 指标 | 含义 | 训练能改善吗 |
| --- | --- | --- |
| 规则命中率 | 压根没用到模型的比例 | **不能**——这靠改关键词表，与模型无关 |
| 模型分类成功率 | 规则漏掉的题里模型分对的比例 | 能，这是训练的主要目标 |
| 改写采纳率 | 模型措辞通过接地校验的比例 | 能，但**被拒不等于缺陷**，是校验在干活 |

**答错时先查关键词表再动模型。** 这条写在脚本 docstring 里，来自首次运行的实测：
八处失败里有五处是规则缺词（"最干的时候湿度多少"里的"最干"不在 MINIMUM 表里），
补词把规则命中率从 69% 提到 78%，而这是再怎么调提示词都做不到的。

## 守卫与复核上线后的重排（2026-09-14）

当日两处改动都落在指令路径上（征询语气守卫、指令的模型复核），09-10 的基线因此不再描述当前行为，
带模型重排一次。**逐项与 09-10 相同**：

| 指标 | 09-10 | 09-14 |
| --- | --- | --- |
| 总体 | 84/87 = 96.6% | **84/87 = 96.6%** |
| 问 / 指令 / 范围外 | 54/57、22/22、8/8 | **完全相同** |
| 规则命中 / 改写采纳 | 87/87 / 49/87 | **完全相同** |
| 中位耗时 | 4.9 s | **3.6 s** |
| 模型请求数 | 63 | **88** |
| 复核拦下（意图判对但等确认） | — | **0** |
| 错误执行（不该动设置却动了） | — | **3** |

三件事值得单独记：

1. **复核一次误报都没有。** 22 条指令模型全部给出与规则相同的标签，没有一条被反问拦下。
   留出题库上估的误报是 8/148，那是问题类；指令类在这个题库上是 0/22。
   **这是"指令多等几秒"之外没有额外代价的直接证据**——但要说准：87 句题库是拟合题库，
   它的指令说法都是规则认得出的标准说法，不能据此说复核在真人口语上也零误报。
2. **请求数 63 → 88，正好多 25。** 22 条指令 + 3 条被规则读成开关的裸开关句，每条一次复核，
   一次不多一次不少。这个算术对上了，说明复核既没有漏掉哪条指令，也没有在别处多调模型。
3. **中位耗时反而降了（4.9 → 3.6 s），整轮 6.1 分钟。** 不是模型变快了：
   以前指令类不发起任何模型请求，而评测脚本会一直等到 `--wait` 耗尽，那 25 条每条空等 20 s；
   现在它们有真实回复，3.6 s 就返回。**产品侧的变化是相反的**——指令由瞬时变成约 3.6 s，
   评测里那 20 s 从来是脚本的等待，不是用户的等待。

**"错误执行 3" 是原有的三条，不是新问题，但它把性质说清楚了。** 这三条
（"那你开开呗""打开""关了吧"）期望走 `bare_switch` 反问，规则却判成 `fan_on`/`fan_off`，
**并且真的改了风扇模式**——此前的报告只说"未通过"，没有说它们有副作用。
复核没能拦住它们：单独问模型同一句话，它给的是 `fan_on` / `fan_on` / `fan_off`，
与规则完全一致（2026-09-14 实测，同一提示词与采样参数）。
**这正是 `Intent_Review_Proposal.md` 第 9 节说的"复核拦不住规则与模型一起判错"那一类**，
现在有了实测而不只是推断。要修得靠规则层：让裸开关句在进入开关词表前先被
`bare_switch` 分支接住（`_FAN_ON_WORDS` 收录"开"之后它就接不住了），维护期内是否调整仍待定。

> 目录里的 `exp_results.json` / `heldout_set.json` 是 `exp_intent_heldout.py` 的**默认输出名**，
> 会被每次运行覆盖。2026-09-14 用 `--rules-only` 复核守卫时覆盖过一次，
> 所以现在那份只有规则列（7 个字段），**完整的三种方式对照在带日期的
> `留出实验结果_20260914_qwen3.5-4b.json` 里**（21 个字段），后者没有被动过。

## 留出题库（2026-09-14）

### 为什么需要它

87 句题库上的 96.6% 是**拟合出来的**：词表是照着上一轮答错的题补的，而 09-10 那次
87 题**全部被规则命中，模型分类一次都没被触发**。所以"换个说法认不认得出""模型分类准不准"
这两个问题，在它之前没有任何数据。

### 规矩

**不许照着留出题库补词表。** 一旦照着它补词，它就变成第二个 87 句题库，失去测泛化的意义。
答错的题要改，就另写新题验证，留出题库本身只用来量。

### 怎么生成

`exp_intent_heldout.py` 用 hassil 风格的模板展开：`(a|b)` 多选一、`[x]` 可选，
按固定种子 `20260914` 每组抽 6 句（范围外 14 句），并剔除 87 句题库里的原句。
共 **148 句：范围内 134、范围外 14**，覆盖 12 个标签与 3 个通道。

局限：模板是本项目自己写的，不等于真人问法；个别题的标注有争议（"湿度通常在多少"算平均还是当前）；
模型部分每种方式只跑一次（固定 `seed=7`、temperature 0.3）。

复现：`python docs/05_Test/baseline/exp_intent_heldout.py`（需要 Ollama 与 `qwen3.5:4b`，约 12 分钟；
`--rules-only` 数秒）。输出写到脚本所在目录，会覆盖同名结果文件。

### 实验 1：只跑规则

| 指标 | 修复前 | 修复后（2026-09-14） |
| --- | --- | --- |
| 范围内正确 | 110/134 = 82.1% | **111/134 = 82.8%** |
| 范围内落空（交给模型） | 5/134 | 5/134 |
| 范围内**规则答错**（模型不会被调用） | 19/134 = 14.2% | 18/134 |
| 其中**被执行成错误指令**（有副作用） | **1** | **0** |
| 范围外被规则误接 | 5/14 | 5/14 |

唯一有副作用的一条："风扇让系统自己决定开关"意为交回自动，却因为没有"自动"二字落到了关闭词表，
在真实组合里把风扇切成了手动常关。已在 `intent._FAN_AUTO_WORDS` 补说法、在 `_FAN_STATE_WORDS`
加问句守卫修掉，回归测试见 `tests/service/assistant/test_intent.py`。**其余错判按用户 2026-09-14 决定
登记为已知局限，不改**，理由是它们没有副作用：数字仍是真实读数，答案写明了答的是哪类问题。

剩下的错判分三类：
- **词表抢先**：带报警词就判成"是否超标"，"温度报警线是多少"本是问阈值
- **退回当前值**：规则认不出统计词或报警意思时退到"当前读数"，如"湿度是不是不正常""最潮的时候湿度多少"
- **字面撞词**：范围外的"帮我查一下湿疹怎么治""空调温度调到 26 度""明天温度多少"被当成问读数

### 实验 2：同一批题绕过规则、直接让模型分类

| | A 现行（自由文本 + `parse_reply`） | B 同一提示词 + JSON Schema 约束 |
| --- | --- | --- |
| 范围内正确 | **122/134 = 91.0%** | 121/134 = 90.3% |
| 范围外正确拒绝 | **13/14** | 12/14 |
| 规则答错的 24 题里模型分对 | **22** | 21 |
| **分错且会执行成指令** | **0** | **1**（"空调温度调到 26 度"→ 改通风阈值） |
| 中位耗时 / 最长 | 4.06 s / 6.21 s | **1.84 s / 2.92 s** |
| 组合（规则优先、落空才用模型，即线上管线） | 121/148 = 81.8% | 123/148 = 83.1% |

读法：

1. **模型比规则更懂换了说法的问题**（91.0% 对 82.8%），规则答错的 24 题它纠正了 22 题。
   但线上管线是"规则优先"，规则一旦自信地答错，模型根本不被调用，所以组合结果只有约 82%。
2. **JSON Schema 约束没有带来准确率提升，还多出一次有副作用的误判。** 自由文本下模型可以含糊、
   可以只回 `unknown`，`parse_reply` 会把含糊的回答拒掉；约束输出**强迫它从枚举里挑一个**，
   挑错时反而更"干脆"。它唯一的收益是快了一倍多。**因此不采用**，除非之后配合"低置信度回退"一起做。
3. 两种方式共同的错：把"站台暖和吗""站台潮湿吗"读成"是否超标"。这类问法本身有歧义，
   不全算模型的错。

## 复合句两两组合（2026-09-15）

### 为什么需要它

当日上线了拆句（一句话里的几段提问加至多一条指令，设计见
[`../../02_Architecture/Assistant_Design.md`](../../02_Architecture/Assistant_Design.md) §12.2）。
87 句题库全是单句，只能证明拆句没有漏进单句，证明不了"一句问两件事"答得好不好。
这批题不另写，直接用 87 句题库两两拼出来：单句的标注现成可用，而且单句都答对这一条件
正好给出对照——组合句答对的比例应当逼近它。

### 怎么生成

从 87 句题库取可组合的 73 条（提问与指令；范围外、裸开关、播报请求、本身已是复合句的除外），
两两有序拼成"A，B"。**两条指令、同一问题问两遍**这两类按设计不拆，不计入。

### 实验 1：规则层全量（`exp_compound_pairs.py`，不接模型，约半分钟）

复合句的提问部分只走规则与模板，模型不参与，所以这一层的结果就是提问部分的最终结果。
判定：拆句结果须恰好认出两件事，且指令真的执行了。

| | 组合数 | 首版 | 补问句标记后 | 两句单独问都对 |
| --- | ---: | ---: | ---: | ---: |
| 问 + 问 | 2390 | 65.9% | **93.5%** | 100% |
| 问 + 指令 | 2244 | 80.4% | **96.1%** | 100% |

首版失败全部归到十个单句，问法集中在"没"字问（超了没有、开了没）、正反问（冷不冷、吵不吵）
与"有多响"，于是补进 `intent._QUESTION_MARKERS` 与 `_A_NOT_A`。补后的失败只与两句有关，
都按设计不修："好闷啊"无问句标记、按体感铺垫处理；"阀值是多少"没点通道，拆句不接管要反问的提问。
逐条明细在 `compound_pairs_failures.json`（只收"两句单独问都对、组合却错"的 244 句）。

> 本文件"首版"一列来自补标记之前的一次运行，那份输出没有存档；带日期的输出文件是补标记之后的结果。

### 实验 2：端到端抽样（`exp_compound_pairs_e2e.py`，需 Ollama，约 4 分钟）

与 `run_all_界面加网关.bat` 相同的组合，固定种子 `20260915`，问 + 指令、问 + 问各抽 25 句。
测的是模型会影响的那部分：指令段的复核。每句前 `reset_conversation()`，执行过的指令随后交回自动。

| | 结果 |
| --- | --- |
| 问 + 指令 | **25/25 直接执行，反问 0**；中位耗时 3.7 s（单句指令 3.6 s） |
| 问 + 问 | 错误执行 0，反问 0 |

局限：各 25 句、只跑一次；模拟器读数随时间变化，回答文本不可逐字复现，可比的是执行与反问两列。

复现：

```bash
python docs/05_Test/baseline/exp_compound_pairs.py        # 规则层，失败明细写到同目录
python docs/05_Test/baseline/exp_compound_pairs_e2e.py    # 端到端，需 Ollama
```

在任意工作目录下都能运行：端到端脚本 import 同目录的规则层脚本，会自行把所在目录加进 `sys.path`。
两者与 `exp_noise_leading.py` 一样写死了仓库根路径 `D:\毕业设计`，换机器需改脚本顶部的 `ROOT`。
