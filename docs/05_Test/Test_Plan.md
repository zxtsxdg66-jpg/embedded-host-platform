# 测试方案

> **本文回答"这个项目靠什么相信自己是对的"**，即测试策略与各层的验证手段。

> `tests/README.md` 讲**怎么跑**，第 6 章讲**跑出了什么**。

## 一、总体策略：分层测试 + 三阶段硬件验证

**分层测试**：每一层只测自己的职责，用最窄的替身隔离下层。协议层用构造好的字节序列测，
不碰串口；服务层用假 transport 测，不碰协议；界面层用 `pytest-qt` 驱动真实控件，
但接的是回环设备而非硬件。**这样一条链路断了，失败的用例直接指出是哪一层断的。**

**三阶段硬件验证**是本项目摸索出来的做法，也写进了论文第 7 章：

| 阶段 | 手段 | 能发现什么 |
| --- | --- | --- |
| 一、纯软件仿真 | `SimulatorDevice` + `LoopbackChannel` | 功能逻辑错误 |
| 二、**真实字节流 + 模拟数据** | `scripts/virtual_stm32.py` + 虚拟串口对 | **粘包/半包、重同步等介质相关缺陷** |
| 三、真实硬件 | STM32F407 + 三个传感器 | 时序、电气、传感器特性 |

中间那一阶段是关键。它的存在源于一次真实教训：**基于内存队列的仿真通道在接口上与真实串口一致，
却天然保留消息边界**，于是上层代码不知不觉依赖了这个额外特性，直到接上真串口才暴露。
仿真验证能覆盖功能逻辑，**但覆盖不了对传输介质特性的隐含假设**。

## 二、各层的验证手段

### 协议层

构造字节序列做单元测试，不依赖任何介质。覆盖：正常帧编解码往返、CRC 失败、帧头不匹配、
长度与实际不符、空 Payload、最大长度 Payload。**边界用例与异常用例是重点**——
正常路径在集成测试里自然会被跑到，异常路径不专门测就没人测。

### 通信层

用 `LoopbackChannel` 测契约。`SerialChannel` 的自动化测试用**显式的假串口**
（`tests/communication/test_serial.py` 里的 `_FakeSerialPort`，只实现 `SerialChannel` 真正用到的
那几个方法），而不是真串口——本机没有硬件，且要能让每个用例精确指定"在第几次读写时失败"。
覆盖连接建立/断开/异常断开的状态流转、超时与重连、多实例互不影响。

**真实串口字节流的验证不在 `pytest` 里**，走上表的第二阶段（WSL2 + `socat` 虚拟串口对 +
`scripts/virtual_stm32.py`），是一次性的人工验证，记录在
[`status/早期归档.md`](status/早期归档.md)。

### 服务层

`InMemoryDataService` 的发布订阅、`InMemoryControlService` 的"共享读、独占写"占用规则、
`SensorDataProcessor` 的统计与区间报警、`VentilationController` 的决策、
`AlarmAnnouncer` 的连续确认与冷却、`assistant/` 的三层管线与出口校验。

这一层的测试**完全不碰协议与通信**——服务层本就不 import 它们，测试若碰了，
反而说明分层被破坏了。

### 应用层

`FrameStreamBuffer` 的粘包/半包/脏字节重同步（**这是二阶段验证暴露的问题落到测试里的地方**）；
三个 dispatcher 的"记录—下发"分离；两种运行模式从 `DataService` 往上共用同一套代码的事实，
由同一批用例分别在两种装配下跑一遍来固定。

### 接口层与呈现层

`api` 的异常转译与控制权规则。`ui` 用 `pytest-qt` 驱动真实控件，
无显示环境下 `QT_QPA_PLATFORM=offscreen`。`gateway` 用 FastAPI 的 `TestClient` 跑真实 ASGI 应用，
REST 与 WebSocket 都测。

### 跨端契约

两处不能靠人工评审：

- **命令码**：PC 侧 `RESERVED_COMMAND_CODES` 与固件头文件的 `PROTOCOL_CMD_*`
  由 `tests/application/test_command_code_contract.py` 直接读头文件逐条比对。
  **不一致不会崩**——采集端对不认识的命令照样回 ACK，表现只是功能安静地不工作。
- **Keil 工程**：`scripts/check_keil_project.py` 校验必需源文件与编译选项是否仍在工程里。
  Keil 曾覆盖 `.uvprojx`，导致新加的文件根本没参与编译，而现象与"代码没生效"完全一样。

### 组合脚本

`scripts/` 下的启动器与工具本身也有测试（`tests/scripts/`）：启动器之间的装配漂移
（一个启动器接了模型、另一个忘了）已经发生过三次，因此改由测试固定。

### 环境问答的评测（不在 `pytest` 里）

问答的"听懂率"依赖模型，结果不确定，所以不进 `pytest`，另外靠题库评测，存档在 `docs/05_Test/baseline/`：

| 题库 | 用途 | 规矩 |
| --- | --- | --- |
| 87 句题库（`scripts/assistant_benchmark.py`） | 回归：改词表、改提示词之后有没有把原来对的弄错 | 可以照着错题补词表，**因此它的分数是拟合出来的**，不代表泛化能力 |
| 148 句留出题库（`exp_intent_heldout.py`） | 泛化：换了说法还认不认得出；训练模型时衡量有没有变好 | **不许照着它补词表**，否则它就变成第二个 87 句题库 |
| 32 句噪声包裹与引导性输入（`exp_noise_leading.py`） | 鲁棒性：无关信息、错误前提、注入、征询语气 | 看最终展示给用户的句子与是否执行了动作，不只看标签 |

规则类的错答一旦修掉，要补 `tests/service/assistant/test_intent.py` 回归用例——
那一部分是确定性的，属于 `pytest` 的职责。

2026-09-14 首次跑留出题库：87 句题库上 96.6%，留出题库上规则只有 82.8%。**两个数要并列报告。**

**2026-09-14 指令复核上线后，87 句题库的判分口径变了**：指令类不再是"问完立刻生效"，
而要等模型复核的裁决，因此必须带模型跑（`--wait` 足够长），不接模型时指令仍是即时执行。
复核判分歧时系统反问、不执行，这类题会记为未通过——**这是实情而不是回归**，
所以报告里新增两项计数把两种"没执行"分开：`复核拦下（意图判对但等确认）`表示设备状态没变、
用户回一句"是"就能继续，`错误执行（不该动设置却动了）`才是有后果的那一种。
**2026-09-14 已按此重排一次**：84/87 逐项不变，复核拦下 0、错误执行 3（即原有那三条裸开关句，
它们是真的改了风扇模式），中位耗时 4.9 → 3.6 s。数据见 `baseline/问答基线_20260914_qwen3.5-4b.txt`。
往后每次动意图或指令路径的代码，都要照这个口径重排并把两项计数记下来。

## 三、四条被固定下来的原则

1. **分层边界靠"能不能跑通"固定，而不是靠断言 import。** 没有任何用例去扫源码检查
   `ui` 有没有 import `device`——那种检查容易写、也容易绕过。真正固定边界的是
   `tests/integration/test_hardware_mode.py` 这类用例：它构造真实对象栈
   （`ApplicationRuntime` + `LocalApi` + `SimulatorDevice`/`RemoteDevice` + `LoopbackChannel`），
   验证两种设备**走完全相同的代码路径**被注册、查询和控制。上层若偷偷依赖了某种设备的
   特性，这类用例会直接失败。
2. **异常路径与正常路径同等对待。** 越限、超时、校验失败、设备被占用，都要有用例。
3. **能在无硬件条件下跑完全部用例。** 这是"每次改动都能全量回归"的前提；
   需要硬件的验证单独走三阶段流程，不混进 `pytest`。
4. **端到端那一趟不能省。** 单元测试全绿而功能实际不工作，在本项目发生过三次
   （启动器没接模型、dispatcher 装了没人驱动、命令没进白名单被静默拒绝），
   三次都是端到端跑一遍才发现的。

## 四、收尾检查

每个任务收尾前跑，全绿才算完成（前三项必跑，后三项按改动范围）：

```bash
pytest                              # 单元与集成
ruff check src tests scripts        # 代码风格
mypy src                            # 静态类型
python scripts/check_keil_project.py   # Keil 工程一致性（动过固件时）
python scripts/check_doc_numbers.py    # 文档里的规模数字是否过期
python scripts/check_doc_links.py      # 文档链接是否失效（改过文档结构时）
python scripts/check_doc_identifiers.py  # 文档里的代码名字是否还存在（人过目，不设退出码）
```
