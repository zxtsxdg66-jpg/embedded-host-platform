### 已验证：全链路端到端（2026-08-16，用户实机确认）

在温湿度链路跑通的基础上，用 `run_all_界面加网关.bat`（硬件模式）做了完整的三端联合验证：

- **PC 界面与 Android 手机同时**显示正确的温湿度数值与曲线
- **物理扰动验证**：包裹传感器并哈气，温湿度数值随之正确上涨

第二条是关键。联调手册第十阶段专门要求做这个动作，理由是"比看似正常更强的验证，能进一步排除看到的是固定假数据的可能"——数值随真实环境变化，说明这条链路从物理量到屏幕像素每一环都在真的工作，而不是某处返回了缓存或默认值。

这一次同时闭环了多条此前分散的待验证项：

### 噪声传感器已到货并接线通过（2026-08-18）

HH_07.06 到货，接线与模块本身已确认正常工作。硬件落地方案"待确认事项清单"第 1 项
（**P2 跳线 / PB10-PB11 能否作原始 TTL**，全项目置信度最低的一条推断）**已闭环**——
依据是《探索者V3 硬件参考手册》图 2.1.9.1 与 2.1.2 节：

- P2 是 2×3 排针，**中间一排（3 脚 = PB11 / 4 脚 = PB10）就是 MCU 侧原始引脚**，
  与 MCU 直连，中间无任何电平转换器件；跳线帽只决定这两个脚向上接 TP3232（RS232 COM3）
  还是向下接 ATK-MODULE 接口 U17。因此**不装跳线帽、直接从中间一排引线**的方案成立
- 手册 2.1.2 节同时确认：主排针 P7/P8/P9 只引出 102 个 IO，PB10/PB11 属于**仅经 P2 引出**
  的那 8 个之一，所以只能从 P2 取，不可能在主排针上找到
- **一处风险描述更正**：上板手册第二阶段 9b 条称误接会碰到"RS232 电平转换芯片的输出端"，
  实测原理图后确认 P2 的 1/2 脚是 TP3232 的**逻辑侧**（DIN2/ROUT2），仍是 3.3V TTL；
  真正的 ±12V RS232 电平在 `U3_232TX/U3_232RX` 上，**不上 P2**。故误接后果是通信不通，
  不是烧模块（但 2 脚是芯片输出，仍应避开，避免输出对顶）
- 出厂默认状态是两个跳线帽扣在 3-5 / 4-6 上（ATK-MODULE 位置），**需拆除**——
  主要原因是它们物理占用 3、4 脚，杜邦线插不进去

### 噪声通道实测（2026-08-19 全部完成）

**噪声通道的全部实测已于 2026-08-19 完成，论文相关章节已回填。** 四项实验：

| 实验 | 结果 |
| --- | --- |
| 噪声试运行（60 s） | Modbus 100%（19/19） |
| 噪声阶跃响应（180 s） | 基线 38.02 → 声源 55.95 dB(A)，恢复后与基线差 1.64 dB |
| 越限报警（180 s） | 两次触发各持续 10 个采样点，均自动解除，无误触发 |
| 环境本底（15 min） | L90 40.0 / L50 40.2 dB(A)，Modbus 100%（291/291） |
| **三通道 1 小时稳定性** | **3489 帧（各 1163），丢帧 0，Modbus 100%（1163/1163）** |

**发现一处可复现的启动特性**：Modbus 链路建立后的**首次读数不可用**——
两次独立实验中该首帧分别为 84.7 dB(A) 与 96.2 dB(A)，而相邻样本均在 40 dB(A) 附近。
论文以"排除首个采样点"处理并在第 9 章 9.2.5 节说明；
更妥当的做法是在固件中丢弃该次读数，已列入第 10 章不足。

**另确认噪声统计不可用算术平均**：1 小时数据的算术均值 44.33 dB 与
等效连续声级 50.95 dB 相差 6.6 dB（分贝是对数量）。论文改用统计声级
L90 40.5 / L50 42.6 / L10 50.2 dB(A)。

**采集方案已确定并落地为 `collect_data_实验数据采集.bat` 的三个新预设**（2026-08-18）：

| 预设 | 时长 | 用途 |
| --- | --- | --- |
| 噪声试运行 | 60 s | 先确认通道出数与 Modbus 成功率 |
| 噪声阶跃响应 | 180 s | 60s 安静 / 60s 白噪声 / 60s 恢复 |
| 环境本底噪声 | 15 min | 为 80 dB 报警阈值取值提供实测依据 |

另需**重跑一次 1 小时长时间稳定性**——现有那份只有温湿度两通道，表 9-3 的噪声列填不了。

**新增的 Modbus 应答成功率统计（重要，避免论文出现误判）**：固件在 Modbus 读取失败时
**根本不上报噪声通道**（`User/main.c`：`if (data.noise.valid)`），只在调试口打
`[noise] read failed`。因此若沿用通用的"间隔跳变"丢帧口径，会把**传感器侧的应答失败
记成通信链路丢帧**——与第 6 章 6.6.3 节已纠正过的"把周期偏差误判为丢帧"属同一类错误。
`collect_thesis_data.py` 新增 `group_cycles()`/`modbus_stats()`：因三通道在同一采集周期
内上报，可据此精确归因——

| 该周期收到 | 判定 |
| --- | --- |
| temp + humi + noise | 正常 |
| temp + humi，缺 noise | **Modbus 读取失败**（传感器侧） |
| 三个都没有 | 链路丢帧 / 固件停止 |

由此得出 **Modbus 应答成功率 = 含 noise 的周期数 ÷ 有效周期数**，是三条链路中唯一
带请求—应答往返的通道特有的指标。报告同时会提示：噪声行的平均间隔/标准差被失败周期
抬高，不可直接引用为"周期不稳"，末列偏差取自**中位数**不受影响。

**剩余未实机验证项**（模块通了但相关代码路径的长期表现尚无数据）：

- `noise_usart.c` 的寄存器级 RXNE+IDLE 中断在长时间运行下的稳定性
- Modbus RTU 超时处理的实际触发率（即上文的应答成功率，待 1 小时数据）

### 已知问题（非阻塞）：断电重启后需接一次 ST-Link 才运行

**现象**：插上 ST-Link 后红绿灯正常闪、程序正常跑；拔掉 ST-Link 后仍继续运行；但**整机断电重启后就不运行**。

**尚未定位**，两种可能都完全符合上述三个现象：

| 可能 | 解释 |
| --- | --- |
| A. BOOT0 上电时为高 | 上电进出厂 bootloader，用户程序不执行；ST-Link 连接时会强制从 Flash 起始地址启动，所以看起来正常 |
| B. 程序未真正写入 Flash，只 load 到 RAM | 拔调试器时 RAM 未掉电所以继续跑，断电后 RAM 清空、Flash 为空 |

**一分钟可分辨的办法**（尚未执行）：用 STM32CubeProgrammer 经 ST-Link 连上后读 `0x08000000`——头两个字是 `0x2000xxxx`（栈顶）+ `0x0800xxxx`（复位向量）说明程序在 Flash（属 A，查 BOOT0 跳线）；一整片 `FFFFFFFF` 说明 Flash 是空的（属 B，多半是 Keil 的 `Debug → Settings → Flash Download` 里 Programming Algorithm 列表为空，需 Add `STM32F4xx Flash 1MB`）。

**用户决定（2026-08-16）：暂不排查**。当前程序功能可用，答辩前接一下烧录器即可，不影响任何功能验证工作。**记录在此以免被后来者当成漏做**；若答辩前想彻底解决，按上面的读回测试走，或直接用 CubeProgrammer 烧 `firmware/stm32f407/Output/atk_f407.hex` 后断电重启复测。

### 硬件模式设备状态显示错误（2026-08-17 发现并修复）

**现象**：硬件模式下界面顶部始终显示"● 未连接"，但实时数据在正常刷新。
是在为论文截取界面图时从截图上发现的——"未连接"与实时数据同框出现，自相矛盾。

**根因**：`SimulatorDevice` 在自己的构造中把状态标为 `CONNECTED`
（`src/device/simulator.py`），而 `RemoteDevice` 用的是 `DeviceStatus` 的默认值
`DISCONNECTED`（`src/device/state.py`），**两个硬件组装函数都从未显式设置过它**。
因此同一件事在两种模式下呈现相反。

**修复**：在 `scripts/run_gui.py` 与 `scripts/run_api_server.py` 的
`build_hardware_runtime()` 中，构造 `RemoteDevice` 时显式传入
`status=DeviceStatus(connection_state=ConnectionState.CONNECTED)`。
语义依据是紧接着的 `register()` 会调用 `channel.connect()` 打开串口，打开成功即链路已建立。
`src/` 未改动，改动仅在两个组装脚本中。

**这是本项目第二次踩"两条装配路径不一致"的坑**（第一次是 2026-08-12 的
`watch_alarms_for()` 漏调用）。因此本次新增 `tests/scripts/test_hardware_device_status.py`
（3 个用例），**同时对两条路径断言**，并额外断言"模拟模式与硬件模式对连接状态的呈现一致"。
