## 12. P1b 实现记录：模型意图识别（2026-09-08）

### 12.1 为什么补这一层

P1 做完之后，模型在这套系统里只干"把模板句换个说法"这一件事——**把它整个删掉，回答在内容上一字不变**。
那是个不好回答的答辩问题，也确实说明模型没有承担任何职责。

补 P1b 之后，模型的职责变成**听懂问题**：规则匹配不上的问句交给模型分类，
分类结果照旧走 §2 的第 ②③ 层。删掉模型，这些问句就重新落回帮助文案——**能力差异是可见的**。

### 12.2 管线位置：只在规则落空处介入

```
问句 ──▶ 规则匹配 ──命中──▶ 取数 ──▶ 模板 ──▶ 立即回答（模型随后可改写措辞）
             │
           落空
             │
             ▼
        模型分类（唯一一次调用，只回一个标签）
             │
        ┌────┴────┐
     可用标签   不可用
        │          │
        ▼          ▼
    取数 ─▶ 模板   保持帮助文案不变，不追加消息
    （source = model_intent）
```

三点是刻意的：

1. **`ask()` 依然同步返回**。模型分类要 2~3 秒，不能挡在关键路径上；用户先拿到帮助文案，
   分类成功后由既有的 `poll_rephrasing()` 送来第二条答案替换它。**没有为此新增任何接口方法**。
2. **一次提问最多一次模型调用**。规则命中 → 只改写；规则落空 → 只分类。分类成功后不再改写，
   否则同一个问题要等两轮生成。
3. **失败就什么都不做**。不追加第二条帮助文案——屏幕上已经有一条，再来一条会读成"问了两遍"。

### 12.3 模型只输出标签，不输出格式

要求 4B 模型返回 JSON，它大多数时候给 JSON，其余时候给 markdown 围栏、道歉或多余逗号——
对一个只有十一种可能答案的任务来说，每一种都是解析失败。所以**回复不做格式解析，只做词元扫描**：
在回复里找已知的标签词与通道词。模型把答案包在什么里都无所谓。

代价是扫描扛不住"复述菜单"式的回复（`可能是 current_value 或 maximum`）。
处理办法是**发现多个标签就整体拒绝**，而不是取第一个——含糊的答案不如没有答案，因为没有答案不花钱。

### 12.4 四道校验

| 校验 | 拒绝的情况 | 理由 |
| --- | --- | --- |
| 非空 | 空回复 | — |
| 唯一标签 | 回复里出现两个及以上标签 | 复述菜单，取谁都是掷硬币 |
| 未自称 unknown | 回复含 `unknown` | 模型自己声明分不出来，含糊的分类不算分类 |
| 通道齐备 | 需要通道的标签却没给通道（或给了两个） | 取数层本就拒绝猜通道，接受它只会把帮助文案换成更差的"没有可用的数据" |

通过校验的意图记 `confidence = 0.6`（规则匹配是 1.0）。目前没有任何分支读它，
但这是**日后加"你是想问……吗"确认所需的信息，且事后无法重建**。

### 12.5 实测（目标机，`qwen3.5:4b` q4_K_M，CPU）

20 个口语化问句，其中 **17 个规则匹配不上**（另 3 个规则本就能识别，不进模型）：

| 结果 | 条数 | 说明 |
| --- | ---: | --- |
| 分类正确并答出 | 11 | 帮助文案被真实答案替换 |
| 分类可争议但不算错 | 1 | "声音大不大" → `alarm_state/noise`（读作"是不是太吵"，不能说错） |
| 安全拒绝 | 5 | 其中 3 条确属系统范围之外，2 条是模型自身回复不合格 |
| **答错** | **0** | — |

平均耗时 **2.7 s**，全程不阻塞界面。

两条值得记的实测细节：

- **"帮我订张票" → 模型回 `unknown device_list`**。多标签校验在这里救了场：
  只取第一个标签会拒绝，只取最后一个会去答"有几个设备在线"。
- **"屋里干不干燥" → 模型只回了 `humidity`**，漏掉标签，被通道校验拒绝。
  提示词里已经写明"只给通道名是错的"，仍会偶发。**没有为此放宽校验**——
  把它补成 `current_value` 是猜测，而这一层的原则是不猜。

### 12.6 提示词里有什么、没有什么

有：标签清单、通道清单（含口语词"冷热/干湿/吵闹"）、四个示例。
**没有：任何读数、阈值、设备信息。** 请求里除了用户原话之外不含系统状态——
§1.1 的硬约束在这一层的表现形式，就是模型连能编造的素材都拿不到。

提示词固定不变，同样是为了 KV 缓存复用（见 §7.0）。代价是分类与改写两套提示词交替出现会互相冲掉缓存，
但分类只在规则落空时才发生，属少数情况，可以接受。

## 13. P1c 实现记录：自然语言下发控制（2026-09-08）

### 13.1 为什么可以让一句话去动执行器

因为它动的**不是执行器，是策略**。这一层只写 `VentilationController` 的设置——
和界面上点一下通风控制面板**写的是同一个对象**，之后由既有的下发逻辑在下一轮轮询把决策变成帧，
包括"应用没拿到控制权就等着"这条既有行为。**一句话能做到的事，界面上点一下同样能做到；
反过来也一样。** 没有新增任何命令通道，也不存在"绕过面板的第二条控制路径"。

白名单只有四项，且都可逆、都在面板上看得见：

| 标签 | 动作 |
| --- | --- |
| `fan_on` / `fan_off` | 风扇切到手动常开 / 手动常关 |
| `fan_auto` | 交回自动，按通风阈值决定开停 |
| `set_vent_threshold` | 修改某个通道的通风阈值 |

**报警阈值不在其中**——那套阈值是论文按 GB 37488—2019 论证过的，不该被一句话改掉。
设备控制权、任意命令下发同样不可达。

### 13.2 没有做二次确认，理由要写清楚

四项动作全部可逆（说反话即可撤销）、全部可见（面板与 LCD 都显示结果）、
且唯一涉及的执行器是一台小风扇。在这种前提下加一步"确定要执行吗"，是**只增加摩擦不增加安全**。
真正需要确认的是白名单之外的东西——而那些东西这一层根本够不着，这是比确认更强的约束。

### 13.3 数值从用户原话里取，不从模型回复里取

这是整个设计的关键一条。

模型只负责说"这是一条改阈值的指令"，**具体数字由代码用正则从用户原话里读**。
理由：模型复述"28"绝大多数时候没问题，但只要有一次说成 38，系统就会安静地按错误的值通风——
而这类错误没有任何下游能发现。把数字的来源钉死在用户自己打的字上，这种可能性**不存在**，
而不是"概率很低"。

这就是 §1.1 那条硬约束（模型不产生数字）用在**输入侧**的样子：
输出侧靠 `numbers_are_grounded` 在出口检查，输入侧则干脆不让模型碰数字。

配套的两条拒绝规则：

- **句子里没有数字** → 拒绝（"调低一点"没说调到多少）；
- **句子里有两个数字** → 也拒绝。"把通风温度阈值从 30 调到 28"取第一个就会设成用户正要离开的值。
  取最后一个看似更聪明，但那是**在猜**，而人就在跟前，让他重说一遍的代价接近于零。

### 13.4 值域校验

温度 0~50 ℃、湿度 0~100 %RH，与论文 P2~P4 论证的量程一致。
"通风阈值调到 300 度"不是一个苛刻的设定，而是一个**够不到的设定**——传感器根本报不出这个值，
风扇会永远不转。拒绝时把用户要的那个数原样引回来（"不能设成 300℃"），
所以那个数必须进 `Facts`，否则模板自己会过不了自己的接地校验。

### 13.5 确认语只说改了什么设置，不说硬件怎么样了

模板说的是「已把风扇切到手动常开」，**不是**「风扇已启动」。
帧要到下一轮轮询才发出去，且要应用持有设备控制权才真的下发——
在这一层承诺硬件状态是一个它兑现不了的承诺。这条写成了测试。

同样地，**指令的确认语不送给模型改写**：一句"我已经帮你把风扇开到最大了"读起来更热情，
但它描述的是一件没发生的事。确认语每次都该一模一样。

### 13.6 一次完整的演示流程实测

用 `run_gui.py` 同一套装配（仿真运行时 + 真实 Ollama + 同一个 `poll_once`）跑无界面演练，
覆盖提问、口语提问、指令、口语指令、该被拒绝的四类共 14 句。结果见下节。

这个演练已经固化成项目工具 **`scripts/demo_rehearsal.py`**（`--no-llm` 可秒跑，
指令类两轮不一致时退出码为 1），答辩前跑一遍即可知道当天模型状态；
说明见 `docs/04_Development/项目代码结构导览.md` §4.10。

演练当场揪出两个**测试没覆盖到**的规则缺口，都已修复并补了回归用例：

1. **「这一阵子最吵到多少」答成了当前值**。规则里 MAXIMUM 只认"最高/最大/峰值"，
   不认"最吵"。它给的不是错数字，只是答非所问——**正因为不是错数字，才容易漏掉**。
2. **「把通风温度阈值调低一点」被当成了问句**，答的是风扇状态。
   原因是阈值指令分支要求句子里必须有数字。改成不要求：先认出这是改阈值的指令，
   再由 `control` 以"没说调到多少"拒绝——**理解了再拒绝，好过没理解就答别的**。

> 这两个都是"看起来完全正常"的错误。单元测试测的是我想到的问法，
> 完整走一遍演示流程测的是我没想到的问法——两者不能互相替代。

### 13.7 稳定性实测（14 句 × 2 轮，修复后重跑）

| 类别 | 条数 | 两轮是否一致 |
| --- | ---: | --- |
| 提问，规则命中 | 4 | 一致 |
| 提问，规则落空→模型识别 | 2 | **1 条不一致**（见下） |
| 指令，规则命中 | 4 | 一致 |
| 指令，规则命中→按规则拒绝 | 2 | 一致（超量程 / 没给数值） |
| 指令，规则落空→模型识别 | 2 | 一致 |
| 范围之外，模型拒绝 | 1 | 一致 |

**指令类 8 条两轮全部一致**，这是最要紧的一项——指令有副作用，提问没有。
模型识别耗时 1.6~3.9 s；规则命中的指令**不调用模型，即时生效**。

**唯一不稳定的是「站里闷不闷」**：三次运行分别被判成"湿度当前值""温度当前值""温度报警阈值"。
这不是模型的毛病，是问题本身有歧义——"闷"同时指向温度与湿度。
三次给出的都是真实读数，只是回答了不同的那一个。**没有为它做特殊处理**：
真要消除歧义，只能靠追问"你是想问温度还是湿度"，而那需要多轮对话（§8 明确不做）。
现状下用户看到答非所问，改问具体一点即可，代价很小。

> 这条也说明了把模型限制在"选标签"上的价值：**模型不稳定的时候，
> 不稳定的是"回答了哪个问题"，而不是"回答里的数字对不对"。**

### 13.8 演练固化成工具之后的三次复跑

演练脚本入库为 `scripts/demo_rehearsal.py` 后又跑了三次（2/2/3 轮），**又改出两处**：

1. **「太热了让那个吹风的转起来」时灵时不灵**——因为"吹风的"不在规则的风扇词表里，
   整句要靠模型分类，而它大约一半的轮次分不出来。**把"吹风"加进规则词表**即可：
   规则认得的说法零延迟、每次都一样，比继续调提示词划算得多。
2. **工具自己误报过一次**：等模型的窗口原为 8 s，某轮分类超过了它，于是报"指令类不一致"——
   而那条指令两轮都执行正确，差别只在脚本的耐心。已把窗口对齐到客户端自身的 20 s 超时，
   并且**指令根本不再等待**（它不调模型）。一个自己制造失败的检查工具比没有更糟。

修好之后的三轮复跑：**全部八条指令完全一致**，退出码 0。仍在波动的只有两条提问：

| 问句 | 波动表现 | 判定 |
| --- | --- | --- |
| 「风扇在转吗」 | 一轮拿到了模型改写，一轮没赶上 | 理解一致，只是措辞来源不同 |
| 「站里闷不闷」 | 有时答出（温度/湿度/最高值皆出现过），有时只给帮助文案 | 是**拒绝**，不是误执行 |

因此工具的退出码判据定成：**只有"同一句话执行出两种不同动作"才算失败**。
把"这轮没听懂"也算失败，会让人很快学会忽略这份报告；
而"没听懂"在本设计里本来就是安全的落点——它什么都不做。

> 一句话总结这套设计经得起的检验：**四次演练、共九轮、没有出现过一次误执行。**
> 出问题的形态永远是"没听懂"，而不是"听错了去做别的"。

## 14. 成功率评测（2026-09-08，`scripts/assistant_benchmark.py`）

> **本节记录的是前两轮。** 当日晚些时候补入"最热/最冷/太热/热吗/干不干/太大了"等词后
> 跑了第三轮：**65/65 = 100%**，规则命中 86.2%，中位耗时 6.4 s。三轮对照见论文第 9 章表 9-10，
> 并在那里说明了这个 100% 是同一批题上的拟合、不代表泛化能力。

65 句固定题库，与 `run_all_界面加网关.bat` 相同的装配，逐条对照期望意图判分。跑了两轮：第一轮暴露问题，
补完规则词表后跑第二轮。

| 指标 | 第一轮 | 补词表后 |
| --- | ---: | ---: |
| 总体 | 87.7% | **92.3%**（60/65） |
| 提问（41 句） | 80.5% | **87.8%** |
| 指令（16 句） | 100% | **100%** |
| 范围外（8 句，应当被拒绝） | 100% | **100%** |
| 规则命中率 | 69.2% | **78.5%** |
| 改写采纳率 | 55.6% | **64.7%** |

模型请求 50 次，**超时 0、失败 0**，中位耗时 3.7 s。

### 14.1 最重要的发现：错答里一多半是规则漏词

第一轮 8 条错答中，**5 条与模型无关**——规则把问句判成了别的意图，模型只是照着改写措辞：

| 问句 | 被判成 | 缺的词 |
| --- | --- | --- |
| 最干的时候湿度多少 | 当前值 | MINIMUM 缺"最干" |
| 平时湿度大概在什么水平 | 当前值 | AVERAGE 缺"平时" |
| 温度超了没有 | 当前值 | ALARM 有"超标"无"超了" |
| 多大声算超标 | 是否超标 | THRESHOLD 缺"多大声算" |
| 湿度低于多少会报警 | 是否超标 | THRESHOLD 缺"低于多少" |

补进 8 个词，另加一条**单位兜底**（问句未点名通道但带单位时，"度"→温度、"%"→湿度，
使「这一阵子平均多少度」「现在多少度」直接命中）。补完后规则命中率涨了 9 个百分点，
这些问句从此零延迟、结果恒定。

**由此得到一条工作方法：遇到答错先查规则词表，再考虑改提示词。** 补一个关键词的收益比任何
提示词调整都直接，且不引入新的不确定性。这条写进了脚本头部注释与 `intent.py` 的词表说明。

### 14.2 剩余 5 条未通过的性质

- 「空气干不干」「潮不潮」：规则未认出，**模型也拒绝了**，回落帮助文案——安全失败。
- 「今天最热的时候多少度」：规则读成当前值（"最热"尚未进 MAX 词表），真正的错答。
- 「站里是不是太热了」「声音是不是太大了」：期望"是否超标"，系统答的是当前值并附带
  "处于正常范围"。**期望值本身可争议**：这样回答实际上把问题答了。

也就是说真正算错的只剩 1 条，其余要么安全拒绝、要么答案可接受。

### 14.3 改写采纳率 64.7% 说明了什么

51 条规则命中的问句里，33 条的模型改写被采纳，18 条退回模板。**超时计数为 0**，
因此这 18 条全部来自接地校验——模型在改写时动了数字（四舍五入、补一个并不存在的阈值），
出口检查抓住并丢弃。**这个数字本身就是那道校验在工作的证据**，而不是缺陷。

## 15. 追问与余量（2026-09-08）

### 15.1 上一轮通道的记忆——存在规则层，不喂给模型

"现在噪声多少" → "最高呢"。第二句没有通道，此前只能回落到帮助文案。

`Assistant` 现在记住上一句问的通道与时间戳（`CHANNEL_MEMORY_SECONDS = 180`），
`intent.recognise(question, default_channel)` 在补全时使用。**这是整套问答全部的对话记忆。**

为什么不是把对话历史送进模型：

| | 记一个词 | 喂历史 |
| --- | --- | --- |
| 延迟 | 0 | 提示词逐轮变长，prefill 是 CPU 推理的主要成本 |
| 稳定性 | 恒定 | 先前标签会影响后一次分类 |
| 可测性 | 单元测试直接断言 | 只能靠采样统计 |

三分钟是演示的节奏，不是测出来的常数。它过期后的行为就是原来的行为——帮助文案，
所以"记错了"的后果是让用户重问一遍，而不是给出一个关于错通道的真实数字。

**两条限制比功能本身重要**：

1. 句子自己说出的通道永远优先，记忆只补空缺。
2. **只补给已经匹配到统计词／报警词／阈值词的句子。** 第一版没有这条，
   结果任意一句话都能继承上一轮的通道——演练里"帮我订张票"被答成了当前湿度，
   "别吹了关上吧"被读成一次湿度提问而没能交给模型分类。记忆的作用是补全一次追问，
   不是替一句没匹配上任何东西的话找个话题。

指令分支在 `_fan_intent()` 里，位于读取 `default_channel` 之前，因此**指令永远不继承通道**：
问句猜错通道只是答非所问，指令猜错通道会改错东西。

### 15.2 "还差多少就超限了"

一句话两个要求是常见说法。`Facts.margin` 由取数层算出（读数与所引用边界之差，
未越限为正、已越限为负），模板据此附一句"距 35℃ 的报警阈值还有 10.3℃"。

**减法放在代码里，不是交给模型。** 模型算出来的差值是一个新数字，会被接地校验拦下；
取数层算出来的差值是一个事实，与读数、阈值同等看待。`margin` 及其绝对值都进了 `Facts.numbers()`，
因此模型改写时可以自由复述它。

### 15.3 演练发现的、尚未处理的一处

接地校验管的是**数字**，不管**结论**。演练中"最高呢"的模型改写写成了
"该值超出了规定的阈值，处于超标状态"——数字都对，但 `MAXIMUM` 的事实里根本没有越限判定这一项
（该通道的最高值确实高于阈值，所以这次说对了，但那是巧合）。要堵住它得校验断言而不只是数字，
成本远高于现在这条；目前的处置是记录在此，并在提示词里已有"不要补充未给出的信息"一句。

## 16. 让模型解释，而不只是改写（2026-09-08）

### 16.1 起因：事实取了一堆，模板只用一个

一次读数提问的 `Facts` 里有：当前值、最小、最大、平均、样本数、阈值（或区间）、
阈值依据、距阈值的余量、是否越限。模板打印其中一到两项，**其余全部丢掉**。
"对 AI 的利用程度太低"，问题不在模型能力，在于送给它的东西太少。

`JOB_EXPLAIN` 把 `phrasing.facts_brief(facts)` 的整张事实清单交给模型，
要求用两到三句说清楚。**送过去的每一个数字都是接地校验随后会认的那些数字**——
它看到的和它被允许说的是同一个集合，因此这一步没有放宽任何约束。

`EXPLAINED_KINDS` 限定为事实明显多于模板输出的几类；"最高值是多少"只有一个数字，
展开只会变成注水，仍走改写。

### 16.2 顺带修掉的一个静默缺陷

`_render_fan()` 会打印 `fan_reason`，而那句话里带数字（"温度 26.0℃ 高于通风阈值 25℃"）。
这些数字**此前不在任何 `Facts` 字段里**，于是：

> 风扇真正在转的时候，风扇答案的模板自身通不过接地校验，
> 因此它的每一次模型改写都被静默丢弃。

从外面看就是"风扇的回答从来不会变好听"，没有任何报错。补进 `vent_temperature_max`、
`vent_humidity_max` 与 `readings` 之后，模板自洽了，改写也能被采纳了。

**这类缺陷值得单独记一笔**：它不是逻辑写错，是一处事实没有登记，
而后果由一条本意是保护系统的校验来承担——出口校验越严，喂给它的事实就越要完整。

### 16.3 报警断言黑名单

`phrasing.ALARM_CLAIM_WORDS = ("超标", "告警", "故障", "危险", "报警状态")`，
`facts.triggered` 不为真时出现即整段作废。

**必须说清楚它和接地校验不是一类东西**：

| | 数字 | 结论 |
| --- | --- | --- |
| 集合 | 闭集，可穷举 | 开集 |
| 检查方式 | 白名单，完备 | 黑名单，不完备 |
| 保证强度 | "不可能编造数字" | "常见的编造会被拦下" |

之所以只做这一条而不做通用断言校验：判断一句中文断言了什么，本身是个语言问题，
最趁手的工具正是被检查的那个模型——用模型校验模型没有底。做成通用白名单则要先把
"允许说什么"结构化，而那等于把模板重写一遍，模型就没有存在的余地了。

已知的误杀：`triggered` 为假时"没有超标"与"超标"一起被拒。代价是一句更生硬的模板，
换来的是不必解析否定辖域。**"报警"一词不在表内**——正常回答里"报警阈值"随处可见。

### 16.4 代价：时延

实测（qwen3.5:4b，纯 CPU）：改写约 2~4 s，解释约 8~14 s。提示词更长、输出也更长。

**这不是阻塞等待**——`ask()` 依旧同步返回模板答案，解释是后来替换上去的。
但演示时"好答案在十几秒后才落地"是要考虑的现场因素，所以 `EXPLAINED_KINDS`
应当保持窄，而不是能展开的都展开。

## 17. 反问澄清（2026-09-08）

### 17.1 起因：一个关于"谁也没提到的通道"的回答

"超标了吗"没说通道。此前 `retrieve()` 直接返回 `available=False`，模板据此渲染成
**"该通道现在还没有有效读数，可能是刚启动或者传感器没接好"**——一句关于谁也没提到的通道的话，
而且把"没听全"说成了"传感器可能坏了"。

`Facts.needs_channel` 把这两种情况分开：`available=False` 是"听懂了，数据还没有"，
`needs_channel` 是"听懂了，不知道问的是谁"。前者报告状态，后者**问回去**。

### 17.2 反问不替代模型，两者同时进行

`ask()` 立刻返回 `你问的是温度、湿度还是噪声？`，**同时照常把原句交给模型分类**。
"这半天里最闹腾的时候到底是多少"的通道藏在"闹腾"里，规则认不出而模型能认出；
模型若认出来，答案就替换掉那句反问；认不出，反问留在屏幕上等用户回一个词。

**问回去和猜一猜不是二选一**：一个是立刻到达的，另一个是随后替换它或者没有。
这也是为什么反问要走模板：改写过的问句是另一个问句，而这句话唯一必须做对的事，
就是把那三个词原样说出来。

### 17.3 一个词怎么被认出是回答

用户回的是"温度"这样一个光秃秃的通道词，规则会把它读成一次 `CURRENT_VALUE` 请求。
判据就用这个：**待答问题存在 + 新句子除了通道什么也没要 = 通道就是答案**，
`replace(pending, channel=...)` 之后走正常流程。

新句子若带着自己的意图（"有几个设备在线"、"把风扇打开"），那就是换了话题，
**待答问题当场丢弃**而不是留着——留着的话，再往后某个通道词会莫名其妙接到它上面。

超时 `CLARIFY_SECONDS = 60`，比 `CHANNEL_MEMORY_SECONDS`（180）短。理由：
记住的话题是个提示，下一句可用可不用；**没答的问题是一份承诺**。用户几分钟后回来说"温度"，
此时给出旧问题的答案，是一个正确但答非所问的回答——这种错比重问一遍难发现得多。

### 17.4 顺带补上的 `reset_conversation()`

有了对话状态之后，演练脚本的两轮就不再等价：第一轮"超标了吗"开局无话题、触发反问，
第二轮继承了第一轮最后的通道、直接作答。两者都对，而稳定性检查恰恰要求两轮从同一处出发。

`Assistant.reset_conversation()` 只清"上一句问的是什么"和"还欠着哪个问题"，
**不动读数、阈值、风扇模式**——那些不是对话。界面上的"清空对话"、下一个走到屏幕前的人，
需要的是同一个方法。

## 18. 移动端问答在 PC 留痕（2026-09-08）

### 18.1 缺的是"谁改的"

设置回流（`Project_Status_Context.md` 同日条目）已经让手机改的风扇模式出现在 PC 面板上，
但它只回答"现在是什么"。**"刚才是谁改的"回答不了**，而多客户端能改同一套设置时，
这是个正当问题——也是有人回头追问"风扇怎么自己开了"时要找的那一行。

### 18.2 网关交出事实，组合根决定措辞

`gateway.server` 新增 `QuestionObserver = Callable[[str, Answer], None]`，
由 `create_app(on_question=...)` 或 `set_question_observer(app, ...)` 挂上
（后者是因为启动器建服务器在建窗口之前）。

**交出去的是整个 `Answer`，不是一句排好版的话。** 指令有没有真的执行在 `facts.applied` 里，
而怎么说这件事是呈现层的决定；在网关里拼这句话等于把呈现塞进无界面服务。
`run_all.py` 据此调 `controller.note_remote_question(...)`，桌面端活动日志出现：

```
移动端提问：现在温度多少 → 温度现在是 21.5℃，距 35℃ 的报警阈值还有 13.5℃。
移动端下发：把风扇打开 → 已把风扇切到手动常开，当前判定是运行。
```

**提问与下发分开标注**：提问只是上下文，下发改变了这台系统的行为。

### 18.3 只留痕，不同步聊天记录

明确不做的是把手机的问答气泡搬进 PC 的问答面板。两端问句交错在一条记录里是噪音；
而且问答本身是只读的，同步过去没有任何后果可言。**有后果的是指令，
而指令的后果由设置回流与这条留痕共同体现。**

### 18.4 顺带修掉的一个观感问题

模型的迟到答复本来就向两端广播（`run_all.py` 的 `deliver_assistant_answer` 扇出），
所以**手机提问的模型改写一直会出现在 PC 问答面板里，而上面没有对应的问句**——
一条没有来由的回答。补上留痕之后，那条答复落在它自己的提问下面。
