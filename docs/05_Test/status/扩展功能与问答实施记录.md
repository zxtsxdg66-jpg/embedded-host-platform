### 关键决策与理由

1. **WiFi 模块舍弃**。AI 跑在 PC 端，而数据本来就经 USB 串口到了 PC，WiFi 不提供新能力。舍弃后连带解决了一个硬冲突——板载 ATK-MODULE 接口走的正是 PB10/PB11，与噪声传感器占用的引脚相同。
2. **报警阈值不动**（温>35℃ / 湿<30% / 噪>80dB，论文按 GB 37488—2019 论证过的那套原样保留）。风扇另设一套**独立的通风阈值**，与报警解耦——这样论文既有论证不受影响，且解决了"湿度是过低报警、吹风扇没有物理意义、且实测湿度 69~95%RH 永远不会低于 30% 因而从未触发"这个逻辑问题。
   - 通风阈值初始值：**温度 30℃ / 湿度 80%RH**，且**可在运行时调整**（答辩演示时调低即可让风扇立刻转起来）。
3. **噪声消隐（重要）**：喇叭播放告警会让噪声传感器读数飙升，可能形成"报警→播报→噪声升高→再报警"的正反馈。
   - **不物理关闭传感器**——HH_07.06 有 400ms 内部刷新周期，且本项目已实测记录"Modbus 链路建立后首次读数不可用"这一缺陷，断电重启会每次都踩中它。
   - 改为**消隐**：播报期间**跳过噪声的 Modbus 请求**（不是读了丢弃，以保住"Modbus 应答成功率"指标的口径），`noise.valid = 0`，现有固件逻辑会自动不上报该通道，**PC 侧零改动**。
   - 播报结束（查询 TTS/播放状态得知）后再延一个采集周期（3s）作为混响拖尾。
   - 分工：**消隐时序放固件**（只有固件知道精确播放时刻），**冷却与去抖放 PC**（便于调参，不用重烧固件）。
4. **播报冷却 30 秒**；报警需**连续 2 个采集周期**（≈6s）超限才判定，避免单个尖峰误触发——顺带落实了论文第 10 章已列出的改进方向"为报警判定引入回差与持续时间确认"。
5. **排班表 / 列车进站时间**：虚拟数据，**本阶段只讨论不开发**。将来若写入论文**必须如实标注为模拟数据**。

> **已核实的关键结论**：AHT20 占用的 PE0/PE1 与 LCD **不冲突**——硬件手册标注它们是 `FSMC_NBL0/NBL1`"SRAM 专用"，而官方探索者 F407 LCD 驱动（`atk_md0280_fsmc.h`）的实际引脚定义里**完全没有 PE0/PE1**，数据线走 PD 口 + PE7~PE15。前提是不启用板载外部 SRAM（本项目本来就不用）。
> ☆ 仍建议在 LCD 接入后实测复核一次软件 I2C 是否仍正常。

### 已知的待办与风险

- ☆ **供电**：LCD 背光 113mA + 风扇电机启动电流，建议改用板载 **DC6~15V 电源输入口**供电，不要靠 USB 取电。
- ☆ **演示触发困难**：报警阈值固定为 80dB/35℃，而实测哈气最高 31.23℃、人为声源最高 55.95 dB(A)，**答辩现场可能无法自然触发语音告警**。通风阈值可调已解决风扇的演示问题，语音告警是否也需要一个明确标注的"演示模式"覆盖，待定。
- ☆ **AI 与 GUI 的线程冲突**：本项目 GUI 目前全同步、无 QThread（见 `src/ui/README.md`），串口轮询也在主线程的 QTimer 上。将来接入 Ollama 时若在主线程等待 HTTP 返回会卡住界面与轮询——**AI 将是本项目第一个真正需要 QThread 的地方**，届时属架构变更，需按 `CLAUDE.md` 修改规则先说明原因。
- ☆ **AI 正确性设计（已达成共识）**：不靠"换大模型"保证不出错，而是**让模型碰不到数值**——数值由代码从 `SensorDataProcessor` 直接取，模型只做意图识别与措辞组织。用户机器为 i5-13500H + 32GB DDR5-5200、**无独立显卡**，纯 CPU 推理，瓶颈是内存带宽；建议用 4B 级别模型并实测确定。

### ⚠️ 踩到的坑：在数据发布回调里下发命令会重入串口（已修复）

第一版把命令下发直接写在 `handle_decision()` 里（即 `DataService` 发布回调链上）。**这在 Hardware 模式下是不安全的**：该回调由 `HardwareRuntimeRunner.run_once()` 读串口的过程中触发，此时下发命令会重入 `DeviceManager.deliver()`，而它的 RemoteDevice 分支要读**同一个串口**等应答、且用的是另一个 `FrameStreamBuffer`——两个读者抢同一条流会互相吃帧，整个往返还会卡住定时器回调。

**不是理论推演**：实测直接把测试进程打崩（`Fatal Python error: Aborted`），且是否触发取决于测试文件的字母顺序——当时的 593 个用例全部显示通过，pytest 却非零退出。这种"绿了却崩"的失败方式最危险，因为它会让整条质量基线不可信。

修复：拆成 `handle_decision()`（只记录，不发送）+ `dispatch_pending()`（由轮询循环调用）。真机上这同时避免了"等应答期间冻结界面并丢掉传感器读数"。

顺带修了 `background_widget.py` 的 `paintEvent`：底层 C++ 对象销毁后仍可能收到排队的重绘事件，而 `paintEvent` 里抛异常会被 Qt 当致命错误 abort 整个进程，现已吞掉并说明原因。

**噪声消隐的实现要点**：播报期间（以及播完后再延一个采集周期让混响衰减）**跳过整个 Modbus 请求**，而不是照常请求再丢弃结果。两个原因：不占用总线；且论文第 9 章的"Modbus 应答成功率"以发出的请求数为分母，跳过的周期不进分母，指标口径才干净。温湿度照常采集上报，噪声通道 `valid=0`，现有固件逻辑会自动不上报该通道，**PC 侧零改动**。

> ⚠️ **音频数据尚未提供**：`alert_pcm.c` 目前三句都是 `sample_count=0` 的静音占位。烧录后播报命令会被正常接受、噪声消隐也会生效，但**听不到声音**。这是有意为之——让整条链路（PC 判定 → 命令下发 → 固件执行 → 消隐）可以先独立验证，不必等音频就绪。
> 补齐方式：自行合成三句 WAV 后运行
> `python scripts/wav_to_c.py 温度.wav 湿度.wav 噪声.wav`，重新编译烧录。
>
> **体积估算**：三句各 3 秒、16kHz/16bit 单声道合计约 288KB，而 F407ZGT6 有 1MB Flash、当前固件仅用约 19KB，余量充足。

**验证程度**：PC 侧 627 个测试全绿；转换脚本已用三种格式的真实 WAV（16k 单声道 / 44.1k 立体声 / 8k 八位）实测通过。**固件侧无法在此编译，音频链路完全未实测。**

**编译过程中踩到的坑（值得记住）**：链接连续两次报 undefined symbol，都出在 Keil 工程的 HAL 文件集合上。

1. `HAL_I2S_Init` 未定义 —— `stm32f4xx_hal_i2s.c` 没被加进工程。文件本身在、`HAL_I2S_MODULE_ENABLED` 也早已开启，纯粹是漏加。
2. `HAL_I2SEx_FullDuplex_IRQHandler` 未定义 —— **`stm32f4xx_hal_i2s.c` 与 `stm32f4xx_hal_i2s_ex.c` 在 F4 上是成对的，不能只要一个**：前者在 `HAL_I2S_Init` 里无条件写入 `hi2s->IrqHandlerISR = HAL_I2SEx_FullDuplex_IRQHandler`，哪怕根本不用全双工。

> ⚠️ **两条操作教训**：
> ① **改 `.uvprojx` 前必须先关闭 Keil**。Keil 在内存里持有整份工程模型，Rebuild/保存时会整个写回磁盘，把外部修改直接覆盖掉（本次因此白跑一轮）。
> ② 检查"HAL 文件是否齐全"时，**必须做传递闭包**——只扫描自写代码引用了哪些 HAL 函数是不够的，HAL 文件之间还有内部依赖。正确做法是把工程内的 HAL 文件也当作消费方反复迭代，并在匹配前**剥离注释与字符串**（否则 `stm32f4xx_hal_pwr.c` 注释里提到的 `HAL_RTC_SetAlarm_IT()` 会被误判成真实调用，导致误加 RTC 文件）。

**三条值得记住的设计决定**：

1. **屏幕只显示固件确实知道的状态**。数值来自本机采集、风扇状态来自 `fan_is_running()`、播报状态来自 `audio_alert_is_playing()`；唯独"正常/报警"固件不可能知道（阈值在 PC），所以由 PC 经新命令 `ALERT_STATE`(0x15) 下发位图。**没有让固件复制一套阈值**——否则同一套 GB 37488-2019 论证会出现第二份并悄悄分叉，现场表现为"PC 报警了、屏幕还是正常"，极难解释。
2. **「语音自检」不上报 PC**。自检不是告警，不进日志、不计入告警次数、不消耗 30 秒冷却窗口；但照样触发噪声消隐（消隐判据是"喇叭在响"，与谁请求的无关）。与"消隐时跳过 Modbus 请求而不是请求了再丢掉"是同一个统计口径原则。
3. **第一版 LCD 上不放手动风扇按钮**。板上按钮与 PC 的"共享读、独占写"占用规则会打架（PC 端有客户端持写权限时，板上按一下算谁的），要圆得在协议里加"本地接管"状态位并上报，工作量与论文解释成本都不小；显示 + 自检已足够撑起 LCD 的演示价值，手动控制 PC 端本来就有。

**顺带修掉的一个真实隐患**：厂商 `lcd.c` 在 `lcd_init()` 末尾有 `printf`，而本工程 `useUlib=0` 且**全项目没有任何 printf 重定向**——ARM Compiler 5 会走半主机，**烧录后脱机上电会直接卡死**在那一句。已在 `debug_log.c` 补 `__use_no_semihosting` + `fputc → USART2`。这个问题与 LCD 一起进来，但性质上是原有工程的缺口。

**HAL 依赖核查方式已改进**：上次漏掉 `hal_i2s_ex.c` 是因为只查了"我们的代码调了什么"，看不见 HAL 内部依赖。这次改成对 `.uvprojx` 里全部 46 个 `.c` 文件取**传递闭包**，剥掉注释与字符串再比对，并解析 `stm32f4xx_ll_fsmc.h` 里 `#define FMC_xxx FSMC_xxx` 这类**对象式宏别名**（第一版因为没解析它而误报了 6 个 `FMC_NORSRAM_*`）。最终结果：**0 unresolved externals**。

**待实机确认**（见 `docs/09_STM32Hardware/STM32F407_硬件落地方案.md` 同名小节）：LCD 是否点亮；首次上电的阻塞式五点触摸校准；**接屏后 AHT20（PE0/PE1）是否仍正常**；屏幕刷新是否影响 Modbus 应答成功率；触摸按钮命中范围。

#### 试用中发现并修复的 bug（2026-09-08）

**连问几个问题时，回答几乎全标「系统」，且出现答案错位**——第一题的改写贴到了第二题的气泡上。
根因：`_start_rephrasing()` 在模型忙时直接 `return`，导致新问题被跳过（"全是系统"），
而旧问题的 pending 状态仍挂着、几秒后投递到已经换了主题的界面上。

后者是本设计最想避免的那类错误的变体：**数字全真，但答的是没问的问题**，比数字错更难察觉。
改为新问题进来时取消在飞请求——在源头消除，而不是让每个消费端自己去防。

#### 试用中发现的第二个 bug：仿真模式的通道订阅（2026-09-08）

**两种模式的设备形态本来就不一样**，而 UI 的通道下拉框是写死的三个预设、与选中设备无关：

| | 设备数 | 每个设备的通道 |
| --- | --- | --- |
| 硬件模式 | 1 个 | temperature + humidity + noise |
| **仿真模式** | **3 个** | **各 1 个** |

于是仿真模式下每选一个设备，三个选项里**有两个是死的**——订阅被接受、活动日志照写"已订阅"、然后永远没有数据：

```
sim-env-1-temp + temperature  →  收到 6 条
sim-env-1-temp + humidity     →  订阅"成功"，收到 0 条
```

**硬件模式把它完全盖住了**（一个设备带全部三个通道，怎么选都对），所以这个只在最常用于演示的仿真模式下犯病的问题一直没被发现。

**修法**：设备能力里本来就声明了通道，只是从没送到 UI。`DeviceStatusView` 加 `channels` 字段（纯追加、带默认值，不新增抽象方法，接口守卫测试不受影响）→ `MainController.device_channels_changed` 新信号（不动旧信号签名）→ `ControlPanelWidget.set_channel_options()` 按选中设备刷新。**只有一个通道时自动选中**，仿真模式从"三选一还要选对"变成"点了就能订阅"。

下拉框保持可编辑（平台不固定通道 id 枚举），设备未声明通道时保留通用预设而非空白。

> 顺带确认：订阅一个**不存在的设备**同样返回成功、同样没数据。`DataService` 是设备无关的（允许先订阅后注册），该语义未改动——问题在于 UI 不该给出无效选项，而不在于底层该报错。

#### 追加：自然语言下发控制（P1c，2026-09-08 晚）

**做法**：指令与提问共用同一次模型分类，只是分类结果走 `service/assistant/control.py` 而不是取数层。
白名单四项——开/关/自动风扇、改通风阈值，全部只写 `VentilationController` 的设置，
**与界面上点一下是同一次写入**，之后由既有下发逻辑在下一轮轮询发帧。没有新增命令通道。

**最关键的一条**：改阈值时**数值从用户原话里正则取，不取自模型回复**。模型只说"这是一条改阈值的指令"。
理由是模型把 28 复述成 38 只要发生一次，系统就会安静地按错值通风，且下游无从发现。
配套拒绝：句子里没有数字（"调低一点"）或有两个数字（"从 30 调到 28"，取第一个会设成用户正要离开的值）都拒绝。
值域按论文 P2~P4 的量程校验（温度 0~50℃ / 湿度 0~100%RH）。

**确认语只说改了什么设置，不说硬件状态**（"已把风扇切到手动常开"而非"风扇已启动"）——
帧要下一轮才发、且要应用持有控制权。指令的确认语也**不送给模型改写**：确认语每次都该一模一样。

**演示流程演练（无界面，但用 `run_gui.py` 同一套装配 + 真实 Ollama + 同一个 `poll_once`）**：
14 句 × 2 轮。**指令类 8 条两轮完全一致**；模型识别 1.6~3.9 s；规则命中的指令不调模型、即时生效。
唯一不稳定的是「站里闷不闷」——三次运行判成了湿度当前值 / 温度当前值 / 温度报警阈值，
因为"闷"本身同时指向温度与湿度。三次都是真实读数，只是回答了不同的那一个，**未做特殊处理**。

**演练当场揪出两个单元测试没覆盖的规则缺口**（都已修复并补回归）：
「这一阵子最吵到多少」答成当前值（MAXIMUM 不认"最吵"）；
「把通风温度阈值调低一点」被当成问句答了风扇状态（阈值指令分支当时要求句子里必须有数字）。
**两个都是"看起来完全正常"的错误**——这正是完整走一遍演示流程不能被单元测试替代的地方。

演练已固化为项目工具 **`scripts/demo_rehearsal.py`**（答辩前跑一遍看当天模型状态；
`--no-llm` 秒跑；**退出码只在"同一句话执行出两种不同动作"时才为 1**——

#### 追加：湿度双向阈值与屏幕构建标记的删除（2026-09-08 深夜）

#### 追加：第二档反问澄清（2026-09-08 深夜）

**起因是一句错得很隐蔽的回答。** "超标了吗"没说通道，此前返回 `available=False`，
模板渲染成"该通道现在还没有有效读数，可能是刚启动或者传感器没接好"——一句关于谁也没提到的通道的话，
还把"没听全"说成了"传感器可能坏了"。`Facts.needs_channel` 把"数据没有"和"不知道问的是谁"分开。

**反问与模型分类同时进行，不是二选一。** `ask()` 立刻返回反问，**同时照常把原句交给模型**；
模型认出通道（"最闹腾的"→噪声）就替换掉反问，认不出则反问留着等用户回一个词。
反问本身不送去改写——改写过的问句是另一个问句。

**一个词怎么被认出是回答**：待答问题存在 + 新句子除了通道什么也没要 = 通道就是答案。
新句子带着自己的意图就是换了话题，待答问题**当场丢弃**而不是留着。
`CLARIFY_SECONDS = 60`，短于 `CHANNEL_MEMORY_SECONDS`（180）：记住的话题是提示，
没答的问题是承诺，几分钟后再兑现会给出"正确但答非所问"的回答。

**新增 `Assistant.reset_conversation()`。** 有对话状态之后演练两轮不再等价（第一轮开局无话题触发反问，
第二轮继承了上一轮的通道直接作答，两者都对），而稳定性检查要求两轮同起点。
只清对话状态，不动读数/阈值/风扇模式。

**第四轮评测：65/65 = 100%，四项指标与第三轮完全一致。** 反问只改变"未指明通道"一类问句的处理，
题库里的问句都点了通道，因此不会侵入已经正确的路径——这正是重测要确认的。
演练脚本实机走通"超标了吗 → 反问 → 噪声 → 答的是越限而非当前值"。

#### 追加：手机端问答的网关侧（2026-09-08）

**做法**：网关加 `POST /assistant/ask`（对应 `ApiInterface.ask`），迟到的模型答案经已有 WebSocket 以

`run_all.py` 用一个 lambda 同时喂桌面控制器和手机——**一个助手，两个呈现端**。

**为什么不是一个请求等到底**：`ask()` 同步返回规则与模板答案（毫秒级），模型改写要数秒。
挂住请求等模型会让没接模型的部署也变慢，手机端一旦超时更是什么都拿不到；

**顺带修好一处 drift**：`run_api_server.py` 此前**根本没有 attach 语言模型**——它是无界面启动器，
没有任何别的地方会做这件事，于是手机方向的问答只能是模板。已补上，并新增一条测试断言两个网关启动器
都出现 `assistant_sink`、无界面启动器还必须出现 `attach_language_model`。

执行并确认、无补送（指令的确认语不交给模型改写）；「帮我订张票」模型拒绝、无补送；空问题返回 400。

#### 值得记入论文的四个调试案例

前两个是"照抄厂商驱动"与"真正理解厂商驱动"之间的差别，很适合作为第 5 章或第 9 章的实证材料：

1. **`tp_scan()` 的返回值恒为 0**。厂商写的是 `return tp_dev.sta & TP_PRES_DOWN;`，而 `TP_PRES_DOWN = 0x8000`、函数返回类型是 `uint8_t`——按下时截断成 0。厂商自己的例程从不看返回值，一律单独判 `tp_dev.sta`。**照抄了函数名却没照抄调用方式**。
2. **出厂遗留的竖屏校准数据**。`tp_init()` 只在 24C02 无校准标记时才校准；开发板出厂测试程序已写过一份**竖屏**校准值，而本项目跑横屏，坐标换算方向不同——数据"存在且合法"，却完全不可用。厂商代码无法察觉这种情况。解决办法是加 KEY0 强制重新校准。
3. **UTF-8 中文字符串被 armcc 按 GBK 解析**。结束引号被当成多字节尾字节吃掉，报 `missing closing quote`，而报错完全指不到真因。加 `--no_multibyte_chars` 解决——该结论是在本机用 armcc 对全工程 46 个文件做过对照实验后确定的，**不是推断**。
4. **风扇全速过快**。原设计刻意不用定时器（避开 TIM1 的引脚冲突），实机发现全速不可持续；改用 PWM 时发现 **PE5 的 AF3 恰好是 TIM9_CH1 且 TIM9 全项目空闲**，因此调速改造**未涉及任何接线变更**。

#### 新增的两道防线

- **`scripts/check_keil_project.py`**：校验 `.uvprojx` 是否包含全部必需文件与编译选项。Keil 会在退出时把内存中的工程模型整体写回、**静默覆盖外部修改**，本项目已因此漏掉 HAL 文件两次（09-07 `hal_i2s.c`、09-08 `hal_tim.c`），两次都是编译报错后才发现，而报错指向 HAL 内部符号、与真因无关。**建议每次从 Keil 退出后执行一次。**
- **屏幕构建标记**（2026-09-08 已移除）：调试期间标题栏右侧显示过 `b3`，改动固件行为时手动 +1。用于排除"改了固件但不确定烧进去的是不是这一版"这一干扰项——尤其在工程文件被覆盖、新文件根本没参与编译时，现象与"代码没生效"完全一致。

#### 一个已知局限（符合设计，未改）

PC 启动后屏幕仍显示"未连接"，需手动触发一次风扇才变为"已连接"。链路指示的判据是"收到过上位机的帧"，而上位机只在状态变化时才下发命令，开机后长时间无下行帧属正常稳态；刻意未做超时回落（会把稳态误报成掉线）。该指示的准确含义是**已与上位机握手**，而非"此刻链路通畅"。可选改进：PC 在硬件设备注册后主动发一次 `PING`，即可让指示开机就亮。

### 已实施：复合句拆句（2026-09-15）——问答第五类改动，设计见 `Assistant_Design.md` §12.2

**起因是真人试用**："现在多少度啊 有点热 你可以帮我打开风扇嘛"只执行了开风扇，温度那一问整段丢掉；
接模型之后回来的是一句莫名的"你是想让我把风扇切到手动常开吗"。两层原因叠在一起：

1. 规则一次只返回一个意图，风扇分支排在通道之前，整句被判成 `FAN_ON`；
2. 09-14 上线的复核把**整句**交给模型，而分类提示词只许回一个标签。模型回了
   `current_value temperature fan_on` 两个标签，被 `parse_reply` 作废、回复非空，于是走了反问。

**模型没有判错——输入里本来就有两件事。** 这一点值得单独记：复核是按"一句话一个意图"设计的，
真人说话不按这个前提来，而缺陷表现在模型那一侧，很容易被误判成模型能力不足。

**做法**：`Assistant.ask()` 在确认问句之后、整句识别之前先试拆句
（`_split_compound` / `_answer_compound`），按句读和空格切分，每段各过一遍规则，
**只在确有两件事时接管**，否则返回 None、整句照旧处理。五条规则都是为了防止"拆出多余的一件"：

| 规则 | 理由 |
| --- | --- |
| 提问段须带问句标记（`intent._QUESTION_MARKERS`） | "太热了，把风扇打开"里的"太热了"会被规则读成问是否超标，拆开单独答就平白多一句 |
| 同种类同通道的提问合并为一件 | "现在温度多少，还差多少超限"后半句继承温度，合并后只剩一件，整句照旧并带余量 |
| **指令至多一条**，两条则不拆 | 一句话里两次改设备状态，任何一条判错用户都要从一次回显里读出来 |
| 紧挨数字的空格、小数点不算断点 | "通风阈值调到 28 度"拆开后读不到数值，指令会被拒 |
| 段内沿用前一段的通道与问法 | "噪声最高多少，平均呢"，与跨轮追问同一套规则 |

**提问部分只用模板、不送改写**：几段事实拼成的一句话没有单一的 `Facts` 供接地校验对照，
放宽校验去迁就它等于拆掉"数字只来自事实"这道闸。指令照常复核，但**只送指令那一段**；
复核结果回来时把已答的提问接在前面（`_pending_prefix`），因为界面会用迟到答案整条替换占位，
不接的话已显示的读数会凭空消失。

**回归用快照法**：87 句题库、148 句留出题库、32 句鲁棒性题的回答、意图、是否执行、风扇模式与阈值
逐句快照前后对比，**267 句逐项不变**，变的只有三句专门构造的复合句，全是预期中的"多答出一件"。
新增测试 12 项（`test_intent.py` 4、`assistant/test_assistant.py` 8）。

**两两组合题库**（脚本与输出归档在 [`../baseline/`](../baseline/)）：把 87 句里 73 条可组合的
问句与指令两两拼成"A，B"，不接模型跑全量。

| | 组合数 | 首版 | 补问句标记后 | 两句单独问都对 |
| --- | ---: | ---: | ---: | ---: |
| 问 + 问 | 2390 | 65.9% | **93.5%** | 100% |
| 问 + 指令 | 2244 | 80.4% | **96.1%** | 100% |

**首版的失败全部能归到十个单句**，问法集中在三类："超了没有""开了没"这类以"没"作问、
"冷不冷""吵不吵"这类正反问、以及"有多响"。它们单独问时规则认得出，放进复合句却被判成
缺问句标记的铺垫、整段丢掉。补上这三类（含 `intent._A_NOT_A` 正反问正则）后，
剩下的失败只与两句有关，而那两句都属于**按设计不拆**：

- **"好闷啊"**：没有任何问句标记，与"太热了"同类。复合句里把体感当铺垫是有意的取舍。
- **"阀值是多少"**：没点通道。单句时系统会反问哪个通道，而**拆句不接管需要反问的提问**，
  于是这一问在复合句里被跳过。这是**已知局限**——一句话里同时挂一个反问与另一件事，
  界面上无法说清下一个"温度"补的是哪一半。端到端看得更直接："设备都连上了吗，阀值是多少"
  只剩一件事可拆，退回整句处理，只回了"你问的是温度、湿度还是噪声？"，设备那一问丢了。
  前面若已有点了通道的提问，后半句会沿用那个通道，不受影响。

全部即时返回（不送模型）。**复核只送指令段之后，25 条指令段模型全部同意**，
