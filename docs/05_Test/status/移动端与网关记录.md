## 5.1 PC↔Android 架构模式已确定（2026-08-14，设计阶段，未编码）

`docs/02_Architecture/Multi_Client_System_Architecture.md` 第 2.3 节已把 Android 接入模式从"预留待定"确定为**网关模式的特化形式：PC 上位机自己兼任网关**（不引入独立第三方网关进程），REST 用于查询/指令类交互、WebSocket 用于实时数据/报警推送，局域网内直接通信（同一 Wi-Fi/热点），不需要云服务器。具体接口设计（REST 端点、WebSocket 消息格式）见新增文档 `docs/10_AndroidClient/PC_Android_接口设计.md`。

**重要发现**：核对 `src/api/`/`src/service/`/`src/application/` 后确认，用户要求的 7 项 Android 能力中 **6 项已有现成的 `ApiInterface` 方法可以直接封装**（设备列表/实时数据/多通道数据/设备状态/报警信息/控制指令），只有**"查看历史数据"这一项当前完全没有 PC 端能力支撑**——历史数据目前只存在于 `ui/widgets/data_panel.py` 的 `DataPanelWidget._history_list`（PyQt6 界面内部状态），`service`/`application`/`api` 三层都没有保存或暴露它。若要支持，需要新增 `service`/`api` 能力（如 `get_history()`），这是修改受保护接口，需要单独提出并获得授权，当前**未获授权、未实施**。

> ✅ **2026-09-17 已获授权并实施**（见 5.5 节）。这一段的**判断本身没有错**——历史数据当时确实
> 只在 `DataPanelWidget._history_list` 里，网关也确实不该伸手去读一个界面控件的内部状态。
> 变的是前提而不是原则：历史现在是平台自己的能力（`ApiInterface.query_history()`），
> 网关照常翻译接口即可。当初"不被历史数据卡住整体进度"的排序事后看是对的，
> 移动端因此早跑通了半个多月。

**当时的状态（2026-08-14，已被 5.2 节取代）**：仅完成架构模式确定与接口设计文档，`src/`、`firmware/` 均未因此产生任何代码改动；PC 端网络接口层（REST+WebSocket 服务）与 Android 客户端项目均**未开始编码**，技术选型（PC 侧 FastAPI/Flask 等、Android 侧 Retrofit/OkHttp 等）也未确定，涉及新增第三方依赖需另行获得授权。

> ✅ **上述"未开始编码"仅指 2026-08-14 当天的状态，次日即被 5.2 节取代**（2026-09-07 补注，

## 5.5 历史查询：网关端点与 Android 历史页（2026-09-17，已实现并验证）

背景与四项决定变更见 [`History_And_Cloud_Design.md`](../../02_Architecture/History_And_Cloud_Design.md) 第 0 节。
与移动端有关的一句话：**手机看的是 PC 本地历史库、经局域网网关**，不直连云端、
本机不存任何历史，因此手机端不持有任何云端凭证，也不需要 STS 临时凭证。
**上云按钮不给手机**——上云要拉起子进程，手机端看不到它的输出，失败了无从判断；
看历史是只读查询，两件事不能混为一谈。

### 契约没有重新设计

`GET /devices/{device_id}/channels/{channel}/history` 是 2026-08-14 就写在
[`PC_Android_接口设计.md`](../../10_AndroidClient/PC_Android_接口设计.md) 2.3 节的草案，
当时标注为"缺 PC 端能力，未实现"。这次**照原契约实现，字段不变**——当初设计得足够克制，
不必推翻。实现时只定下两处草案没说的细节，已回填进该文档，以免 Android 端照草案写解析器：

- **`unit` 放在顶层，不在每个点里**：它是通道的属性、不是读数的属性，逐点重复 500 遍
  不多说明任何事。来源与实时推送同一份（`gateway/channel_units.py`），
  所以同一通道在 WebSocket 与本端点拿到的单位必然相同。
- **`timestamp` 是带时区的 ISO-8601（`+00:00`）**，不是草案里的 `Z` 写法。存储层一律存 UTC，
  这里原样渲染，且与 WebSocket 的 `data` 消息共用 `gateway.events.isoformat_or_none`，两端不会漂。

查询参数 `start`/`end`/`limit`（默认 500）。**时间戳格式错误返回 400，不退化成全量查询**——
"我要最近一小时、拿回了全部"是客户端察觉不到的错答案。未知设备或通道不算错误，返回空 `points`。

`gateway/server.py` 新增该端点，仍然只是对 `ApiInterface.query_history()` 的翻译，
`api`/`service`/`application` 在网关这一步零改动（接口扩展本身属 P0，见主文件基线表）。

### Android 侧：`HistoryActivity`

按设计文档分期表里的 P1b 做，仿问答页的结构，但有两处刻意不同，都是照这一页自己的情况定的：

- **不开 WebSocket**。历史是过去的数据，不会自己变；要最新的就下拉重查。少一条连接，
  页面也少一份要在 `onDestroy` 里收拾的状态。
- **一次只看一条通道**。三条通道混在一张表里，"某个时刻温度多少"这种问题反而更难回答；
  顶部三个按钮切换，切换即重查。默认温度，与首页指标卡的排列顺序一致。

仍然沿用问答页的做法：`ScrollView` + `LinearLayout` 逐条加视图，**不引入 RecyclerView**。
理由是它是一个**尚未缓存**的新依赖，离线环境下拿不到，答辩前的构建不该为一个列表冒这种险；
而 200 行在 `LinearLayout` 里完全够用——**查询上限定在 200 是与这个取舍配套的数字**，不是随手取的。

`HistoryParser` 与 `MessageParser` 同一取向：**不依赖任何 Android API 的纯 Kotlin 对象**
（只用 `org.json`），因此能在普通 JVM 单测里直接跑；解析逻辑若留在 `GatewayClient` 里
就跑不了测试，那个类依赖 OkHttp。两者有一处刻意不同：**这里用异常，不用 sealed Result**——
WebSocket 那边解析的是消息流，一条坏消息不该中断整条连接，所以需要 `Malformed` 这个
可继续处理的返回值；这里是一次性的请求-响应，调用方本就用 `Result` 包着。
必需与可选的划分与 `MessageParser` 一致：**数值不能有默认值**，用 0.0 顶替一条读不出来的读数
比报错危险得多——界面会把编造的 0 当成真实读数画出来。另有一个与 `deviceStatus.occupant`
同源的坑：服务端在时间戳缺失时发 JSON `null`，`optString` 会把它读成字符串 `"null"`，必须显式判空。
