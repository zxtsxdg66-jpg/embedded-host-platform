## 10. 归档：硬件在环演示排障记录（已于 2026-08-12 验证通过）

完整排障过程已精简为摘要；不再是"新会话必读"的阻塞项。

**结论**：`com0com` 在本机走不通（Secure Boot 已开启，两个来源的驱动均报 `ConfigManagerErrorCode 52` 数字签名校验失败；解决办法是关 Secure Boot + `bcdedit testsigning on`，用户明确选择不走这条路，**不要重新建议**）。改走 **WSL2 + socat** 创建一对 Linux PTY 虚拟串口，最终验证成功。

**关键环境事实（未来在其他机器上复现或排障时参考）**：

1. **WSL 本身的安装在本机踩过坑**：`Get-WindowsOptionalFeature` 显示 WSL 功能 `Enabled`，但底层 `LxssManager`/`WSLService` 服务未真正部署——根因是启用该功能时需联网从 Windows Update 拉取组件负载，国内网络访问该通道很慢/不稳定。修复：`DISM /Online /Cleanup-Image /RestoreHealth` + 重新 Disable/Enable 一次 WSL 可选功能 + **重启两次**（第一次装运行时，第二次让重新部署的组件生效）。若未来换机器/环境遇到类似"功能显示已启用但 `wsl -l -v` 报没有分发版"的情况，直接照此修复，不需要重新摸索。
2. **WSL2 的 PTY 不会映射成 Windows COM 口**：因此 `virtual_stm32.py` 和 `run_gui.py --mode hardware` **必须都跑在 WSL 里**，不能一边 WSL 一边 Windows 原生。GUI 通过 WSLg 显示到 Windows 桌面。这意味着 WSL 里需要单独一份 Python 环境（本次用 `.venv-wsl`，装了 `PyQt6`/`pyserial`），与 Windows 侧的开发环境完全独立、互不影响。
3. **pyserial 在 Linux 下的 `list_ports.comports()` 不会发现任意 PTY**——只 glob `/dev/ttyS*`/`/dev/ttyUSB*`/`/dev/ttyACM*` 等固定命名模式（`serial/tools/list_ports_linux.py`），`socat` 默认建在 `/tmp/` 下的链接（如 `/tmp/ttyV0`）不会被识别，`SerialChannel.connect()`（不可修改的 communication 接口）会报"串口未找到"。**解决方式**：让 `socat` 把链接直接建在 `/dev/ttyUSB50`/`/dev/ttyUSB51` 这样匹配 glob 规则的路径下（需要 root），并加 `mode=666` 让普通用户可读写：
   ```bash
   sudo socat -d -d pty,raw,echo=0,link=/dev/ttyUSB50,mode=666 pty,raw,echo=0,link=/dev/ttyUSB51,mode=666
   ```
4. **WSLg 图形通道偶发卡死**（症状：任务栏能看到窗口但点击无反应，标题带 `[WARN: COPY MODE]`，与 PyQt6 无关——连最简单的 `xeyes` 都一样卡住）：本机通过 `wsl --shutdown` 后重新拉起 WSL 解决了一次；如再次出现，先用 `xeyes`（`apt install x11-apps`）单独排查是不是 WSLg 本身的问题，而不是先怀疑 PyQt6 代码。
5. **中文字体缺失**：全新 Ubuntu 没有 CJK 字体，PyQt6 界面里中文显示不出来是正常现象，装 `fonts-noto-cjk`（`apt install fonts-noto-cjk`，约 60MB）即可，与代码无关。
6. **演示过程中发现并修复的两个 Hardware 模式真实 bug**：见第 2 节 Application Layer——(1) `HardwareDeviceReceiver` 字节流拼帧问题（订阅无数据）；(2) `DeviceManager.deliver()` 命令下发在 Hardware 模式下崩溃。两者都是"Simulator 模式用 `LoopbackChannel` 掩盖了问题，第一次真正接真实字节流时才暴露"的同一类根因，值得在设计新功能时留意：任何只在 Simulator 模式测过的 Hardware 相关代码路径，都不能默认它在真实字节流下同样成立。修复 (2) 时还在 `scripts/virtual_stm32.py` 自己新写的最小化拼帧逻辑里犯过一次一模一样性质的错误（resync 时误删了整个缓冲区而不是只删垃圾前缀），提醒自己：写这类"重新实现一遍、不能共享代码"的设备侧 stand-in 逻辑时，即使逻辑很短也值得对照已测试过的版本仔细核对，不能因为"简单"就跳过验证。

**真实硬件场景说明**：以上全部是"没有真实 STM32、用虚拟串口在环验证"这一步骤专属的环境要求。接入真实 STM32 时，`SerialChannel` 直接用 Windows 原生 COM 口即可，不受 WSL/socat/pyserial-glob 限制。
