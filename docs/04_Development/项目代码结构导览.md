# 第一部分 PC 上位机核心（src/）

## 1.1 分层与依赖方向

`src/` 下共 9 个 Python 包（`core`、`device`、`protocol`、`communication`、`service`、`application`、`api`、`ui`、`gateway`）。概念上是五层架构（UI / Application / Protocol / Communication / Hardware Device），代码上把其中的支撑与桥接职责细分成了 `core`、`service`、`api` 三个包，并在接入 Android 后增加了与 `ui` 平级的 `gateway`。依赖方向严格单向，禁止跨层反向引用：

```
  ui  ──►  api  ──►  application  ──►  service
                          │               │
                          ├──► protocol ──┘
                          ├──► communication
                          └──► device
  gateway ──► api                （与 ui 是同层的两个"呈现端"）
  core                            （被所有层依赖，不依赖任何人）
```

这条依赖链上有三个被反复强调、并且写进了自动化测试的边界：

- `src/ui/*` 只能 import `src/api`（且只经由 `ui/controller.py` 一个文件），不得 import `device`/`communication`/`protocol`/`application`/`service` 的实现类。
- `src/api/*` 只依赖 `application` 与 `core`/`service` 中的共享数据模型，不得被 `service`/`application` 反向依赖。
- 具体通信介质相关的对象（`SerialChannel`、`HardwareDeviceReceiver`、`RemoteDevice` 等）只允许在 `src/application/*` 或 `scripts/` 的组合脚本中被创建与装配，**绝不出现在 src/ui/* 里**。

`gateway` 与 `ui` 是架构上的对等物：两者都只消费 `api.ApiInterface`，谁也不 import 谁。这一点在 `src/gateway/channel_units.py` 的文件头注释里有专门记录——那个文件是 `ui/channel_display.py` 的一份有意为之的副本，原因是 import `ui` 包会连带把 PyQt6 拉进来，而网关必须能在没有图形库的环境下运行。

## 1.2 core —— 共享基础类型

三个文件，不含任何业务逻辑。

`core/models.py` 定义四个字符串类型别名：`DeviceId`、`ClientId`、`ChannelId`、`CommandType`。这里刻意**不定义共享实体类**——`core` 不应该知道"设备""命令"是什么，那是 `device` 与 `service` 的知识。用别名而非裸 `str`，是为了让静态类型检查器（mypy）能在调用点上区分出参数含义。

`core/exceptions.py` 定义平台通用异常基类 `PlatformError` 及其子类 `NotFoundError`、`ValidationError`、`StateTransitionError`、`OperationTimeoutError`。`core/timestamps.py` 提供 `now_utc()` 与 `monotonic_ms()` 两个时间工具，前者用于数据点时间戳，后者用于超时判定（单调时钟，不受系统时间调整影响）。

## 1.3 protocol —— 自定义通信协议编解码

这是通信协议设计这条论文主线在代码上的落点，四个文件。

### 帧格式

所有多字节整数一律**大端序**（网络字节序）：

| 字段 | 帧头 | 设备ID | 命令类型 | 数据长度 | Payload | CRC |
|---|---|---|---|---|---|---|
| 长度 | 2 字节 | 1 字节 | 1 字节 | 2 字节 | 变长 | 4 字节 |
| 取值 | 0xAA 0x55 | 0~255 | 0~255 | 0~65535 | 任意字节 | CRC-32 |

CRC-32 采用 CRC-32/ISO-HDLC（多项式 0xEDB88320，初值 0xFFFFFFFF，末尾取反），**校验范围是设备ID + 命令类型 + 数据长度 + Payload，不含帧头**。排除帧头的理由写在 `encoder.py` 的文件头注释里：帧头是固定不变的同步标记，本身不携带任何需要保护的信息。PC 端直接调用 Python 标准库 `zlib.crc32`，不引入第三方依赖。

### frame.py

定义不可变数据类 `Frame(device_id, command_type, payload)`，只表达"结构化的消息"，与字节无关。构造时在 `__post_init__` 中校验三个字段的取值范围（0~255 / 0~255 / ≤65535 字节），越界抛 `FrameValueError`。`device_id` 与 `command_type` 在这一层是**不透明的整数**，其业务含义由别处（设备能力描述符）定义——这是保证协议层通用、不绑死某一具体设备的关键设计。

### encoder.py

单个函数 `encode(frame) -> bytes`，14 行：

```python
def encode(frame: Frame) -> bytes:
    body = (
        frame.device_id.to_bytes(DEVICE_ID_SIZE, BYTE_ORDER)
        + frame.command_type.to_bytes(COMMAND_TYPE_SIZE, BYTE_ORDER)
        + len(frame.payload).to_bytes(LENGTH_SIZE, BYTE_ORDER)
        + frame.payload
    )
    crc = zlib.crc32(body).to_bytes(CRC_SIZE, BYTE_ORDER)
    return HEADER + body + crc
```

### decoder.py

`decode(data) -> Frame`，按顺序做四重校验：总长度是否达到最小帧长 → 帧头是否为 0xAA55 → 声明长度与实际字节数是否吻合 → CRC 是否匹配。任何一项不过就抛出对应的异常（`FrameLengthError` / `FrameSyncError` / `ChecksumError`），**绝不返回"部分解出来"的半成品**。

这里有一个重要的职责划分：`decode()` 要求传入的字节数恰好是一整帧，不多不少。**在连续字节流里定位帧边界（粘包/半包处理）不是它的职责**，那属于更上层的 `application/frame_stream.py`。这个划分让 `protocol` 包保持纯函数式、无状态、易于单元测试。

## 1.4 communication —— 字节级传输抽象

### interface.py

抽象基类 `CommunicationChannel`，定义统一的字节传输契约：属性 `is_connected`，方法 `connect()` / `disconnect()` / `send(bytes)` / `receive() -> bytes`。

这一层的边界规定得非常死：**只搬运字节**。它不解析帧（那是 `protocol`），不认识设备和服务（那是 `device` 和 `service`），也不绑定任何具体介质。任何传输方式——UART、USB、TCP/IP、蓝牙，以及本项目的回环通道——都实现同一套接口，于是协议层和应用层永远不需要知道自己在和哪种介质说话。

`receive()` 的契约是**非阻塞**的：没有数据时返回 `b""` 而不是等待。

### serial.py —— 真实串口实现

基于 pyserial 的 `SerialChannel`，是本项目唯一的真实物理传输实现。三个设计要点：

- **非阻塞接收**：串口以 `timeout=0` 打开，且 `receive()` 会先查 `in_waiting` 拿到已缓冲的字节数，只读这么多，绝不向操作系统索要尚未到达的数据。这样 `SerialChannel` 与 `LoopbackChannel` 在协议层看来行为完全可互换。
- **显式检查端口存在性**：pyserial 无论"端口不存在"还是"端口存在但打不开"都抛同一个 `SerialException`。所以 `connect()` 先用 `list_ports.comports()` 查一遍，端口不存在时抛更具体的 `SerialPortNotFoundError`，而不是笼统的 `SerialConnectionError`。
- **异常翻译**：所有 pyserial 异常在这个模块的边界上被翻译成 `communication.exceptions` 里的类型。上层通过 `CommunicationChannel` 接口调用时，永远不需要 import 或 catch pyserial 的异常类型。

### loopback.py —— 内存回环实现

`LoopbackChannel` 内部是一个 `deque`，`send()` 写进去、`receive()` 按 FIFO 取出来，模拟一条把数据回环给自己接收端的通道。它让协议层的编解码往返、以及更上层的完整数据流，都能在完全没有硬件的条件下端到端跑通。

它与 `SerialChannel` 有一个**行为差异，且这个差异是刻意的**：`LoopbackChannel` 恰好保持"一次 send 对应一次 receive"的消息边界，而真实串口没有边界。这个差异正是 `frame_stream.py` 存在的原因。

## 1.5 device —— 设备抽象与传感器模拟

### interface.py / capability.py / state.py

`DeviceInterface` 定义成 `typing.Protocol`（结构化类型）而不是 ABC 基类：服务层应该能把"任何结构上长得像设备的东西"当设备用，而不强制它们继承某个具体基类。契约只有三项：`device_id`、`capability`、`status`。

`DeviceCapability` 是设备能力描述符，由 `CommandDescriptor`（支持哪些命令）与 `ChannelDescriptor`（上报哪些数据通道）两个元组构成。命令类型和通道 id 在这里都是不透明字符串，业务含义由描述这台设备的人定义。

`DeviceStatus` 是**不可变值对象**：包含连接状态（`DISCONNECTED`/`CONNECTING`/`CONNECTED`/`ERROR`）与占用状态（`FREE`/`OCCUPIED`）+ 占用者。所有状态迁移方法（`with_connection`、`occupy`、`release`）都返回新实例而非原地修改，这样持有旧引用的对象不会悄无声息地观察到别的客户端造成的改变。构造时还校验状态自洽性：占用态必须有占用者，空闲态必须没有。

### simulator.py —— 设备模拟器

`SimulatorDevice` 结构上满足 `DeviceInterface`，能按配置的通道生成 `DataPoint`。通道值来自可注入的 `ValueGenerator`（常量 / 序列 / 均匀随机），这些生成器本身**不承载任何物理量含义**——含义属于配置它的人，不属于模拟器。

### sensors/ —— 三个环境传感器预设

`sensors/channels.py` 集中定义三个通道 id 常量：`"temperature"`、`"humidity"`、`"noise"`。集中定义的目的是让 `device/sensors/*` 与 `service/sensor_data_processor.py` 永远不会在这三个字面量上产生漂移——固件端 `sensor_data.h` 与 Android 端 `Channels` 对象也都对齐到这三个字符串。

`sensors/generators.py` 扩展出两种更贴近真实物理量形态的生成器：

- `SmoothRandomWalkGenerator`：有界随机游走。每次在 `[-max_step, max_step]` 内随机取一步，加到当前值上再钳回 `[low, high]`，产生连续、物理上合理的漂移趋势，而不是每次独立采样的跳变。用于温度、湿度。
- `NoiseWithSpikesGenerator`：绝大多数时候在基线区间取值，以 `spike_probability` 的概率跳到一个更高的尖峰区间，模拟关门声、车辆经过这类短促响声。用于噪声。

三个预设子类只是**组合与配置**，一行都没有改动 `SimulatorDevice`：

| 类 | 通道 | 取值范围 | 生成器 |
|---|---|---|---|
| `TemperatureSensorSimulator` | temperature | 20~40 °C，单步 ≤0.3 | 平滑随机游走 |
| `HumiditySensorSimulator` | humidity | 相对湿度 % | 平滑随机游走 |
| `NoiseSensorSimulator` | noise | 基线 40~60 dB，尖峰 75~95 dB，尖峰概率 0.15 | 基线+尖峰 |

### remote.py —— 真实设备的被动表示

`RemoteDevice` 代表一台真实的外部设备（本项目就是 STM32）。它与 `SimulatorDevice` 的根本区别在于：**它永远不自己产生数据**——真实设备通过自己的物理链路产生数据。因此它：

- 没有任何数据生成方法（没有 `generate`）
- 没有任何串口/UART 逻辑
- 不依赖 `communication` 包，连抽象的 `CommunicationChannel` 都不 import

它只承载服务层眼中这台设备的身份、能力与状态。字节最终如何抵达真实设备，完全在这个类的关注范围之外——这与通信层"只搬运字节、永不认识设备"的边界，正好是同一条界线的两侧。

## 1.6 service —— 业务服务层

### data_models.py / data_service.py / data_service_impl.py

`DataPoint(device_id, channel, value, timestamp, valid)` 是全平台流动的数据单元。

`DataService` 是发布/订阅抽象：`subscribe(device_id, channel, callback) -> 订阅id`、`unsubscribe(订阅id)`、`publish(data_point)`。`InMemoryDataService` 是其同步、进程内实现——`publish()` 遍历所有订阅，对 device/channel 精确匹配的订阅者，**在调用线程上同步执行其回调**。整个平台的实时数据分发都建立在这 20 行代码上。

### command_models.py / control_service.py / control_service_impl.py

`Command(device_id, command_type, origin, parameters, command_id, issued_at)` 与 `CommandResult(command_id, status, message, completed_at)`，状态枚举为 `PENDING`/`SUCCESS`/`FAILED`/`TIMEOUT`。

`InMemoryControlService` 实现两件事：

- **1.** **占用管理**，落实"共享读、独占写"规则。`acquire()` 在无人占用或占用者就是自己时返回 True 并记录占用；被别人占用时返回 False。`release()` 只有当前占用者本人才能释放。`submit_command()` 在派发前先检查 `command.origin` 是否就是当前占用者，不是就抛 `StateTransitionError`——**没有先 acquire 就不允许下发命令**。
- **2.** **命令派发与结果留存**。派发通过一个极窄的 `CommandTransport` 协议（只有一个 `deliver(command) -> CommandResult` 方法）完成。这个模块因此**完全不 import protocol 或 communication**，对"命令如何抵达设备"一无所知。当前由 `application/manager.py` 提供这个 transport；将来换成网络网关也不需要改动本模块一行。

### sensor_data_processor.py —— 统计与阈值报警

这是 `service` 里唯一带"环境监测业务含义"的模块，257 行。它的 `handle_data_point` 方法签名与 `DataCallback` 完全一致，因此它本身就能作为一个普通订阅者挂到 `DataService` 上。

**滑动统计**：为每个 `(device_id, channel)` 维护一个 `_RunningStatistics` 累加器（current / minimum / maximum / total / count），每来一个数值就 O(1) 更新，对外产出不可变快照 `ChannelStatistics(current, minimum, maximum, average, sample_count)`。非数值（含 bool——它虽然是 int 的子类但不是有意义的传感器读数）直接忽略，不做静默类型转换。

**阈值报警**。规则表 2026-09-08 起是**区间制**（`AlarmBand`），两侧边界都可缺省：

| 通道 | 区间 | 说明 |
|---|---|---|
| temperature | ≤ 35.0 °C | 单边上限 |
| humidity | 30.0 ~ 75.0 %RH | **双向**。上限是复核时补的——标准给的 40~65% 是双向区间，而系统原先只判低限，第 6 章实测湿度长期 62~78%、已高于标准上限却一次没提示过 |
| noise | ≤ 80.0 dB | 单边上限，GB 37488—2019 |

`AlarmBand.evaluate(value)` 返回 `(kind, threshold, triggered)` 三元组：越限的读数按它真正越过的那一侧报告，正常的读数按**更近的那一侧**报告——否则会把 62%RH 说成"远高于 30%"。

这里有一个值得说明的设计：模块同时提供 `on_alarm` 与 `on_status` 两套回调。`AlarmEvent` 只在真正越限时产生；而 `ThresholdStatus` 对**每一个**落在有规则通道上的数值都产生，并带一个 `triggered` 布尔字段。这是因为只有报警事件的话，界面能把一行变红，却永远不知道什么时候该把它变回来——`on_status` 就是为"恢复正常"这个信号存在的。第三套回调 `on_statistics` 则对任意数值通道触发，不限于这三个有规则的通道。

### ventilation_controller.py —— 风扇该不该转

与 `SensorDataProcessor` 结构对称（`handle_data_point` 同样匹配 `DataCallback`），但回答的是**另一个问题**：前者回答"要不要提醒人"（阈值按 GB 37488—2019 论证过，**固定不可改**），本模块回答"风扇该不该转"（阈值**可运行时调整**）。两套阈值分开，使论文既有的论证不受运行时改动影响。

支持 `FanMode.AUTO / MANUAL_ON / MANUAL_OFF` 手动覆盖；**只决策、不执行**——把决策变成指令是 `application.fan_dispatcher` 的事。

### alarm_announcer.py —— 什么时候该播报

夹在"哪个通道越限了"和"喇叭放什么"之间，只回答**什么时候值得出声**。两条规则：**连续确认**（默认 2 次，单次尖峰不播报）与**全局冷却**（默认 30 s，跨通道共享——只有一个喇叭）。

streak 键 2026-09-08 起是 `(device, channel, 哪一侧)`：湿度有两个边界，从"太干"漂到"太湿"是**新的一次越限**，必须重新累计确认次数。

### assistant/ —— 环境问答（8 个模块）

| 文件 | 职责 |
|---|---|
| `intent.py` | 阶段一：关键词规则把问句归类。**唯一值得往上提的指标**——规则命中零延迟、每次一致，现命中 86.2% |
| `retrieval.py` | 阶段二：**唯一产生数字的地方**。阈值直接引用 `sensor_data_processor` 的公开常量，不另抄一份 |

## 1.7 application —— 组装根与桥接层

这一层是整个 PC 端最核心、也是最能体现"通用平台"设计的地方：**两种运行模式的差异，全部被限制在这一层以下**。

### frame_stream.py —— 粘包/半包处理

`FrameStreamBuffer` 解决真实字节流没有消息边界的问题：一次 `receive()` 可能返回好几个连在一起的帧，也可能返回半个帧。用法是 `feed(bytes)` 喂数据、`extract_frame()` 取出恰好一整帧的字节（不够就返回 `None` 并把残余留在缓冲区里等下次）。

它内部先 `_resync()`：在缓冲区里找帧头 0xAA55，把它前面的无效字节全部丢弃，这样一个杂散字节不会永久卡死缓冲区。找到帧头后读出声明长度字段，算出整帧总长，够了才切出来。

这个文件里记着一段很有价值的实测教训。`_resync()` 早期版本在缓冲区里找不到完整帧头时**无条件计一次"帧同步错误"**。但"缓冲区里恰好只剩半个帧头、正在等后半个字节到达"是字节流传输的正常状态，不是错误；而且在等待期间每次轮询都会重新走到这里，一次正常的边界切分会被反复累加。2026-08-18 的噪声阶跃实验因此报出 13 次"帧同步错误"，而实际是 0 丢帧（58 个采集周期全部收齐 3 帧）。修正方式是：只有真的丢弃了字节才计数，尾部的部分帧头匹配予以保留。若不修，会把并不存在的通信错误写进论文。

### manager.py —— 设备注册表与线级桥接

`DeviceManager` 是 `application` 层最大的模块（326 行），承担三件事。

**第一，字符串 DeviceId 与数值 wire id 的映射。** 服务层用可读的字符串标识设备（如 `"mcu-1"`），协议帧里是 1 字节整数。`register()` 为每台注册的设备按序分配 1~255 的 wire id，并在需要时顺手把通道 `connect()` 起来。

**第二，线上约定（wire convention）。** 这两个约定定义在这里，而不在 `protocol` 包里——协议层始终对 payload 内容一无所知：

| 命令类型 | 取值 | 方向与含义 |
|---|---|---|
| `DATA_REPORT_CODE` | 0x01 | 设备 → 上位机，数据上报 |
| `COMMAND_ACK_CODE` | 0x02 | 设备 → 上位机，命令应答 |
| 业务命令 | 0x10 起 | 上位机 → 设备，首次见到某个 `command_type` 字符串时动态分配 |

Payload 一律是 UTF-8 编码的 JSON 文本（用标准库 `json`，无第三方依赖）：数据上报是 `{"channel": ..., "value": ...}`，命令应答是 `{"status": "success"}`。

**第三，上下行的完整往返。**

`report_data()` 是上行（仅模拟模式）：让设备生成一个 `DataPoint` → 序列化成 JSON → 组成 DATA_REPORT 帧 → `channel.send()` → `channel.receive()` 读回来 → 解码还原成 `DataPoint`。真实设备调用它会抛 `ValidationError`——因为 `RemoteDevice` 不实现 `generate()`，让 `DeviceManager` 替真实设备生成数据是编程错误，不是"暂时没数据"这种正常情况，所以必须报错而不是静默返回。

`deliver()` 是下行，也是 `CommandTransport` 契约的实现。它把命令组成请求帧发出去，然后**两种模式在这里分叉**：

- 模拟模式走 `_simulate_device_ack()`：`LoopbackChannel` 那头没有一个独立的"设备"角色会读命令并回应，所以 `DeviceManager` 在本地扮演这个角色——把刚发出去的请求（自己的回声）读回来丢掉，再根据 `registration.accepted_commands` 伪造一个应答帧。这个捷径只在回环通道保持消息边界、且零传输延迟的前提下成立。
- 硬件模式走 `_await_device_ack()`：真正等待设备（真实固件，或 `scripts/virtual_stm32.py` 替身）自己发回来的 ACK 帧。接受与否是设备的职责，主机这边无法伪造。因为真实链路没有消息边界、命令执行也不是瞬时的，这里用 `FrameStreamBuffer` 轮询，带 2 秒超时上限，每 20ms 轮询一次；超时抛 `OperationTimeoutError`。

`_await_device_ack()` 里还有一个被明确记录下来的取舍：等待期间到达的、不是本次 ACK 的帧（最常见的就是恰好插进来的 DATA_REPORT 帧）会被直接跳过。因为只有 `HardwareDeviceReceiver` 的轮询循环才负责发布 DataPoint，而从这里够不到它。代价是**一次命令往返在途期间最多可能漏掉一个传感器读数**，换来的是保持整条链路同步、不必在 `DeviceManager` 与 `HardwareDeviceReceiver` 之间共享一个接收循环。

### hardware_runtime.py —— 硬件模式接收循环

`HardwareDeviceReceiver` 是硬件模式上行数据的完整实现，把这条链路串起来：

```
SerialChannel.receive() → FrameStreamBuffer 切帧 → protocol.decode()
     → 校验 wire id 与命令类型 → JSON 解析 → DataPoint
     → DataService.publish() → 各订阅者（统计报警处理器、界面、网关）
```

`poll_once()` 处理至多一帧；`poll_until_empty()` 反复排空（带 1000 次的安全上限），因为一次 `receive()` 可能带回好几帧。它维护两个计数器供上层观测：`error_count`（CRC/同步/长度错误、JSON 解析失败、重同步丢字节）与 `ignored_frame_count`（帧完好但 wire id 或命令类型对不上）。这两个计数器就是论文里通信可靠性数据的直接来源。

这个模块被刻意做成**独立于设备注册表**的：它直接拿到设备已约定好的 wire id，不走 `DeviceManager` 的自动分配。这样加入它时，`manager.py` 与 `runtime.py` 一行都没有改。

### hardware_runner.py / simulator_runner.py —— 两种模式的驱动器

两个 Runner 提供相同形状的接口：`start()` / `stop()`（幂等，仅记录状态）、`running`、`poll_interval_seconds`、`run_once()`。它们本身不起线程、不带定时器——`poll_interval_seconds` 只是给外部驱动者（PyQt6 的 QTimer、脚本里的循环）的**唯一真值来源**。这个设计让同一套逻辑既能被 GUI 的事件循环驱动，也能在测试里被手动单步调用。

`run_once()` 的关键性质是**永不抛异常**：任何来自接收器或通信通道的异常都被捕获、计入 `error_count`、记入 `last_error`，然后返回空列表。一次瞬时的接收失败不能污染 runner 自身的启停状态，也不能传播到驱动它的事件循环里去。

`SimulatorRuntimeRunner` 驱动一组 `(device_id, channel_id)` 目标依次 `report_data()`，某个目标失败不影响其余目标继续；`HardwareRuntimeRunner` 持有恰好一个 `HardwareDeviceReceiver`，多设备就持有多个 runner，这个类不管理注册表。

### runtime.py —— 组装根

`ApplicationRuntime` 持有并接好三样东西：`DeviceManager`、`InMemoryDataService`、`InMemoryControlService`（其 transport 就是 DeviceManager），外加一个独立的 `SensorDataProcessor`。它对外提供一个薄门面：设备查询（`list_devices`、`get_device_status`）、数据通路（`subscribe`/`unsubscribe`/`subscribe_alarm_status`/`subscribe_statistics`/`report_data`）、控制通路（`acquire`/`release`/`submit_command`/`get_result`）。

`register_device()` 除了注册，还会自动把报警处理器订阅到该设备能力描述符里声明的每一个通道——**报警评估不应该是按需开启的**，一个通道可能在没人看它的时候就已经越限了。

`DeviceStatusView` 是一个专门为 API 层准备的解耦快照，**故意不复用 device.state 里的枚举类型**，而是暴露普通的 bool/str 字段。这样 `api` 层（它按规矩绝对不能 import `device`）才能消费设备状态。这是分层边界如何影响具体数据结构设计的一个典型例子。

### 三个 dispatcher —— 把决策变成帧

`fan_dispatcher.py` / `alarm_state_dispatcher.py` / `answer_dispatcher.py` 形状完全相同，都遵循同一条**在这个项目里踩出来的规则**：

> **在数据回调里记录，在轮询循环里下发。**

原因是回调运行在数据分发的调用栈上，此时下发命令会**重入串口**——第一次踩到时把测试进程直接打崩，而当时的 593 个用例全绿、退出码却非零。所以三者都是 `record()/handle_*()` 只记不发、`dispatch_pending()` 由 `make_poll_once()` 驱动。

| 模块 | 下发什么 | 命令码 |
|---|---|---|
| `fan_dispatcher` | 风扇启停 | 0x10 / 0x11 |
| `alarm_state_dispatcher` | 每通道报警位图，供板载 LCD 每行显示"正常/报警" | 0x15 |
| `answer_dispatcher` | 最近一条问答，供 LCD 第二页 | 0x16 |

`answer_dispatcher` 值得单独说一句：它下发的**不是文本，是"哪一类答案 + 数值"**（六个无符号整数）。直接原因是板子字库是子集、画不出任意中文；但真正的好处是**模型改写措辞不影响屏幕**——屏上出现的永远是事实。负数读数**拒发而不回绕**：字段在固件侧无符号，-2.0 ℃ 会变成一个很大的正数被满有把握地画出来。

`alert_dispatcher.py` 与它们同层，把 `AlarmAnnouncer` 的播报决定变成 0x12~0x14 三条语音命令。

**两种模式的对照**，从 `DataService` 往上完全共用同一套代码：

| | 模拟模式 | 硬件模式 |
|---|---|---|
| 设备对象 | `SimulatorDevice`（+三个传感器预设） | `RemoteDevice` |
| 通信通道 | `LoopbackChannel` | `SerialChannel` |
| 数据来源 | 软件生成，主机侧回环 | STM32 主动上报 |
| 上行驱动 | `SimulatorRuntimeRunner.run_once()` | `HardwareRuntimeRunner.run_once()` |
| 命令应答 | 主机本地伪造 | 真实等待设备 ACK，2s 超时 |
| DataService 及以上 | **完全相同** | **完全相同** |

## 1.8 api —— 统一调用门面

`ApiInterface`（抽象基类）是 PC 端与 Android 端面向的**同一套概念接口**，共 10 个方法：

| 方法 | 功能 |
|---|---|
| `list_devices` | 查询设备列表 |
| `get_device_status` | 查询设备状态 |
| `subscribe_data` / `unsubscribe_data` | 按 (设备, 通道) 订阅实时数据 |
| `acquire_control` / `release_control` | 获取/释放控制权 |
| `submit_command` | 提交控制命令 |
| `get_command_result` | 查询命令结果 |
| `subscribe_alarm_status` | 全局订阅阈值状态 |
| `subscribe_statistics` | 全局订阅统计快照 |

注意后两个订阅是**全局的**，不像 `subscribe_data` 那样按设备/通道细分——调用方（典型就是界面）关心的是全平台范围内的报警，而不只是它当前正在显示的那几个通道。

`LocalApi` 是进程内实现，本身只做两件事：转调 `ApplicationRuntime`，以及把 `core.exceptions` 里的通用异常翻译成 `api.exceptions` 里更具体的类型（`DeviceNotFoundError`、`CommandAuthorityError`、`CommandDeliveryError`、`CommandNotFoundError`），好让门面的调用方能分支处理。整个 `api/` 包里没有任何一处 import `device`、`communication` 或 `protocol`——这个边界是靠 import 语句本身来强制的。

将来的网关模式实现会用网络传输实现同一个 `ApiInterface`，而它上面的调用方一行都不用改。

## 1.9 gateway —— 面向 Android 的 REST + WebSocket 网关

三个文件，把 `ApiInterface` 暴露到局域网上。

### server.py

基于 FastAPI，`create_app(api, subscriptions, mode_label)` 构建应用。每一个端点都只是某个已有 `ApiInterface` 方法的薄翻译，为此没有改动 `api/`、`service/`、`application/` 中的任何东西：

| 方法与路径 | 对应的 ApiInterface 方法 |
|---|---|
| `GET /health` | （存活探测 + 模式标签 + 订阅者/发布/丢弃计数） |
| `GET /devices` | `list_devices` |
| `GET /devices/{id}/status` | `get_device_status` |
| `POST /devices/{id}/control/acquire` | `acquire_control` |
| `POST /devices/{id}/control/release` | `release_control` |
| `POST /devices/{id}/commands` | `submit_command` |
| `GET /devices/{id}/commands/{cmd_id}` | `get_command_result` |
| `WS /ws` | 推送 data / alarm_status / statistics |

**刻意没有实现历史数据接口**。PC 端的历史记录当前只存在于 `ui/widgets/data_panel.py` 的表格控件内部（那是一个 PyQt6 控件自己的状态），`service`/`application`/`api` 三层根本没有历史数据能力。要加就得扩展受保护的接口，需要明确批准。这个服务器不会去伸手掏某个界面控件来伪造一份历史数据。

CORS 开成了宽松模式，因为唯一的客户端就是同一个局域网里的手机，这个阶段既没有认证也没有敏感数据——文件头注释里写明了在把它暴露到可信网络之外前必须先看这条说明。

### event_hub.py

`EventHub` 解决一个真实存在的线程模型冲突：`ApiInterface` 的订阅回调是**同步的、在发布数据的那个线程上执行**；而 WebSocket 发送必须在 uvicorn 的 asyncio 事件循环上进行。从发布线程直接碰 asyncio 原语是竞态。

它的做法是：`publish()` 可从任意线程调用（同步、不阻塞、永不向发布者抛异常），内部用 `loop.call_soon_threadsafe` 把消息交给事件循环，再由事件循环扇出给每一个已连接的订阅者队列。

**背压处理**：每个订阅者一个有界队列（默认 100）。客户端消费太慢时，**只丢它自己那条队列里最旧的一条消息**，而不是无限增长，更不是阻塞发布者——阻塞发布者会连带把喂给 PyQt6 界面的那条数据流水线一起卡住，因为发布线程是共享的。丢弃有计数（`dropped_count`），是可观测的而不是静默的。

### events.py / channel_units.py

`events.py` 负责把三种回调载荷序列化成 WebSocket 消息。除了 `unit` 之外，每一个字段都取自已有的 PC 端类型，没有发明字段。`unit` 是唯一的例外——`DataPoint` 本身没有单位（单位是展示层的事），由服务端在推送时附加，好让 Android 客户端不必自己硬编码一份映射。

`channel_units.py` 曾是那份有意为之的重复（三个通道的单位映射 °C / % / dB）。**2026-09-18 已按当初写下的方案修掉**：映射抽进零依赖的 `src/core/channel_display.py`，本模块与 `ui/channel_display.py` 都改为转读它，公开名字一个未变。当初重复的理由（import `ui` 会拉进 PyQt6；`gateway` 与 `ui` 是对等层，互相 import 属横向依赖）反对的是 import `ui`，不是共享定义——缺的只是一个两个平级模块都不拥有的落点。触发点是归档导出成为第三个消费方，而"必须手工保持同步"这条要求同一天刚在手机端失效过一次。

## 1.10 ui —— PyQt6 桌面界面

### controller.py —— MVC 的中介者

`MainController(QObject)` 是**整个 ui/ 包里唯一 import api 的文件**。它不重新实现任何业务逻辑，只把 `ApiInterface` 的调用与结果适配成 Qt 信号/槽。

它向界面发出 8 个信号：

| 信号 | 携带内容 |
|---|---|
| `devices_changed` | 设备 id 列表 |
| `device_status_changed` | 设备id, 是否连接, 是否被占用, 占用者 |
| `data_received` | 设备id, 通道, 数值 |
| `control_acquired` | 设备id, 是否获得 |
| `command_result_ready` | 设备id, 状态, 消息 |
| `error_occurred` | 错误文本 |
| `alarm_status_changed` | 设备id, 通道, 值, 阈值, 方向, 是否触发 |
| `statistics_changed` | 设备id, 通道, 当前/最小/最大/平均/样本数 |

反方向则是界面调用它的普通方法（`refresh_devices`、`subscribe`、`acquire_control`、`submit_command` 等）。

### main_window.py —— 仪表盘布局

`MainWindow` 把各个控件组合成工业监控风格的分层布局：

## 1.11 llm —— 本地语言模型适配层

只有一个 `ollama.py`（`OllamaClient`）。它与 `communication` 平级，但接的不是设备。

三条约束值得记住：

- **只能在 `src/application` 或 `scripts/` 中被创建**，且**不得被 `src/service` import**。`LlmClient` 协议定义在消费方 `service/assistant/llm_port.py`——依赖倒置，服务层声明自己要什么，而不是去认识某个具体客户端。
- **提交—轮询形态**，不是阻塞调用。纯 CPU 推理要数秒而上位机是单线程的，所以 `submit()` 立即返回、`poll()` 由同一个轮询循环取回。
- **没有模型也能工作**。注入 `NullLlmClient` 即可，问答照常，只是措辞不变。

裸 socket + 分块 + NDJSON，不引第三方 HTTP 库——依赖越少，答辩前出意外的面越小。

## 1.12 一次完整的数据流

以硬件模式为例，从传感器到手机屏幕：

```
STM32 读 AHT20/噪声传感器
  → protocol_frame.c 组帧（0xAA55 + id + 0x01 + len + JSON + CRC32）
  → USART1 → CH340C → USB
  → SerialChannel.receive()
  → FrameStreamBuffer 切出整帧
  → protocol.decode() 校验帧头/长度/CRC
  → HardwareDeviceReceiver 解析 JSON → DataPoint
  → InMemoryDataService.publish()
        ├→ SensorDataProcessor：更新统计、评估阈值
        │      ├→ on_statistics → LocalApi → MainController → StatisticsPanelWidget
        │      └→ on_status    → LocalApi → MainController → StatusBannerWidget / 行变红
        ├→ MainController._handle_data_point → data_received 信号 → 指标卡 + 曲线 + 数据表
        └→ EventHub.publish → WebSocket → Android MessageParser → MetricCardView
```

模拟模式只是把最前面的"STM32 + 串口"换成 `SimulatorDevice` + `LoopbackChannel`，从 `DataService.publish()` 往后完全一样。

## 2.2 main.c —— 主循环与采集周期状态机

主循环节拍为 10ms（`delay_ms(10)`），采集周期 300 拍 = **3 秒一轮**。选 3 秒的依据是同时满足 AHT20 说明书"采集周期应大于 1 秒"和噪声传感器 400ms 内部刷新周期的要求，并留有充分余量。

状态机只有两态：

| 状态 | 行为 |
|---|---|
| `CYCLE_IDLE` | 等待下一个采集周期；到点则调 `noise_sensor_start_request()` 发出 Modbus 请求，转入下一态 |
| `CYCLE_NOISE_WAIT` | 每拍调一次 `noise_sensor_poll()`；返回 PENDING 就继续等，成功或超时则落定，接着读 AHT20 并统一上报，回到 IDLE |

这个"噪声异步、AHT20 同步"的混合设计是有意的，理由写在文件头：噪声传感器走 Modbus 请求-应答，做成**非阻塞轮询**，这样 `pc_link_poll()` 不会被阻塞，PC 端下发的命令仍能及时响应；而 AHT20 因为软件 I2C 本身固有的阻塞式时序加上传感器要求的测量延时，读取过程约 80~100ms 是阻塞的——但它安排在噪声结果落定之后才发起，每个采集周期只阻塞这一小段，不影响整体响应性，也避免了为了让 AHT20 读取"看起来异步"而引入不必要的复杂状态机。

上报逻辑：三个通道**分别独立上报**，只上报本次读数有效的通道。任一传感器读失败只影响它自己那一条，不会拖累另外两条。每完成一轮采集上报翻转一次 LED1，作为肉眼可见的运行节奏指示；LED0 每 300ms 翻转一次作为存活指示。

```c
static void report_channel(const char *channel, float value)
{
    char payload[64];
    int payload_len = snprintf(payload, sizeof(payload),
                                "{\"channel\":\"%s\",\"value\":%.2f}",
                                channel, (double)value);
    if (payload_len > 0 && (size_t)payload_len < sizeof(payload))
    {
        pc_link_send_frame(STM32_DEVICE_ID, PROTOCOL_CMD_DATA_REPORT,
                            (const uint8_t *)payload, (uint16_t)payload_len);
    }
}
```

命令处理方面，收到 PC 下发的帧后：命令类型若是 0x01/0x02 则忽略（PC 不应下发这两种），否则一律回一个 `{"status":"success"}` 的 COMMAND_ACK 帧。

AHT20 初始化失败时**不进入死循环阻塞**，而是打一条日志继续运行——噪声传感器和 PC 链路不该因为温湿度传感器暂时不可用而停摆；后续每个采集周期仍会尝试读取，接线恢复后自然恢复工作。

## 2.3 protocol_frame.c + crc32.c —— 与 PC 端严格一致的帧编解码

`protocol_encode()` 与 `protocol_decode()` 逐字段实现第 1.3 节的帧格式，字节序、CRC 覆盖范围与 PC 端完全一致。文件头注释里明确写了一条规则：命令类型取值的**权威定义处仍是 PC 端的 src/application/manager.py**，固件这边只是同步记录，如有不一致以 PC 端为准。

`crc32_calculate()` 逐位实现 CRC-32/ISO-HDLC，不用查表——注释里说明了理由：代码量小、正确性容易核对（MCU 上省 1KB 的 ROM 表空间，且这个协议帧本身很短，逐位计算的耗时可以忽略）。

```c
uint32_t crc32_calculate(const uint8_t *data, uint32_t length)
{
    uint32_t crc = 0xFFFFFFFFu;
    for (uint32_t i = 0; i < length; i++)
    {
        crc ^= data[i];
        for (uint8_t bit = 0; bit < 8; bit++)
        {
            crc = (crc & 1u) ? ((crc >> 1) ^ 0xEDB88320u) : (crc >> 1);
        }
    }
    return crc ^ 0xFFFFFFFFu;
}
```

与 PC 端一样，本模块**只负责单帧的编解码，不负责在连续字节流中定位帧边界**——那是 `pc_link.c` 的职责。这个职责划分与 PC 端 `protocol/decoder.py` 和 `application/frame_stream.py` 的划分完全对称。

## 2.4 pc_link.c —— 上位机链路

USART1（PA9=TX / PA10=RX），经开发板 P10 跳线默认接板载 CH340C，即 USB_UART 口，无需额外接线。默认波特率 115200。

**三级缓冲结构**：

- **1.** **ISR 环形缓冲区**（256 字节）。`HAL_UART_RxCpltCallback` 每收到一个字节只做"搬运"，不做拼帧——中断服务程序里的工作量必须尽可能小。环形缓冲区满时丢弃并计入错误计数。
- **2.** **拼帧线性缓冲区**（256 字节）。`pc_link_poll()` 在主循环里把环形缓冲区的字节搬到这里，然后做重同步与拼帧。
- **3.** **就绪帧 Payload 拷贝区**。检测到完整帧后，Payload 必须立刻从拼帧缓冲区拷出来，否则 `pc_link_take_frame()` 返回的指针会指向已被后续字节覆盖的位置——这个坑在注释里被专门标注了。

`pc_link_resync()` 与 PC 端 `FrameStreamBuffer._resync()` 语义对应：找帧头 0xAA55，丢弃其前的无效字节。缓冲区里没有完整帧头时，会保留最后一个字节（如果它恰好是 0xAA），防止跨两次搬运的帧头被误丢。

拼帧流程：搬字节 → 若上一帧还没被取走则先返回 → 重同步 → 字节数不足 6 就等 → 读出声明长度算总长 → 声明长度超出本地缓冲容量则判为脏数据丢弃重同步 → 收全后调 `protocol_decode()` → 成功则置就绪标志，失败则计错误 → 无论成败都把这一帧的字节从缓冲区移出，继续处理后面的。

`pc_link_get_error_count()` 对外暴露错误计数，是固件侧可靠性数据的来源。

## 2.5 AHT20 温湿度传感器（aht20.c + soft_i2c.c）

**引脚选择**：SDA=PE0，SCL=PE1，软件 I2C。选这两个脚的依据写在 `soft_i2c.h` 头部：《探索者V3硬件参考手册》把 PE0/PE1 标注为 FSMC_NBL0/NBL1、"SRAM 专用"，只有当 FSMC 外设被初始化用于驱动外部 SRAM/LCD 时才会被占用；本项目按约束不引入 TFTLCD/摄像头/外部 SRAM，从不调用 FSMC 初始化函数，因此这两个脚在本项目中始终只是普通 GPIO。

不用板载硬件 I2C1（PB8/PB9）的原因：该总线已被 24C02 EEPROM、ST480MC 磁力计、ES8388 音频编解码器共用；且 ATK-MB016 的官方驱动本身就是软件 I2C 实现（myiic.c），本模块沿用同样的技术路线。注释里同时诚实标注了这属于"依据手册文字的合理推断，尚未用万用表实测确认电气空闲"，并说明若发现异常占用，只需改本文件的引脚宏即可切换，不影响其它模块。

**通信参数全部有出处，未凭型号猜测**，均引自《AHT20说明书》第 5 节与官方驱动 `atk_aht20.c/.h`：

| 项 | 取值 | 出处 |
|---|---|---|
| I2C 地址（8位含方向位） | 写 0x70 / 读 0x71 | 官方驱动 `ATK_AHT20_IIC_ADDR` |
| 初始化命令 | 0xBE + 0x08 + 0x00 | 官方驱动 INIT 宏 + 固定参数 |
| 测量命令 | 0xAC + 0x33 + 0x00 | 官方 START_TEST 宏；与说明书 5.2 节一致 |
| 读回 | 7 字节：状态字1 + 湿度20bit + 温度20bit + CRC8 | 说明书 5.2 节 |
| CRC8 | 多项式 0x31（X8+X5+X4+1），初值 0xFF | 说明书 5.2 节 |

温湿度换算（湿度与温度共用中间那个字节的高低半字节）：

```c
humi_data = ((raw[1] << 16) | (raw[2] << 8) | raw[3]) >> 4;
*humidity = (float)humi_data * 100.0f / 1024.0f / 1024.0f;

temp_data = ((raw[3] << 16) | (raw[4] << 8) | raw[5]) & 0xFFFFF;
*temperature = (float)temp_data * 200.0f / 1024.0f / 1024.0f - 50.0f;
```

**与官方 Demo 的两处差异，都是主动加强**：

- **1.** 官方 `atk_aht20.c` 未做 CRC8 校验，本驱动补上了——呼应"异常帧/CRC 处理"的要求，读回数据但 CRC 不过时判为无效读数（`AHT20_ERR_CRC`）。
- **2.** 状态字 Bit[7]=1 表示传感器仍在测量中，此时读到的是上一次的陈旧数据。本驱动把这种情况判为无效（返回 NACK 错误），要求调用方等下一个采样周期重试，而不是拿这份陈旧数据充数。

初始化流程按官方驱动：`soft_i2c_init()` → 延时 40ms 等硬件稳定 → 发初始化命令 → 延时 500ms → 读状态字，检查 Bit[3]（校准计算使能）是否为 1。

## 2.6 噪声传感器（noise_sensor.c + noise_usart.c + modbus_crc16.c）

传感器为 HH_07.06，工作在 Modbus RTU 模式（出厂默认可能是主动/被动模式，需先用厂商配套的配置工具切换）。USART3（PB10=TX / PB11=RX），默认 115200。

**应用层 noise_sensor.c**，依据《噪声检测模块(HH_07.06)应用手册V1.2》3.3 节：用 03H 功能码读保持寄存器，协议地址 0x0000，寄存器数量 1，返回 2 字节数据，每单位 0.1dB。

请求帧 8 字节：`从机地址 + 0x03 + 起始地址(0x0000) + 数量(0x0001) + CRC16`。注意 **Modbus 的 CRC-16 是低字节在前**，与本项目 PC↔STM32 协议帧的大端序无关，这是两套独立的字节序约定。

应答校验分四步，任何一步不过都计错误并返回对应错误码：长度必须恰好 7 字节（地址1+功能码1+字节数1+数据2+CRC2）→ 地址、功能码、字节数字段必须匹配 → CRC-16 必须匹配 → 数据字段高字节在前，乘 0.1 得到分贝值。

**超时处理**：`noise_sensor_poll()` 用 `HAL_GetTick()` 判超时，超时则复位接收状态、计错误、返回 `NOISE_SENSOR_ERR_TIMEOUT`。整个接口是非阻塞的：没结果就返回 PENDING，由 main 的状态机继续轮询。

**底层 noise_usart.c 采用与 pc_link 完全不同的判帧方式**，理由写在头文件里：Modbus RTU **没有帧长度字段**，标准规定以 3.5 个字符时间的总线空闲来界定一帧结束。本实现用 STM32 USART 外设自带的 **IDLE 中断**——收完一帧后总线空闲时硬件自动置位，效果等价且无需自行计时。为此它直接操作 USART3 的 SR/DR 寄存器完成收发，不走 `HAL_UART_Receive_IT`/`HAL_UART_RxCpltCallback` 那一套（那是给 pc_link 按声明长度拼帧准备的），避免两种拼帧语义混在一起，也避免与 HAL 的全局回调冲突。GPIO/时钟/NVIC 初始化仍统一走 `HAL_UART_MspInit()`。

顺带说明 `board_uart_msp.c` 存在的原因：HAL 库的 `HAL_UART_MspInit()` 回调在整个工程里**只能有一份定义**，所以 USART1/USART2/USART3 的引脚配置全部汇总在这一个文件里，避免各驱动文件里重复定义导致链接冲突。

## 2.7 固件与 PC 端的一致性保障

两端各自独立实现了同一套协议，一致性靠三条措施保证：

- **1.** **格式定义单点权威**。帧格式定义在 `docs/03_Communication/Protocol_Design.md`；命令类型取值的权威处是 PC 端 `application/manager.py`，固件注释里明确写"如与 PC 端代码不一致以 PC 端为准"。
- **2.** **通道名字符串对齐**。`"temperature"` / `"humidity"` / `"noise"` 三个字符串在 PC 端 `device/sensors/channels.py`、固件 `sensor_data.h`、Android `Channels` 三处保持一致，每一处都在注释里指向另外两处。
- **3.** **交叉核对**。CRC32/CRC16/协议帧编码逻辑用 Python 等价实现与 PC 端真实代码逐字节比对过；Modbus 请求应答格式用厂商文档给出的真实报文示例核对过。

## 3.2 data 层

### Models.kt

四个数据类，每个字段都对应 PC 端已有的真实类型，**没有自行发明字段**：

| Android 类型 | 对应的 PC 端类型 |
|---|---|
| `DeviceStatus` | `application.runtime.DeviceStatusView` |
| `RealtimeData` | `service.data_models.DataPoint`（+ 服务端附加的 `unit`） |
| `AlarmStatus` | `service.sensor_data_processor.ThresholdStatus` |
| `Statistics` | `service.sensor_data_processor.ChannelStatistics` |

`Channels` 对象持有三个通道 id 常量，注释里注明必须与 PC 端 `device/sensors/channels.py` 保持一致。

### MessageParser.kt

刻意做成**不依赖任何 Android API** 的纯 Kotlin 单例（只用 `org.json`），这样它能在普通 JVM 单元测试里直接跑，不需要模拟器也不需要真机。`GatewayWebSocket` 负责连接与线程调度，解析规则集中在这里——二者分开之后，"字段解析是否正确"这件事才能被自动化测试真正验证到（`MessageParserTest.kt` 就是这份测试）。

解析结果是一个 sealed interface，五种情形：`Data` / `Alarm` / `Stats` / `Unknown`（未知消息类型，不视为错误——旧版 App 应当容忍服务端新增消息）/ `Malformed`（JSON 非法或必需字段缺失）。

有一条明确的原则：**解析失败一律返回 Malformed，绝不抛异常，也绝不用 0.0 之类的默认值蒙混过去**——注释原话是"显示一个编造出来的 0 比显示'数据异常'更危险"。这是环境监测类应用非常重要的一条工程判断。

### GatewayClient.kt

REST 客户端，基于 OkHttp，连接与读取超时各 5 秒。三个方法：`listDevices()`、`deviceStatus(id)`、`health()`。

两个设计决定：**所有方法都是阻塞式的**，必须在后台线程调用（`MainActivity` 用协程的 IO 调度器调），刻意不在这一层内部起线程，让调用方对线程有完全的控制权；**返回 Result 而不是抛异常**，因为网络失败在真机环境里是常态（PC 没开、IP 填错、不在同一局域网、防火墙拦截），调用方需要把失败原因显示给用户而不是崩溃。

解析 `occupant` 字段时显式判空——JSON null 用 `getString` 会读成字符串 `"null"`，这是个真实的坑。

### GatewayWebSocket.kt

带自动重连的 WebSocket 客户端，覆盖六种情况（前提是不假设 WebSocket 永远稳定）：

| 情况 | 处理 |
|---|---|
| 1 连接成功 | `onConnected()` |
| 2 连接失败 | `onDisconnected()` + 自动重连 |
| 3 异常断开 | `onDisconnected()` + 自动重连 |
| 4 重新连接 | **指数退避** 1s → 2s → 4s → 8s…上限约 30s，避免 PC 没开时疯狂重试耗电 |
| 5 非法数据 | 丢弃该条并回调 `onMalformedMessage`，**不中断连接**（一条坏消息不该导致整条链路重连） |
| 6 未知消息类型 | 回调 `onUnknownMessage`，同样不中断连接（PC 将来新增消息类型时旧版 App 应继续正常工作） |

OkHttp 配置上有两处针对长连接的调整：`readTimeout` 设为 0（WebSocket 是长连接，空闲期不应被当成超时断开）；`pingInterval` 设为 20 秒（自动心跳，帮助尽早发现"网络断了但 TCP 还没察觉"的假死连接）。

所有回调统一切到主线程，调用方可以直接更新 UI。

## 3.3 ui 层

### ConnectionUiState.kt —— 六态连接状态机

这是移动端最有价值的一个设计。六种状态**完全由已有回调派生，没有向网络层要任何新能力，没有改动 data/ 下任何一行**：

| 状态 | 由什么派生 |
|---|---|
| `DISCONNECTED` | 初始态 / 用户主动断开 |
| `CONNECTING` | 发起连接 → `/health` 返回前 |
| `ONLINE` | `onConnected()` 之后，且 10 秒内有数据 |
| `STALLED` | `onConnected()` 之后，但超过 10 秒没有新数据 |
| `RECONNECTING` | `onDisconnected()` 之后，连续失败次数 < 3 |
| `ERROR` | `/health` 失败，或连续失败 ≥ 3 次 |

其中 `STALLED` 最有价值：WebSocket 假死（TCP 没断但服务端不再推送）时，界面看起来一切正常，用户无从察觉；现在会明确降级提示。枚举还带一个 `isLive` 属性，非在线状态下指标卡会降低透明度，提示"这是旧值"。

### MetricCardView.kt

一个环境指标卡（温湿噪各一张），基于 `MaterialCardView` 的自定义 View。它只消费 `RealtimeData` / `AlarmStatus` / `Statistics` 三个**已有**模型，不新增字段、不发起任何网络请求——所有数据都由 `MainActivity` 从 WebSocket 回调转发进来。状态色变化用 `ArgbEvaluator` + `ValueAnimator` 做平滑过渡。

### SparklineView.kt

极简折线图，纯 `Canvas` 自绘，刻意不引入 MPAndroidChart 等第三方图表库——需求只有"一条线"。

注释里有一条重要澄清：**它画的不是历史数据**。PC 端 `service`/`application`/`api` 三层没有历史数据能力，本视图的每个点都是 WebSocket 当场推过来、App 顺手记在内存里的，断开重连即清空，卡片上固定标注"本次连接以来"。注释明确要求：不要把它当成历史曲线，也不要给它加持久化。

### ChannelFormat.kt

按通道决定小数位，而不是统一 `%.1f`：湿度传感器精度约 ±2%，显示 "58.0 %" 是**虚假精度**，显示 "58 %" 才诚实。格式化时固定用 `Locale.US`，保证小数点是 "." 而不随手机地区变成 ","。

## 3.4 MainActivity 的连接流程

分三步，顺序是第一阶段真机验证通过后保持不变的：

- **1.** **先用 /health 做连通性探测**。这一步能把"PC 没开 / IP 填错"与"WebSocket 本身有问题"区分开来。同时读回 `mode` 字段，若为 `simulator` 则在界面上显示一条醒目横幅——明确提示数据来源，**避免把模拟数据误认为真实 STM32 数据**。
- **2.** **拉设备列表 + 逐台查状态**（`GET /devices` → 逐个 `GET /devices/{id}/status`），渲染设备区。
- **3.** **建立 WebSocket**，开始接收实时数据。

每次新连接建立时清空所有曲线（`clearSeries()`），因为曲线只代表"本次连接以来"。界面上还有一个每秒一跳的 ticker，用于驱动 `STALLED` 状态的判定和运行时长显示。

从设置页返回时，只有当地址真的变了才重连，没变就不打断已有连接。

### ServerConfig.kt

地址持久化在 SharedPreferences，改一次之后重启 App 仍有效，不需要重新编译。

默认值填 `10.0.2.2`——这是 Android 模拟器访问宿主机 PC 的专用回环地址，用模拟器测试时开箱即用。注释里特别强调：**刻意不硬编码 localhost/127.0.0.1**，那两个地址在手机上指向手机自己，永远连不到 PC；真机测试时必须在设置页改成 PC 的局域网 IP。

# 第四部分 启动与工具脚本（scripts/）

## 4.1 定位：组合根，不是示例代码

`scripts/` 下的 11 个脚本是**项目的正式功能入口**，不是可有可无的 demo。它们承担架构上一个明确的角色：**组合根（composition root）**。

前面第 1.1 节讲过一条硬性边界——具体通信介质相关的对象（`SerialChannel`、`RemoteDevice`、`HardwareDeviceReceiver`、`HardwareRuntimeRunner`）绝不允许出现在 `src/ui/*` 里。那它们该在哪里被创建？答案就是这里。**所有"哪种模式、接哪个串口、用哪个传感器预设、多久轮询一次"的装配决策，全部集中在 scripts/ 中**，`src/` 里的模块只提供能力，不决定如何组装。

这些脚本本身**不含业务逻辑**：只构造对象、调用它们已有的公开 API。这与 `tests/integration/`、`tests/ui/` 里的装配方式是同一套模式。

十一个文件分三类：

| 类别 | 文件 | 作用 |
|---|---|---|
| 组合根 | `run_gui.py`、`run_api_server.py`、`run_all.py` | 真正的装配与启动逻辑 |
| 交互式外壳 | `run_gui_hardware.py`、`run_api_server_launcher.py`、`run_all_launcher.py`、`collect_data_launcher.py` | 问清楚串口/模式，再委托给上面的组合根 |
| 工具 | `virtual_stm32.py`、`collect_thesis_data.py`、`lan_address.py`、`demo_rehearsal.py`、`assistant_benchmark.py`、`check_keil_project.py`、`hz_font_to_c.py`、`wav_to_c.py`、`question_log.py` | 虚拟设备、论文数据采集、局域网地址探测、演示流程演练、问答成功率评测、Keil 工程校验、字库与音频生成、**问答日志**（2026-09-17 新增，记真人提问供日后补题库，接线在 `automation_wiring.py`，三个组合根共用） |

项目根目录下的 5 个 `.bat` 只是双击入口：设置 UTF-8 代码页（`chcp 65001`，否则 Windows 返回的中文串口描述会乱码）、优先使用项目自带的 `.venv\Scripts\python.exe`、转发全部参数、失败时 `pause` 让报错留在屏幕上。

## 4.2 run_gui.py —— 桌面界面的组合根

两个装配函数，返回值形状对称，都是 `(runtime, runner)`：

**build_simulator_runtime()** 注册三台传感器模拟器（各自独立的 device id：`sim-env-1-temp` / `-humi` / `-noise`），每台配一个 `LoopbackChannel`，接受 `PING` 命令，然后构造 `SimulatorRuntimeRunner` 驱动它们。

这个函数的注释里记着两条来自实际踩坑的设计决定：

- **为什么要返回 runner。** 2026-08-15 之前这个函数只返回 runtime，运行中的程序里没有任何东西调用 `report_data()`——于是模拟模式打开的窗口**一个数据点都不会显示**（`report_data()` 当时只在测试里被调用过）。`main()` 里加的那个 QTimer 才是修复。
- **为什么用 temperature/humidity/noise 而不是原来的 ch1/ch2 演示设备。** 窗口的指标卡、阈值报警、单位标签全都以这三个通道 id 为键。用 ch1/ch2 时卡片一片空白、报警永远不会触发，模拟模式也就无法充当"没有硬件时的替身"。改成与硬件模式相同的三个通道，两种模式看起来才完全一致——这正是设置模拟模式的意义。

**build_hardware_runtime(port, baudrate, device_id)** 装配 `SerialChannel` → `RemoteDevice` → `HardwareDeviceReceiver` → `HardwareRuntimeRunner`，发布到**同一个** `ApplicationRuntime.data_service`，所以从界面看过去与模拟模式无从分辨。

这里有两处必须留意的细节：

- 它直接调 `runtime.devices.register(...)`（`DeviceManager` 自己的方法）而不是 `ApplicationRuntime.register_device()` 门面，**目的是从返回的 DeviceRegistration 里读回分配到的 wire id**——`HardwareDeviceReceiver` 需要它来判断哪些帧是发给这台设备的。代价是门面方法里自动做的报警订阅不会发生，所以紧接着必须手动调 `runtime.watch_alarms_for(device)`。漏调这一句曾经是一个真实的 bug（记录在 `Project_Status_Context.md`，2026-08-12）。
- `RemoteDevice` 构造时显式设成 `ConnectionState.CONNECTED`。注释解释得很清楚：串口在 `register()` 里被打开，打开成功即认为链路已建立；不设这个状态的话 `RemoteDevice` 会一直停在默认的 `DISCONNECTED`，界面上就会出现"顶部显示未连接、数据却在刷新"的矛盾——而 `SimulatorDevice` 内部本来就把自己标为 CONNECTED，两种模式此前对同一件事给出了不一致的呈现。

`main()` 里两种模式的驱动方式**完全相同**：建一个 `QTimer`，间隔取 `runner.poll_interval_seconds`，`timeout` 接到 `runner.run_once`。两个 Runner 都不自带循环（见第 1.7 节），驱动者就该在组合根里。

## 4.3 run_gui_hardware.py —— 交互式选串口

硬件模式需要 `--port COMx`，但 COM 号**不稳定**：插到不同 USB 口会变，拔插一次也可能变。所以它没法像模拟模式那样烧进一个双击就能跑的 .bat 里——这个脚本改成问，而不是硬编码。

为什么不干脆自动选唯一的那个口：一台普通 Windows 机器上本来就有**不是开发板**的串口。写这个脚本的开发机上，插板子之前 COM3 和 COM4 就已经存在了，都是蓝牙虚拟串口（`BTHENUM` 硬件 id）。默默选"第一个串口"会选中蓝牙口，然后给出一个莫名其妙的超时，而不是一个明确的错误。

所以它列出每个串口及其描述，并给硬件 id 看起来像 USB 转串口桥的那些打上标记（探索者 V3 通过板载 CH340C 连 PC，会显示成其中之一）：

- 正向特征：`CH340`、`CH910`、`CP210`、`FT232`、`FTDI`、`USB-SERIAL`、`USB\VID`、`SILICON LABS`、`PROLIFIC`
- 反向排除：`BTHENUM`、`BLUETOOTH`

只有一个候选时按回车即用它作默认值；一个候选都没识别出来时，会额外提示"可能都是蓝牙等虚拟串口，请确认 CH340 驱动已装"。

两个小而实在的健壮性处理：

- `_safe()` 函数把串口描述按当前控制台编码做一次可打印化。串口描述来自 Windows 且是本地化的（这台机器上是中文），双击 .bat 时的控制台代码页可能编不了这些字——**仅仅列个串口就抛 UnicodeEncodeError 是荒谬的失败方式**。
- `main()` 捕获 `SerialPortNotFoundError` 与 `SerialConnectionError` 两种异常，各自打印中文原因清单（板子被拔了 / COM 号变了 / 串口被串口助手、另一个本程序窗口、STM32CubeProgrammer 占用）。给双击 .bat 的人扔一个原始 traceback 说明板子掉线，是很糟糕的告知方式。

它不重复任何装配逻辑，只决定 `--port` 的值，然后转调 `run_gui.main(args)`。

## 4.4 run_api_server.py —— 网关的组合根

`run_gui.py` 的同位体：同样的组合根角色、同样两种模式，只是最后启的是 HTTP/WebSocket 服务而不是 PyQt6 窗口。

两个装配函数与 `run_gui.py` 的基本一致（硬件模式那份连 `watch_alarms_for()` 和 `CONNECTED` 状态那两处细节都一样），额外多返回一个 `targets` 列表——`create_app()` 需要它来知道该订阅哪些 (设备, 通道) 对，好把数据推给 WebSocket 客户端。

有两个值得说的点：

**驱动方式不同。** 网关没有 Qt 事件循环，所以 `_start_runner_thread()` 用一个普通的**守护线程**跑 `while runner.running: runner.run_once(); sleep(...)`。守护线程的意义是 Ctrl+C 能干净退出而不必 join。这正好印证了 Runner 不自带循环的设计价值：同一个 Runner，GUI 用 QTimer 驱动，服务器用线程驱动，Runner 本身一行都不用改。

**两个 port 参数刻意取了不同的名字。** `--port` 是这个 HTTP 服务监听的 TCP 端口，`--port-serial` 是 STM32 的串口。命名区分开是为了它们不可能被混淆。

启动时会打印模式标签，模拟模式下额外打一行 `NOTE: data is software-simulated, NOT from a real STM32.`——**明确提示数据来源，避免把模拟数据当成真实数据**。这条提示与 Android 端那条黄色横幅是同一件事在两端的呈现。

## 4.5 run_all.py —— 界面与网关同进程

这个脚本存在的理由非常具体：`run_gui.py` 和 `run_api_server.py` 各自构建自己的 `ApplicationRuntime`，硬件模式下也就各自打开自己的 `SerialChannel`。模拟模式下这没问题（两个进程、两套独立模拟器），但**硬件模式下不可能**——一个 COM 口只能被一个进程打开，启第二个会直接失败：

```
SerialConnectionError: failed to open serial port 'COM10':
PermissionError(13, '拒绝访问。')
```

物理上只有一块 STM32、一根线，那就只能有一个读取者。这个脚本就是那个唯一的读取者：构建**一个** runtime（一个 SerialChannel、一个 HardwareDeviceReceiver），把**两个**消费者都挂上去。

注释里强调了一点：**这不是绕过限制的权宜之计，而正是架构本来的设计意图**。`ui/` 与 `gateway/` 是对等物，都消费 `api.ApiInterface`，互不知晓。串口字节被解码一次、向 `DataService` 发布一次，然后扇出给两边。

线程模型是这个脚本最需要讲清楚的部分：

| 线程 | 承担 | 理由 |
|---|---|---|
| Qt 主线程 | 持有驱动 `runner.run_once()` 的 QTimer | 于是每一次 `DataService.publish()`、进而每一次界面更新，都发生在 Qt 线程上，符合 PyQt6 的要求 |
| 后台守护线程 | uvicorn 及其 asyncio 事件循环 | `EventHub.publish()` 明确文档化为可从任意线程调用（内部用 `call_soon_threadsafe` 转交），正是这个场景 |

延迟方面：一个数据点经由同一次解码抵达手机，只多一次 `call_soon_threadsafe` 跳转。没有轮询、没有中继、没有二次解析，这已经是双消费者扇出能做到的最直接形式。

窗口关闭时 Qt 循环结束，脚本会顺手 `runner.stop()` 并置 `server.should_exit = True`，让进程真正退出而不是挂在守护线程上。

## 4.6 三个交互式启动器

`run_api_server_launcher.py`、`run_all_launcher.py`、`collect_data_launcher.py` 都是"问清楚再转调"的外壳。它们之间**复用而非复制**：模式提问 `_prompt_mode()`、手机地址横幅 `_print_phone_banner()` 定义在 `run_api_server_launcher.py`，串口选择器 `choose_port()` 定义在 `run_gui_hardware.py`，另外两个启动器直接 import 过来用。注释里写明了理由：无论用户双击哪个 .bat，这几个交互行为都应该表现一致，复制会让它们各自漂移。

`run_api_server_launcher.py` 回答的是两个每次都要现查的问题：跑哪种模式（模拟/硬件，硬件还要选串口），以及**手机上该填什么地址**——后者是实践中真正会出错的地方，所以启动器直接打成横幅，而不是让用户自己去 `ipconfig`。

`collect_data_launcher.py` 内置了一组与 `docs/07_Thesis/范文分析与写作计划.md` 对应的**实验预设**（菜单文字、时长、时序表采样间隔、标签、操作提示），让数据采集可复现、标注一致。噪声相关的三个预设是噪声传感器到货后新增的，采样间隔比温湿度实验短，因为声压级变化快得多，15 秒一采会把过程糊掉。

## 4.7 lan_address.py —— 找手机该连的局域网地址

这不是一行代码能解决的问题。常见做法是开一个"发往 8.8.8.8"的 UDP socket 再读 `getsockname()`，但它返回的是操作系统**对外路由**会走的那个地址。在跑 VPN/代理的机器上，那是隧道的地址，不是 Wi-Fi 的地址。

这台开发机上实测：该技巧返回 `198.18.0.1`（一个 Mihomo/Clash "Meta Tunnel" 虚拟网卡），而手机真正需要的是 `192.168.2.153`（Intel 无线网卡）。把隧道地址交给别人往手机里填，只会连不上，且没有任何有用的报错来解释原因。

所以这个模块枚举**每一块网卡**，剔除不可能被手机访问到的（名称/描述里含 `LOOPBACK`、`HYPER-V`、`VETHERNET`、`VIRTUALBOX`、`VMWARE`、`TAP-WINDOWS`、`TUNNEL` 等），再对剩下的排序——优先持有私网地址的真实 Wi-Fi/以太网卡。

关键设计：**它报告所有候选而不只是最佳猜测**，这样猜错时是可见、可纠正的，而不是默默误导。Windows 是主要目标平台（本项目的启动器是 .bat、串口是 COM 口），走 PowerShell 拿网卡名；其它平台退化为无名称的枚举，但地址范围过滤仍然生效。

## 4.8 virtual_stm32.py —— 虚拟 STM32

目的是在**没有实体 MCU** 的情况下，把硬件模式**完整的真实接收链路**跑通：

```
SerialChannel.receive() → protocol.decode() → HardwareDeviceReceiver
    → DataService.publish() → … → UI
```

与本项目其它所有测试替身（`LoopbackChannel`、被 mock 的 pyserial）都不同，这个脚本写入的是**真实的操作系统串口**。配合虚拟串口对（Windows 下用 com0com）的另一端跑一个真实的 GUI 进程（`run_gui.py --mode hardware`），就得到了在没有 STM32 的条件下最接近硬件在环测试的东西。

这个脚本有两处**刻意的重复**，理由都写在文件头，很值得答辩时讲：

- **它硬编码 DATA_REPORT_CODE = 0x01 和 COMMAND_ACK_CODE = 0x02，而不是从 application.manager import。** 因为这个脚本扮演的是链路上**设备（MCU）那一侧**，而真实的 STM32 固件会在 C 代码里硬编码同样的值，不会去 import 上位机的 Python。在这里复制常量，比与主机应用共享代码，更忠实地还原了真实固件的处境。**两侧只通过协议规范达成一致，绝不通过共享代码。**
- **它本地重新实现了一小段帧边界恢复逻辑（_extract_frame），而不是 import application.frame_stream.FrameStreamBuffer。** 理由同上：真实 MCU 无论如何都得用 C 从头实现这套逻辑。

它复用的只有 `device/sensors/` 的值生成器（通过三个传感器预设拿 `.generate(channel).value`），纯粹是为了让模拟出来的数值与项目其余部分一致，而不是又抄一遍量程常量。

除了每轮发送三个 DATA_REPORT 帧，它还会在两轮之间监听并**应答**发给自己的命令帧（回 COMMAND_ACK），这样 `run_gui.py --mode hardware` 的"发送命令"动作能得到一个来自虚拟设备的**真实响应**——而不是像模拟模式那样由主机侧的 `DeviceManager.deliver()` 在本地伪造。它无条件接受所有命令类型：不像模拟模式有 `accepted_commands` 这道闸，真实设备的接受/拒绝决策是在自己的固件里做的。

## 4.9 collect_thesis_data.py —— 论文数据采集与统计

`scripts/` 里最大的文件（673 行），也是三个工具里与论文关系最直接的一个。

为什么要单独做一个工具而不是从界面上读数：论文需要的是**量化**结果（帧数、周期抖动、误码率），从屏幕上读既不准确也不可复现。这个脚本给每一个收到的帧打时间戳记录下来，然后算统计量，同时输出 CSV（原始数据，用于画图）和 Markdown 表格（可直接粘进论文）。

它**复用项目自己的接收路径**（`SerialChannel` → `HardwareDeviceReceiver`），而不是另写一份帧解析。所以这里报告的 CRC 校验、字节流重组、`error_count`/`ignored_frame_count` 计数，都是**被测系统里真实的那一份**，不是一个可能与之不一致的第二实现。阈值也是从 `service.sensor_data_processor` import 的 `NOISE_ALARM_MAX`，不在脚本里另写字面量——报告里说的"越限"必须与界面上真正触发报警的判据是同一个数。

核心是四个**纯函数**（因此可被单元测试，见第 5.6 节），每一个的实现里都沉淀了一次统计口径的修正：

**group_cycles()** 按到达时间把记录分组成固件的采集周期。固件在一个周期末尾把三个通道背靠背发出（`main.c::finish_cycle_and_report`），所以同一周期的帧相隔毫秒级，而周期之间相隔约 3 秒；间隔小于半个周期的就算同一周期。**为什么按时间分组而不是以温度帧为锚**：温湿度共用 AHT20、会一起失败（`main.c` 用一次读取的结果设置两个 valid 标志），所以 AHT20 失败的那个周期根本没有温度帧可锚，却可能仍有噪声帧。

**modbus_stats()** 单独统计噪声传感器 Modbus 请求-应答的成功率。**为什么噪声通道需要自己的指标**：Modbus 读失败时固件根本不上报这个通道（`main.c` 里的 `if (data.noise.valid)`），只往调试串口打日志。所以缺失的噪声帧是**传感器侧**的失败，而通用丢帧指标会把它算到串口链路头上——这正是"周期 vs 丢帧"分析已经纠正过一次的那类误归因。因为所有通道都在同一周期内上报，两种原因可以区分开：**收到了别的通道却没有噪声帧 = Modbus 失败；整个周期一片空白 = 链路问题**，后者体现为缺失的周期。

**threshold_segments()** 把噪声序列切成"越限/未越限"的连续段。报警规则是逐点判定、**没有迟滞**的（`_evaluate_threshold` 里就是一个裸的 `value > threshold`），所以界面上显示的正是这一串连续段。报告每段持续了多久，而不只是有多少个点越限，才能区分"声源开着时报警一直稳定保持"和"报警在闪烁"——这两种情况在 min/max 表里长得一模一样。

**summarize()** 算出论文需要的每一个统计量。这里有三处口径上的讲究：

- **丢帧按通道分别估算，不做全局统计**。因为固件会跳过读取失败的那个通道，缺失的帧是关于那个传感器的有意义信息，而不是关于链路的。
- **判丢帧的参照量用中位数而不是均值**。丢帧本身会把均值抬高，丢得越多参照越偏，可能把两帧的空档误判成一帧；中位数对离群值免疫。判据是"该处间隔约为正常值的整数倍"，而**不能**用"实收帧数 vs 设计周期折算的理论帧数"——固件的实际周期与设计值存在系统性偏差，那样算会把周期偏差误报成丢帧。
- **周期偏差用均值算，与表格里"平均间隔"一列同口径**。中位数只用于上面的丢帧判定。两者混用会让同一行的两列对不上：读者拿平均间隔除以设计周期算出的偏差，与本字段给出的数不一致。

其余函数：`collect()` 打开串口按时长录制（并在约 30 秒仍无噪声帧时预警——本底实验曾因模块未上电空跑 15 分钟）、`write_csv()`/`read_csv()` 落盘与回读（可以对已录数据重新出表而不必重跑实验）、`to_markdown()`/`sample_table()` 出表、`parse_cues()` 解析 `--cue 60:开始播放白噪声` 这样的时间标记。

脚本头部明确警告：**串口是独占的**，跑之前必须关掉 `run_all_界面加网关.bat` / `run_gui_hardware_真实硬件界面.bat` / 任何串口助手，否则会以 `PermissionError(13)` 失败。

## 4.10 demo_rehearsal.py —— 答辩前把演示流程走一遍

演示当天要说的那十几句话，提前用**同一套装配**（`build_simulator_runtime()` + `attach_language_model()` + `make_poll_once()`，全部取自 `run_gui.py`）跑一遍，只是没有窗口。用途是回答一个别的检查回答不了的问题：**今天这个本地模型状态如何。**

```bash
python scripts/demo_rehearsal.py            # 默认两轮
python scripts/demo_rehearsal.py --rounds 3
python scripts/demo_rehearsal.py --no-llm   # 只走规则与模板，秒完
```

台词表刻意混了四类：规则能直接认出的问法、规则认不出要靠模型分类的口语问法、指令、以及**应当被拒绝的三句**（超量程、没给数值、系统范围之外）。最后一类不能省——只跑顺利路径的演练，发现不了一个"开始对什么都说好"的系统。

**比较的是"这句话被理解成了什么"（意图类别 + 指令是否执行），不是回答的字面。** 读数每轮本来就在变，风扇该不该转也跟着变，比字面会把正常波动报成不稳定。

**退出码只在"同一句话执行出了两种不同动作"时才为 1。** 其余不一致会列出来但不算失败，因为那些轮次系统并没有做错事：

| 现象 | 判定 |
| --- | --- |
| 同一句话一次开风扇、一次关风扇 | **失败**（从未观察到，真出现就是严重问题） |
| 一次听懂并执行、一次只给帮助文案 | 列出，不失败——它是**拒绝**，不是误执行 |
| 歧义问句（"站里闷不闷"）回答了不同的读数 | 列出，不失败 |

这个区分就是这个工具的价值所在：笼统地报"不稳定"会被读成"可能会乱动"，而那恰恰是整套设计要排除的事。

它是被 `tests/scripts/test_demo_rehearsal.py` 覆盖的（`--no-llm` 模式，快且不需要装任何东西），因为**一个悄悄丢掉了拒绝用例的演练脚本，会通过项目里其他所有测试**。

> 写它的起因是临时验证，结果第一次跑就抓出两个 800 多个单元测试都没抓到的规则缺口（"最吵到多少"答成当前值、"阈值调低一点"答成风扇状态）。两个都给出了看起来完全正常的回答——单元测试测的是想到的问法，演练测的是没想到的。详见 `docs/02_Architecture/Assistant_Design.md` §13.6。

## 4.11 assistant_benchmark.py —— 问答成功率评测

`demo_rehearsal.py` 回答"今天这场演示会不会出岔子"，这个脚本回答另一个问题：**答对率是多少，
错在哪里**。它把 87 句固定题库打进与 `run_all_界面加网关.bat` 相同的装配里，逐条对照期望意图判分。

```bash
python scripts/assistant_benchmark.py            # 接模型，约 7 分钟
python scripts/assistant_benchmark.py --no-llm   # 只测规则覆盖，数秒
```

题库四类：书面问句、口语问句、指令、**应当被拒绝的八句**（股市、笑话、订票、天气……）。
最后一类不能省——只测顺利路径的评测，发现不了一个"对什么都说好"的系统。

**三个数字必须分开看**：

| 指标 | 含义 |
| --- | --- |
| 规则命中率 | 有多少问句根本不需要模型。**这是唯一值得往上提的数**——规则命中零延迟、每次一致 |
| 模型分类成功率 | 规则落空的那些里，模型判对了多少 |
| 改写采纳率 | 模型改写的措辞有多少通过了接地校验。被拒不是缺陷，是那道校验在工作 |

判分口径有两处刻意从严：**指令必须真的执行了**（只认出意图、`applied` 不为真，判错——认出来却没落到设置上等于没做）；**通道答错与意图答错同罪**（把湿度问题答成温度，数字是真的但答非所问）。

**退出码只在"指令类"或"范围外"出现错答时为 1**。这两类错了有后果：指令有副作用，而范围外答出内容意味着系统给自己编了个话题。问句答错只列出、不判失败——用户换个说法再问一遍即可。`--no-llm` 那趟永远返回 0，因为口语说法本就该在没有模型时落到帮助文案。

> **写它的直接收益**：第一次跑出 8 条错答，其中 **5 条根本不是模型的问题，而是规则词表缺词**——
> 「最干的时候湿度多少」被读成当前值，只因 MINIMUM 词表认得"最低"不认得"最干"。补上 8 个词之后
> 规则命中率 69% → 78.5%，总体 87.7% → 92.3%。**遇到答错先查词表再改提示词**，这条经验写进了脚本头部注释。

配套测试 `tests/scripts/test_assistant_benchmark.py`（8 项，跑 `--no-llm` 模式）守住两件事：
题库不能悄悄丢掉拒绝用例，判分口径不能松。

## 5.2 无硬件条件下如何测串口

这是整套测试里最关键的一个问题：开发环境里没有真实硬件，`SerialChannel` 怎么测？

答案是 `tests/communication/test_serial.py` 里的 `_FakeSerialPort`——一个**显式的、最小的"虚拟串口"**，只实现 `SerialChannel` 真正会用到的那部分 pyserial 接口（`is_open`、`write`、`in_waiting`、`read`、`close`），并允许每个测试精确指定"什么时候该发生什么故障"。配合 `unittest.mock.patch` 替换掉 `serial.Serial` 构造函数与 `serial.tools.list_ports.comports()`。

这样能覆盖到真实硬件上很难稳定复现的场景：端口不存在、端口存在但打不开、写超时、读异常、连接后被拔掉。它验证的正是第 1.4 节讲的那套异常翻译——**每一种 pyserial 异常都被翻译成 communication.exceptions 里的对应类型**。

同样的技术被 `tests/scripts/test_run_gui.py` 复用来测硬件模式的装配。

## 5.3 分层边界靠测试固定

第 1.1 节讲的那三条依赖边界，不是只写在文档里的君子协定——它们被测试固定住了。测试构造真实的对象栈（`ApplicationRuntime` + `LocalApi` + `SimulatorDevice` + `LoopbackChannel`），验证上层确实只经由允许的接口拿到东西。

`tests/integration/test_hardware_mode.py` 是这类测试里最有代表性的一个：它验证 `SimulatorDevice` 与 `RemoteDevice` **能通过完全相同的 ApplicationRuntime/LocalApi/DeviceManager 代码路径**被注册、查询和控制——`device/` 以上任何地方都没有针对设备类型的 if/else 分支。9 个用例覆盖：两种设备共存于一个 runtime、状态查询对 RemoteDevice 同样有效、控制链路对 RemoteDevice 有效、命令被拒的情况、**设备不应答时超时**、以及 `report_data()` 对 RemoteDevice 必须抛错。

这个文件里的 `_seed_ack()` 辅助函数也值得一提：因为硬件模式的 `deliver()` 会等待设备真正发回的 ACK（不像模拟模式在本地伪造），所以测试必须自己扮演设备那一方，往 `LoopbackChannel` 里预先放一个 ACK 帧。注释解释了这为什么可行：`deliver()` 的等待循环不在意到达顺序，只在意能否找到一个 wire id 匹配、命令类型为 `COMMAND_ACK_CODE` 的帧——预置的 ACK 在第一次轮询就会被取到，效果等同于 `virtual_stm32.py` 通过真实串口应答一个真实请求，只是没有线路延迟。

## 5.4 四条端到端集成链路

`tests/integration/` 的四个文件各自验证一条完整链路：

| 文件 | 链路 |
|---|---|
| `test_data_pipeline.py` | SimulatorDevice → Protocol → Communication → Service，验证数据点被正确重建、订阅精确匹配、退订生效、多通道互不干扰、多设备互不干扰 |
| `test_command_pipeline.py` | 命令从提交、占用检查、编帧、下发到应答的完整往返 |
| `test_sensor_pipeline.py` | 传感器模拟器 → DataService → SensorDataProcessor → 统计/报警 |
| `test_hardware_mode.py` | 双设备模式的对等性（见上节） |

这些测试不 mock 中间任何一层——用的是真实的编解码、真实的通道、真实的服务实现。所以它们真正验证的是**层与层之间的接缝**，这恰恰是单元测试最容易漏掉的地方。

## 5.5 界面测试：pytest-qt 打通到设备

`tests/ui/` 用 `pytest-qt` 的 `qtbot` fixture。这里的做法值得注意：**界面测试没有 mock 掉后端**。`test_main_window.py` 构造的是一个真实的 `ApplicationRuntime` + `LocalApi` + `SimulatorDevice` + `LoopbackChannel` 栈，然后验证界面上真的出现了那个数值。

也就是说，一条 UI 测试实际上跑完了：设备生成 → 编帧 → 回环通道 → 解帧 → DataService 发布 → Controller 转成 Qt 信号 → 控件更新。**从设备到像素的整条链路被一个测试闭合**。

`tests/gateway/test_server.py` 用的是同样的思路：FastAPI 的 `TestClient` 在进程内跑**真实的 ASGI 应用**（真实路由、真实序列化、真实 WebSocket 握手），对接的是按 `run_api_server.py` 完全相同方式组装出来的真实 `ApplicationRuntime` + `LocalApi`——API 层没有任何 mock。

## 5.6 对脚本本身的测试

`tests/scripts/` 有 56 个用例，覆盖那些"看起来不像需要测试"的组合脚本：

- `test_run_gui.py` 不调用 `main()`（它会 `app.exec()` 阻塞住），而是复用 `main()` 自己的装配函数 `build_simulator_runtime()` / `build_hardware_runtime()`，再手动驱动。硬件模式用 mock 掉的 pyserial 跑。它验证的正是第 4.2 节讲的那件事：硬件模式确实把 `SerialChannel` → `HardwareDeviceReceiver` → `HardwareRuntimeRunner` 接到了**界面已经在读的那个** `data_service` 上，而且手动 `run_once()` 一次，数据就像模拟模式那样送达界面。
- `test_hardware_device_status.py` 固定住了第 4.2 节那个"顶部显示未连接、数据却在刷新"的矛盾不再复现。
- `test_collect_thesis_data.py` 是 `tests/scripts/` 里最大的一个（367 行）。文件头写明了理由：录制那一半需要真实硬件，但**对论文真正要紧的那一半——把原始帧变成表格里那些数字的算术——是纯函数，在这里被测掉了。一个算错的丢帧率或一个算错的平均周期，否则会不声不响地进到论文里。**

这最后一条是整个测试套件里立场最鲜明的一处：测试的目标不是覆盖率数字，而是**防止错误的实验结论被写进论文**。

## 5.7 每个任务的收尾检查

项目约定每个开发任务收尾前必须跑三项检查，且不得在明知未通过的情况下汇报完成：

```
pytest              # 1278 个用例
ruff check src tests # lint：E/W/F/I/B/C4/UP 规则集，行宽 88
mypy src            # 类型检查：disallow_untyped_defs、warn_return_any、warn_unused_ignores
```

`mypy` 配置里的 `disallow_untyped_defs = true` 是一条强约束：**src/ 下每一个函数都必须有完整的类型标注**。这也解释了第 1.2 节里为什么要给 `DeviceId`、`ChannelId` 这些定义类型别名——有了别名，mypy 才能在调用点上区分出参数含义，而不是看到一堆无差别的 `str`。
