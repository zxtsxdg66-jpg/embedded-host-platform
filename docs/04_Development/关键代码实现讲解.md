## 一条数据的完整旅程

先建立整体心智模型。以一次温度读数为例，它经过的环节是：

```
AHT20 芯片
  │  ① 软件 I2C 时序读出 6 字节原始数据，CRC8 校验，换算成 ℃
  ▼
STM32 固件 finish_cycle_and_report()
  │  ② 拼成 JSON 文本 {"channel":"temperature","value":26.35}
  ▼
protocol_encode()  →  USART1
  │  ③ 套上帧头 AA55 + 设备号 + 命令码 + 长度 + CRC-32，写进串口
  ▼
=================== 物理链路：USB 转串口 ===================
  ▼
SerialChannel.receive()
  │  ④ 读回一批字节——注意：可能是半帧，也可能是三帧粘在一起
  ▼
FrameStreamBuffer.extract_frame()
  │  ⑤ 从字节流里精确切出恰好一帧（本系统最关键的一段代码）
  ▼
protocol.decoder.decode()
  │  ⑥ 校验帧头、长度、CRC-32，任一不过就抛异常
  ▼
HardwareDeviceReceiver._process_frame()
  │  ⑦ 解 JSON，包装成 DataPoint
  ▼
DataService.publish()
  │  ⑧ 发布—订阅扇出
  ├─────────────────┬──────────────────┐
  ▼                 ▼                  ▼
SensorDataProcessor  ui（PyQt6）      gateway（FastAPI）
统计 + 阈值报警      MainController    REST / WebSocket
                     → 界面刷新         → Android 客户端
```

**这条链路上有两处"边界"值得特别注意**，它们是本系统设计的两个支点：

1. **③ 与 ⑤ 之间**：发送方按"一帧"发送，接收方拿到的却是"一串字节"。
   这个不对称是所有串口通信 bug 的温床，第 3 节专门讲。
2. **⑧ 处**：`DataService.publish()` 之后，下游三个消费方**都不知道数据来自哪里**——
   是模拟器还是真串口，是本机还是远程。这使得 Simulator 与 Hardware 两种模式
   从这里往上的代码完全一致，也是"接真板子时 `src/` 零改动"的原因。

## 协议层：一帧到底长什么样

### 帧结构

```
+--------+-----------+--------------+--------+-----------+-----+
| Header | Device ID | Command Type | Length | Payload   | CRC |
| 2B     | 1B        | 1B           | 2B     | Length B  | 4B  |
| AA 55  |           |              | 大端   |           | 大端|
+--------+-----------+--------------+--------+-----------+-----+
                     ↑                                  ↑
                     └──────── CRC-32 覆盖范围 ─────────┘
```

固定开销 10 字节（2+1+1+2+4）。一条温度读数的 payload 是 39 字节 JSON，整帧 49 字节。

### 编码：`src/protocol/encoder.py`

```python
HEADER = b"\xaa\x55"
DEVICE_ID_SIZE = 1
COMMAND_TYPE_SIZE = 1
LENGTH_SIZE = 2
CRC_SIZE = 4
BYTE_ORDER: Literal["big"] = "big"


def encode(frame: Frame) -> bytes:
    body = (
        frame.device_id.to_bytes(DEVICE_ID_SIZE, BYTE_ORDER)
        + frame.command_type.to_bytes(COMMAND_TYPE_SIZE, BYTE_ORDER)
        + len(frame.payload).to_bytes(LENGTH_SIZE, BYTE_ORDER)
        + frame.payload
    )
    crc = zlib.crc32(body).to_bytes(CRC_SIZE, BYTE_ORDER)
    return HEADER + body + crc
```

**逐点讲解：**

- **`BYTE_ORDER = "big"`（大端序）**。为什么不用小端？因为 STM32 是小端机，
  如果直接内存拷贝会依赖两端的 CPU 字节序，换个平台就崩。大端序即网络字节序，
  是跨平台协议的通行约定，固件侧也显式按 `>> 8` / `& 0xFF` 拼装，
  **两端都不依赖各自 CPU 的天然字节序**。

- **`crc32(body)` 而不是 `crc32(HEADER + body)`**。这是有意的：帧头是固定的 `AA 55`，
  永远不变，它不携带任何需要保护的信息。把不变量放进校验范围，
  既不增加检错能力，还让"校验范围"与"有效载荷"这两个概念不再对齐。
  **答辩如果被问"为什么 CRC 不包含帧头"，标准答法就是这句。**

- **`len(frame.payload)` 写进 Length 字段**。这是接收侧能"知道该收多少字节"的唯一依据，
  也是第 3 节拼帧算法的核心输入。

### 解码：`src/protocol/decoder.py`

```python
def decode(data: bytes) -> Frame:
    if len(data) < _MIN_FRAME_SIZE:
        raise FrameLengthError(...)              # ① 长度下限
    if data[:_HEADER_SIZE] != HEADER:
        raise FrameSyncError(...)                # ② 帧头

    offset = _HEADER_SIZE
    device_id = int.from_bytes(data[offset : offset + DEVICE_ID_SIZE], BYTE_ORDER)
    offset += DEVICE_ID_SIZE
    command_type = int.from_bytes(data[offset : offset + COMMAND_TYPE_SIZE], BYTE_ORDER)
    offset += COMMAND_TYPE_SIZE
    declared_length = int.from_bytes(data[offset : offset + LENGTH_SIZE], BYTE_ORDER)
    offset += LENGTH_SIZE

    payload_end = offset + declared_length
    crc_end = payload_end + CRC_SIZE
    if len(data) != crc_end:
        raise FrameLengthError(...)              # ③ 声明长度一致性

    payload = data[offset:payload_end]
    received_crc = data[payload_end:crc_end]
    body = data[_HEADER_SIZE:payload_end]
    expected_crc = zlib.crc32(body).to_bytes(CRC_SIZE, BYTE_ORDER)
    if received_crc != expected_crc:
        raise ChecksumError(...)                 # ④ CRC-32

    return Frame(device_id=device_id, command_type=command_type, payload=payload)
```

**四类校验各自防什么：**

| 校验 | 防的是 | 抛出 |
| --- | --- | --- |
| ① 长度下限 | 连帧头都没收全就来解析 | `FrameLengthError` |
| ② 帧头 | 从错误的位置开始解析（不同步） | `FrameSyncError` |
| ③ 声明长度一致性 | 长度字段被干扰成了错值 | `FrameLengthError` |
| ④ CRC-32 | 传输过程中的位翻转 | `ChecksumError` |

**为什么抛异常而不是返回 `None`？** 这是项目遵循的 "fail loud" 原则：
返回 `None` 会让调用方很容易忘记检查，把可疑数据当成正常数据继续往上传。
抛异常则强制调用方显式处理。更重要的是——**四类异常互相区分**，
使上层能分辨"没收全"（`FrameLengthError`）与"收错了"（`ChecksumError`）
这两种性质完全不同的情况。第 6 章能把"帧同步错误 / 丢帧 / 校验失败"
分成三项独立统计，根子就在这里。

> **注意 `decode` 的一个刻意限制**：它要求 `data` **恰好是一帧**，
> 不多不少。"在一串不知道从哪开始、可能不完整的字节里找到帧边界"
> **不是它的职责**——那是下一节的事。这个职责切分写在它自己的 docstring 里，
> 也正是后面那个真实 bug 的判据。

## 最关键的一段：字节流拼帧

### 问题：串口没有"消息"这个概念

这是初学串口最容易栽的地方。你在固件里调用了 3 次 `pc_link_send_frame()`，
PC 侧调用 `receive()` 拿到的**不保证**是 3 次、每次一帧。真实情况可能是：

```
情况 A（粘包）：一次 receive() 返回 147 字节 = 3 帧连在一起
   AA55...49B...AA55...49B...AA55...49B...
   
情况 B（半包）：一次 receive() 只返回 30 字节 = 半帧
   AA55 01 01 0027 7B22 6368 616E ...（还差 19 字节）
   
情况 C（最糟）：一次 receive() 返回 60 字节 = 1 帧 + 下一帧的开头
   AA55...49B完整...  AA55 01 01（下一帧只到这里）
```

**为什么开发前期一直没暴露？** 因为 Simulator 模式用的 `LoopbackChannel`
内部是一个 `deque`，一次 `send()` 对应一次 `receive()`，**天然保留了消息边界**。
代码里那个"一次 receive 就是一帧"的隐含假设，在回环通道下永远成立。
直到接上真串口（WSL + socat 虚拟串口对，`virtual_stm32.py` 连发 3 帧无间隔）
才第一次暴露。**这是本项目"测试全绿 ≠ 功能可用"的第一个实例。**

### 解法：`FrameStreamBuffer`

```python
_LENGTH_OFFSET = len(HEADER) + 1 + 1        # 帧头(2) + 设备号(1) + 命令码(1) = 4
_FIXED_PREFIX_SIZE = _LENGTH_OFFSET + LENGTH_SIZE   # 再加长度字段(2) = 6


class FrameStreamBuffer:
    def __init__(self, on_discard=None):
        self._buffer = bytearray()          # 跨多次 receive() 累积的字节
        self._on_discard = on_discard       # 丢字节时的回调（用于错误计数）

    def feed(self, data: bytes) -> None:
        if data:
            self._buffer.extend(data)

    def extract_frame(self) -> bytes | None:
        self._resync()                                      # ① 先对齐到帧头
        if len(self._buffer) < _FIXED_PREFIX_SIZE:
            return None                                     # ② 连长度字段都没收到

        declared_length = int.from_bytes(
            self._buffer[_LENGTH_OFFSET : _LENGTH_OFFSET + LENGTH_SIZE], BYTE_ORDER
        )                                                   # ③ 读出声明长度
        total_size = _FIXED_PREFIX_SIZE + declared_length + CRC_SIZE
        if len(self._buffer) < total_size:
            return None                                     # ④ 还没收全，原样保留

        frame_bytes = bytes(self._buffer[:total_size])       # ⑤ 精确切出一帧
        del self._buffer[:total_size]                        # ⑥ 从缓冲区移除
        return frame_bytes
```

**核心思想只有一句：不猜，只按协议自己声明的长度算。**

具体走一遍情况 C（1 帧 + 下一帧开头共 60 字节）：

1. `_resync()` 发现缓冲区开头就是 `AA55`，直接返回，不动;
2. 缓冲区 60 字节 ≥ 6，可以读长度字段；
3. 从偏移 4~5 读出 `declared_length = 39`；
4. `total_size = 6 + 39 + 4 = 49`，缓冲区 60 ≥ 49，够了；
5. 切出前 49 字节作为完整一帧返回；
6. 缓冲区剩下 11 字节（下一帧的开头），**原样留着**，等下次 `feed()` 补齐。

调用方 `HardwareDeviceReceiver` 会循环调用直到返回 `None`
（`poll_until_empty()`），所以粘在一起的 3 帧会在一次轮询里被全部取出。

### 重同步：不让一个脏字节卡死整条链路

```python
    def _resync(self) -> None:
        if not self._buffer:
            return
        index = self._buffer.find(HEADER)
        if index == 0:
            return                                  # 已经对齐，最常见的情况
        if index == -1:
            # 缓冲区里根本没有完整帧头
            partial_tail_len = 0
            for size in range(min(len(HEADER) - 1, len(self._buffer)), 0, -1):
                if bytes(self._buffer[-size:]) == HEADER[:size]:
                    partial_tail_len = size          # 尾部是"半个帧头"，要保住
                    break
            discarded = len(self._buffer) - partial_tail_len
            if partial_tail_len:
                del self._buffer[:discarded]
            else:
                self._buffer.clear()
            if discarded and self._on_discard is not None:
                self._on_discard()                   # 只有真丢了字节才计数
            return
        del self._buffer[:index]                     # 丢掉帧头之前的脏字节
        if self._on_discard is not None:
            self._on_discard()
```

**为什么需要它？** 设想线路上因干扰多出来一个字节 `0x37`，缓冲区变成
`37 AA55 01 01 ...`。如果不重同步，`extract_frame` 会从 `0x37` 开始算，
长度字段读到的是错位的值，算出的 `total_size` 完全不对，这一帧废掉——
更糟的是缓冲区永远对不齐，**后面每一帧都废掉**，链路从此瘫痪。
`_resync` 用 `find(HEADER)` 定位到真正的帧头，把前面的脏字节丢掉，
一次干扰只损失一帧。

**"半个帧头"这个分支是最微妙的一处**，也是后来出过问题的地方：

假设 `receive()` 返回的字节恰好在帧头中间断开，缓冲区里只剩一个 `AA`。
`find(b"\xaa\x55")` 返回 `-1`（找不到完整帧头）。此时**绝不能把这个 `AA` 丢掉**——
它极可能是下一帧的第一个字节，后半个 `55` 还在路上。所以那个 `for` 循环
从长到短试探"缓冲区尾部是不是帧头的前缀"，是的话就保留。

而 `discarded` 的计算 `len(buffer) - partial_tail_len` 决定了**是否计一次错误**：
如果缓冲区里就只有这半个帧头，`discarded == 0`，**不计错误**——
因为什么都没丢，这只是字节流传输的正常中间状态。第 6 节会讲这里踩过的坑。

## 采集端固件：状态机与非阻塞等待

### 采集周期状态机

固件的主循环是 10 ms 一拍的前后台结构，采集周期是 300 拍 = 3 秒：

```c
#define SENSOR_CYCLE_INTERVAL_TICKS  300u    /* 300 * 10ms = 3 秒 */

typedef enum {
    CYCLE_IDLE = 0,       /* 等待下一个采集周期到来 */
    CYCLE_NOISE_WAIT,     /* 已发起 Modbus 请求，等待应答或超时 */
} sensor_cycle_state_t;
```

```c
while (1)
{
    pc_link_poll();                              /* ① 每拍都先伺候 PC 链路 */
    if (pc_link_frame_ready()) {
        handle_incoming_pc_frame();
    }

    switch (cycle_state)
    {
        case CYCLE_IDLE:
            if (loop_ticks >= next_cycle_tick) {
                next_cycle_tick = loop_ticks + SENSOR_CYCLE_INTERVAL_TICKS;  /* ② */
                noise_sensor_start_request();
                cycle_state = CYCLE_NOISE_WAIT;
            }
            break;

        case CYCLE_NOISE_WAIT:
        {
            float noise_db = 0.0f;
            noise_sensor_status_t status = noise_sensor_poll(&noise_db);
            if (status == NOISE_SENSOR_PENDING) {
                break;                            /* ③ 没答就先走，下一拍再看 */
            }
            {
                sensor_reading_t noise_reading;
                noise_reading.valid = (status == NOISE_SENSOR_OK) ? 1u : 0u;
                noise_reading.value = noise_db;
                finish_cycle_and_report(noise_reading);
            }
            cycle_state = CYCLE_IDLE;
            break;
        }
    }

    loop_ticks++;
    delay_ms(10);
}
```

**三个设计要点：**

**② 下一周期的时刻在本轮"开始"时就定死。**
`next_cycle_tick = loop_ticks + 300` 这一句写在发起请求**之前**，
而不是等本轮上报完再算。差别在哪？如果写在末尾，那么每轮的实际周期
= 3 秒 + 本轮噪声应答耗时，应答慢一点周期就长一点，**误差会累加漂移**。
写在开头则等待时间被吸收在周期内部，周期长度稳定。

> 这一点有实测支撑：1 小时实验中三个通道的平均间隔均为 3.094 s，
> 标准差仅 0.023 s，且与设计值的偏差是**系统性的 +3.14%**（来自 `delay_ms(10)`
> 的实际耗时略大于 10 ms），而不是随机漂移。

**③ 等待被拆成多轮轮询，而不是阻塞。**
如果这里写成 `while (!answered) {}` 死等，那么在等噪声应答的这段时间里，
`pc_link_poll()` 不会被执行，PC 发来的指令字节会堆在环形缓冲区里甚至被覆盖。
改成"没答就 `break`，下一拍再来看"，PC 链路在整个等待期间始终保持响应。
**这正是把采集周期做成状态机（而不是顺序执行）的根本理由。**

**① `pc_link_poll()` 在 switch 之前。** 顺序不是随意的：无论采集处于哪个状态，
PC 链路每一拍都会被处理，优先级最高。

### Modbus 非阻塞轮询

```c
noise_sensor_status_t noise_sensor_poll(float *out_db)
{
    if (!s_request_pending) {
        return NOISE_SENSOR_PENDING;            /* 尚未发起过请求 */
    }

    if (noise_usart_frame_ready())
    {
        uint16_t len;
        const uint8_t *frame = noise_usart_take_frame(&len);
        s_request_pending = 0u;

        /* 期望：地址(1)+功能码(1)+字节数(1)+数据(2)+CRC(2) = 7 字节 */
        if (len != 7u) {                                        /* ① 长度 */
            s_error_count++;
            return NOISE_SENSOR_ERR_FORMAT;
        }
        if (frame[0] != s_slave_address                          /* ② 字段 */
            || frame[1] != MODBUS_FUNC_READ_HOLDING_REGISTERS
            || frame[2] != 0x02u) {
            s_error_count++;
            return NOISE_SENSOR_ERR_FORMAT;
        }
        {
            uint16_t crc_expected = (uint16_t)frame[5] | ((uint16_t)frame[6] << 8);
            uint16_t crc_actual = modbus_crc16_calculate(frame, 5u);
            if (crc_actual != crc_expected) {                    /* ③ CRC16 */
                s_error_count++;
                return NOISE_SENSOR_ERR_CRC;
            }
        }
        {
            uint16_t raw = ((uint16_t)frame[3] << 8) | (uint16_t)frame[4];
            *out_db = (float)raw * 0.1f;                         /* 每单位 0.1 dB */
        }
        return NOISE_SENSOR_OK;
    }

    if ((HAL_GetTick() - s_request_sent_tick) > NOISE_SENSOR_TIMEOUT_MS)
    {
        s_request_pending = 0u;
        noise_usart_reset_rx();                  /* ④ 关键：清掉残缺字节 */
        s_error_count++;
        return NOISE_SENSOR_ERR_TIMEOUT;
    }

    return NOISE_SENSOR_PENDING;
}
```

**注意两处细节：**

**字节序在这里"反过来"了。** `crc_expected` 是 `frame[5] | (frame[6] << 8)`——
**低字节在前**；而数据 `raw` 是 `(frame[3] << 8) | frame[4]`——**高字节在前**。
这不是笔误：Modbus RTU 规定 CRC16 小端传输、寄存器数据大端传输，
两者本来就不一致。而这又与 PC↔STM32 自定义协议的大端序完全无关——
**同一个固件里同时存在三套字节序约定**，各自遵循各自协议的规定。
答辩若被问到，这是个能体现细致程度的点。

**④ `noise_usart_reset_rx()` 为什么必须有。** 超时说明这次应答没收全，
接收缓冲区里躺着半截数据。如果不清掉，下一轮的应答会接在这半截后面，
拼成一个长度、字段都可能"看起来合法"的错误帧。清空是唯一安全的做法。

### 通道有效性隔离

```c
if (data.temperature.valid) { report_channel("temperature", data.temperature.value); }
if (data.humidity.valid)    { report_channel("humidity",    data.humidity.value);    }
if (data.noise.valid)       { report_channel("noise",       data.noise.value);       }
```

**读失败的通道根本不上报**，而不是上报一个 `-999` 之类的占位值。
好处是上位机只会收到有效数据，不需要自己判别真伪。

> **但这条设计有个统计上的后果，必须知道**：噪声通道 Modbus 读取失败时不上报，
> 所以如果沿用"相邻同通道帧间隔跳变即算丢帧"的通用口径，
> 会把**传感器侧的应答失败**误算成**通信链路丢帧**。
> 第 6 章因此为噪声通道单列了"Modbus 应答成功率"指标：
> 某个周期收到了别的通道、唯独没有噪声帧 → 记一次 Modbus 失败；
> 整个周期一帧都没有 → 才算链路丢帧。1 小时实验结果是 1163/1163，100%。

### 固件侧也有一套拼帧

`pc_link_poll()` 做的事和 PC 侧的 `FrameStreamBuffer` 完全对称——
中断把字节收进环形缓冲区，主循环搬进线性缓冲区后按同样的
"重同步 → 读长度 → 够不够一帧"三步走：

```c
uint16_t declared_len = ((uint16_t)s_assembly_buf[4] << 8) | (uint16_t)s_assembly_buf[5];
uint16_t total_len = (uint16_t)(PROTOCOL_OVERHEAD_SIZE + declared_len);

if (total_len > PC_LINK_ASSEMBLY_CAPACITY) {
    /* 声明长度超出缓冲区容量 → 判定脏数据，丢弃帧头重新同步 */
    s_assembly_buf[0] = s_assembly_buf[1];
    s_assembly_len = 1u;
    s_error_count++;
    return;
}
if (s_assembly_len < total_len) {
    return;                      /* 还没收全一帧 */
}
```

**固件多了一层 PC 侧没有的防护**：`total_len > 缓冲区容量` 时直接判脏。
因为 MCU 上缓冲区是固定大小的静态数组，一个被干扰成 `0xFFFF` 的长度字段
如果不拦住，会导致永远等不到"收全"，链路死锁。PC 侧是动态 `bytearray`，
没有这个风险，靠 CRC 兜底即可。**同一套协议，两端按各自的资源约束做不同防护，
这是个可以讲的点。**

## 上位机：从字节到界面

### 帧 → DataPoint

```python
    def _process_frame(self, raw: bytes) -> DataPoint | None:
        try:
            frame = decode(raw)
        except ProtocolError:
            self.error_count += 1                    # ① 协议级错误
            return None

        if frame.device_id != self._wire_id or frame.command_type != DATA_REPORT_CODE:
            self.ignored_frame_count += 1            # ② 不是给我的 / 不是数据帧
            return None

        try:
            body = json.loads(frame.payload.decode("utf-8"))
            channel_id: ChannelId = body["channel"]
            value = body["value"]
        except (ValueError, KeyError):
            self.error_count += 1                    # ③ 负载解析失败
            return None

        point = DataPoint(device_id=self._device_id, channel=channel_id, value=value)
        self._data_service.publish(point)
        return point
```

**注意 ① 和 ② 用了两个不同的计数器**。`error_count` 记的是"出错了"，
`ignored_frame_count` 记的是"没出错，但这帧不归我处理"（比如命令应答帧）。
把它们混在一起会让实验数据失去意义——第 6 章表格里"已忽略的非数据帧"
之所以能单独成一行，就是因为这里分开了。

### 发布—订阅：为什么 ui 不认识串口

`DataService.publish()` 之后，数据通过回调扇出给所有订阅者。
关键在于**订阅者拿到的是 `DataPoint`，一个纯数据对象**，
里面只有 `device_id` / `channel` / `value` / 时间戳，
**没有任何关于"这条数据怎么来的"的信息**。

这带来一个可以量化的结论：从 Simulator 模式切换到真实 STM32，
`protocol` / `communication` / `service` / `application` / `api` / `ui`
六层**没有为适配硬件改过一行代码**。串口相关的对象
（`SerialChannel` / `HardwareDeviceReceiver` / `RemoteDevice`）
只出现在 `scripts/` 下的组装脚本里，`src/ui/` 目录 0 处 import。

### 统计与阈值评估

```python
TEMPERATURE_ALARM_MAX = 35.0
HUMIDITY_ALARM_MIN = 30.0
HUMIDITY_ALARM_MAX = 75.0  # 2026-09-08 补入，见下
NOISE_ALARM_MAX = 80.0
```

```python
    def handle_data_point(self, point: DataPoint) -> None:
        if isinstance(point.value, bool) or not isinstance(point.value, int | float):
            return                                   # ① 非数值直接忽略
        value = float(point.value)

        key = (point.device_id, point.channel)
        existing = self._statistics.get(key)
        if existing is None:
            existing = _RunningStatistics.start(value)
            self._statistics[key] = existing
        else:
            existing.update(value)                   # ② 增量更新，不存全量

        snapshot = existing.snapshot()
        for stats_callback in self._statistics_callbacks:
            stats_callback(point.device_id, point.channel, snapshot)

        self._evaluate_threshold(point.device_id, point.channel, value)
```

**① `isinstance(point.value, bool)` 这个判断为什么单独写？**
Python 里 `bool` 是 `int` 的子类，`isinstance(True, int)` 为 `True`。
如果不特判，一个 `True` 会被当成 `1.0` 混进统计里，
污染最小值/平均值且极难排查。这是个典型的 Python 陷阱。

**② 统计是增量的**（`_RunningStatistics` 只维护计数、和、最值），
不保存历史数据点。1163 个样本和 100 万个样本占用内存一样，
适合长期无人值守运行。代价是**上位机没有历史数据能力**——
这也是移动端"历史查询"功能有意未实现的根本原因，
并非漏做（`tests/gateway/test_server.py` 里有一条测试断言该端点返回 404，
把这个决定固定下来）。

```python
    def _evaluate_threshold(self, device_id, channel, value) -> None:
        rule = _ALARM_RULES.get(channel)
        if rule is None:
            return                                   # 没有规则的通道不评估
        kind, threshold = rule
        triggered = (
            value > threshold if kind is AlarmKind.ABOVE_MAX else value < threshold
        )
        status = ThresholdStatus(..., triggered=triggered)
        for status_callback in self._status_callbacks:
            status_callback(status)                  # ① 每次都发，带 triggered
        if not triggered:
            return
        ...                                          # ② 只有越限才发 AlarmEvent
```

**两套回调并存的原因**：`on_alarm` 只在越限时触发，适合写日志；
但界面需要知道**什么时候恢复正常**才能把标红的行清除。
`on_status` 每次评估都触发并携带 `triggered: bool`，
界面直接用它驱动"标红/清除"，不依赖两个信号谁先到达，
因此恢复正常后颜色能自动清掉，不需要额外的"复位"事件。

**注意阈值判定没有回差（迟滞）**：`value > threshold` 是单点比较。
读数在阈值附近抖动时状态会跟着翻转。第 6 章的报警实验特意用
"暂停播放"（本底 41 dB，距阈值 39 dB）而非"降到接近阈值"来构造低电平，
就是为了避开这个已知局限；该局限已如实写进第 6 章 6.4 节与第 7 章 7.2 节。

## 四个真实缺陷及其修复

这一节是答辩的高价值素材：**能讲清楚自己踩过什么坑、怎么定位、怎么修，
比声称"系统运行正常"有说服力得多。**

### 缺陷一：字节流拼帧缺失

- **现象**：接上真串口后，界面订阅成功但永远没有数据，且没有任何报错。
- **根因**：`poll_once()` 把每次 `receive()` 的返回值整体丢给 `decode()`，
  隐含假设"一次 receive 就是一帧"。这个假设只对 `LoopbackChannel` 成立。
  真实串口下多帧粘连或半帧到达时 `decode()` 抛 `FrameLengthError`，
  被 `run_once()` 的兜底 `except` 吞掉，于是**静默失败**。
- **定位**：注意到 `decode()` 自己的 docstring 早就写明"在任意字节流中定位帧边界
  不是它的职责"，说明缺的是调用方的一层。
- **修复**：新增 `FrameStreamBuffer`（第 3 节），只改 `application/`，
  未触碰 `protocol` / `communication` 任何接口。
- **教训**：`LoopbackChannel` 保留消息边界这一"便利"，恰恰掩盖了真实传输的核心难点。
  新增了 `_StreamChannel` 测试替身——它与 `LoopbackChannel` 的区别正是**不保留消息边界**，
  能在无硬件条件下复现这个 bug。

### 缺陷二：Hardware 模式下发命令直接崩溃

- **现象**：硬件模式点"发送命令"，整个 GUI 进程崩溃。
- **根因**：`DeviceManager.deliver()` 对所有设备都走"发送后本地立即自问自答"的逻辑
  （`send()` 后紧接着本地 `receive()` 构造 ack）。这对 `LoopbackChannel` 成立，
  但真实串口对面的设备不会瞬间应答，`receive()` 立即读到空字节，
  `decode()` 抛出未捕获异常。
- **修复**：按设备类型分两条路径——`SimulatorDevice` 保留原有自环逻辑；
  `RemoteDevice` 改为**真正等待**设备侧的 ack 帧（复用 `FrameStreamBuffer` 处理粘连），
  带 2 秒超时，超时抛 `OperationTimeoutError`，
  经 `api` 转译为 `CommandDeliveryError`，被 `ui` 已有的 `except ApiError` 兜底
  变成界面提示而非崩溃——**`ui/` 本身零改动**。

### 缺陷三：Hardware 模式报警从未被评估

- **现象**：WSL 硬件在环演示时发现"温度早就超过阈值但界面毫无反应"，Simulator 模式一切正常。
- **根因**：`scripts/run_gui.py` 的 `build_hardware_runtime()` 为了拿到 `wire_id`，
  **刻意绕开** `ApplicationRuntime.register_device()` 直接调 `runtime.devices.register(...)`。
  而新加的报警自动订阅逻辑只放进了 `register_device()` 里。
- **修复**：把订阅逻辑拆成公开方法 `watch_alarms_for(device)`，两条路径都显式调用。
- **教训（已写成项目规约）**：**任何"设备注册后要做的事"，
  必须同时检查 `register_device()` 和 `build_hardware_runtime()` 两处**——
  后者不是前者的包装，是刻意绕开的另一条路径。这个坑后来又踩过一次
  （硬件模式设备状态显示"未连接"），所以现在有专门的测试同时断言两条路径。

### 缺陷四：13 次并不存在的"帧同步错误"

- **现象**：2026-08-18 噪声阶跃实验报出 13 次帧同步错误，但丢帧为 0
  （58 个采集周期全部收齐 3 帧）。
- **根因**：`_resync()` 中，当缓冲区尾部只剩"半个帧头"（等后半个字节到达）时，
  早期实现**无条件计一次重同步**。而在等待期间每次轮询都会重新走到这个分支，
  于是**一次正常的边界切分被反复累加**。
- **修复**：只有 `discarded > 0`（真的丢了字节）才触发计数回调。
- **为什么这个 bug 特别值得讲**：它**不影响任何功能**，数据一条没丢。
  但如果没发现，论文里就会出现"13 次帧同步错误"这个**并不存在的通信缺陷**，
  而且很可能被写成"系统存在偶发同步问题"。
  **这是一个测量口径的缺陷，不是通信的缺陷**——
  能把这个区分讲清楚，本身就是实验严谨性的体现。

## 答辩追问预案

> 完整的答辩问答见 `docs/07_Thesis/答辩问答准备.md`，此处只列与本文档代码直接相关的。

**Q：为什么自己设计协议，不用现成的 Modbus？**
A：系统里两者都在用——STM32 与噪声传感器之间就是标准 Modbus RTU。
自定义协议用在 PC↔STM32 这一段，因为需要传输的是变长的多通道数据，
Modbus 的寄存器模型需要预先约定寄存器映射，扩展一个通道就要改两端的映射表；
而本协议用 `command_type` + 变长 payload，新增通道只是 payload 里多一个 JSON 字段。

**Q：CRC-32 会不会太浪费？帧才 49 字节。**
A：确实，对这个帧长 CRC-16 的检错能力理论上已够。选 CRC-32 的理由是
STM32F407 有硬件 CRC 单元、Python 有 `zlib.crc32` 标准库实现，两端都零成本，
且为将来 payload 增大留了余量。这个取舍在第 3 章有论证。

**Q：你怎么证明真的没丢帧？**
A：判据是**相邻同通道帧的时间间隔是否出现跳变**（丢一帧会表现为间隔约为正常值的整数倍），
而不是用实收帧数与理论帧数相减——后者会把固件周期的系统性偏差（+3.14%）误报成丢帧。
1 小时实验 3489 帧、三通道各 1163 帧，帧数完全相同，说明每个周期都完整上报了三个通道。

**Q：JSON 文本负载在 MCU 上开销大不大？**
A：目前用 `snprintf` 生成，payload 39 字节，3 秒一次，在 168 MHz 的 M4F 上开销可忽略。
选文本格式是为了 phase-1 阶段调试方便——串口助手直接能看懂。
若后续采集频率提高到百毫秒级，应改为紧凑二进制格式；
改动只影响 `application/manager.py`、`hardware_runtime.py` 与固件的编解码约定，
`protocol` / `communication` 层不受影响。这一点已列入第 7 章 7.2 节展望。

**Q：为什么不用多线程接收串口？**
A：`HardwareRuntimeRunner` 刻意不起线程、不自循环，`run_once()` 由外部驱动
（GUI 里是 `QTimer`，网关里是后台线程）。这样 `DataService.publish()`
与随之而来的界面刷新都发生在 Qt 主线程上，符合 PyQt6 的线程约束，
不需要任何跨线程加锁。真正需要跨线程的地方只有网关的 `EventHub`，
它用 `loop.call_soon_threadsafe` 把同步回调桥接到 asyncio。
