## 二、逐日详录

### 2026-08-12 —— 硬件在环演示：三个真实 bug 集中暴露

这是整个项目**技术含量最高的一天**：第一次让代码面对真实的字节流，此前被回环通道掩盖的问题集中暴露。

**环境搭建走了弯路。** 原计划用 `com0com` 建虚拟串口对，但本机 Secure Boot 已开启，两个来源的驱动均报 `ConfigManagerErrorCode 52`（数字签名校验失败）。解决办法是关 Secure Boot + `bcdedit testsigning on`，**用户明确选择不走这条路**。改走 WSL2 + socat 创建一对 Linux PTY，最终验证成功。

过程中还踩了三个环境坑，都已记录以免重复摸索：WSL 功能显示 `Enabled` 但底层服务未真正部署（需 `DISM /RestoreHealth` + 重启两次）；WSL2 的 PTY 不映射成 Windows COM 口，所以设备侧脚本与 GUI **必须都跑在 WSL 里**；pyserial 的 `list_ports.comports()` 只 glob 固定命名模式，socat 建在 `/tmp/` 下的链接不会被识别，必须建到 `/dev/ttyUSB50` 这类路径。

**发现并修复了三个真实 bug**：

一是 `HardwareDeviceReceiver` 的字节流拼帧问题。原实现直接把每次 `channel.receive()` 的返回值整体丢给 `decode()`，而真实字节流没有消息边界——订阅后收不到任何数据。修复方式是新增 `application/frame_stream.py`，把帧边界恢复抽成一个共享组件。

二是 `DeviceManager.deliver()` 在硬件模式下命令下发会崩溃。原实现无论模拟还是硬件设备都走同一套"发送后本地立即自答"的逻辑，而真实设备的应答需要等。修复后对 `RemoteDevice` 真正等待设备侧应答，带超时、优雅失败；`scripts/virtual_stm32.py` 也相应实现了命令监听与应答。

三是 `watch_alarms_for()` 在硬件模式下漏调用。硬件装配函数为了拿到 wire id 而直接调 `runtime.devices.register(...)`，绕过了会自动订阅报警的门面方法。**这是本项目第一次踩"两条装配路径不一致"的坑**，后来在 08-17 又踩了第二次。

还有一次"自伤"值得记下：修复第二个 bug 时，在 `virtual_stm32.py` 自己新写的最小化拼帧逻辑里犯了**性质完全相同**的错误（resync 时误删整个缓冲区，而不是只删垃圾前缀）。源文档对此的总结是：写这类"重新实现一遍、不能共享代码"的设备侧替身逻辑时，即使逻辑很短也值得对照已测试过的版本仔细核对，不能因为"简单"就跳过验证。

**同日完成的功能接入**：阈值报警接入界面（`api.subscribe_alarm_status` → 活动日志红字 + 数据表格行标红，恢复正常后自动清色）；统计信息接入界面（`api.subscribe_statistics` + 新增独立控件 `StatisticsPanelWidget`，当前值/最小/最大/平均/样本数按 (设备, 通道) 实时展示）；数据面板新增"清空历史记录"；控制面板新增"暂停接收"。

统计信息接入时**复用了报警接入时刚修好的 watch_alarms_for() 机制**，硬件模式无需再修一遍——同一个坑没有踩第二次。

### 2026-08-15 —— 三端打通与一个"从来没工作过"的功能

实测结果：REST 全部正常（含未知设备 404、无控制权发命令 409、获取控制权后成功）；WebSocket 三种消息都能收到；`published_count` 持续增长证明数据在真实流动。

**发现了一个此前完全未被察觉的缺陷：模拟模式从来没有数据驱动。** `report_data()` 当时**只有测试在调用**，`scripts/run_gui.py` 与 `src/ui/` 里没有任何定时器或线程驱动它。实测确认：订阅后等 3 秒收到 **0** 条数据，手动调一次才收到 1 条。也就是说，**模拟模式的图形界面实际上从来没有显示过数据**，而文档里"订阅通道后曲线会展示模拟数据"的描述与实际不符。

### 2026-08-16 —— 第一批硬件到货：项目的分水岭

**这一天是整个项目的分水岭：第一次跑通"真实物理传感器 → MCU → 串口字节流 → PC"的完整链路。** 此前所有硬件模式验证都是靠 `scripts/virtual_stm32.py` 模拟设备侧。

开发板与 ATK-MB016（AHT20）到货并接线完成，固件烧入真板子后，温度与湿度两个通道的读数在 PC 端正确显示。由此**一次性实证了多个此前只是推断或只经过纯逻辑核对的环节**：

| 环节 | 此前状态 | 到货后 |
|---|---|---|
| PE0=SDA / PE1=SCL 是否真的空闲可用 | 仅凭手册文字推断 | 实证可用 |
| `soft_i2c.c` 的 GPIO 位翻转时序 | 未实机验证 | 实证可用 |
| `aht20.c` 数据换算 + CRC8 | 仅与厂商手册交叉核对 | 实证正确 |
| USART1 协议帧上报（帧格式 + CRC-32） | 仅与虚拟设备对接验证过 | 实证与真实 MCU 互通 |
| 接线方案 | 方案设计 | 实证正确 |

**当天还做了全链路端到端验证**，用 `run_all_界面加网关.bat` 硬件模式：PC 界面与 Android 手机**同时**显示正确的温湿度数值与曲线；并做了**物理扰动验证**——包裹传感器并哈气，数值随之正确上涨。

第二条是关键。联调手册专门要求做这个动作，理由是"比看似正常更强的验证，能进一步排除看到的是固定假数据的可能"：数值随真实环境变化，说明这条链路从物理量到屏幕像素每一环都在真的工作，而不是某处返回了缓存或默认值。

这一次同时闭环了多条此前分散的待验证项，其中最值得记的一条是：文档此前预测"PC 侧在实机联调阶段预期不需要修改"，**预测成立**——接真板子的全过程，`src/` 下**零改动**。从模拟模式到 WSL 虚拟串口再到真实 STM32，`protocol`/`communication`/`service`/`application`/`api`/`ui` 六层没有为了适配真实硬件改过一行。源文档明确指出，这可以作为论文中架构有效性的实证材料。

**run_all_界面加网关.bat 也在当天新增**，解决的是硬件到货后立刻暴露的问题：一个 COM 口只能被一个进程打开，界面与网关各自开串口时第二个必然失败（`PermissionError(13)`）。解法是一个 runtime、一次解码、扇出两个消费方。模拟模式与硬件模式当天都实测通过。

**Android 第二阶段 UI/UX 优化**同日完成编码：固定深色工业主题（配色与 PC 端同源）、首页四层信息层级、指标卡（数值 44sp、等宽数字消除抖动、按通道决定小数位、接入此前**被完全丢弃的** `statistics` 消息）、连接状态六态（含"已连接暂无数据"）、10 秒数据停滞检测、会话内折线、连接设置独立成页、背景图与面板半透明、App 图标、锁定竖屏。守住的边界是 `data/` 下五个文件**一行未改**，`src/`、`firmware/` 零改动，**未新增任何第三方依赖**。

**修了一个编码 bug**：`run_api_server_手机网关.bat` 选模式 1 后崩溃，报 `UnicodeDecodeError: 'gbk' codec can't decode byte 0x91`。根因是 `lan_address.py` 调 PowerShell 时用了 `text=True`，它按系统默认编码解码。

**记录了一个已知问题并决定暂不排查**：断电重启后需接一次 ST-Link 才运行。两种可能（BOOT0 上电为高 / 程序只 load 到 RAM 未写入 Flash）都完全符合现象，源文档给出了一分钟可分辨的办法（读 `0x08000000` 头两个字）。**用户决定暂不排查**——当前功能可用，答辩前接一下烧录器即可。记录在案以免被后来者当成漏做。

### 2026-08-17 —— 论文成稿日

**参考文献取得突破。** 此前受限于 CNKI 需机构账号、IEEE Xplore 为 JS 渲染，"研究现状"类文献几乎空白——绪论「国外研究现状」整节没有任何可引文献。本次改用**开放学术数据库 OpenAlex**（免注册、返回结构化题录且每条带 DOI），补充 **16 条外文文献**：国外研究现状从整节空白到 6 条，串口协议/帧格式方向从完全空白到 2 条，噪声监测嵌入式 5 条，地铁站环境 3 条。绪论据此写实，不再是占位块。源文档同时要求：所有新增外文文献**定稿前须逐条通过 DOI 核对原文**（已发现 1 例年份与卷期不一致）。

### 2026-08-18 —— 第二批硬件到货：最低置信度推断闭环

**噪声传感器 HH_07.06 到货，接线与模块本身确认正常工作。**

**硬件落地方案"待确认事项清单"第 1 项闭环**——P2 跳线 / PB10-PB11 能否作原始 TTL，是**全项目置信度最低的一条推断**。依据《探索者V3 硬件参考手册》确认：P2 是 2×3 排针，中间一排（3 脚 = PB11 / 4 脚 = PB10）**就是 MCU 侧原始引脚**，与 MCU 直连，中间无任何电平转换器件；跳线帽只决定这两个脚向上接 TP3232 还是向下接 ATK-MODULE 接口。因此"不装跳线帽、直接从中间一排引线"的方案成立。手册同时确认 PB10/PB11 属于仅经 P2 引出的 8 个 IO 之一，主排针上找不到。

**同时更正了一处风险描述**：上板手册称误接会碰到"RS232 电平转换芯片的输出端"，实测原理图后确认 P2 的 1/2 脚是 TP3232 的**逻辑侧**，仍是 3.3V TTL；真正的 ±12V RS232 电平不上 P2。故误接后果是通信不通，**不是烧模块**（但 2 脚是芯片输出，仍应避开）。

**采集方案落地为三个新预设**（噪声试运行 60 s / 噪声阶跃响应 180 s / 环境本底 15 min），`collect_data_实验数据采集.bat` 扩为 7 种预设。

**新增了 Modbus 应答成功率统计，这一项避免了论文出现误判。** 固件在 Modbus 读取失败时**根本不上报噪声通道**，只在调试口打日志。因此若沿用通用的"间隔跳变"丢帧口径，会把**传感器侧的应答失败记成通信链路丢帧**——与此前已纠正过的"把周期偏差误判为丢帧"属同一类错误。解法是新增 `group_cycles()` / `modbus_stats()`：因三通道在同一采集周期内上报，可据此精确归因——收到 temp+humi 但缺 noise 判为 Modbus 读取失败，三个都没有才是链路丢帧。

**仪表盘为论文截图重新布局一轮，同时修掉两个真实 bug**，其一是设备列表文字重叠：`QListWidgetItem` 自带的文字与叠加卡片里的同一个 device_id 被画了两遍，在 08-13 面板改半透明后才显形。

同期还修了帧同步误报：`FrameStreamBuffer._resync()` 早期版本在等待半个帧头到达时会重复计错，导致噪声阶跃实验**报出 13 次"帧同步错误"而实际 0 丢帧**（58 个采集周期全部收齐 3 帧）。若不修，会把并不存在的通信错误写进论文。

### 2026-09-08（再续）—— 试用暴露的两个 bug

助手做完后交给用户试用，当场问出两个问题，**都只在真人按真实节奏操作时才会暴露**。

烧录器到手，三个扩展模块首次跑在真板子上。**除 PC 下发报警状态一项（用户判断展示价值不大、暂不投入）外全部实机通过**：LCD 显示、电阻触摸、语音播报、风扇、「语音自检」按钮。

最费时的是触摸完全无响应，实际是**两个独立原因叠加、症状完全一样**：其一，厂商 `tp_scan()` 写的是 `return tp_dev.sta & TP_PRES_DOWN;` 而 `TP_PRES_DOWN = 0x8000`、返回类型却是 `uint8_t`，**按下时截断成 0**——厂商例程从不看这个返回值，我照抄了函数名却没照抄调用方式；其二，开发板出厂测试程序已在 24C02 里留了一份**竖屏**校准值，而本项目跑横屏，`tp_init()` 见有校准标记就跳过校准，数据"存在且合法"却完全不可用。后者加了 KEY0 强制重新校准解决，且刻意做在主循环而非初始化里——只在上电瞬间检测的话，用户无从判断是"没这功能"还是"没按对时机"。

风扇全速过快、持续运行有过热保护风险，改用 PWM。原设计特意避开定时器（TIM1 引脚被占），这次发现 **PE5 的 AF3 恰好是 TIM9_CH1 且 TIM9 全项目空闲**，因此调速改造**没有涉及任何接线变更**；20kHz 载波、60% 占空比、150ms 满占空比启动脉冲。

Keil 又一次在退出时把 `.uvprojx` 写回、覆盖掉新加的 HAL 文件（09-07 是 `hal_i2s.c`，这次是 `hal_tim.c`）。为此写了 `scripts/check_keil_project.py` 把"工程该长什么样"变成可执行断言，并在屏幕标题栏加了构建标记，用于排除"不确定烧进去的是不是这一版"这个干扰项。

### 2026-09-08（四续）—— 模型意图识别、自然语言控制与演练工具

问答此前只让模型改写措辞，**删掉模型回答一字不变**。这轮把模型的职责改成"听懂问题"：
规则落空时由模型分类（只回一个标签，不回 JSON——4B 模型的格式稳定性不够，改成词元扫描），
四道校验（非空 / 唯一标签 / 未自称 unknown / 通道齐备）任一不过就保持帮助文案不变。
随后追加自然语言下发控制，白名单四项、全部只写通风策略，**要改成多少这个数值由代码从用户原话里正则取，
不取自模型回复**——模型复述数字只要错一次，系统就会安静地按错值运行，而这类错误没有下游能发现。

演练与评测两个工具随之入库：`scripts/demo_rehearsal.py`（答辩前跑一遍看当天模型状态，
退出码只在"同一句话执行出两种不同动作"时为 1）、`scripts/assistant_benchmark.py`
（65 句题库判分，退出码只在指令类或范围外错答时为 1）。

**两个工具各自抓出了单元测试没覆盖的问题**：演练抓出"最吵到多少"被答成当前值、
"阈值调低一点"被当成问句；评测抓出 8 条错答里 5 条源于规则词表缺词。**由此确立一条工作方法：
遇到答错先查规则词表，再考虑改提示词**——补一个关键词的收益比任何提示词调整都直接，
且补进去的问句从此零延迟、结果恒定。补词后规则命中率 69.2% → 78.5%，总体成功率 87.7% → 92.3%。

### 2026-09-08（六续）—— 手机端问答与 App 图标

### 2026-09-08（七续）—— 湿度双向阈值：一条从未触发过的规则

第 10 章列的不足里，只有一条是真缺陷而不是取舍：湿度只判低限。标准给的 40%~65% 是双向区间，
而系统在"太湿"这一侧根本没有判据，第 9 章实测湿度长期 62%~78%、已高于标准上限，一次提示都没给过。

规则表由"一通道一条单边规则"改为"一通道一个区间"。改动之所以小，是因为 `AlarmKind` 本来就有两侧、
`AlarmEvent` 与 `ThresholdStatus` 本来就带 `kind` 和 `threshold`——**下游没有加任何字段**，
网关、界面、LCD 位图、固件全都没动。真正要想清楚的是两处：告警播报的连续确认计数原先只按通道记，
湿度从低限翻到高限时会串味，改成连"哪一侧"一起记；问答检索在读数正常时该引用哪一侧的边界，
定为更近的那一侧，否则会把 62%RH 说成"远高于 30%"。

**没有为它补做实验，而是把已有的 11 组记录回放了一遍**——数据是原来的数据，判据是新的判据。
4344 个湿度样本里 413 个高于新上限；更要紧的是另一个数：原有的低限规则在这 4344 个样本上
**一次都没有触发过**。它不是一条严格的规则，是一条在本地气候下不可能成立的规则，
于是系统的"湿度正常"从来不是判出来的，是默认出来的。这句话写进了第 9 章 9.5.1。

温度两级门限同时评估后**决定不做**：它引入"严重程度"这个系统里目前不存在的维度，
要动 `AlarmEvent`、网关 payload、语音选词、LCD 位图（五位不够要加第六位）直到固件重烧，
而它修的不是缺陷、只是把粒度做细。留在第 10 章展望里，是个可辩护的取舍。

顺带删掉了 LCD 标题栏那个调试用的构建标记 `b3`：固件行为已定型，
`check_keil_project.py` 也能直接查出工程文件被覆盖，它的用处没有了。

### 2026-09-08（八续）—— 让模型解释，以及一处被自己的校验罚掉的功能

用户提出"对 AI 的利用程度太低"。诊断下来，低的不是模型能力，是被允许触碰的范围：
一次读数提问的事实有九项，模板只打印一两项，其余全部丢弃。于是新增 `JOB_EXPLAIN`，
把整张事实清单交给模型写两三句。**这一步没有放宽任何约束**——送过去的每个数字，
都是接地校验随后会认的那些，模型看到的与它被允许说的是同一个集合。

范围保持窄，依据是量出来的：把当前读数一类也纳入时中位耗时 3.7 s → 9.7 s，
而"现在温度多少"是最常问的一句、模板本已给出读数与余量，六秒换来一句采样点数。
收窄到"是否越限 + 风扇状态"后成功率不变、中位回到 4.4 s。

**做这一步时暴露出一处此前无声的缺陷**：风扇答案的模板会打印判定原因，
那句话里带数字（"温度 26.8℃ 高于通风阈值 25℃"），而这些数字不在任何事实字段里。
后果是——风扇真正在转的时候，风扇模板自身通不过接地校验，**它的每一次模型改写都被静默丢弃**。
从外面看只是"风扇的回答从来不会变好听"，没有任何报错。这类缺陷值得单独记：
它不是逻辑写错，是一处事实没登记，而后果由一条本意保护系统的校验来承担。
**出口校验越严，喂给它的事实就越要完整。**

出口另加了一条报警断言黑名单（`triggered` 不为真时不许说"超标/告警/故障"）。
写它的时候把话说清楚了：**这和接地校验不是一类东西**。数字是闭集、可逐个溯源，是完备的白名单；
结论是开集、只能列禁用词，是不完备的黑名单。判断一句中文断言了什么本身就是语言问题，
最趁手的工具正是被检查的那个模型——用模型校验模型没有底。所以只对实测出现过的一种失败设防，
并把保证强度如实写成"常见的编造会被拦下"。

三轮评测：87.7% → 92.3% → **100%（65/65）**，规则命中 69.2% → 78.5% → **86.2%**。
但 100% 的性质要讲明白：题库固定，而后两轮的词表正是照着前一轮的错答补的，
**这是同一批题上的拟合，不是泛化能力**。真正有方法论价值的是错答来源——
三轮里超过一半的错答都是词表缺词而非模型判断失误，补一个词就能把一句话变成零延迟、恒定的规则命中。

### 2026-09-08（九续）—— 反问澄清，以及"问回去"和"猜一猜"不是二选一

"超标了吗"没说通道。此前系统答的是"该通道现在还没有有效读数，可能是刚启动或者传感器没接好"——
一句关于谁也没提到的通道的话，而且把"我没听全"说成了"传感器可能坏了"。
问题被听懂了，缺的是对象，那就该问回去。

做的时候有一个判断值得记：**反问不替代模型分类，两者同时进行**。有些问句的通道藏在口语里
（"这半天里最闹腾的时候"），规则认不出而模型能认出。所以系统立刻显示反问、同时仍把原句交给模型：
模型认出来就替换掉反问，认不出反问就留着等用户回一个词。一个是立刻到达的，
另一个是随后替换它或者没有——它们根本不冲突，第一版把它们写成了二选一，是我想窄了。

待答问题的有效期定为 60 s，比通道记忆的 180 s 短。记住的话题只是个提示，下一句可用可不用；
**没答的问题是一份承诺**，几分钟后再兑现，用户拿到的是一个正确但答非所问的回答，
这种错比重问一遍难发现得多。

顺带补了 `reset_conversation()`：有了对话状态之后，演练的两轮不再等价——
第一轮"超标了吗"开局无话题、触发反问，第二轮继承了上一轮最后的通道、直接作答。
两者都对，而稳定性检查恰恰要求两轮从同一处出发。

第四轮评测 65/65，四项指标与第三轮完全一致：反问只改变"未指明通道"这一类问句的处理，
题库里的问句都点了通道，所以它不侵入已经正确的路径——这正是重测要确认的事。

### 2026-09-09 —— LCD 第二页：屏幕上不该出现系统不敢负责的话

板载屏加了「数据」「问答」两个页签。分页而不是下拉滚动，是因为这块是**电阻屏**：
单点、需按压、没有惯性滚动，而拖动恰恰最吃触摸校准误差——那个坑本项目已经踩过一次
（KEY0 强制重新校准就是为它加的）。离散页签按偏几个像素照样命中。

设计上真正要想清楚的是**下发什么**。第一反应是把答案文本推给板子，但字库根本画不出来——
本板字库是从 `UI_TXT` 字面量生成的子集，完整 GBK 要外挂 SPI Flash、其总线占 JTAG 引脚，
这个取舍当初就否掉了。于是改成下发"哪一类答案 + 数值"，板子用自己的模板渲染。

**被约束逼出来的方案，回头看比原方案更好**：模型在 PC 那边怎么改写措辞，屏幕都不受影响，
**屏上出现的永远是事实**。这和整套问答"模型管措辞、系统管数字"的分工是同一条原则，
不是巧合——两处都来自同一个判断：让不可靠的那一方只碰不要紧的东西。

顺着这条线，**帮助文案、反问澄清、所有指令都不上屏**。指令这条是刻意的：
它的结果本来就在屏上活着（风扇那一行、报警位图），再摆一句"已把风扇打开"，
只会随时间变成一句挂在活指示旁边的过期的话。屏幕只显示系统能负责的那部分。

两个顺带产出。一是**补了命令码契约测试**：`manager.py` 的注释一直明写着
"nothing but review catches a mismatch"，而 PC 与固件的码不一致根本不会崩——
板子照样回 ACK，表现是某个功能安静地不工作。加第六个码的时候顺手把这个洞堵了。
二是**抓到一个真 bug**：`ANSWER_SHOW` 漏在 `ACCEPTED_COMMANDS` 里，
每一帧都在到达串口前被拒、全程零日志，单元测试全绿——端到端跑一遍才看出来。
这已经是同一类"装了但没接上"的第三次（前两次是 `run_api_server` 没 attach 模型、
装了 dispatcher 却没人驱动），端到端那一趟不能省。

### 2026-09-14 —— 换一批题，96.6% 变成 82.8%

先做了一轮文档审计，把 09-10 的 LLM 启停入口和 09-12 的论文转向同步进十几份文档。

然后问了一个一直没问过的问题：87 句题库上的 96.6% 能说明什么。答案是不太能——
那 87 句**全部被规则命中，模型分类一次都没被触发过**，而词表本来就是照着它补的。
于是用模板生成 148 句没见过的题，规则范围内只对 82.1%，更要紧的是 19 句**自信地答错**：
规则一旦给出判断，模型根本不会被调用。其中一句"风扇让系统自己决定开关"在真实组合里
把风扇切成了手动常关——没有"自动"二字，"开关"里的"关"命中了关闭词表。

同一批题绕过规则直接问模型，对了 91.0%，规则错的 24 句它纠正了 22 句。

还把"空调温度调到 26 度"判成了改通风阈值——强迫模型从枚举里挑一个，挑错时反而更干脆。不采用。

### 2026-09-15 —— 一句话里的两件事

用户试用时说了一句"现在多少度啊 有点热 你可以帮我打开风扇嘛"，系统只开了风扇，
温度那一问整段丢掉；接模型之后更难看，回来的是一句莫名的"你是想让我把风扇切到手动常开吗"。
两层原因叠在一起：规则一次只返回一个意图，风扇分支排在通道之前，整句被判成 `FAN_ON`；
复核又把**整句**交给模型，而分类提示词只许回一个标签，模型回了两个标签被作废，于是走了反问。
**模型没有判错，是输入里本来就有两件事。**

做法是在确认问句之后、整句识别之前先试拆句，按句读和空格切分，每段各过一遍规则，
**只在确有两件事时接管**，否则返回 None 让整句照旧处理。几条规则都是为了防止"拆出多余的一件"：
提问段必须带问句标记，否则"太热了，把风扇打开"里的"太热了"会被读成问是否超标、平白多答一句；
同种类同通道的两问合并为一件；**指令至多一条**，两条就不拆——一句话里两次改设备状态，
任何一条判错，用户都要从一次回显里把它读出来；紧挨数字的空格不算断点，否则"阈值调到 28 度"
拆开后读不到数值，指令反而会被拒。

提问部分**只用模板、不送改写**：几段事实拼出来的一句话没有单一的 `Facts` 供接地校验对照，
为了迁就它去放宽校验，等于把"数字只来自事实"这道闸拆掉。指令照常复核，但**只送指令那一段**。

回归用的是快照法：87 句题库、148 句留出题库、32 句鲁棒性题的回答、意图、是否执行、风扇模式与阈值
逐句存下来前后对比，**267 句逐项不变**，变的只有三句专门构造的复合句，全是预期中的"多答出一件"。
然后把 87 句里 73 条可组合的问句与指令两两拼成"A，B"跑全量：问+问 2390 组、问+指令 2244 组，
首版只对 65.9% 和 80.4%。**失败全部能归到十个单句**，问法集中在三类——"超了没有"这类以"没"作问、
"冷不冷""吵不吵"这类正反问、以及"有多响"。它们单独问时规则认得出，放进复合句却被当成
没有问句标记的铺垫整段丢掉。补上这三类标记后升到 93.5% 与 96.1%，剩下的失败只与两句有关，
而那两句都属于**按设计不拆**："好闷啊"没有任何问句标记；"阀值是多少"没点通道，
拆句不接管需要反问的提问——一句话里同时挂一个反问和另一件事，界面上说不清下一个"温度"补的是哪一半，
这条如实记为已知局限。端到端接真模型抽样各 25 句：问+指令 25/25 直接执行、反问 0，
问+问 错误执行 0。87 句基线重跑仍是 84/87、逐题与 09-14 相同——这批题全是单句，
重跑要确认的本来就不是拆句答得好不好，而是**拆句的判定没有漏进单句**。

第 4 章助手占 6 页作核心，四个实测缺陷升进正片；讲稿按 P01–P25 重写、15 分钟、时间向助手倾斜；

用户跑过之后提了两条：数值保留两位小数，三条通道分成三列各自展示。

**"三列"有两种做法，差别不在样子而在会不会撒谎。** 一种是并成一张按时刻对齐的表，

对齐意味着要假设"这一行的三个数属于同一刻"，而**某条通道一旦丢帧，
这一行就会把第 N 轮的温度和第 N+1 轮的湿度排在一起**：每个数字都是真的，

**取整只发生在显示这一步**，存储、问答引用、上云用的仍是原始浮点——
这条项目一直守着，显示上的方便不能变成对数据的悄悄编辑。

### 2026-09-18（续）—— 让模型碰上传，但不让它碰删除

用户问：怎么合理地让本地模型执行上传与删除脚本，是不是就用那个"收到指令由我确认"。
**上传是，删除不是**，而且这两件事的差别正好是整套边界设计的缩影。

先查了一件事：上云的按钮方案在 09-17 的设计文档里写得很完整，标着"P3 时做，答辩之前"，
而 **P3 交付时这一块一行都没实现**——`CLOUD_SYNC_HINT` 在代码里根本不存在，
文档读起来却像已经做完了。

**上传给按钮。** 三条准入性质它一条都不满足（不可逆、要拉子进程、参数说不清），
所以不进指令白名单，改成模型出标签、界面出按钮、人点一下才执行。
台账怎么到助手手里是个分层问题：`service` 不得 import `storage`，于是沿用 `HistoryStore`
的先例——协议定义在消费方，只给一个 `pending_upload_count() -> int`，
**刻意不返回台账自己的记录类型**，否则光是类型标注就把 storage 拖进 service 了；
适配器放在 `application/`，是唯一同时碰两边的地方。助手拿到的因此只是一个整数，
**接上它不可能让助手获得上传的能力**。

**删除不给按钮，做成"认出但拒绝"。** 理由里最硬的一条不是我想出来的，是项目自己已经判过：
09-17 把「清空历史记录」按钮的语义收窄成只清屏幕显示，docstring 里的原话是
"删数据是不可逆的，不该藏在一个看起来只是'清屏'的按钮后面"。
**也就是说，对删除而言一个按钮已经被判定太弱**；再让模型去点亮这个按钮，
等于把当时否掉的方案装回来，前面还多接了一个模型。

另外两条：参数取不自用户原话（"把旧数据清一清"根本没有范围，猜一个正是删错东西的方式），
以及没有撤销——白名单四项都能设回去，上云最坏是文件早传了一会儿，删除没有对应的回退。
还有一层是"删除数据"今天其实是三件事，而且耦合着：台账用 `is_exported(slot)` 挡重复导出，
手删了 `exports/` 里的 CSV 而台账仍记着"已导出"，那个时段就再也不会被重新导出，
界面上什么都看不出来。

拒绝不只是姿态，它堵的是一个**已经存在的坑**：数据在日常句子里紧挨着通道词，
"把噪声数据清一清"没有专门分支时会被噪声分支抢走，于是一条要求删除的话
拿回一个真实声压级——与 09-09"试一下播报能不能响"被答成噪声读数是同一种错。

规则分支是早返回，抢错一句就会顶掉原来的答案，所以先拿 87 句基线与 148 句留出题库
在规则层跑了一遍：**383 句零命中**。这个结论比它看起来强——分支不触发，
后面的管线就一个字节都不会变。词表上有两处刻意的排除：不收单字「清」
（它长在「说清楚点」里），不收「掉」「关掉」（那是关风扇的说法）。

最要紧的一条是复合句：一句话里既有删除又有真指令时，指令绝不能被执行。
实测"清空历史记录，顺便把风扇关了""把数据删了，然后把风扇打开"——
拆句在这里刻意不接管（删除段没有问句标记，只剩一件事），整句退回删除分支，
**风扇一动不动**。代价是同句里的提问会被丢掉，这条如实记成了已知局限：
静悄悄答了半句、把删除请求当没看见，比少答一个问题糟——用户会以为删除也照做了。

**按钮做完之后照例离屏跑了一次真窗口，抓到两个测试抓不到的问题。**

一是**按钮根本没出现**。答案文字完全正确，底下就是空的。原因是控制器发的标签是
意图枚举的值 `cloud_sync_hint`，而面板的处理器注册在 `cloud_sync` 下——
标签送到了、匹配不上、什么都没发生，**全程没有任何报错**。
如果我先写测试、两边又都照抄同一个错常量，这个 bug 会一路绿着过去。
现改成由 `OFFER_TAGS` 显式做一次翻译，并补了一条把两端钉在一起的测试。

二是**台账读不到时按钮仍然出现**，而那句答话写的是"我查不到还有多少没传，
可以直接双击 cloud_sync_导出并上传.bat"——按钮就摆在这句话下面，读起来像助手不信自己的建议。
改成只有待传数真的大于 0 才给按钮：0 是"都传完了"，给按钮等于说还有事可做；
`None` 是"读不到"，那句话已经告诉用户该怎么办了。

顺带修掉一处真缺陷：`ApplicationRuntime.attach_language_model()` 重建 Assistant
却不记住 llm，于是第二个可注入项一出现，两次 attach 就会互相把对方的注入冲掉，
谁后调用谁生效。已统一成一处 `_rebuild_assistant()`。
三个启动器全部接上台账（`run_api_server` 只接台账、不装按钮——它没有界面，
而手机端按设计本来就不给上传按钮），并逐个 `--help` 真跑过一遍，
09-17 那次"四个启动器全起不来而测试全绿"不能再来一次。

`pytest` 1241 → **1266**。

### 2026-09-18（五续）—— 上云那张表换成人能读的，以及首帧问题闭环

用户打开上云的归档文件后说"很奇怪"。逐条看确实有四处硌人：表头是英文标识符；
两列 ISO-8601 带时区的时间戳 **Excel 根本不认**，会当文本左对齐、排不了序也画不了图；
同一时刻的三个读数散在三行；`valid` 写成 0/1，看的人不知道那是什么。

**改成宽表之前，先去查了一件事**：真实硬件下同一轮内三个通道的时间戳到底差多少。
查历史库得到的答案是 **约 2 毫秒**（27.44 / 57.35 / 40.7 那一组是 .172288、.173732、
.174122），而轮与轮相差 **3 秒**——差一千五百倍。这个数字才是宽表敢做的依据。

**它和界面历史表那次的结论相反，而这不矛盾。** 09-18 早些时候我拒绝把历史表按时刻对齐，
理由是丢一帧就会把第 N 轮的温度和第 N+1 轮的湿度排进同一行、且看不出来。那边成立，
是因为那边只有到达顺序、**没有每条读数的时刻**；这里每条都带微秒级时间戳，
丢帧的结果是**那一格空着**，不会被下一轮的值顶上。
差别不在谨慎程度，在有没有可依据的事实——同一个动作，证据变了，答案就该变。

分轮除了间隔还加了第二条规则：**同一通道在本轮出现第二次即开新一轮**。
只按间隔切的话，某一轮只有噪声、下一轮紧接着也只有噪声时，两条会被并成一行、
直接丢掉一条读数。

还分了两种"没有数"：`噪声未上报`（没答上来）与 `噪声读数无效（原值 999.9）`（帧到了但数不可信）。
后者不进数值列——一个不可信的数字放进数值列，会被照样画进曲线里；但它也**不算"未上报"**，
那一帧确实到了。备注里分得开，读的人才判断得出是链路断了还是传感器读坏了。

编码用 **utf-8-sig**。中文表头配无 BOM 的 UTF-8，在中文 Windows 的 Excel 里就是整行乱码；
这条不是推测，本项目两天内已经被 GBK 咬过两次。

## 训练代码的位置定了：顶级 `training/`

维护期三个开放问题里的头两个，借这次一并了结。

**放顶级而不放 `src/` 下**，与 `firmware/`、`android/` 同一个理由：独立工具链，
不与 `src/` 共用构建与测试流程。训练依赖重（PyTorch 一类）且与上位机毫无关系，
写进 `pyproject.toml` 等于让每个只想跑界面的人先下几个 GB；一个要几小时、还要 GPU 的流程
也不该挂在"每个任务收尾前跑一遍"的三项检查上。

**尤其不能放 `src/llm/`**——那是运行期适配层，只能由 `application`/`scripts` 创建、
不得被 `service` import，因为它接的是外部服务。训练是离线的，塞进去会让一个本就受约束的
适配层同时承担两种生命周期，而这两种约束正好互相矛盾。

**`src/` 与 `training/` 互不 import。** 交接面是 Ollama 的模型名，不是 Python 符号。
这条保证了训练怎么折腾都伤不到已经稳定的平台——维护期那句"改一处就要问它是否值得
让已稳定的部分重新承担风险"，在这里是免费拿到的。要复用评测逻辑就照抄，不要 import：
`assistant_benchmark.py` 假定有一个活着的 `ApplicationRuntime`。

**产物管理**（第二个开放问题）：`training/runs/<日期>_<模型>_<轮次>/` 一轮一个目录、
**不覆盖**，权重与配置快照放一起；`training/datasets/` 放数据集。两者都进 `.gitignore`——
训练集可能含真人问过的原话，与 `logs/` 同因。不覆盖这一条是重点：第二轮盖掉第一轮就
再没有可比基线，而**能不能比较正是这件事唯一的判据**。

第三个开放问题（怎么衡量变好）不必新造，抓手是现成的：`assistant_benchmark.py` +
87 句拟合题库 + 148 句留出题库，基线已于 09-10 存档。README 里写明两个题库**必须都看且分开报**
——87 句那套规则全命中、模型分类一次没被触发，它只说明规则没退化；留出题库那 82.8%
才是泛化的量级参考。2026-09-14 正是搞混这两者才发现问题的。

README 里还钉了一条不随训练改变的线：**数字永远由检索层产出，模型不得说出任何读数、
阈值或统计量。** 训练能改进的是理解与措辞，不是让它获得说出数字的资格。

## 三、专题一：八个真实 bug 的发现与修复

项目推进中一共记录了八个**真实 bug**（不含设计取舍与待办项）。它们值得单独归总，因为其中六个有清晰的共同根因。

| # | 日期 | 问题 | 根因 |
|---|---|---|---|
| 1 | 08-12 | `HardwareDeviceReceiver` 拼帧错误，硬件模式订阅后收不到数据 | 回环通道保持消息边界，掩盖了真实字节流无边界的事实 |
| 2 | 08-12 | `DeviceManager.deliver()` 硬件模式命令下发崩溃 | 同上：本地立即自答的捷径只在回环通道下成立 |
| 3 | 08-12 | `watch_alarms_for()` 硬件模式漏调用，报警不触发 | 两条装配路径不一致（第一次） |
| 4 | 08-12 | `virtual_stm32.py` 自写 resync 误删整个缓冲区 | 重写替身逻辑时未对照已测版本核对 |
| 5 | 08-15 | 模拟模式从来没有数据驱动，界面从未显示过数据 | `report_data()` 只有测试在调用，无人驱动 |
| 6 | 08-16 | `lan_address.py` 调 PowerShell 崩溃（GBK 解码） | `text=True` 按系统默认编码解码 |
| 7 | 08-17 | 硬件模式界面显示"未连接"但数据在刷新 | 两条装配路径不一致（第二次） |
| 8 | 08-18 | 帧同步误报 13 次，实际 0 丢帧；设备列表文字重叠 | 正常的半帧头等待被计为错误；半透明化后旧的重复绘制显形 |

**共同根因一：回环通道掩盖了真实字节流的问题（#1、#2、#4）。** 源文档对此的总结是——"任何只在模拟模式测过的硬件相关代码路径，都不能默认它在真实字节流下同样成立"。

**共同根因二：两条装配路径不一致（#3、#7）。** 硬件模式的装配函数为了读回 wire id 而绕过了门面方法，于是门面方法里顺带做的事（自动订阅报警、隐含的状态语义）全部丢失。第二次踩坑后新增了**同时对两条路径断言**的测试，把这个类别的问题固定住。

**值得注意的是这些 bug 的发现方式**：#1、#2 是硬件在环演示时暴露的，#5 是接网关时顺带发现的，#7 是**为论文截图时从截图上看出来的**，#8 是界面改半透明后才显形的。没有一个是靠通读代码发现的——都需要让系统真正跑起来、并且换一个视角去看它。

## 四、专题二：硬件验证的四级推进

项目对"真实性"的验证不是一步到位，而是分四级逐步逼近，每一级都比上一级更接近真实：

| 级别 | 手段 | 验证到什么 | 时间 |
|---|---|---|---|
| 一 | `LoopbackChannel` 内存回环 | 分层契约、编解码往返、业务逻辑 | 08-12 之前 |
| 二 | mock pyserial（`_FakeSerialPort`） | 串口异常路径：端口不存在、打不开、写超时、读异常 | 持续 |
| 三 | WSL2 + socat 真实 PTY + `virtual_stm32.py` | **真实字节流**：粘包半包、帧边界恢复、命令往返 | 08-12 |
| 四 | 真实 STM32 + 真实传感器 | 物理时序、传感器换算、电气可用性、端到端 | 08-16 / 08-18 |

第三级是关键跳板：它在没有任何硬件的条件下暴露了三个真实 bug（专题一的 #1、#2、#4），使得第四级到货时**没有再遇到软件侧的阻塞**——`src/` 下零改动就接通了真板子。

第四级又分两批：08-16 开发板 + AHT20（温湿度两通道），08-18 噪声传感器（第三通道 + Modbus 链路）。每一批到货都把一组"仅凭手册推断"的结论转成"实证"，其中 PB10/PB11 的 TTL 可用性是全项目置信度最低的一条推断，08-18 闭环。
