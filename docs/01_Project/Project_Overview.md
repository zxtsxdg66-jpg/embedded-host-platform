# 项目概述

## 项目背景

随着嵌入式开发中设备种类（STM32、MSPM0、ESP32 等）和通信方式（UART、USB、TCP/IP、蓝牙）的多样化，开发者往往需要为每个项目重复编写上位机调试工具，导致代码重复、结构混乱、难以维护和复用。

本项目旨在构建一个**与具体硬件解耦**的通用上位机开发平台，作为未来嵌入式项目（包括本科毕业设计）的基础设施，避免"每换一个设备就重写一套上位机"的问题。

## 毕设应用场景与选题定位（2026-08-14 收敛）

经过前期通用框架搭建与"温度/湿度/噪声环境监测"验证场景的开发，本科毕设的应用场景与论文叙事已正式收敛，不再是开放式的"通用设备管理工具"：

- **应用场景**：以**地铁站公共空间环境监测**为典型应用场景，对多参数（温度、湿度、噪声）环境监测与远程管理系统进行设计、实现与验证——是"面向该场景的验证性系统"，不声称已建成地铁站生产级监控系统，也不要求当前阶段模拟完整地铁站。
- **论文主线（作者通信工程专业）**〔**2026-09-12 已抽象为上一层，见下节；本条保留为修订前记录**〕：论文的核心学术贡献定位为**嵌入式通信协议的设计与可靠性验证**（帧结构、CRC 校验、字节流粘包/半包处理、命令下发超时重试等，详见 `docs/03_Communication/Protocol_Design.md` 与 `docs/05_Test/Project_Status_Context.md` 第 2 节 Application Layer 记录的三处硬件在环验证中真实发现并修复的字节流级缺陷），地铁站环境监测场景是这条协议主线的**验证载体**。
- **工程亮点（非论文主线）**：多参数采集 + PC 上位机 + Android 移动端远程查看构成的**完整系统链路**是论文的工程亮点与"协议在真实系统中可用"的佐证，但不是第一叙事重心——章节篇幅上应向通信协议设计与测试章节倾斜，系统集成/界面/移动端章节相应收缩。
- **能力边界**：系统定位为"监测 + 异常预警 + 设备管理"，**不包含环境自动干预/执行器控制**（现有"控制"能力面向 STM32 设备本身的查询/重置/配置，不是对温度/湿度/噪声的主动调节），后续论文与文档均应如实反映这一边界，不做超出实际能力的表述。
  - **2026-09-12 更正**：本条已被后续开发超出。通风控制（`service/ventilation_controller.py` 判定 + `application/fan_dispatcher.py` 执行 + PWM 调速）属于对温度的主动干预，语音播报亦为执行器输出。现行边界应表述为"监测 + 异常预警 + 设备管理 + 有限的环境干预（通风、播报）"，**仍不包含**任意执行器控制与闭环调节。改动理由：原表述与已实现并实机验证的功能矛盾，若不更正会被论文正文与答辩材料继承。
- **不受影响的部分**：以上收敛只影响应用场景解释与论文叙事重心，`protocol`/`communication`/`device`/`service`/`application`/`api`/`ui` 现有分层边界与已实现代码**不因此调整或重构**，`device/sensors/` 下的三个传感器模拟器（temperature/humidity/noise）继续保留，定位明确为"地铁站环境监测场景的软件仿真数据源"。

## 论文主线的抽象（2026-09-12 修订）

上节"论文主线"一条自 2026-08-14 起定为"嵌入式通信协议的设计与可靠性验证"。
现修订为更高一层的抽象：

> **把不可靠的部件放在不承担正确性责任的位置。**
> 通信协议的可靠性保障与环境问答助手是同一原则的两个实例。

标注为**暂定**，后续可能再调整。

### 动机

两条，一条是选题差异化，一条是论证本身更完整。

**差异化**是主要动机。温湿度环境监测是历年毕设的高频选题，采集、显示、报警这条链路评委已相当熟悉，
以它作为第一叙事重心，很难回答"与往年同类选题的区别在哪"。环境问答助手所处理的问题——
一个会产生幻觉的语言模型如何被安全地接入一个要求读数准确的监测系统——在本科毕设中少见，
且本项目对它给出的不是"提示词写得更严"这类缓解手段，而是结构性的约束
（模型接触不到数值、没有执行权、输出须过五道确定性校验），并有实测数据支撑。

**论证完整性**是次要动机。抽象后，原有的协议主线并未被替换而是成为其中一个实例，
且与项目中另外两条早已存在的设计线索归入同一原则——
报警阈值只在 `service/sensor_data_processor.py` 一份、不复制进固件；
通风的判定在 `service/ventilation_controller.py` 而执行在 `application/fan_dispatcher.py`。
这三条加上助手共四个实例，此前在 `docs/02_Architecture/Assistant_Design.md` §1.1 已并列成表，
本次修订只是把该表的原则提为论文主线。

### 一条必须守住的写作纪律

助手章的 3,000 字**不得用于实现与部署细节**（Ollama 部署、提示词原文、采样参数取值一律不进正文）。
底层是调用现成开源模型，篇幅一旦花在实现上，创新性反而被削弱；
该章的价值全部在"约束是什么、拦住了什么、代价多少"，这恰好与论文的结果导向要求一致。


## 开发目标

- 建立分层清晰、职责单一的软件架构
- 抽象出通用的通信层与协议层，屏蔽底层硬件差异
- 提供可扩展的 UI 层，支持不同设备/场景下的界面定制
- 保证系统在需求未完全确定的情况下仍具备良好的可扩展性

## 功能规划

以下为平台级功能规划，具体实现优先级将根据后续毕设选题调整：

- 设备连接管理（串口/USB/网络/蓝牙的发现、连接、断开）
- 通信数据收发与日志记录
- 协议帧的编解码与校验
- 设备参数配置与指令下发
- 实时数据可视化（波形、数值面板等）
- 历史数据记录与回放
- 多设备管理（并行连接与切换）

## 非功能需求

- **可扩展性**：新增设备类型或通信方式时，不应影响现有模块
- **可维护性**：模块间低耦合，单个模块可独立测试和替换
- **稳定性**：通信异常（断线、超时、校验失败）应被妥善处理，不影响整体运行
- **可移植性**：核心逻辑尽量与操作系统/UI 框架解耦
- **文档完备性**：每个功能模块需有对应设计文档

## 未来可能应用方向

当前本科毕设已按上文"毕设应用场景与选题定位"一节收敛为地铁站公共空间环境监测场景；以下仍为平台架构层面保留的通用扩展方向，不代表当前毕设范围，仅说明通用框架本身的可扩展性并未因选题收敛而被牺牲：

- STM32 系列设备的调试与数据监控上位机（当前毕设选定路线）
- MSPM0 系列设备的通信与参数配置工具（架构层面预留，非当前毕设范围）
- ESP32 无线数据采集与远程监控平台（架构层面预留，非当前毕设范围）
- 面向其他具体课题（如控制系统、传感器网络等）的专用上位机派生版本（架构层面预留，非当前毕设范围）
