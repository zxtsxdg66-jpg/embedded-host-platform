# 验证

这份文档回答一个问题：**凭什么相信它能用。** 依次是验证的层级、自动化测试、真实硬件上的实测、
故障注入、开发中遇到的真实缺陷，以及问答部分的评测。每个数字都注明了出处与复现方式。

## 四级验证

对"真实性"的验证是逐级逼近的，每一级都比上一级更接近真实硬件：

| 级 | 手段 | 能验证什么 | 验证不了什么 |
| --- | --- | --- | --- |
| 1 | 内存回环通道 | 分层契约、编解码往返、业务逻辑 | 字节流没有消息边界这件事 |
| 2 | 假串口（替换 pyserial） | 端口不存在、打不开、写超时、读异常等难以在真机上稳定复现的异常路径 | 真实时序 |
| 3 | 真实字节流 + 虚拟设备 | 粘包、半包、帧边界恢复、命令往返 | 物理时序、传感器、电气 |
| 4 | 真实 STM32 与传感器 | 端到端 | — |

第 3 级是关键跳板：它在没有任何硬件的时候暴露了三个真实缺陷（见下文），
所以开发板到货时**软件侧没有再被阻塞**，`src/` 零改动就接通了真板子。
第 3 级最早用 WSL + socat 的虚拟串口对实现，现在由进程内的字节管道承担（`--mode virtual`），不再需要任何系统工具。

另有 Android 单元测试 41 项（`android/`，Gradle 运行）。

几类值得一提的测试：

- **尽量不用 mock。** 网关测试跑的是真实 FastAPI 应用，对接按启动脚本同样方式装配出的真实运行时；
  界面测试用真实的后端栈。只有物理资源（串口、云存储、模型服务）用替身
- **规则读源码核对。** 依赖规则测试用 `ast` 读每一条 import；命令码契约测试直接读固件的 C 头文件，
  比对两侧数值
- **启动器真的能启动。** 曾经所有测试全绿，但四个启动器全部起不来：守卫测试只检查了源码文本，
  而 pytest 以包路径导入、恰好绕开了那个导入错误。现在用子进程真实运行每一个入口
- **测试不可能碰到真实凭证。** 有一次没打桩的用例读到了默认凭证、真的连上了公网对象存储。
  现在 `tests/conftest.py` 自动兜底，任何测试都拿不到真实凭证

## 真实硬件上的一小时

STM32F407 + AHT20 + HH_07.06 噪声传感器，连续运行一小时，上位机经串口接收：

| 项 | 值 |
| --- | --- |
| 接收帧数 | 3489 |
| 采集周期 | 1163，三个通道各收到 1163 帧 |
| 丢帧 | 0 |
| 帧同步错误 | 0 |
| Modbus 应答成功率（噪声传感器） | 100%（1163 / 1163） |
| 采集周期实测 | 3.094 s，σ = 0.023 s，最小 3.073 s，最大 3.139 s（设计值 3.0 s） |

原始数据：[`experiment-data/长时间稳定性_20260819_001038.csv`](../experiment-data/)。
上表可以用仓库里的工具从原始数据复算：

```bash
python scripts/collect_experiment_data.py --from-csv "experiment-data/长时间稳定性_20260819_001038.csv" --label 复算
```

口径说明：

- **丢帧按间隔跳变判定**（某处间隔约为正常值的整数倍即计丢帧），而不是用"时长 ÷ 设计周期"算理论帧数再相减——
  实测周期比设计值系统性地长 3%，后一种算法会把周期偏差误报成丢帧
- **噪声通道单独算 Modbus 成功率。** 噪声是唯一经请求—应答获取的通道，读取失败时固件不上报。
  所以"某一轮收到了温湿度、唯独没有噪声"计为传感器没应答，"一整轮什么都没收到"才计为链路丢帧
- **第一个噪声读数是 84.7 dB。** 这是传感器上电后的首个伪值，不是环境噪声。
  固件后来改为丢弃首次读数，复测时首点与其后最小值齐平；这份数据采于修改之前，原样保留

浏览器控制台的在线演示回放的就是这一小时：每条读数被按协议重新编码成帧，送进真实的接收器，
报警、统计、通风的消息都由系统自己的代码现场产生（`scripts/build_web_replay.py`）。

## 故障注入

真实开发板一小时里没有出现过一次错误，这恰好说明不了错误处理是否正确。
所以虚拟设备可以故意出错（`scripts/virtual_stm32.py` 的 `FaultPlan`），每一种都有预期的结果：

| 故障 | 真实串口会发生吗 | 主机侧应当 | 固定种子下的一次会话 |
| --- | --- | --- | --- |
| 一帧拆成两次写入 | 会 | 静默拼回，不计错 | 注入 33 次，计错 0 |
| 一轮三帧粘成一次写入 | 会 | 静默切开，不计错 | 注入 18 次，计错 0 |
| 帧前插入杂散字节 | 会（干扰、上电毛刺） | 重同步一次 | 注入 15 次 → 重同步 **15** |
| 翻转 CRC 的一个比特 | 会（干扰） | 判出 CRC 失败，丢弃该帧 | 注入 15 次 → CRC 失败 **15** |

计数必须**恰好相等**，多一次少一次都说明拼帧或计数逻辑有问题。这个断言写在回放生成脚本里，
也写在 `tests/application/test_link_monitor.py` 里。在线演示的"故障注入会话"就是这一次。

**故障注入没有覆盖的：长度字段被破坏。** 这是一处已知缺陷——上位机会按错误的长度停顿最多约 11 分钟，
固件一侧已有对应的检查而上位机没有。触发条件、量化影响、实际发生的可能性与修法见
[`protocol.md`](protocol.md#已知缺陷长度字段被破坏)。

## 真实缺陷

开发中一共记录了八个真实缺陷（不含设计取舍）。归总它们，是因为其中五个有清晰的共同根因：

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | 硬件模式订阅后收不到数据，也没有任何报错 | 接收端把每次读取当作恰好一帧，没有拼帧 |
| 2 | 硬件模式下发命令时程序崩溃 | 发送后立即读应答，只在内存回环里成立 |
| 3 | 硬件模式下阈值报警从不触发 | 硬件装配路径绕开了统一注册入口，漏掉了报警订阅 |
| 4 | 虚拟设备自己写的重同步误删整个缓冲区 | 替身代码重写时没有对照已测过的实现 |
| 5 | 模拟模式启动后界面从来没有数据 | 生成数据的方法只有测试在调用，运行时没人驱动 |
| 6 | 获取局域网地址时崩溃 | 调用系统命令时按系统默认编码（GBK）解码输出 |
| 7 | 硬件模式界面显示"未连接"，数据却在刷新 | 硬件装配路径没有设置连接状态 |
| 8 | 报出 13 次帧同步错误，实际丢帧 0 | 见下 |

**共同根因一：模拟环境的抽象泄漏（#1、#2、#4）。** 内存回环通道在接口上与串口一致，
却在接口没有约定的行为上不一致：保留消息边界、即时回送、没有传输延迟。上层代码在模拟下正确，
只是因为无意中依赖了这些额外性质。结论是：**模拟能验证功能逻辑，不能验证对传输介质的假设。**
凡与介质特性相关的路径——帧边界、时序、延迟、失败方式——都必须在真实字节流上验证。
这也是 virtual 模式存在的理由。

**共同根因二：两条装配路径不一致（#3、#7）。** 硬件模式的装配代码为了拿到数值设备号，
绕过了统一的注册入口，于是入口里顺带做的事（订阅报警、设置连接状态）全部丢失。
第二次踩到之后，补了同时对两条路径断言的测试，把这一类问题固定住。

**#8 值得单独说**，因为它一个功能都没影响。一次实验报出 13 次帧同步错误，而同一次实验丢帧为 0——
二者矛盾：真发生 13 次重同步，意味着链路上出现过 13 次脏字节却没丢一帧，概率上说不通。
追下去问题出在计数条件：缓冲区末尾恰好只剩帧头的前半个字节时，这个字节必须保留、等后半个到达，
这是字节流的正常状态；初版在这个分支上无条件计一次重同步，而等待期间每次轮询都会再进来，
于是一次正常的帧边界切分被累加成多次"错误"。不修的话，实验结论里就会出现根本没发生过的通信错误。

这些缺陷的发现方式也值得注意：#1、#2 在第 3 级验证时暴露，#5 在接网关时顺带发现，
#7 是从一张截图上看出来的（"未连接"和实时数据出现在同一张图里），#8 是数字互相矛盾。
**没有一个是通读代码发现的**——都需要让系统真正跑起来，并换一个角度去看它。

## 问答评测

问答分两部分评：意图识别认不认得出，以及模型改写有没有越界。

### 意图识别：拟合题库与留出题库分开报

| 题库 | 规模 | 结果 | 能说明什么 |
| --- | --- | --- | --- |
| 拟合题库 | 87 句 | 84 / 87 = 96.6% | **只说明规则没退化**。词表是照着这批题补的 |
| 留出题库 | 148 句（范围内 134、范围外 14） | 见下表 | 泛化能力的量级参考 |

留出题库用模板按固定种子展开生成，剔除了拟合题库里的原句，**规定不许照着它补词表**——
一旦照着补，它就变成第二个拟合题库。

| | 规则 | 模型直接分类 |
| --- | --- | --- |
| 范围内正确 | 111 / 134 = 82.8% | 122 / 134 = 91.0% |
| 范围内答错 | 18 | — |
| 答错且被**执行成错误指令** | **0** | **0** |
| 规则答错的题里模型分对 | — | 24 题中 22 题 |

线上管线是"规则优先、落空才问模型"，所以规则自信地答错时模型不会被调用，组合结果约 82%。
规则答错的题都没有副作用：回答里的数字仍然是真实读数，答案写明了答的是哪一类问题。
唯一一次有副作用的错判（"风扇让系统自己决定开关"被判成关风扇）已修复并加了回归测试。

局限：留出题是本项目自己用模板写的，不等于真人的问法；模型部分每种方式只跑了一次。

### 模型改写有没有越界

模型只负责把模板答案换一种说法。每次改写都要过出口检查，下列任何一条不满足就丢弃、回退模板：

| 检查 | 拦下什么 |
| --- | --- |
| 接地 | 改写里出现事实对象里没有的数字 |
| 越限断言 | 事实没有越限，改写却说"超标" |
| 凭空判断 | 模板没有表态，改写表了态 |
| 建议措辞 | 添加了"建议开窗"之类的建议 |
| 长度 | 比原句长出太多 |

在开发用的模型与参数下（`qwen3.5:4b`，温度 0.3），一组 42 次改写全部通过、零拦截。
把温度调到 0.8 故意让模型更"放飞"，录了 24 个问题、28 次改写，出口检查拦下 4 次，
每一次被拦的原文、判定和回退后的答案都录了下来——在线演示的"环境问答"页可以逐条展开看。

这组录制是展示用的，不是统计样本。**出口检查的价值不在于拦下的比例，而在于它与模型无关：**
换模型、换参数，数字从哪里来这件事不变。
