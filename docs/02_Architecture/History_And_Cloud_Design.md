## 1. 动机

系统当前**没有任何持久化**：`InMemoryDataService` 只做进程内的同步分发，
`SensorDataProcessor` 的统计存在内存里，界面的"历史记录"是 `DataPanelWidget` 内部一张
上限 500 行的表格。进程一退，数据全部消失。

这带来三件具体的事：

1. 论文第 6 章 6.2 节把"历史数据能力缺失，系统重启即丢失既有读数"列为不足；
2. 答辩问答 F4"手机上能看历史数据吗"的回答是"服务层和接口层本身就没有这个能力"——
   2026-09-17 起手机端要能看历史，这条回答连同底下的能力一起要改（第 9 节）；
3. 想把数据上云，连"上传什么"都没有——没有历史库，上传器只能自己再攒一份数据，
   那等于把持久化做两遍。

因此顺序是确定的：**先做本地历史记录，再做上云**。上云的断网补传也直接用历史库当待发队列。

## 2. 不做什么

写在前面，避免实现时范围膨胀：

- **不做远程控制**，云端不接收任何指令；
- **不做手机直连云端**：手机看历史走局域网网关、查的是 PC 本地历史库（2026-09-17 改定，见第 0 节），
  手机端不持有任何云端凭证；
- **不让问答去查历史**（第 6 节说明为什么单独留出来）；
- **不引入时序数据库、不引入消息队列**，数据量用不上（见 2.1）；
- **不改协议、不改固件**：历史与上云全部发生在上位机侧。

### 2.1 数据量的量级

三通道、约 3.09 s 一轮，即约 1 条/秒：

| 口径 | 条数 | SQLite 体量（估） |
| --- | ---: | ---: |
| 一天 | 约 8.4 万 | 约 4 MB |
| 一个月 | 约 250 万 | 约 120 MB |
| 一年 | 约 3000 万 | 约 1.5 GB |

毕设的实际运行是"演示与实验时才开机"，真实体量远小于上表。结论：**标准库 `sqlite3` 足够**
（本机 3.50.4），不需要新依赖，也不需要外部数据库服务。年级别的体量若真出现，
用第 4.4 节的降采样与保留期处理。

## 3. 落点与依赖方向

### 3.1 数据流

```
device → protocol → communication → application(runtime)
                                        │
                                   DataService.publish()
                                        ├─→ SensorDataProcessor（统计与报警，内存，现状不变）
                                        ├─→ VentilationController（通风判定，现状不变）
                                        └─→ HistoryRecorder（新增：攒批 → HistoryStore.append）
                                                                    │
                                              api.query_history() ──┤
                                                                    ├─→ ui 历史表
                                                                    ├─→ gateway 历史端点
                                                                    └─→ 归档导出器 → 文件 → 云盘
```

要点：历史记录器是 `DataService` 的**又一个订阅者**，与统计、通风两个处理器地位相同，
由 `ApplicationRuntime.watch_device_channels()` 在注册设备时一并订阅。
协议层、通信层、设备层与固件**零改动**。

三个目录都在仓库根下、都不入库、都可以随时删——删掉只是丢历史，不影响系统运行。
选 `data/` 而不是散在根目录，是因为将来若加保留期清理或备份，目标是一个目录而不是一串文件名。

### 4.1 存什么

沿用 `DataPoint` 的五个字段，不引入新语义：

```sql
CREATE TABLE readings (
    id        INTEGER PRIMARY KEY,
    device_id TEXT    NOT NULL,
    channel   TEXT    NOT NULL,
    value     REAL    NOT NULL,
    ts_utc    TEXT    NOT NULL,   -- ISO-8601，UTC，与 core.timestamps.now_utc 一致
    valid     INTEGER NOT NULL
);
CREATE INDEX idx_readings_lookup ON readings (channel, ts_utc);
```

两点说明：

- **时间戳存 UTC**，展示时再转本地。`DataPoint.timestamp` 本来就是 `now_utc()`，
  存原样可避免夏令时与时区改动带来的歧义；导出文件另附本地时间列，方便人直接看。
- **`valid` 照存不丢**。固件在 Modbus 读取失败时根本不上报噪声通道，
  而上位机侧的无效读数（若有）是判断链路质量的材料，丢掉就再也补不回来。

### 4.2 写入时机：攒批，且不在数据回调里落盘

`DataService.publish()` 是**同步**的，回调直接跑在轮询线程上；而 `poll_once()` 的下一步就是
取模型结果。若每条读数都同步写盘，模型答案的显示会被磁盘 IO 拖慢。

做法：记录器在内存里攒批，满 **50 条**或距上次落盘超过 **5 秒**才写一次，
进程退出时 flush。SQLite 开 WAL，单写入者就是轮询线程。

> 这条不是凭空定的：09-07 有过"在数据发布回调里下发命令导致串口重入、测试进程崩溃"的教训，
> 结论是**回调里只做内存操作，耗时的事交给轮询循环**。本设计沿用该结论。

### 4.3 读取：谁来查，怎么查

接口层新增一个方法（已授权）：

```python
def query_history(
    self,
    device_id: DeviceId,
    channel_id: ChannelId,
    start: datetime | None = None,
    end: datetime | None = None,
    limit: int = 500,
) -> list[HistoryPoint]:
    """按时间范围查历史读数，新的在前。"""
```

- **默认 limit 500**，与界面现有的历史上限一致，避免一次查询把几十万行拉进内存；
- 网关的历史端点直接转调它，请求参数同名；
- 界面把现有的内存表换成"启动时查一次 + 新数据到达时追加"，
  `clear_history()` 的语义相应改为**只清显示、不删库**（删库要单独的入口，避免误触）。

并发：网关在另一个线程里查，SQLite 连接**按线程创建**，只读连接开 `immutable=false, check_same_thread=True` 的默认严格模式，不共享连接对象。

### 4.4 保留期与降采样（本期只留接口，不实现）

表结构与查询已经能支持，但本期**不实现**：一是毕设的实际运行时长用不上，
二是"多久以前的数据可以丢"是一个需要你拍板的策略，不该由实现顺手定。
留在文档里的默认建议：原始数据保留 30 天，更早的按分钟聚合（最大/最小/平均/样本数）。

## 5. 数据上云（阿里云盘）

### 5.1 形态

**定时把历史库里的一段导出成文件，再送上云盘。** 云端只是文件的存放处，
不做查询、不做计算、不接指令——这与你定的"云端只存数据"一致。

- **触发方式**：**手动跑脚本**（2026-09-17 用户改定）。系统运行期间只往历史库写，
  **不含任何定时器、后台线程或上传队列**；想上云时双击根目录的 **`cloud_sync_导出并上传.bat`**
  （实际逻辑在 `scripts/cloud_sync.py`），它把"尚未导出的时段"一次补齐并上传。
  这样断网重试、退避、后台失败告警统统不需要——下次运行脚本自然补上，而"下次"由你决定。
- **入口位置**：根目录，与 `run_gui_模拟数据界面.bat`、`start_llm_启动本地模型.bat` 等**七个双击入口放在一起**
  （2026-09-17 用户要求）。`.bat` 照既有模板写：定位项目根、优先用 `.venv\Scripts\python.exe`、
  转发参数、`chcp 65001` 防中文乱码、失败时 `pause` 把原因留在屏幕上。
  届时 `docs/06_UserGuide/User_Manual.md` 的"七个一键启动器"一节要改成八个。
- **粒度**：**每小时一个文件**（2026-09-16 用户确认）。注意这是**文件切分**的粒度，
  不是上传频率：一次手动运行可能产出多个小时片。按小时切而不是整段导出，
  是为了让补传、去重与出错重跑都以小时为单位，不必整库重来。
- **命名**：`env_YYYYMMDD_HH.csv`，本地时间。与 `scripts/collect_thesis_data.py`
  既有的 `{label}_{YYYYmmdd_HHMMSS}.csv` 同一套习惯。
- **格式**：CSV，列为 `ts_local, ts_utc, device_id, channel, value, valid`。选 CSV 而不是二进制，
  理由与协议载荷选 JSON 时相同——**这一步的瓶颈不在体积，而在出了问题时能不能直接打开看**。
- **幂等**：`exports` 表记录每个文件覆盖的时间区间与行数，重复导出同一区间**不产生第二份**；
  上传成功后标记，断网时未标记的文件下次继续传。这张表就是"待发队列"。

> **2026-09-18：归档 CSV 改为宽表。** 原先是长表
> （`ts_local,ts_utc,device_id,channel,value,valid`，一行一个读数），
> 用户实际打开之后反馈"很奇怪"。逐条看确实有四处硌人：表头是英文标识符；
> 两列 ISO-8601 带时区时间戳 **Excel 根本不认**，会当文本左对齐，排不了序也画不了图；
> 同一时刻的三个读数散在三行；`valid` 写作 0/1，看的人不知道那是什么。
>
> 现为 `时间,温度(°C),湿度(%RH),噪声(dB),设备,备注`，一行一个采集时刻，
> 时间用 `YYYY-MM-DD HH:MM:SS`，文件带 BOM（中文 Windows 的 Excel 打开无 BOM 的
> UTF-8 会按 GBK 解，中文表头直接乱码）。
>
> **为什么这里敢按时刻合并，而界面的历史表不敢**（见 `ui/README.md`）：
> 那边只有到达顺序、没有每条读数的时刻，丢一帧就会把第 N 轮的温度与第 N+1 轮的
> 湿度排进同一行，且看不出来。这里每条读数都带微秒级时间戳，实测同一轮内三通道
> 相差约 **2 毫秒**、轮与轮相差约 **3 秒**（差一千五百倍），按 500 毫秒分轮离两边
> 都有两个数量级余量；**丢帧的结果是那一格空着**，不会被下一轮的值顶上。
> 差别不在谨慎程度，在有没有可依据的事实。
>
> 分轮还有第二条规则：**同一通道在本轮出现第二次即开新一轮**。只按间隔切的话，
> 某一轮只有噪声、下一轮紧接着也只有噪声时，两条会被并成一行、丢掉一条读数。
>
> 中文名、单位、小数位取自 `core/channel_display.py`——这次改版让它成为第三个

## 6. 对 LLM 侧的影响

**直接影响：没有。** 问答的取数层 `FactRetriever` 读的是 `SensorDataProcessor` 的内存统计与
`VentilationController`，不经过 `DataService`，更不碰历史库；分类与改写的提示词一个字不改，
因此 KV 前缀缓存、出口的数字校验、87 句基线与 148 句留出题库的结果都不受影响。

**一处必须改的文案**：`phrasing.SCOPE_NOTICE` 现在写的是"系统只保留本次运行以来的数据，给不出更早的时段"。
有了历史记录后这句话变成假话——界面上能翻到昨天，问答却说给不出。改为
"问答只按本次启动以来的数据回答，更早的请看历史记录"一类表述。句中无数字，接地校验不受影响；
`tests/service/assistant/test_phrasing.py` 中 3 处相关断言需同步。

**一个必须说清楚的口径差**：历史库从启动那一刻起是连续的，而问答的统计每次重启清零。
于是"今天最高多少度"可能与历史页对不上（上午到过 29 ℃、中途重启、下午问答只答 27 ℃）。
两个数都是真实读数，差别在覆盖时段。本期的处理是**在措辞里写明覆盖范围**，不做合并。

### 6.1 能不能让模型下指令启动上云脚本（2026-09-17 定：**按钮方案**）

用户问：可不可以对助手说一句"把数据传上去"，由它启动上云脚本。

技术上能做——助手已有指令通道与"模型复核 + 用户点头"的确认机制。**但它不该走这条路**，
理由是白名单的三条准入性质（见 §13 与第 4 章 4.5 节）它一条都不满足：

| 准入性质 | 现有白名单四项 | 启动上云 |
| --- | --- | --- |
| **可逆** | 改通风阈值、切风扇模式，随时改回来 | **不可逆**。文件一旦传到云端就在那了，删除要另外的权限与操作 |
| **只写本机的一个设置** | 只动 `VentilationController` 的内存设置 | **拉起一个子进程**，读凭证、连公网、写别人的存储 |
| **数值来自用户原话** | 阈值数字由代码正则取 | 传哪个时间段、传到哪个 Bucket，都不是一句话能说清的参数 |

播报当初也是因为同一组理由被**认出但拒绝**的（`ANNOUNCE_REQUEST`）——它直驱硬件、不可撤回。
上云比播报更重：播报最坏是响一声，上云最坏是把不该传的数据传了出去，而且发生在用户看不见的子进程里。

**所以不把上云放进指令白名单，改用按钮方案**（2026-09-17 用户确认采用）。
让模型只做它一贯做的事——出一个标签：

> 用户说"把数据传上去" → 规则或模型识别出意图 → 助手回一句话，**界面上出现一个按钮**
> 「导出并上传（12 个待传时段）」 → **人点一下**才真正执行。

模型提议、人发起，与"模型能否决、不能发起"是同一条线。既拿到了自然语言的便利，
又没有把一个不可逆的外部动作放进模型的输出路径。

> ✅ **2026-09-18 已实现。** 本节此前只是设计——`CLOUD_SYNC_HINT` 在代码里并不存在，
> 而 P3（09-17）交付时这一块被漏掉了，文档读起来却像已经做完。现落地情况见下表「落点」一列，
> 与当初的设计一致，另有两处实现时才定的细节记在表后。

**实现要点**（P3 时做，答辩之前）：

| 环节 | 落点 | 约束 |
| --- | --- | --- |
| 意图识别 | 新增一类意图（如 `CLOUD_SYNC_HINT`），**规则优先**，模型落空时才分类 | 它**不进** `control.CONTROL_KINDS`——那是会写设置的白名单，这一类什么都不写 |
| 取数 | 检索层查 `exports` 台账，产出"待传时段数"这一个事实 | 数字仍由代码取，模型看不到；答案里的"12"要登记进 `Facts`，否则接地校验会把改写整句退回（风扇模板踩过这个坑） |
| 措辞 | 模板回一句"有 12 个时段没传，要现在传吗"，可交模型改写 | 与其它答案同一条出口校验 |
| 按钮 | `ui/` 的问答面板，点击后走**与双击 `cloud_sync_导出并上传.bat` 完全相同**的入口 | 按钮只出现在桌面端；**手机端不给**——手机看不到子进程的输出，失败了无从判断。与"手机可看历史"不冲突：看历史是只读查询，上云要拉子进程 |
| 执行 | 组合根拉起 `scripts/cloud_sync.py` | 助手本身不碰子进程，与"只写通风设置、不构造命令、不碰串口"同一条边界 |

**2026-09-18 实现时才定的两处：**

| 细节 | 决定与理由 |
| --- | --- |
| **只有待传数 > 0 才给按钮** | 0（都传完了）与 `None`（台账读不到）都不给。0 给按钮等于说还有事可做；`None` 那句答话让用户自己去双击 `cloud_sync_导出并上传.bat`，按钮会跟紧挨着的这句话打架。**这两条是离屏跑窗口时看出来的**，不是测试发现的——按钮当时出现在"我查不到还有多少没传"底下，读起来像助手不信自己的建议 |
| **视图侧的标签是一次翻译，不是枚举的拼写** | 第一版直接发 `IntentKind.CLOUD_SYNC_HINT.value`（即 `cloud_sync_hint`），而面板的处理器注册在 `cloud_sync` 下，于是标签送到了、匹配不上、答案底下什么都没有，**全程没有任何报错**。现由 `ui/controller.OFFER_TAGS` 显式映射，并有一条测试把两端钉在一起 |

**台账怎么到助手手里**：`service` 不得 import `storage`，所以沿用 `HistoryStore` 的先例——
协议 `ExportStatus` 定义在消费方 `service/assistant/export_status_port.py`，只有一个
`pending_upload_count() -> int`（**刻意不返回台账自己的记录类型**，否则光是类型标注就
把 storage 拖进 service 了）；适配器 `application/export_status.py` 是唯一同时碰两边的地方；
由 `scripts/automation_wiring.attach_export_status()` 注入，三个启动器共用。
**只读**：这个口子给出的是一个整数，attach 它不可能让助手获得上传的能力。

**顺带修掉的一处**：`ApplicationRuntime.attach_language_model()` 此前重建 Assistant 却不记住
llm，于是第二个可注入项一出现，两次 attach 就会互相把对方的注入冲掉——谁后调用谁生效。
已统一为 `_rebuild_assistant()`，调用顺序不再影响结果。

### 6.1.1 查看云端归档也走按钮（2026-09-19）

`cloud_view.py` 只读——列出 Bucket 里已有的文件并打开控制台，不上传、不删除。
即便如此，它**仍然走按钮而不是由助手直接执行**，理由只有一条：
**它要拉起一个子进程，而那是助手不跨的线。** 准入判的从来不是"这个动作多危险"，
而是"该不该由助手来发起它"。

与上传那一档的两处差别：

| | 上传（`CLOUD_SYNC_HINT`） | 查看（`CLOUD_VIEW_HINT`） |
| --- | --- | --- |
| 有无数字 | 有（待传时段数，须登记进 `Facts`） | **无**——云上有什么要连上才知道，那是按钮背后脚本的事 |
| 出按钮的前提 | 待传数 **> 0**；0 与"读不到"都不给 | **无前提**——"云上什么都没有"本身也是值得看到的答案 |

措辞里**明写"只读，不会上传也不会删除"**：用户看到一个与"上传"长得差不多的按钮，
第一反应是"点了会不会又传一遍"，把它不做什么写在按钮旁边比事后解释省事。
这句话与两句拒绝句一样不送模型改写——它不含数字，接地校验对它无从下手，
一次把"不会上传"润色掉的改写，现有的出口校验一条都拦不住。

两个按钮的 runner 共用 `_make_script_runner()`：子进程而非 import、不等它结束、
启动失败只留一行活动日志不抛异常——这三条约定必须对两个按钮同时成立，
复制一份就等于让它们各有一个版本。

### 6.1.2 `--slot`：只处理指定时段（2026-09-19）

原先 `cloud_sync.py` 是全有或全无：把所有没导过的时段导出来、把所有没传的传上去。
演示时想"只传一个时段给评委看"做不到。现新增 `--slot 20260918_17`，可重复给多个。

两处实现判断：

- **导出与上传两侧都过滤。** 用户说的是"只处理这个时段"，不是"只导出这个、
  顺便把别的都传了"——只过滤导出侧会让这个开关名不副实，而代价是演示时
  按一下把积压的全发出去。
- **时段名拼错直接报错退出，而不是静默跳过。** 拼错的表现会是"什么都没发生"，
  与"这些时段都传过了"看起来一模一样；演示时按下去没反应，没人分得清是哪一种。

`--dry-run` 同时增列**待传队列**：演示前要确认的是"按下去会发生什么"，
而待传与待导出是两件事——上一次断网留下的积压不会出现在"待导出"那张表里。

### 6.2 能不能让模型触发**删除**脚本（2026-09-18 定：**不能，认出但拒绝**）

用户问：上云走按钮方案，删除数据是不是也这么办。**不这么办**，三条理由：

| 理由 | 说明 |
| --- | --- |
| **按钮这一档对删除已经被判定太弱** | 2026-09-17 把桌面端「清空历史记录」按钮的语义**收窄**成只清屏幕显示，理由写在 `DataPanelWidget.clear_history` 的 docstring 里：删数据是不可逆的，不该藏在一个看起来只是"清屏"的按钮后面。再让模型去点亮这个按钮，等于把当时否掉的方案装回来，前面还多接了一个模型 |
| **参数取不自用户原话，且比上云更严重** | 铁律是指令的数值由代码从原句正则取。"把旧数据清一清"根本没有范围，猜一个正是删错东西的方式。上云说不清参数最坏是传多了，删除说不清参数是删多了 |
| **没有撤销** | 白名单四项都能原样设回去；上云最坏是文件早传了一会儿，**删除没有对应的回退** |

**还有一层**："删除数据"今天是三件事——本机历史库、`exports/` 归档、OSS 上已传的对象——
后果各不相同，而且**是耦合的**：台账用 `is_exported(slot)` 挡重复导出，手删了 `exports/`
里的 CSV 而台账仍记着"已导出"，那个时段就再也不会被重新导出，界面上什么都看不出来。
删除功能要先把这三者的关系定清楚，那是另一份设计文档的量。

**所以助手对删除做「认出但拒绝」**，与 `ANNOUNCE_REQUEST` 同一套（`IntentKind.DELETE_REQUEST`）。
这不只是防御姿态，它挡住一个**已经存在的坑**：数据在日常句子里紧挨着通道词，
"把噪声数据清一清"没有专门分支时会被噪声分支抢走，于是一条要求删除的话拿回一个真实声压级——
与 09-09"试一下播报能不能响"被答成噪声读数是同一种错。

**真要删除**，它应该是一个独立的、人工双击运行的脚本（形如 `cloud_sync_导出并上传.bat`），
默认 `--dry-run`、必须显式给时间范围、执行前打印"将删除 N 条 / M 个文件"。助手全程不参与。
**本期不做**，未获授权。

**答辩可用**：这套设计正好是"为什么不让 AI 直接操作设备"的现成回答——
与 `xiaozhi-esp32` 经 MCP 让模型直接调设备工具的取向相反，理由在上面那张准入性质对照表里。

**让问答查历史属于第二期，本期不做**，理由：它要在分类提示词里新增标签，
从而作废现有的模型基线（87 句与 148 句都要重排），还要把时间范围解析写成代码
（"昨天""前两个小时"必须由代码解析，不能让模型给，与"阈值数值只取用户原话"同理），
并把日期时刻登记进 `Facts`，否则改写会被接地校验整句拒掉——09-08 风扇模板就踩过这个坑。
维护期内不值得为它重排基线，等本地模型训练告一段落再议。
