## 1. 定位

给平台加一个能用自然语言问答的入口，回答与地铁站环境监测相关的问题：

- **本系统的实测数据**——"现在温度多少"、"过去十分钟湿度平均多少"、"噪声超标了吗"、"风扇为什么在转"
- **系统状态**——"有几个设备在线"、"上位机连上了吗"
- **（可选）领域常识**——"地铁站噪声标准是多少分贝"

### 1.1 唯一的硬约束：模型不接触数值

**所有出现在回答里的数字，必须由代码从 `DataService` 取得；语言模型只负责"听懂问题"和"把结果说成人话"，永远看不到读数本身。**

这不是保守，是这个功能能不能用的前提。模型把 76.3 说成 78、把"未超标"说成"已超标"，在答辩现场无法解释也无法补救；而这类错误恰恰是语言模型最容易犯的。把数值从模型的视野里彻底拿掉，这类错误就不是"概率很低"，而是**结构上不可能发生**。

这与本项目已有的两条设计线索是同一个论证：

| 已有决策 | 共同的原则 |
| --- | --- |
| 报警阈值只在 `service/sensor_data_processor.py` 一份，不复制进固件，由 PC 下发 `ALERT_STATE` 位图 | 唯一事实来源，不让不可靠/不同步的副本参与判定 |
| 通风的**决策**在 `service/ventilation_controller.py`、**执行**在 `application/fan_dispatcher.py` | 把承担正确性责任的部分与不承担的部分分开 |
| **本设计**：模型做意图识别与措辞，数值由代码取 | 同上——把不可靠的部件放在不承担正确性责任的位置 |

## 2. 三层管线

```
用户问句
    │
    ├─① 意图识别 ──────────  规则优先，模型兜底
    │     "过去十分钟湿度平均多少"
    │       → Intent(kind=AVERAGE, channel=humidity, window=600s)
    │
    ├─② 取数 ──────────────  纯代码，无模型参与
    │       → Facts(value=76.3, samples=200, unit="%RH", threshold_state=NORMAL)
    │
    └─③ 措辞 ──────────────  模板优先，模型润色
            → "过去十分钟湿度平均 76.3 %RH，处于正常范围。"
```

| 层 | 是否需要模型 | 失败时 |
| --- | --- | --- |
| ① 意图识别 | 否（规则可覆盖全部预期问法）；模型用于提高问法的容错 | 回落到规则；规则也不匹配则回"我不确定你想问什么"，并列出会答的问题 |
| ② 取数 | **绝不** | 数据缺失时如实说"该通道当前没有有效读数" |
| ③ 措辞 | 否（模板足够）；模型用于让回答更自然 | 回落到模板 |

> **2026-09-08 补充**：输入框里除了提问还可以下指令（"把风扇打开"、"通风阈值调到 28 度"）。
> 指令与提问共用第 ① 层，之后不走第 ②③ 层，改走 `control.ControlExecutor`——
> 白名单四项、只写通风策略、数值从用户原话里取。详见 §13。
>
> **2026-09-14 补充：指令在第 ① 层多一次复核。** 规则判出指令后不立即执行，先把同一句话
> 交给模型独立判一次（`JOB_REVIEW`，与分类任务同一套提示词），两边读出同一类指令才执行；
> 不一致、或只有模型判成指令时，改为反问一句、等用户点头。模型在这里仍然只给一个标签，
> 执行什么由规则的判定决定，数值仍从用户原话里取——**它可以否决一个动作，不能发起一个动作**。
> 模型不可用或超时（回复为空）时这一步整个不出现，指令照常即时执行，可靠性下限不变。
> 依据、裁决表与阶段划分见 [`Intent_Review_Proposal.md`](Intent_Review_Proposal.md)。
> 问题类**暂不复核**（该方案的阶段二），理由是问题答错没有副作用，而每句都问模型会带来
> 留出题库上约 8/148 的误报反问。

**模型在 ① 和 ③ 都是可选的**。这决定了整个功能的可靠性等级：模型没装、没启动、超时、被卸载，问答**照常工作**，只是措辞死板一些。这与"AHT20/ES8388/LCD 任一外设缺失都不让整机停摆"是同一条处理原则。

## 3. 消费端：问答界面与 LCD 时刻表共用同一套后端

这一节记录一个**在动手之前就要考虑进去**的设计点，写进去几乎不增加工作量，但能省掉以后返工。

### 3.1 时刻表查询本质上就是一个意图

"下一趟车什么时候到" 与 "现在温度多少" 在管线里是同一种形状：

```
"下一趟车几点到"  →  Intent(kind=NEXT_TRAIN, direction=UP)
                  →  Facts(line=2, direction=UP, hh=8, mm=42, eta_minutes=6)
                  →  ③ 措辞 / 或者直接推给 LCD
```

差别只在**第 ② 层从哪里取数**：环境问题取自 `DataService`，列车问题取自时刻表数据源。**①③ 两层完全不用改。**

### 3.2 因此 `Facts` 必须是结构化的，不能是一句拼好的话

如果第 ② 层直接产出 `"下一班 08:42 开往 XX，还有 6 分钟"` 这样一个字符串，它就只能喂给屏幕或界面**其中之一**：

- 界面要的是可以再润色的中文
- **LCD 要的是编号，不是文案**——见 3.3

所以 `Facts` 是一个结构化对象，`③ 措辞`（面向人）与 `LCD 推送`（面向设备）是它的**两个平级消费端**，形状与 `ui` / `gateway` 平级消费 `api.ApiInterface` 完全一致。**是同一套后端的两个出口，不是两套系统。**

### 3.3 推给 LCD 时传编号，不传文案

若把整句中文推给固件，固件就得从 JSON 里抠 UTF-8 字符串——要处理转义、变长与缓冲区，比现有那个只认十进制整数的 `protocol_payload_get_uint()` 复杂一个量级。

改成推结构：

```json
{"line": 2, "dir": 0, "hh": 8, "mm": 42, "eta": 6}
```

固件用 `line`/`dir` 查本地固定文案表（这些文案写在 `UI_TXT("...")` 里，字库脚本自动收录），数字用 ASCII 画。**沿用现有整数扫描器，一行新解析代码都不用加**，措辞哪边改都不必重新烧录固件。

这与"报警状态传位图而不传『报警』两个字"是同一个决定：**跨程序边界只传结构，不传措辞。**

### 3.4 字库不是障碍——真正的分界线是词汇表封不封闭

之前的判断（"AI 返回的任意中文需完整 GBK 字库，因此 AI 不上 LCD"）**划错了线**，在此更正：

| | 词汇表 | 上屏可行性 |
| --- | --- | --- |
| 时刻表查询 | 封闭——线路名、方向、站名，数得清 | **可行**。一条线 20~30 站，去重后 60~120 字，24×24 点阵约 4~9 KB；当前 ROM 才用 2.4% |
| 开放式问答 | 不封闭 | 不可行（需完整 GBK，要外挂 SPI Flash 并禁 JTAG） |

所以：**时刻表、系统状态这类封闭词汇的结果可以上屏；开放式问答留在 PC 端。**

> 现有字库脚本 `scripts/hz_font_to_c.py` 只扫描 `UI_TXT("...")` 字面量。按 3.3 的"传编号"做法，站名写在固件的固定文案表里，会被自动收录，**脚本不需要改**。只有当决定让 PC 下发任意站名字符串时，才需要给脚本加一个补充词汇入口（如 `--extra`）。

### 3.5 但时刻表本身暂不开发

用户已明确：排班表与列车时间的数据源为虚拟方案，**先讨论不开发**。本节的作用是让 Assistant 的接口形状（结构化 `Facts`、意图可扩展）从第一天起就容得下它，而不是现在就实现它。

## 4. 模块划分与依赖方向

```
src/service/assistant/          问答管线（纯逻辑，无 I/O）
    models.py                   Intent / Facts / Answer 数据模型
    intent.py                   规则意图匹配器
    retrieval.py                Intent → 查询 DataService/统计 → Facts
    phrasing.py                 Facts → 中文回答（模板）
    llm_port.py                 LlmClient 协议 + NullLlmClient
    assistant.py                门面：ask(question) -> Answer

src/llm/                        【新增顶层包】LLM 后端适配器
    ollama.py                   OllamaClient（非阻塞，stdlib）
    exceptions.py               LlmError 及子类

src/application/runtime.py      装配：enable_assistant(...)
src/ui/widgets/assistant_panel.py   聊天面板
```

依赖方向：

- `service/assistant/` 只依赖 `core` 与 `service` 内部（`DataService`、统计），**不依赖 `api`/`application`/`ui`/`llm`**
- `LlmClient` **协议定义在 `service/assistant/llm_port.py`**，即消费方——这与 `CommandTransport` 定义在 `service/control_service_impl.py`、具体 transport 由外部注入的既有约定一致
- `src/llm/` 只依赖 `core`，**不 import `service`**：`OllamaClient` 靠结构化匹配满足协议（鸭子类型），mypy 在 `application` 的装配点上验证
- 只有 `application/` 与 `scripts/` 可以创建 `OllamaClient` —— 与"`SerialChannel` 等具体通信对象只能在 `application`/`scripts` 中被创建"是同一条规矩

### 4.1 为什么新增 `src/llm/` 这个顶层包（动机 / 影响 / 替代方案）

**动机**：需要一个放"连接本地模型服务的具体实现"的地方。

**替代方案取舍**：

| 方案 | 取舍 |
| --- | --- |
| A. 新增 `src/llm/`（**采用**） | 语义干净：它是"外部模型服务接入层"，与 `communication/`（**设备**接入层）平级但不是同一件事。代价是多一个顶层包 |
| B. 放进 `src/communication/` | 不新增包，但该层的定义明确写着"与具体通信介质的字节收发，向上给 `protocol` 提供统一字节流"（见 `src/communication/README.md`）。本地模型服务既不是设备，产出也不是喂给 `protocol` 的字节流。塞进去会把这一层的定义搞浑，而这层的边界清晰正是本项目反复强调的架构成果 |
| C. 放进 `src/application/` | 与现有惯例冲突：`application` 是**装配**具体对象的地方，不是**定义**它们的地方（`SerialChannel` 定义在 `communication/`，只在 `application` 里被创建） |

**影响范围**：新增一个顶层包，不改动任何现有包的职责与依赖方向；`Software_Structure.md` 的"实际落地结构"一节需要在实现时由九个包更新为十个包。

### 4.2 需要扩展受保护接口（**待授权**）

PC 界面要有聊天面板，而 `src/ui/*` 只能 import `src/api`，因此 `ApiInterface` 需要新增一个方法：

```python
def ask(self, question: str) -> Answer: ...
```

这是第三次扩展受保护接口（前两次为通风阈值的四个方法）。**按 `CLAUDE.md` 需要用户明确授权后才能实施**，本文档先记录必要性。

若不希望扩展 `ApiInterface`，替代方案是把聊天入口只做在 Android 端（`gateway` 是 `api` 的另一个平级消费方），但那样 PC 端演示时就没有这个功能，不推荐。

## 5. 非阻塞：为什么不用线程

本项目 PC 侧是**完全同步、单线程**的：`QTimer → poll_once() → runner.run_once() + 各 dispatcher.dispatch_pending()`，没有 QThread 也没有 asyncio。这是刻意的设计，也让整个数据链路可以被测试确定性地驱动。

而 CPU 上跑 4B 模型，一次回答要 5~10 秒。**任何形式的阻塞调用都会把界面冻住 5~10 秒**，这在演示时是不可接受的。

因此 `OllamaClient` 采用与项目其它部分一致的**非阻塞轮询**形态：

```python
client.submit(prompt)      # 立即返回，只发出请求
client.poll() -> str | None  # 每个轮询周期调用一次，返回本次新增的文本片段
client.is_busy() -> bool
```

用 stdlib 的非阻塞 `socket` 增量读取 Ollama 的 NDJSON 流式响应，由现有的 `poll_once()` 驱动，与 `fan_dispatcher.dispatch_pending()` 并列。

这样有三个好处，且**不需要引入任何新的 Python 依赖**：

1. 界面全程不冻结，回答逐字出现（流式），感知延迟大幅降低
2. 不引入线程，就不引入竞态；现有测试的驱动方式原样适用
3. 与固件里 `noise_sensor_poll()` 的非阻塞请求-应答是**同一个模式**——论文里可以作为"同一套并发处理思路在两端的一致应用"来写

> 之所以不用 `httpx`（项目已有，但仅为 dev 依赖）：`httpx` 的流式读取仍然阻塞调用线程，不加线程解决不了冻结问题。既然要自己做非阻塞，stdlib 就够了。

## 6. 降级策略

| 情况 | 行为 |
| --- | --- |
| Ollama 未安装 / 未启动 | 启动时探测一次，失败则装配 `NullLlmClient`，全程走规则 + 模板 |
| 请求超时（默认 20 s） | 放弃本次模型调用，用模板回答，界面提示"（模型未响应，已用标准措辞回答）" |
| 模型返回的意图标签不可用（空 / 含多个标签 / 缺通道 / 自称 unknown） | 丢弃，界面停留在已经显示的帮助文案，**不追加第二条消息**（见 §12） |
| 模型润色后的文本里出现了数字 | **丢弃润色结果，改用模板**——数字只能来自第 ② 层，这是硬校验 |

最后一条是对 §1.1 那个硬约束的**运行时兜底**：即使提示词写得再好，也不依赖模型"守规矩"，而是在出口处检查。

## 7. 性能预算

### 7.0b 采样参数实测（2026-09-09）

出口检查反复退回的那几句补话——「请注意保暖」「环境状态良好」
「目前已确认该数值为历史最高值」——一直被当成"模型不听提示词"。
2026-09-09 测下来不是：**是采样随机性**。模型知道该说什么（另一组 72 次调用中，
含状态断言的 52 次全部与事实相符），只是在高温下时不时飘一句出去。

**temperature（此前未设，用 Ollama 默认 0.8）**

| temperature | 改写被采纳 | 均耗时 |
| --- | --- | --- |
| 默认 0.8 | 27/30 | 5.1 s |
| **0.3** | **30/30** | 4.8 s |
| 0.0 | 30/30 | 3.8 s |

单批 27/30 对 30/30 说明不了什么（Fisher p≈0.24）。但默认温度下当天共采过三批
（20/30、25/30、27/30，合计 **72/90**），低温两批合计 **60/60**，
这个对比 p≈0.0005，站得住。低温还快约 5%——采样少走偏路，生成的 token 也更少。

**定为 0.3 而非 0.0**：两者准确率相同、0.0 更快，但重写机制依赖第二次输出与第一次不同；
温度 0.0 时唯一的变量只剩换过的系统提示词。留一点抖动，等于给重写多一条退路。

这一项**不改变任何保证**：出口五道检查原样保留，只是从"日常在挡"退回"兜底"。

**解释档要不要放宽：测了，不放**

`EXPLAINED_KINDS` 只有 `ALARM_STATE` 与 `FAN_STATE`，读数类问题只做单句改写。
当初收窄的依据是"65 句题库中位应答由 3.7 s 升到 9.7 s"，而那次测量在 temperature 0.8 下做。
温度定到 0.3 后改写档快了约 25%，**据此推测解释档也会便宜不少——推测错了**：

| | 调用 | 采纳 | 中位 | 最长 | 平均字数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 改写档（现状） | 28 | 28 | **3.5 s** | 5.7 s | 17 |
| 解释档 | 28 | 27 | **10.0 s** | 14.3 s | 97 |

与 0.8 下的 3.7 s → 9.7 s 几乎一致。原因是把两件事混了：**温度管采样随机性，
不管输出长度**。改写档快，是因为低温让它不再画蛇添足、少生成了 token；
解释档的长度由提示词定死（"用两到三句"），低温没有东西可裁。97 字 ÷ 10.4 tok/s
≈ 10 秒，这个账与温度无关。

因此当初的取舍在新参数下重新成立：多花 6.5 s 换 5.7 倍字数，对"现在温度多少"
是过度作答；而是否越限、风扇为何在转那两类本就需要交代来龙去脉，留在解释档是对的。
另需留意 **最长 14.3 s**：演示时连问两句解释档问题会明显卡顿。

（28 次中有 1 次被出口检查退回。日志只留了前 60 字，按记录重建后跑五道检查全部通过，
无法确认真实原因；先怀疑是标准号 37488/2019 过不了接地校验，验证后**不是**，
那两个数被容忍。1/28 在噪声范围内，不为它编一个解释。）

**num_predict：测了，不动**

原以为收紧它是"比出口长度上限更早一步"的办法——在生成阶段截住话痨。100 次改写实测
（160 / 80 / 48 / 按模板长度自动）**四档全是 25/25、零截断、耗时无差**：温度定下来之后，
一句改写只有二三十个 token，够不着任何一档天花板。

**而且它有实伤。** `num_predict` 由改写档与解释档共用一个客户端，而解释档要用约 57 个 token：

```
num_predict=160 → 57 tok，收尾正常
num_predict=48  → 48 tok，截断：「…距离报警阈值 35℃ 仍有 11.0℃」
```

正好断在数字后面，读起来像系统坏了，比话多糟得多。**只测改写档会得出"48 完全安全"的
结论并真的去改**——这是同一个盲区第二次出现（第一次是出口长度上限误伤解释档），
两次都靠单独跑一遍解释档才发现。教训记在这里：**这两个档共用客户端与 `choose()`，
任何针对"输出太长"的改动都必须两个档各测一遍。**

### 7.0 实测结果（2026-09-08，`qwen3.5:4b` q4_K_M，目标机实机）

**以下是实测数字，不是估算。** 测试条件：`think=false`、`num_thread=8`、系统提示 115 token。

| 指标 | 冷（首次调用） | 热（系统提示已缓存） |
| --- | --- | --- |
| 模型加载 | 3.92 s（仅进程启动后第一次） | **0.00 s** |
| prefill | 74.4 tok/s | **740.1 tok/s** |
| **首字延迟** | **1.55 s** | **0.16 s** |
| **生成速度** | **10.3 tok/s** | **10.5 tok/s** |

三条结论：

1. **生成 10.3~10.5 tok/s**，落在预估的 8~13 区间内。一句 40 字的回答约 4 秒，**可用**。
2. **KV 前缀缓存的收益是 10 倍**（prefill 74 → 740 tok/s，首字 1.55 s → 0.16 s）。这直接坐实了
   §7 那条"系统提示固定不变、变动内容放最后"的建议——**这不是微调，是数量级的差别**。
3. **`OLLAMA_KEEP_ALIVE=-1` 生效**：第二次调用 `load_duration = 0`，模型常驻内存，没有重载开销。

> **架构更正**：早先根据 Qwen3.5 系列的宣传材料，本文档曾推断 4b 也是 MoE（稀疏专家）架构，
> 并据此预期生成会快于 dense。**该推断错误**：`ollama show` 与 GGUF 元数据中**没有 `expert_count` 字段**，
> 这个 4.7B 是 **dense** 的；MoE 只适用于 Qwen3.5 的大尺寸型号（397B-A17B、122B-A10B、35B-A3B，
> 带 "A" 的才是激活参数）。
> 不过"线性注意力"那半是对的：`block_count = 32` 且 `full_attention_interval = 4`，
> 即 32 层里只有 8 层是完整注意力、其余 24 层为线性注意力——这解释了 prefill 为何相对便宜。

> **实测踩到的坑（与本项目代码无关，但会误导调试）**：用 PowerShell 的 `Invoke-RestMethod` 直接传中文
> 请求体，中文会变成一串 `?`——`ConvertTo-Json` 产生的字符串默认不以 UTF-8 发送。必须显式
> `[System.Text.Encoding]::UTF8.GetBytes($json)` 再传。**Python 侧不存在这个问题**（`json.dumps` +
> `.encode("utf-8")` 是自然写法），但用 PowerShell 手工验证 Ollama 时一定会撞上，第一次的测试结果
> 就是因此完全无效的。

### 7.2 一次真实的幻觉，以及它印证了什么

上述测试里问了一句"噪声超标了会怎么处理？"，模型的回答是：

> "噪声超标时系统会自动触发警报并立即**开启排风换气**，同时通过**手机 APP 通知**你查看详情。"

**两处都是编的**：本系统的风扇由**温湿度**触发（见 `service/ventilation_controller.py`），与噪声无关；
Android 端也**没有**推送通知功能，它只是被动展示数据。模型没有任何本系统的知识，却用完全肯定的语气
描述了系统行为。

这恰好从反面印证了 §1.1：**模型不能回答"本系统会怎么做"这类问题**，正如它不能报数值。

因此对 §9 的 P2 阶段做一处收紧：**开放式问答只允许覆盖领域常识**（地铁环境、噪声标准、法规依据），
凡是涉及"本系统的行为、配置、能力"的问题，必须走模板回答，不得交给模型。这条边界需要在意图识别阶段
就划清——识别不出的问题宁可回"我不确定"，也不能让模型自由发挥。

---

纯 CPU 推理由内存带宽决定。目标机 i5-13500H + 32 GB DDR5-5200（双通道理论 83 GB/s，llama.cpp 实测通常 50~58 GB/s），**无独立显卡、无 NPU**：

| 模型规模 | Q4_K_M 体积 | 生成速度 | 80 字回答耗时 |
| --- | --- | --- | --- |
| **`qwen3.5:4b`（4.7B）** | **3.16 GB** | **10.4 tok/s（实测）** | **约 8 s** |
| `qwen3.5:9b` | 6.6 GB | 5~7 tok/s（估） | 15~20 s |
| `qwen3.5:2b` | 2.7 GB | 更快（未测，备选） | — |

**结论：选 4B 级，已实测确认可用（见 §7.0）。** 若后续觉得 10.4 tok/s 仍嫌慢，备选是 `qwen3.5:2b`；
9b 不建议——在本设计里模型只影响措辞好不好听，不影响答案对不对，为措辞付两倍延迟不划算。 在本设计里模型大小只影响措辞好不好听，不影响答案对不对，为措辞付三倍延迟不划算。

真正的瓶颈是 **prefill（读提示词）**，CPU 上 4B 约 40~80 tok/s，400 token 的提示要 5~10 秒才吐第一个字。三条对策：

1. **提示词必须短**——这正是"模型不接触数值"的第二重好处：不需要把读数塞进上下文
2. **系统提示固定不变、变动内容放最后**——Ollama 会复用相同前缀的 KV 缓存，第一次慢，之后只算新增部分
3. **`OLLAMA_KEEP_ALIVE=-1`**——默认 5 分钟不用就卸载，下次要从磁盘重载数秒；演示现场这一下很致命

另外两项建议实测对比：线程数设 **8**（4 个 P 核 + 超线程），不要给满 12/16，E 核在 llama.cpp 里通常拖后腿；若模型带 thinking 模式**必须关掉**，思考链会再加 10~30 秒。

## 7.1 本机部署实况（2026-09-08 实施）

运行时（Ollama）已安装完成，**模型与代码尚未接入**。这里记录实际的落地位置与理由，避免新会话重复踩坑。

| 项 | 值 | 说明 |
| --- | --- | --- |
| Ollama 版本 | 0.33.3（winget `Ollama.Ollama`） | |
| 程序目录 | `D:\Ollama`（2.8 GB） | **不是** C 盘默认位置，也**不在 `D:\毕业设计` 里** |
| 模型目录 | `D:\Ollama\models` | 由用户级环境变量 `OLLAMA_MODELS` 指定 |
| 常驻设置 | `OLLAMA_KEEP_ALIVE = -1` | 用户级环境变量，防止 5 分钟空闲后卸载模型 |
| 选定模型 | `qwen3.5:4b`（= `4b-q4_K_M`，3.4 GB） | |

**为什么不放 C 盘**：目标机 C 盘仅剩 49.6 GB，D 盘剩 523.7 GB。Ollama 默认把程序装到
`%LOCALAPPDATA%\Programs\Ollama`、模型放 `%USERPROFILE%\.ollama\models`，**两者都在 C**，
而模型是会持续增长的部分（每个 4B 模型 3.4 GB）。已用 `winget install --location "D:\Ollama"` 重装，
并确认 C 盘原目录已清除。

**为什么不放进 `D:\毕业设计`**：Ollama 是开机自启、监听 11434 的**机器级服务**，不是项目产物。
放进工程目录会让毕设打包时凭空多出十几 GB，也会污染 `项目代码结构导览.md` 的顶层目录表与代码行数统计。
`D:\Ollama` 同样一个文件夹删干净，但不碰工程树。

**验证模型路径是否生效（零下载做法）**：设好 `OLLAMA_MODELS` 后重启服务，Ollama 会在该目录下自动建
`blobs/` 与 `manifests/` 两个子目录。检查这两个目录出现在 D、且 `%USERPROFILE%\.ollama\models` 仍为空，
即可确认写入位置正确——**不需要先下一个模型来试**。

> ⚠ **改环境变量后必须重启 Ollama 服务**才生效。而且用 `[Environment]::SetEnvironmentVariable(...,"User")`
> 写入的是注册表，**已经在运行的进程（包括安装器自动拉起的托盘程序）不会重新读取**——必须先
> `Stop-Process -Name ollama*` 再重新启动，否则会看到"变量明明设了却还往 C 盘写"的假象。

### 模型目录漂移与 junction 兜底（2026-09-10 补）

**事故**：某次自动升级后 `start_llm_启动本地模型.bat` 报"模型 qwen3.5:4b 未下载。已装：（无）"，
而 `D:\Ollama\models` 里 3.16 GB 权重与 manifest 一个字节没少。服务日志
（`%LOCALAPPDATA%\Ollama\server.log` 启动那行 `msg="server config"`）显示
`OLLAMA_MODELS:C:\Users\wwwzx\.ollama\models`、`total blobs: 0`。

**原因**：Ollama 0.33 起桌面应用把设置迁进了自己的 `%LOCALAPPDATA%\Ollama\db.sqlite`
（`settings.config_migrated = 1`），其中 `settings.models` 一列**优先于环境变量**
`OLLAMA_MODELS`；迁移时该列被填成了 C 盘默认路径。注册表里的变量仍是 `D:\Ollama\models`，
但已经不再决定行为——上面那条 ⚠ 里"改完重启服务就生效"的结论，从这个版本起只对**没被应用接管**
的部署成立。

**兜底做法**：把 C 盘那个默认路径本身做成指向真实目录的**目录联接**，让配置漂到哪儿都落在同一份数据上：

```
mklink /J "%USERPROFILE%\.ollama\models" "D:\Ollama\models"
```

junction 工作在文件系统层，位于应用配置层之下，因此**升级、重装、强制更新改的都是"用哪个路径"，
而这一层已经被重定向**。不必为此关掉自动更新（关了也挡不住强制更新，还会一并失去安全修复）。
两个前提：卸载 Ollama 前应先删掉 junction（个别卸载程序会递归删除用户目录，可能顺着链接删到 D 盘真实数据，
删链接本身不会动目标）；日后若想把模型改回 C 盘，需先拆链接。

**检查方式随之改掉**：`scripts/start_llm.py` 原先读注册表里的 `OLLAMA_MODELS` 就打 ✓，
这次事故里它一边打 ✓ 一边报模型没装。现改为 `effective_config()` 解析服务日志中**实际生效**的
模型目录与 `total blobs` 数，并在与注册表不一致时明确报出漂移。

### 量化选择：q4_K_M，且这是下限而非折中

`qwen3.5:4b` 这个不带后缀的标签本身就指向 `q4_K_M`（3.4 GB），直接 pull 即可。

- **为什么 Q4 够**：量化损伤主要落在长链条推理、数学与代码上，而模型在本设计里只做"短问句→意图 JSON"
  与"Facts→一句中文"，两者都不是质量敏感任务；答案的正确性本来就不依赖模型质量（§1.1 + §6 的出口校验）。
  在纯 CPU 的带宽瓶颈下，模型小一半就快接近一倍，Q4 在质量与速度两个维度上都占优。
- **为什么不能更低**：Qwen3.5 是 MoE 架构，**MoE 对激进量化比 dense 更敏感**——每个专家参数本就少，
  量化误差不像 dense 那样能被平均掉。Q3/Q2 是假省钱，可能直接把意图识别搞崩。
- **别碰的标签**：`4b-mlx*` 是 Apple Silicon 专用，`4b-nvfp4`/`4b-mxfp8` 需要较新的 N 卡，本机一个都用不上。

> 一个已知的净负担：所有 4b 标签都标注 "Text, Image input"，官方**没有提供纯文本变体**。
> dense 4B 的 q4_K_M 通常约 2.5 GB，这里是 3.4 GB，多出的约 1 GB 大概率是视觉编码器。
> 我们永远不喂图片，这部分只占内存与加载时间，但不参与逐 token 生成，对生成速度影响不大。无法优化，知悉即可。

## 8. 明确不做的事

1. **不让模型算数、比大小、判断超标。** 全部走代码。
2. **不上 RAG / 向量库。** 知识面就那么大（三个通道 + 阈值依据 + 设备状态 + 未来的时刻表），规则和模板完全够。向量库会引入嵌入模型、索引、相似度阈值一堆新的失败点，收益为零。
3. **开放式问答不上 LCD**（词汇表不封闭，见 §3.4）。
4. **不做多轮对话记忆。** 单轮问答已覆盖全部演示场景；多轮会引入指代消解，而指代消解错了就会答非所问。

## 10. 实现记录：落地与设计不一致的三处（2026-09-08）

设计文档写在动手之前，实现过程中有三处必须偏离它。都不是随手改的——每一处都是实测或测试把问题顶出来的。

### 10.1 标准号必须是"事实"，不能写在模板里

**设计原文**：措辞层用模板渲染，模型改写后用"数字必须来自 Facts"校验。

**实际问题**：模板里硬写的 `GB 37488—2019` 带着 `37488` 和 `2019` 两个数字，而 Facts 里没有——
`numbers_are_grounded()` 会判定它们是编造的。后果是**系统自己的输出通不过自己的检查**，
阈值类问题的模型改写会被永久拒绝。

**改法**：给 `Facts` 增加 `citation` 字段，由取数层提供；模板打印它给的内容，没有就省略这一小句。
校验函数把 citation 里的数字也纳入允许集合。

这也更正确：标准号本来就是**数据**而不是措辞，温湿度阈值是工程取值、没有可引的出处，
模板不应该自作主张替某个通道决定"背后有没有权威"。

> 这个问题是被 `test_every_template_is_grounded_in_its_own_facts` 抓到的——那条测试断言
> "模板必须满足它自己强加给模型的规则"。实测中模型确实原样保留了 `GB 37488—2019`，
> 若不修，那条本来完全正确的改写会被丢掉。

### 10.2 模型客户端缓冲整段，不向上逐字流式

**设计原文**（第 5 节）："界面全程不冻结，回答逐字出现（流式），感知延迟大幅降低"。

**实际改为**：`OllamaClient` 内部消费流式分片（以便判定完成与超时），但**响应完整之前不向调用方交付任何文本**。

两个理由：

1. **感知延迟本来就已经解决了**——模板答案在 22 毫秒内就显示出来了，模型版本只是替换它。
   逐字揭示一个"替换品"看起来是答案在闪烁，不是在加载。
2. **截断的句子在这里是危险的**，和普通聊天应用不同："噪声现在 76.3dB，一切正" 会**通过**
   grounding 校验并被当成答案显示。只交付完整响应，从根上消除这个失败模式，
   好过在下游想办法识别它。

同时修正了 `Assistant.poll_rephrasing()` 的一个真实缺陷：它原本把一次 `poll()` 当成完整回答，
面对流式客户端只会拿到**最后一个分片**——那个分片几乎必然通不过 grounding，
于是改写功能会**静默失效**。改成累积。（由 `test_streamed_fragments_are_accumulated_into_one_answer` 覆盖。）

### 10.2b 新问题必须放弃在飞的改写（试用时发现的 bug）

**症状**：用户连着问几个问题时，回答几乎全标「系统」，偶尔还出现**第一题的答案贴在第二题底下**：

```
你              现在温度多少
助手 · 系统        温度现在是 24.3℃。
你              噪声超标了吗
助手 · 模型改写      当前温度是 24.3℃，处于正常范围。   ← 错位
```

**根因**是一条链上的两个后果。`_start_rephrasing()` 原本写的是 `if self._llm.is_busy(): return`：

1. 第二个问题在模型还忙时提出，于是**被整个跳过、永远拿不到改写**——这就是"全是系统"。
2. 更糟的是第一题的 pending 状态还挂着，几秒后改写回来，而视图已经无从判断它属于哪一题，于是**贴到了第二题的气泡上**。

第 2 条正是本设计最想避免的那类错误的变体：**数字全部真实，但回答的是用户没问的问题**。它比数字错更难被察觉，因为每一处都经得起核对。

**改法**：新问题进来时 `cancel()` 掉在飞的请求并清空 pending，然后提交新的。理由有二，第二条才是要害——用户已经翻篇，旧措辞没有价值；而**在源头取消就让陈旧投递不可能发生**，好过要求每个消费端各自去防。这与 `application/alert_dispatcher.py` 的"迟到的播报比不播更糟"是同一个判断。

由 `test_the_abandoned_rephrasing_is_never_delivered` 直接覆盖。原有的 `test_a_second_question_while_busy_does_not_queue` 断言的是旧的错误行为，已改写。

### 10.3 没有为"取回改写结果"再扩 `ApiInterface`

**设计原文**（第 4.2 节）只提到需要 `ask()`。实现时发现还需要一条把**迟到的**改写结果送回界面的路径。

**没有**再加一个 `poll_assistant()` 到受保护接口上，而是：

- `ApplicationRuntime.poll_assistant()` —— 应用层方法，不进 `api`
- `MainController.deliver_assistant_answer(text, source)` —— 只收两个**普通字符串**，由组合根推入
- `scripts/automation_wiring.py` 的 `make_poll_once()` 在轮询循环里把两者接起来

理由：轮询是**组合根**才需要知道的事，界面只需要"有新答案时告诉我"。
为一个只有启动器关心的机制去加宽受保护接口，代价大于收益。
`ui` 依然只 import `api`，`MainController` 依然拿不到任何 service 类型。

## 12. 最终形态一览（2026-09-09）

设计推进到今天的实际样子，四档交互性做完前三档：

| 能力 | 谁负责 | 关键约束 |
| --- | --- | --- |
| 意图识别 | 规则优先，落空时模型分类 | 规则命中 86.2%，零延迟且每次一致；模型只回一个标签，四道校验 |
| 取数 | 检索层 | **唯一产生数字的地方**。阈值引用 `sensor_data_processor` 的公开常量 |
| 措辞 | 模板；模型可改写或展开 | 出口双检：数字白名单（完备）+ 报警断言黑名单（不完备，是缓解） |
| 多轮指代 | **规则层**存一个词 + 时间戳 | 3 分钟；只补给已匹配到其它关键词的句子 |
| 反问澄清 | 规则层 | 60 秒；反问与模型分类**同时进行**，不是二选一 |
| 下发控制 | `ControlExecutor` | 白名单四项可逆设置；**数值由代码从用户原话正则取** |
| 手动播报 | `IntentKind.ANNOUNCE_REQUEST` | **认出但拒绝**：播报要构造 `ALERT_*` 帧直驱硬件且不可撤回，两条都与白名单的准入性质相抵 |
| 触发上云 | `IntentKind.CLOUD_SYNC_HINT`，**2026-09-18 已实现**，见 [`History_And_Cloud_Design.md`](History_And_Cloud_Design.md) §6.1 | **不进白名单**：不可逆、要拉子进程、参数说不清，三条准入性质全不满足（比播报更重——播报最坏响一声，上云最坏把不该传的数据传出去）。用**按钮方案**：模型出标签、界面出按钮、人点击才执行，与"模型能否决、不能发起"同一条线。助手拿到的是一个只读的整数（待传时段数），**没有任何上传的能力**；按钮只给桌面端 |
| 查看云端归档 | `IntentKind.CLOUD_VIEW_HINT`，**2026-09-19 新增** | **按钮方案，与上传同一条线**。`cloud_view` 只读（列清单、开控制台，不传不删），但仍不直接执行——准入判的是"该不该由助手发起一个子进程"，不是"这个动作多危险"。与上传的两处不同：不带数字、也没有出按钮的前提（"云上什么都没有"本身也值得看到）。措辞里明写"只读"，因为它与上传的按钮长得像 |
| 删除数据 | `IntentKind.DELETE_REQUEST` | **认出但拒绝**（2026-09-18），与播报同一档，**不给按钮**。三条准入性质同样全不满足，而且比上云更重：上云早传了一会儿没有损失，删除没有回退。另一层理由是项目自己已经判过——09-17 把「清空历史记录」按钮收窄成只清显示，正是因为"删数据不该藏在一个看起来只是清屏的按钮后面"。具体隐患：数据紧挨通道词，"把噪声数据清一清"没有专门分支时会被答成一个真实声压级 |
| 上板显示 | `answer_dispatcher` | 下发"答案种类 + 数值"，**不下发文本** |

**唯一没做的是第四档（让模型选调用哪个检索）**，理由见实现记录：它改的是架构，
收益只是"更像 agent"，而本设计已有一条更硬的性质——模型不可能编造数字。

实测（87 句题库，qwen3.5:4b 纯 CPU，2026-09-10 基线）：**84/87 = 96.6%**，指令类与范围外各 100%，
模型请求 50 次、超时 0、失败 0。**这个 100% 是同一批题上的拟合**（词表照着前一轮错答补），
不代表泛化能力——详见论文第 6 章表 6-10。

### 12.1 泛化能力与已知局限（2026-09-14 留出题库实测）

用 148 句模板生成、未参与调词表的新题复测（细节与复现方式见
[`../05_Test/baseline/README.md`](../05_Test/baseline/README.md)"留出题库"一节）：

| | 拟合题库（87 句） | 留出题库（148 句） |
| --- | --- | --- |
| 规则，范围内正确 | 96.6%（总体） | **82.8%**（修复后） |
| 规则自信地答错（模型不会被调用） | 0 | 18/134 |
| 模型直接分类，范围内正确 | 未测到（87 题全被规则命中） | **91.0%** |
| 错误执行成指令 | 0 | **0**（修复前 1） |

这组数字改变的是**对第 ① 层的描述**，不改变结构：

- **理解层会错，而且主要错在规则上**，不在模型上。规则的问题不是认不出，而是**自信地认错**：
  词表抢先（带报警词就判成超标）、退回当前值、范围外的句子撞上通道字。
- **错了之后的后果仍被结构兜住**：取数层不经过模型，答错的是"答的是哪个问题"，
  答案里的数字仍然是真实读数，而且答案会写明答的是哪个通道、哪一类。指令只有白名单四项，都能撤回，
  执行后有回显。唯一一次错误执行（"风扇让系统自己决定开关"→ 手动常关）已修复。
- **"指令类 100%"不能再单独引用**，要与留出题库的结果并列。

**已知局限（登记不修）**：阈值问法被判成是否超标、统计与报警问法退回当前值、
范围外的句子因含"湿/温/声"被当成问读数、"明天温度多少"答成当前温度（过去时间有范围提示，
将来时间没有）。它们都不产生动作。

**模型分类会编通道**（2026-09-14 用户实测）："我可以问你什么问题"规则没认出，交给模型后，
接模型复现 5 轮里有 1 轮回了 `current_value temperature`，答成了当前温度。分类提示词的第一个例子
正是"现在多热 -> current_value temperature"，生产调用又不固定随机种子，模型偶尔会照着例子答。
"当前读数必须带通道"的检查挡不住它，因为通道是模型自己给的。这一句已由规则补词修掉；
**这一类（规则认不出、模型单方面给出判断）没有结构性的防线**，是
[`Intent_Review_Proposal.md`](Intent_Review_Proposal.md) 第 4.1 节"认不出 / 判出 Y"那一行要处理的情形。
同日另一处规则 bug 与此无关但同批发现："今天"对当前读数误加了"只保留本次运行数据"的提示，已修。

**征询语气会被执行成指令**（2026-09-14 实测 → **同日修复**）："风扇是不是该开了""要不要把风扇打开你说呢"
"温度超过30度就开风扇对吧""假设温度到了35度风扇会不会开""是不是该把通风阈值调到20度"，
7 句引导性指令里 5 句被直接执行。`_FAN_STATE_WORDS` 的问句守卫只认状态词（开着、在转），
认不出征询与假设——两类句子在关键词层面同形，差别只在语气。

修法是在 `intent.py` 增设 `_CONSULTATIVE_WORDS`（是不是该、该不该、要不要、需不需要、会不会、
对吧、是吧、你说呢、假设、假如、如果、要是……），在 `_fan_intent()` 里**先于每一条指令分支**判定：
命中则问到阈值的答 `THRESHOLD_INFO`，其余答 `FAN_STATE`——后者取到的事实本就包含通风阈值与当前读数
（`ThresholdRetriever._fan_facts`），正是"要不要开"这个问题需要的两样东西。两处取舍：

- **"能不能"刻意不收**。它读起来像征询，实际是请求的常见说法——`_FAN_ON_WORDS` 的注释里记着
  真实用户说过"能开风扇不"。同理不收单字"该""要"，"该关了""要开风扇"就是命令。
- **误判方向偏向"当作提问"**。把命令读成提问，用户再说一句就是了；把征询读成命令，风扇已经转了。

修后 32 句鲁棒性题在规则层错误执行 **5 → 0**，三条真实指令（"风扇别开了吧""帮我把风扇打开吧"
"帮我订张票，然后把通风温度阈值调到28度"）仍照常执行；148 句留出题库结果**逐项不变**
（范围内 82.8%、错误执行 0）。87 句题库整库**不含任何征询词**，守卫不可能在它上面触发，基线不受影响。
回归测试三项见 `tests/service/assistant/test_intent.py`。

**模型复核（`Intent_Review_Proposal.md` 阶段一）已于同日实施**：它处理的是另一类——规则与模型
判断不一致时改为反问。第 9 节实测过它拦不住"规则与模型一起判错"的情形，而那正是守卫补上的缺口；
反过来，守卫也拦不住语气正常、只是词表抢先的错判，那正是复核补上的。两者互补，缺一类就漏一类。

落点：`assistant.Assistant._start_review()` / `_finish_review()` / `_settle_confirmation()`，
新增 `JOB_REVIEW`。三条裁决分支与它们各自的依据写在 `_finish_review` 的 docstring 里。
两处实现上的判断值得记下来：

- **补通道的回答不再复核**（`_settled_question` 非空时跳过）。一句"温度"补的是上一条指令缺的
  那一半，那一条已经裁决过；单独拿这个词去问模型，回来的必然是"在问当前温度"，
  于是每一次补全都会被读成分歧，用户永远说不完一句话。
- **空回复按"模型不可用"处理，照原样执行**。超时与连接断在这里都表现为回复为空，
  而裁决表里那一行写的是"与改动前完全一样"——一次超时不该把用户的指令吃掉。
  模型真的作答但读不出标签时走的是反问分支，两者靠回复是否为空区分，不靠猜。

实测（`qwen3.5:4b`，模拟器运行时，2026-09-14）：一致执行的指令端到端约 **3.6～4.1 s**，
首次调用因冷启动为 10.1 s；"风扇是不是该开了"由守卫拦在执行之外，走的是提问路径。

**87 句题库当日重排**（`baseline/问答基线_20260914_qwen3.5-4b.txt`）：84/87 逐项与 09-10 相同，
**22 条指令模型全部同意，零误报反问**；模型请求 63 → 88，正好多出 25 次复核
（22 条指令 + 3 条被规则读成开关的裸开关句），一次不多一次不少。
但那三条裸开关句（"打开""关了吧""那你开开呗"）**复核没能拦住**——单独问模型同一句话，
它给的是 `fan_on`/`fan_on`/`fan_off`，与规则完全一致。这就是"规则与模型一起判错"那一类，
复核按设计就覆盖不到，要修只能回到规则层（让裸开关句先被 `BARE_SWITCH` 接住）。
**零误报这个数出自拟合题库**，其中指令都是规则认得出的标准说法，不能据此说真人口语上也零误报。
7 项回归测试覆盖一致执行、分歧反问、否认、未作答即作废、空回复照执行、无模型即时执行、
补通道不复核。

同一批实验也确认了结构约束的效果：错误前提、注入要求 13 句，**回答里的数字与结论一次都没被带偏**，
因为改写档只拿到模板句、解释档只拿到事实清单，用户原话到不了措辞阶段。

**同类开源系统怎么做**：2026-09-14 检索结果记在
[`同类开源实践参考.md`](同类开源实践参考.md)。三条与本设计同构（Snips NLU 的确定性解析器在前、
概率解析器在后；Rasa 的两阈值回落与 Two-Stage Fallback；Home Assistant Assist 的"优先本地处理"
与暴露实体白名单），一条取向相反（`xiaozhi-esp32` 经 MCP 让模型直接控制设备），
一条指向本项目评测的短板（中文智能家居拒识基准 11,913 条，本项目范围外只有 14 句）。

**试过但不采用**：Ollama JSON Schema 约束输出。准确率没有提升（90.3% 对 91.0%），
还把"空调温度调到 26 度"判成了改通风阈值；因为它强迫模型从枚举里挑一个，
而自由文本下模型可以回 `unknown` 或含糊作答，被 `parse_reply` 拒掉。耗时从 4.1 s 降到 1.8 s。

### 12.2 一句话里的几件事：拆句（2026-09-15）

**问题**（用户试用发现）："现在多少度啊 有点热 你可以帮我打开风扇嘛"只执行了开风扇，温度那一问被丢掉；
接模型时更糟，收到的是一句莫名的"你是想让我把风扇切到手动常开吗"。两层原因叠加：

1. 规则一次只返回一个意图，风扇分支排在通道之前，整句判成 `FAN_ON`。
2. 复核把**整句**交给模型，而分类提示词只许回一个标签。模型挑了前半句答 `current_value temperature`，
   与规则不一致，按裁决表走了反问。模型没有判错，是输入里本来就有两件事。

**做法**：`Assistant.ask()` 在确认问句之后、整句识别之前先试拆句（`_split_compound` / `_answer_compound`）。
按句读和空格切分，每段各过一遍规则。**只在确有两件事时接管**，否则返回 None、整句照旧处理：

| 规则 | 理由 |
| --- | --- |
| 提问段须带问句标记（多少、几、吗、呢、？……，`intent._QUESTION_MARKERS`） | "太热了，把风扇打开"里的"太热了"会被规则读成问是否超标，拆开单独答就平白多一句 |
| 同种类同通道的提问合并为一件 | "现在温度多少，还差多少超限"后半句继承温度，合并后只剩一件，整句照旧并带余量 |
| **指令至多一条**，两条则不拆 | 一句话里两次改设备状态，任何一条判错用户都要从一次回显里读出来 |
| 紧挨数字的空格、小数点不算断点 | "通风阈值调到 28 度"拆开后读不到数值，指令会被拒 |
| 段内沿用前一段的通道与问法 | "噪声最高多少，平均呢""温度最高多少，湿度呢"，与跨轮追问同一套规则 |

复合回答的处理：提问部分**只用模板**，不送改写——几段事实拼成的一句话没有单一的 `Facts`
供接地校验对照，放宽校验去迁就它等于拆掉"数字只来自事实"这道闸。指令照常复核，
但**只送指令那一段**。复核结果回来时把已答的提问接在前面（`_pending_prefix`），
因为界面会用迟到答案整条替换占位，不接的话已显示的读数会凭空消失。
返回的 `intent`/`facts` 取指令那一条（无指令时取第一个提问），消费端的 `facts.applied`
判断与上板显示都只认单个意图。

**回归**：不接模型，把 87 句题库、148 句留出题库、32 句鲁棒性题的回答、意图、是否执行、
风扇模式与阈值逐句快照，改动前后对比：**267 句逐项不变**，变化的只有三句专门构造的复合句，
全部是预期中的"多答出一件"。新增测试 12 项（`test_intent.py` 4 项、`test_assistant.py` 8 项）。

**真模型复核**（`qwen3.5:4b`，分类提示词不变，各 3 次）：整句"现在多少度啊 有点热 你可以帮我打开风扇嘛"
3 次都回 `current_value temperature fan_on`，含两个标签被 `parse_reply` 作废、回复非空，于是走反问——
与用户看到的现象一致；只送指令段"你可以帮我打开风扇嘛"，3 次都回 `fan_on`，与规则一致，直接执行。

**87 句基线重跑**（`baseline/问答基线_20260915_qwen3.5-4b.txt`）：84/87，**逐题与 09-14 相同**，
中位耗时 3.6 s；模型请求 90 次（09-14 为 88），差的两次是改写被退回后的重试，超时与失败均为 0。
这批题都是单句，不会走拆句路径，重跑确认的是拆句的判定没有漏进单句。

**两两组合题库**（2026-09-15，脚本与输出归档在 `../05_Test/baseline/`，
复现方式见其 [README](../05_Test/baseline/README.md)"复合句两两组合"一节）：把 87 句基线里 73 条可组合的问句与指令两两拼成"A，B"，
不接模型，全量检查拆句是否同时认对两件事。两条指令、同一问题两遍这两类按设计不拆，未计入。
提问部分只走规则与模板，模型不参与，因此规则层的结果就是这部分的最终结果。

| | 组合数 | 首版 | 补问句标记后 | 两句单独问都对 |
| --- | ---: | ---: | ---: | ---: |
| 问 + 问 | 2390 | 65.9% | **93.5%** | 100% |
| 问 + 指令 | 2244 | 80.4% | **96.1%** | 100% |

首版的失败全部可以归到十个单句，而且问法集中在三类："超了没有""开了没"这类以"没"作问，
"冷不冷""吵不吵"这类正反问，以及"有多响"。它们单独问时规则认得出，放进复合句却被判成
缺问句标记的铺垫，整段丢掉。补上"没""多响"与正反问正则（`intent._A_NOT_A`）后，
剩下的失败只与两句有关，两句都属于**按设计不拆**：

- **"好闷啊"**：没有任何问句标记，与"太热了"同类。复合句里把体感当铺垫是有意的取舍，
  否则"好闷啊，把风扇打开"会平白多答一句湿度。
- **"阀值是多少"**：没点通道。单句时系统会反问哪个通道；拆句不接管需要反问的提问，
  于是这一问在复合句里被跳过。这是**已知局限**：一句话里同时挂一个反问与另一件事，
  界面上无法说清下一个"温度"补的是哪一半。端到端抽样里看得更直接：
  "设备都连上了吗，阀值是多少"只剩一件事可拆，退回整句处理，只回了一句"你问的是温度、湿度还是噪声？"，
  设备那一问丢了。前面若已有点了通道的提问（"现在多少读，阀值是多少"），后半句会沿用那个通道，不受影响。

**端到端抽样**（接 `qwen3.5:4b`，与 `run_all_界面加网关.bat` 相同的组合，随机种子固定，各 25 句）：

| | 结果 |
| --- | --- |
| 问 + 指令 | **25/25 直接执行，反问 0**；中位耗时 3.7 s（单句指令 3.6 s） |
| 问 + 问 | 错误执行 0，反问 0；全部即时返回（不送模型） |

复核只送指令段之后，模型对 25 条指令段全部同意，没有一句出现首版那种莫名的反问。
回答顺序固定为先答提问、再报执行结果，与用户说话的先后无关——"把风扇打开，最干的时候湿度多少"
回的是湿度在前。这是有意的：执行结果要等复核，放在最后才能让先到的部分不被迟到的部分打断。

### 12.3 问答日志：把真人说过的话留下来（2026-09-17）

**动机**：现有两套题库都不是真人语料——87 句是拟合题库（词表照着它的错答补过），
148 句留出题库由模板展开生成。而本功能**真正有价值的缺陷全部来自真人试用**：
09-08 连问两句答案错位、09-09 说"开风扇"规则认不出、09-15 一句话问两件事被丢掉一半，
这三个题库一条也测不出来。以前这些句子问完就没了，系统不记录提问，
于是每次改进都要专门坐下来"想测试用例"，而想出来的仍然是模板。

**做法**：`scripts/question_log.py`，一问一答一行 JSONL，写在 `logs/assistant/`。
每条含提问原话、立即返回的模板答案、几秒后迟到的模型改写、识别出的意图与通道、
是否执行了指令、迟到耗时。分析时最有用的是三类行：`final.source == "fallback"`（没听懂）、
`intent` 与预期不符（听错了）、`applied` 为真却不该执行的（误动作）。

**边界**（与本文档 §1.1 的取向一致）：

| 约束 | 说明 |
| --- | --- |
| `src/` 零改动、未扩接口、无新依赖 | `LoggingApi` 继承 `LocalApi` 只覆盖 `ask()`；做成子类而非包装器，是为了避免"接口新增方法后忘了在包装器里补一遍"的漂移 |
| 三个启动器共用一套接线 | 放在 `automation_wiring.py`，与通风/播报/模型接入同理；顺带补上 `run_api_server` 此前**根本没有设置提问观察者**的漏洞 |
| **不上板载屏、不推手机** | 屏幕只显示系统能负责的读数（见 §3.3），日志是开发设施，没有它的位置 |
| 绝不抛异常 | 磁盘写不动也不能把问答带下水——与"模型缺席时问答照常工作"是同一条原则，失败只计数 |
| 不入库 | `logs/` 已进 `.gitignore`，里面是真人说过的话 |

**一个实现缺陷，由测试逼出来**：初版用**写盘时刻**决定文件名，而一条记录要等模型改写
几秒才落盘。跨零点时，昨晚 23:59 那一问会被写进第二天的文件；配对落盘的更是必然错位。
改为每条记录带上自己的提问时刻、按它归档，并补了一条专测跨零点的用例。
日志是拿来回溯"那天问了什么"的，归错一天就白记了。

**怎么用**：平时正常用系统即可，攒够几十句后从三类行里挑出答错与误报的句子，
补进题库与回归测试。这与"照着留出题库补词表"是两回事——留出题库是**量**泛化的尺子，
不许照它补词；真人日志是**新的语料来源**，本就该照它改进。
