# 多端系统架构设计（PC 上位机 + Android 客户端扩展）

## 文档定位

`System_Architecture.md` 定义了单一 PC 上位机场景下的五层架构（UI / Application / Protocol / Communication / Hardware Device）。本文档在其基础上做**横向扩展**，设计一个可同时支持 **PC 上位机（PyQt6）** 与 **Android 客户端** 接入、且底层嵌入式设备（STM32 等 MCU）可替换的多端系统架构。

本文档不替代 `System_Architecture.md`，而是回答一个新增问题：**当客户端从"一个 PC 程序"扩展为"多种客户端形态"时，架构应该如何演进，才能不破坏原有分层原则？**

> 本文档仅为架构设计，不包含任何代码实现，不绑定具体传感器或设备型号，不修改当前 Skill 配置。

## 设计约束（延续项目既有原则）

- 沿用 `docs/02_Architecture/System_Architecture.md` 中"UI 不得跨层直接操作通信/协议"的分层禁令
- 沿用 `docs/03_Communication/Protocol_Design.md` 中定义的通用帧协议（帧头/设备ID/命令类型/数据长度/Payload/CRC），作为多端共享的协议基础
- 不为 STM32 / MSPM0 / ESP32 中的任何一种设备做架构级硬编码
- 不假设最终只有 PC 端或只有 Android 端，两者需要能够**独立存在，也能够共存**

## 1. 系统总体架构

系统在原有五层架构基础上，纵向新增"客户端形态"维度，横向新增"设备接入方式"维度，形成如下总体结构：

```
                ┌───────────────────────┐   ┌───────────────────────┐
                │   PC 上位机客户端       │   │   Android 客户端       │
                │   (PyQt6 UI Layer)     │   │  (Android UI Layer)   │
                └───────────┬───────────┘   └───────────┬───────────┘
                            │                            │
                            │      Client Application Layer      │
                            │  （设备管理 / 数据处理 / 任务调度，  │
                            │    两端各自实现，接口语义一致）      │
                            └───────────┬────────────────┘
                                        │
                    ┌───────────────────┴───────────────────┐
                    │            Protocol Layer               │
                    │   （通用帧协议编解码，PC/Android 共享同一套  │
                    │     协议规范，具体实现按各自语言分别落地）    │
                    └───────────────────┬───────────────────┘
                                        │
        ┌───────────────────────────────┼───────────────────────────────┐
        │                               │                               │
┌───────┴────────┐            ┌─────────┴─────────┐            ┌────────┴───────┐
│ Communication   │            │  Communication      │            │ Communication   │
│ Layer（PC 侧）  │            │  Layer（Android 侧） │            │ Layer（可选网关） │
│ UART/USB/TCP/BT │            │ BLE/WiFi(TCP)/USB   │            │ TCP/WebSocket   │
└───────┬────────┘            └─────────┬──────────┘            └────────┬───────┘
        │                                │                                │
        └────────────────┬───────────────┴────────────────┬──────────────┘
                          │                                │
                ┌─────────┴─────────┐            ┌─────────┴─────────┐
                │ Hardware Device    │            │ Hardware Device    │
                │ Layer（STM32 等，  │  ……可替换…… │ Layer（同一协议下   │
                │ 可被任意支持该协议  │            │ 的其他 MCU 型号）    │
                │ 的 MCU 替换）       │            │                   │
                └────────────────────┘            └────────────────────┘
```

**关键设计判断：**

1. **UI Layer 按客户端平台分别实现**（PyQt6 / Android 原生或跨平台 UI 框架），彼此独立、互不依赖，但都必须遵守"不得跨层直接访问 Protocol/Communication Layer"的原则。
2. **Application Layer 在语义上统一、在实现上允许分别落地**：PC 与 Android 分别用各自的技术栈（Python / Kotlin 或 Java 等）实现业务逻辑，但对外暴露的能力集合（设备连接、参数配置、数据订阅、指令下发）应保持一致的概念模型，避免"PC 能做的事 Android 端做不到"这类能力割裂。
3. **Protocol Layer 是多端共享的核心契约**：`docs/03_Communication/Protocol_Design.md` 中定义的帧协议是唯一事实来源（Single Source of Truth），PC 与 Android 各自实现该协议的编解码，但字段定义、命令类型表必须共用同一份规范文档，禁止出现"PC 协议"和"Android 协议"两个分叉版本。
4. **Communication Layer 允许按客户端能力差异化实现**：PC 端保留 UART/USB/TCP/蓝牙的直接连接能力；Android 端优先支持 BLE、WiFi(TCP)、USB（需 OTG）等移动端更常见的通信方式；两端也可以通过一个可选的**网关（Gateway）**间接接入设备（见第 3 节）。
5. **Hardware Device Layer 保持可替换**：只要设备实现符合 Protocol Layer 定义的帧协议，具体是 STM32、MSPM0 还是 ESP32 对上层架构透明。

## 2. PC 上位机、Android 客户端、STM32 之间的关系

### 2.1 关系模型

三者是"多客户端 — 单协议契约 — 可替换设备"的关系，而不是"PC 主、Android 从"的主从关系：

- **PC 上位机（PyQt6）**：定位为功能最完整的开发/调试/监控终端，适合长时间运行、多设备并行管理、复杂数据分析与可视化场景。
- **Android 客户端**：定位为轻量化、移动化的监控与控制终端，适合现场快速查看状态、临时下发指令、脱离电脑环境的场景。
- **STM32 等 MCU 设备**：是被管理、被采集数据的对象，不感知也不区分是 PC 还是 Android 在与它通信——设备只认协议帧，不认客户端类型。

三者的关系可以概括为：**客户端多样化，协议唯一化，设备可替换化。**

### 2.2 两种接入模式

为兼顾"PC/Android 各自独立可用"与"未来可能需要多端同时监控同一设备"两种需求，架构上预留两种接入模式，二者不互斥，可根据具体部署场景选择：

**模式一：直连模式（Direct Mode）**

```
PC 客户端  ──(UART/USB/TCP/蓝牙)──>  STM32 设备
Android 客户端 ──(BLE/WiFi/USB)──>  STM32 设备
```

- 每个客户端独立、直接地与设备建立连接
- 实现简单，延迟最低，适合单客户端场景或调试阶段
- 局限：同一设备通常同一时刻只能被一个客户端独占连接（尤其是 UART/BLE 等点对点介质）

**模式二：网关模式（Gateway Mode，可选、后续阶段引入）**

```
PC 客户端      ──┐
                 ├──(TCP/WebSocket)──>  Gateway 服务  ──(UART/USB/TCP/BLE)──>  STM32 设备
Android 客户端  ──┘
```

- 引入一个独立的网关/代理服务，负责与设备的实际物理连接，并将设备数据通过网络协议（如 TCP、WebSocket）分发给多个客户端
- 优点：支持多客户端**同时**监控同一设备，设备连接方式与客户端解耦（客户端只需支持 TCP 即可，不必关心设备实际是 UART 还是 BLE）
- 代价：引入额外的服务进程/角色，增加部署与维护复杂度

> 当前阶段（尚未确定最终毕设方向）建议以**直连模式**作为默认设计基线，网关模式作为架构上"预留但不立即实现"的扩展点，避免过早引入不必要的复杂度（详见第 6 节）。

### 2.3 本项目最终选定的具体模式（2026-08-14 确认）

随着毕设方向收敛为地铁站环境监测场景（见 `docs/01_Project/Project_Overview.md`），PC/Android 的接入模式已从"预留待定"确定为**网关模式的一种特化形式：PC 上位机本身兼任网关**，而不是引入第三个独立的网关服务进程：

```
STM32 设备
    │  UART/USB（直连模式，PC 侧不变）
    ▼
PC 上位机（同时扮演"直连客户端"与"网关"两个角色）
    │  串口接收、协议解析、数据清洗、状态判断、报警、历史记录（均已实现，见 service/application 现有代码）
    │
    ├── PC 端 Presentation Layer（PyQt6，本地直接调用 ApiInterface，进程内，无网络开销，现状不变）
    │
    └── 新增：PC 本地网络接口层（REST + WebSocket，局域网内监听）
            │  Wi-Fi / 手机热点等局域网
            ▼
      Android 客户端（不直连 STM32，不感知 COM 口/波特率/CRC/帧格式等任何底层通信细节）
```

**与第 2.2 节"网关模式"定义的关系**：这不是一种新模式，而是网关模式的一个特例——第 2.2 节描述的通用网关模式假设网关是一个"独立的网关/代理服务"，本项目里这个角色由 PC 上位机进程自己承担（PC 已经持有到 STM32 的物理连接，直接在同一进程内加一层网络接口对外暴露即可，不需要再启动一个额外的独立服务）。这样选择的原因：

1. PC 上位机已经完整实现了"设备管理、数据处理、控制指令"等全部网关职责（`service`/`application`/`api` 三层），额外启动一个独立网关进程只是重复劳动
2. 毕设阶段只有"一台 PC + 一台手机"的部署规模，不需要网关与客户端分离带来的可伸缩性收益
3. 局域网环境（PC 和 Android 连同一个 Wi-Fi/热点），不需要公网/云服务器，进一步降低了引入独立网关进程的必要性

**通信方式确定**（对应第 3 节"通信方式设计"原则 2"优先选择两端能力对等的通信方式"，TCP/IP(WiFi) 已经是该节列出的首选）：

- **REST**（HTTP 请求-响应）：用于设备列表、设备状态、历史数据、控制指令下发等"一次性查询/操作"场景
- **WebSocket**：用于实时数据推送、实时报警推送等"持续性、服务端主动推送"场景
- 二者的选型对应关系与 `docs/02_Architecture/Core_Service_Design.md` 第 8 节"网关模式的网络 API 设计"里预留的候选方向完全一致（"候选形式包括请求-响应式（REST/RPC）用于设备查询与指令下发、长连接推送式（WebSocket）用于数据订阅推送"），本次是把候选选型正式确定下来，不是新增决策方向

**Android 端职责边界确定**：Android 不处理 STM32 串口协议的任何细节（不知道 COM 口、波特率、CRC、帧格式），只通过 REST/WebSocket 消费 PC 已经处理好的结构化数据（`device_id`/`channel`/`value`/`unit`/`status`/`timestamp` 等字段）——这与本文档第 4 节"软件分层设计"里"Presentation Layer 按客户端平台分别实现，但都通过统一的概念接口"的原则完全一致，Android 端相当于通过网络间接调用 `ApiInterface`，而不是重新实现一遍 Protocol/Communication Layer。

**具体的 REST 端点与 WebSocket 消息格式设计**：见新增文档 `docs/10_AndroidClient/PC_Android_接口设计.md`，本文档只确定架构层面的模式选择，不在此处展开接口细节。

## 3. 通信方式设计

> **本节只讲选型理由与消息类别。** 具体的 REST 端点、路径、请求/响应字段与
> WebSocket 消息格式，唯一来源是 [`../10_AndroidClient/PC_Android_接口设计.md`](../10_AndroidClient/PC_Android_接口设计.md)；
> 那份与 `src/gateway/server.py` 对照维护，本节不再复制一份端点表。

### 3.1 客户端侧通信能力对照

| 通信方式 | PC 上位机（PyQt6） | Android 客户端 | 说明 |
| --- | --- | --- | --- |
| UART（直接串口） | 支持 | 通常不支持（受限于移动设备无原生串口） | PC 场景的主要调试通道 |
| USB（转串口/CDC） | 支持 | 支持（需 USB OTG + 权限） | 两端均可用，但 Android 端需额外处理权限与 OTG 兼容性 |
| TCP/IP（WiFi） | 支持 | 支持 | 面向具备网络能力的设备（如 ESP32），两端能力对等，是多端共存的首选通道 |
| 蓝牙（经典蓝牙/BLE） | 支持（经典蓝牙为主） | 支持（以 BLE 为主） | 两端底层蓝牙协议栈不同，需分别实现，但对上层暴露统一的收发接口 |

### 3.2 通信层设计原则（延续并细化 `Communication_Design.md`）

1. **统一抽象接口，按平台分别实现**：无论是 PC 端的 UART 实现，还是 Android 端的 BLE 实现，都必须实现同一套抽象通信接口（连接、断开、发送、接收、状态回调），Protocol Layer 与 Application Layer 不感知具体是哪个平台的哪种通信方式。
2. **优先选择两端能力对等的通信方式作为"多端协同"首选**：在需要 PC 与 Android 交互同一设备的场景中，优先使用 TCP/IP（WiFi）而非 UART/经典蓝牙，因为后两者在 Android 侧支持成本更高、限制更多。
3. **允许"部分设备只服务单一客户端类型"**：不强制要求每种设备都必须同时支持 PC 与 Android 接入。例如通过 UART 直连的设备，可以设计为"仅 PC 可直接调试，Android 端通过网关间接访问"（对应第 2.2 节的网关模式）。
4. **连接状态与设备占用状态需可观测**：当同一设备可能被多个客户端（直连或经网关）访问时，Application Layer 需要能够感知"设备当前是否已被占用/由谁占用"，为后续的多客户端协同或互斥访问策略预留信息基础（具体策略在功能需求明确后再设计，本文档不做强绑定）。

## 4. 软件分层设计

在 `System_Architecture.md` 原有五层基础上，多端场景下的分层关系调整为如下结构（以概念层次表达，不涉及具体代码组织）：

```
┌───────────────────────────────────────────────────────────┐
│  Presentation Layer（原 UI Layer 的多端展开）                 │
│  ├─ PC Presentation（PyQt6）                                 │
│  └─ Android Presentation（Android UI）                        │
│  职责：交互与展示，平台相关，彼此独立实现                          │
├───────────────────────────────────────────────────────────┤
│  Application Layer（业务领域层，概念统一）                       │
│  职责：设备管理、数据处理、任务调度、多端能力的统一语义定义           │
├───────────────────────────────────────────────────────────┤
│  Protocol Layer（协议契约层，多端共享同一规范）                   │
│  职责：帧编解码、校验，定义在 Protocol_Design.md，是多端的公共基础  │
├───────────────────────────────────────────────────────────┤
│  Communication Layer（通信适配层，按平台/介质分别实现）             │
│  职责：屏蔽 UART/USB/TCP/蓝牙/BLE 等具体介质差异                  │
├───────────────────────────────────────────────────────────┤
│  Hardware Device Layer（设备层，协议兼容即可替换）                │
│  职责：实际 MCU 设备，对上层架构透明，可按协议规范替换任意型号        │
└───────────────────────────────────────────────────────────┘
```

**与原五层架构的关系说明：**

- 仅 **UI Layer** 演化为 **Presentation Layer**，并按客户端平台拆分为多个并列的实现；其余四层（Application / Protocol / Communication / Hardware Device）的职责定义与 `System_Architecture.md` 完全一致，未发生变化
- Application Layer **不因客户端增多而拆分成多份互不相关的实现**，而是要求"语义统一"：即无论 PC 还是 Android，"连接设备""下发指令""订阅数据"这些能力在概念上必须是同一套模型，具体用 Python 还是 Kotlin 实现是平台工程细节，不是架构分裂的理由
- Protocol Layer 是整个多端架构中**唯一不允许因客户端而分叉**的一层：它是保证"PC 和 Android 说同一种语言"的关键契约层

## 5. 数据流设计

### 5.1 单客户端数据流（与原架构一致）

```
下行（指令下发）：
Presentation Layer → Application Layer → Protocol Layer → Communication Layer → Hardware Device

上行（数据上报）：
Hardware Device → Communication Layer → Protocol Layer → Application Layer → Presentation Layer
```

该数据流对 PC 与 Android 两端分别成立，互不干扰。

### 5.2 多客户端并存时的数据流（预留设计，非当前必须实现）

当采用网关模式（第 2.2 节）、或未来出现"同一设备被多客户端观察"的需求时，数据流在 Application Layer 与 Hardware Device 之间需要增加**一对多的分发环节**：

```
Hardware Device
      │  （单一物理连接，由网关或某一客户端持有）
      ▼
Communication Layer（连接持有方）
      │
      ▼
Protocol Layer（解析为结构化数据）
      │
      ▼
   数据分发点（Fan-out）
      │
      ├──> PC 客户端 Application Layer → PC Presentation Layer
      └──> Android 客户端 Application Layer → Android Presentation Layer
```

**设计原则：**

- 物理连接（Communication Layer 实际持有的连接）应保持**单一持有者**，避免多个客户端同时抢占同一 UART/BLE 连接导致的冲突
- "多客户端看到同一份数据"应通过**上层数据分发**实现，而不是让多个客户端各自尝试建立到设备的物理连接
- 指令下发方向（下行）需要考虑**指令来源仲裁**：当 PC 与 Android 都可能向同一设备下发指令时，需要有明确的处理策略（如后到覆盖、需人工确认、按客户端优先级等），具体策略留待功能需求明确后在专门文档中设计，本文档仅标注这是一个必须被架构预留、但当前不做强约束的问题点

## 6. 后续扩展方案

### 6.1 客户端维度扩展

- 当前设计已将 UI 层拆分为 Presentation Layer 的多平台实现，未来如需新增 Web 端、桌面端（其他 GUI 框架）等客户端形态，只需新增一个 Presentation 实现并复用同一套 Application Layer 语义模型与 Protocol Layer 契约，无需改动 Communication Layer 与 Hardware Device Layer
- Android 客户端本身也可以分阶段扩展：第一阶段仅做"状态查看"（只读），第二阶段再开放"指令下发"（读写），降低移动端的实现与测试复杂度

### 6.2 设备维度扩展

- 沿用 `docs/03_Communication/Protocol_Design.md` 的通用帧协议作为设备替换的基础契约：任何新增的 MCU 设备，只要能够按该协议规范收发帧，即可接入系统而无需改动上层架构
- 设备 ID 字段（协议规范已定义）为多设备、多类型设备并存提供了基础，未来可扩展为"设备类型 + 设备实例"的二级寻址方式（具体设计留待多设备管理需求明确后再展开）

### 6.3 网关模式的引入时机（已于 2026-08-14 触发，见第 2.3 节）

- 原定的触发条件是以下任一情况出现：
  - 明确需要 PC 与 Android **同时**监控/操作同一台设备
  - 设备数量增多，需要一个常驻服务统一管理设备连接的生命周期，而非依赖某个客户端保持在线
  - 需要将设备数据长期记录、跨客户端共享历史数据（网关可承担数据持久化职责）
- **第一条已经成立**：本项目确定 Android 要与 PC 同时使用（PC 做主监控，Android 做移动端查看），因此已按第 2.3 节确定的"PC 内置网关"方式启动网关模式，不再是"预留但不实现"的状态
- 采用的是**特化形式**（PC 自己兼任网关），不是引入独立第三方网关进程，因此没有触发"设备数量增多需要常驻服务"这一条对应的额外部署复杂度

### 6.4 协议版本演进

- 多端共存后，协议的向后兼容性要求会高于单客户端场景（PC 端与 Android 端的升级节奏可能不一致），建议在协议成熟后尽早引入版本标识字段（`Protocol_Design.md` 中已列为后续工作项），避免出现"新版 PC 端与旧版 Android 端协议不兼容"的问题

### 6.5 安全与鉴权（预留）

- 当通信介质从本地直连（UART/USB）扩展到网络介质（TCP/WiFi），尤其是引入网关模式后，需要考虑设备访问的身份鉴权与传输安全，当前阶段不做具体机制设计，仅在架构上标注为"网关模式配套引入"的必需能力
