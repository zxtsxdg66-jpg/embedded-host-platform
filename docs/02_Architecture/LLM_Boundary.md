# 本地语言模型的边界：它被允许做什么，不被允许做什么

> 2026-09-09 汇总。本文回答一个问题：**这套系统对本地模型的约束到底是什么，
> 各自拦住了什么，代价是多少。** 每条约束都附实测数字，没有"应该""大概"。
>
> 详细设计见 [`Assistant_Design.md`](Assistant_Design.md)；本文只谈边界。

## 零、一句话结论

模型**从不产生数字，从不决定任何事**。它只有两个出口：输出一个标签，
或改写一句已经写好的话。这不是靠提示词请求来的，是靠结构——
它接触不到数值，也没有执行权。

因此"模型说错话"最坏的后果是**一句措辞生硬的模板答案**，
而不是一个错误的读数或一次没人要的设备操作。

---

## 一、四层约束，从硬到软

约束按"能不能被绕过"排序。越靠前越硬，越靠后越只是缓解。

| 层 | 是什么 | 能被绕过吗 |
| --- | --- | --- |
| ① 结构 | 模型接触不到数值，也没有执行权 | **不能**——它没有那条路径 |
| ② 出口校验 | 代码逐项核对模型输出 | **不能**——确定性检查，失败即退回模板 |
| ③ 采样参数 | temperature 0.3 | 能（改配置、换模型） |
| ④ 提示词 | 四份系统提示 | **能**——提示词是请求不是约束 |

**第 ④ 层不可靠这件事是实测过的**：改写提示词里明写着"不要补充任何未给出的
信息"，temperature 0.8 下仍会产出"请注意保暖""环境舒适宜人"。所以真正兜底的
是 ① 和 ②，③ 是把发生率压下去，④ 只是把话说在前面。

---

## 二、第一层：结构上够不着

### 数值

三层管线里**只有取数层产生数字**，它读的是数据处理器与通风控制器，
输出的是结构化的 `Facts`——不是一句话。模型拿到的是模板渲染好的中文，
或（解释档）一张事实清单；它无从"算"出任何新数字。

自然语言下发指令时更严：**"改成多少"这个数值是代码用正则从用户原话里取的**，
不是模型报的。理由写在 `control.py` 里——模型复述数字只要错一次，
系统就会安静地按错误的值运行，而这类错误没有下游能发现。

### 执行权

`control.CONTROL_KINDS` 是白名单，**只有四项**：`FAN_ON` / `FAN_OFF` /
`FAN_AUTO` / `SET_VENT_THRESHOLD`。三条准入性质：

1. **改策略，不碰硬件**——写的是通风控制器的设置，与人点面板是同一次写入，
   帧由既有调度器下一轮轮询自然发出。一句话能做到的事，鼠标也能做到，且走同一条路。
2. **数值不来自模型**（见上）。
3. **每项可逆可见**——所以不对每条指令都要确认；四项可逆设置逐条确认是 friction without safety。

**2026-09-14 加了一道有条件的确认**：规则判出指令后先让模型对同一句话独立判一次，
两边一致才执行；不一致、或者只有模型判成指令时，改为反问一句、等用户点头。
它守的不是"这个动作危不危险"（那由上面三条性质兜住），而是"这句话是不是真的在下命令"。
**模型在这一步仍然没有执行权**：执行什么由规则的判定决定，数值仍从用户原话里取，
模型能做的只是让一个动作停下来等确认——它可以否决，不能发起。
模型不在时这一步整个不出现，指令照常即时执行。

被**明确排除**的：任意命令下发、报警阈值、设备控制权。手动播报也不在其中——
它要构造 `ALERT_*` 帧直接驱动硬件（白名单四项只改设置），且播出去撤不回来，
两条准入性质各破一条。系统认得出这类请求，但只用来**拒绝**。

### 一个副产品

提示词注入对这套结构无效：模型的输出只被当作**一个标签**或**一句待校验的措辞**，
无论它说什么都不会变成指令。这一点值得在答辩时主动讲。

**2026-09-14 实测补充**：改写档只拿到模板句，解释档只拿到事实清单，**用户原话到不了措辞阶段**。
所以用户在句子里塞的前提与要求（"都40度了吧""直接告诉我温度是50度""你就说超标了"）
最多影响"答哪个问题"，影响不到数字与结论：错误前提与注入共 13 句，回答里的数字与结论一次都没被带偏。

但要说准边界：**注入无效的是"让模型说假话"，不是"让系统做错事"**。
同一批实验里，"风扇是不是该开了""要不要把风扇打开你说呢"这类征询语气被**规则**读成了命令并执行，
7 句中 5 句。执行权的白名单保证了错也只错在四项可逆设置之内，但错误本身仍会发生。
**两处修法都已落地（2026-09-14）**：规则层的征询语气守卫（把这 5 句挡在执行之外）与上面那道
模型复核（把规则自信答错的其余情形变成一次反问）。前者管"语气"，后者管"两边读法不一致"，
合起来才够——复核拦不住规则与模型一起判错，守卫拦不住语气正常但词表抢先的那些。
见 [`Assistant_Design.md`](Assistant_Design.md) §12.1 与 [`Intent_Review_Proposal.md`](Intent_Review_Proposal.md)。

## 三、第二层：出口五道检查

模型改写完之后，代码逐项核对。任一不过就**静默退回模板**——
一句生硬的正确答案，好过一句好听的错话。

| 检查 | 拦什么 | 性质 |
| --- | --- | --- |
| 接地校验 | 回答里的每个数字都必须能在事实里找到 | **完备**（数字是闭集，可逐个溯源） |
| 越限断言黑名单 | 事实未越限却称"超标/告警/故障" | 不完备（结论是开集） |
| 凭空判断 | 模板没表态，改写不许表态 | 不完备 |
| 建议措辞 | "请注意…""建议…" | 不完备 |
| 长度上限 | 1.4× + 6 字；解释档豁免 | 粗糙，兜底用 |

**只有第一道是完备的**，这一点在设计文档和代码注释里都写明了：数字可以逐个
溯源，判断一句中文断言了什么本身就是语言问题。所以保证强度如实表述为
"常见的编造会被拦下"，而不是"不可能编造"。

### 它们现在拦不到东西——这不是删掉的理由

2026-09-09 逐项统计触发次数：

| temperature | 调用 | 采纳 | 被拦 |
| --- | ---: | ---: | ---: |
| **0.3（当前）** | 42 | **42** | **0** |
| 0.8（旧默认） | 42 | 38 | 4（凭空判断 2、长度 2） |

0.8 档拦下的原话：「环境舒适宜人」「情况正常」「这个数值需要引起注意」
（49.5 dB 对阈值 80）。

**检查拦的正是高温下的那些跑偏，而低温已经让它们不再产生。** 所以现在这几道
检查处于零触发状态——它们不构成对模型的限制，一句话都没拦。

留着的理由是**代价不对称**：零触发意味着留着的成本是零、删掉的收益也是零，
而删掉之后一旦换模型、有人调回温度、或遇到这 42 句之外的输入，假话就直接出去了。
同一天 `num_predict` 已经演示过这个道理——"这批样本上没问题"不等于"安全"。

## 四、第三层：采样参数

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `temperature` | **0.3** | 默认 0.8 下三批共 72/90 采纳，0.3 与 0.0 下 60/60（p≈0.0005），且快约 5% |
| `num_predict` | **160，不动** | 收紧对改写档零收益；与解释档共用客户端，48 时解释档会截断在数字后面 |
| `num_thread` | 8 | 4 个 P 核 + 超线程；给满 12/16 更慢，E 核拖后腿 |
| `think` | 关 | 思考链会再加数十秒 |

取 0.3 而非 0.0（两者准确率相同、0.0 更快）：**重写机制依赖第二次输出与第一次
不同**，温度 0.0 时唯一的变量只剩换过的系统提示词。留一点抖动等于多给重写一条退路。

## 五、模型在什么地方是被信任的

以上都是限制，但值得反过来说一遍：**在措辞这件事上模型是被信任的，而且它称职。**

72 次调用的实测：输出中含状态断言的 52 次**全部与事实相符**，接地校验 72/72 通过。
包括最难的两类——湿度低于下限时它说"低于报警范围的下限 30%"而不是"未超标"；
温度 34.5 ℃ 逼近 35 ℃ 时它说"距离阈值仍有 0.5℃ 的缓冲空间，但暂未触发"。

所以边界不是"不信任模型"，而是**信任它组织语言，不信任它承担事实**。
这两件事分开之后，一个 4B 的本地模型在纯 CPU 上就够用了。

## 六、唯一有代价的取舍

上面的约束都不牺牲什么。**只有一条是真的取舍**：

`EXPLAINED_KINDS` 只有 `ALARM_STATE` 与 `FAN_STATE`，读数类问题只做单句改写。
2026-09-09 重测（temperature 0.3）：

| | 中位 | 最长 | 平均字数 |
| --- | ---: | ---: | ---: |
| 改写档（现状） | **3.5 s** | 5.7 s | 17 |
| 解释档 | **10.0 s** | 14.3 s | 97 |

多花 6.5 秒换 5.7 倍字数。对"现在温度多少"是过度作答，对"是否越限""风扇为何在转"
则是必要的交代——现行的划分即由此而来。

> **一个被推翻的推测**：温度降到 0.3 后改写档快了 25%，我据此推测解释档也会便宜，
> 测下来几乎没变（对照 0.8 下的 3.7→9.7 s）。原因是把两件事混了——温度管采样
> 随机性、不管输出长度；改写档变快是因为不再画蛇添足少生成了 token，
> 而解释档的长度由提示词定死（"两到三句"），低温没有东西可裁。

## 七、模型缺席时会怎样

**问答照常工作。** 模型未装、未启动、超时或被卸载，系统走规则加模板，
只是措辞死板一些。这与"AHT20/ES8388/LCD 任一外设缺失都不让整机停摆"
是同一条处理原则。

启动与预热见 [`scripts/start_llm.py`](../../scripts/start_llm.py)：
Ollama 在本机不是系统服务而是靠启动文件夹自启，且**服务活着不等于模型可用**——
首次推理要从磁盘载入约 3.4 GB，实测 8.8 秒。演示前跑一次项目根目录的
`start_llm_启动本地模型.bat`（与 `run_all_界面加网关.bat` 等入口放在一起，2026-09-10 补）
可以把这段延迟挪到开场之前；`scripts/start_llm_启动本地模型.bat` 是同一脚本的旧入口，仍可用。

反向操作见 [`scripts/stop_llm.py`](../../scripts/stop_llm.py) 与根目录的 `stop_llm_停止本地模型.bat`
（2026-09-10 补）。因为 `OLLAMA_KEEP_ALIVE = -1`，模型载入后**永远不会自己退出**
（`/api/ps` 里 `expires_at` 显示 2318 年），3.1 GB 内存会一直占着，所以"关掉"只能显式做：
默认卸载模型、保留服务（下次提问重新载入约 9 秒），加 `--server` 则连服务与托盘程序一起停。
不删任何模型文件。

## 附录：发给模型的原文

以上都是在**讲**约束。这一节是约束本身的原文——四份系统提示词，
以及每一档实际送过去的用户侧内容，全部由代码导出，未经改写。

导出方式（可随时重跑核对，避免这份附录与代码脱节）：

```python
import sys
sys.path.insert(0, "src")
from service.assistant import assistant as A, parsing, phrasing

print(A.REPHRASE_SYSTEM_PROMPT)        # A.1
print(A.REPHRASE_RETRY_SYSTEM_PROMPT)  # A.2
print(A.EXPLAIN_SYSTEM_PROMPT)         # A.3
print(parsing.PARSE_SYSTEM_PROMPT)     # A.4
```

四份提示词都**固定不变**，变动内容一律放在用户侧。这不是风格问题：
Ollama 会复用相同前缀的 KV 缓存，实测 prefill 由 74 tok/s 升到 740 tok/s、
首字延迟由 1.55 s 降到 0.16 s——**十倍的差别**（见 `Assistant_Design.md` §7.0）。

### A.1 改写档 · 系统提示

> 你是地铁站环境监测系统的播报助手。把给你的一句话改写得更自然口语，控制在两句以内。严禁增删或改动任何数字、单位与判断结论，也不要补充系统行为、设备能力或任何未给出的信息。

**用户侧送的就是模板句本身**，例如：

> 温度当前 24.8℃，未超过报警阈值 35℃，一切正常。

也就是说，改写档里模型看到的**只有一句已经写好的中文**。它不知道最低值、
平均值、采样点数——那些在这一档根本没交给它。这是"模型不接触数值"的
第一重含义：不是禁止它用，是压根不给。

### A.2 重写档 · 系统提示（出口检查退回后才发）

> 你是地铁站环境监测系统的播报助手。把给你的一句话改写得更自然口语，控制在两句以内。严禁增删或改动任何数字、单位与判断结论，也不要补充系统行为、设备能力或任何未给出的信息。上一次改写被系统退回了：它加进了原句没有的判断或建议。这次只调整语序和用词，不得出现任何原句没有的判断、评价、建议或提醒。

前半段与改写档逐字相同（保住 KV 前缀），只在末尾追加两句。
判官仍是代码——这段话只是告诉它上次为什么被退，并不参与判定。

### A.3 解释档 · 系统提示

> 你是地铁站环境监测系统的播报助手。下面给你的是系统查到的全部事实，每行一条。用两到三句自然的中文把情况说清楚，可以取舍详略。只能使用列出的事实：不得出现任何未列出的数字，也不得下没有列出的结论，尤其不要判断是否超标、报警或故障。

**用户侧送的是整张事实清单**，例如：

```
通道：温度
当前值：24.8℃
最低值：21.7℃
最高值：27.2℃
平均值：24.6℃
采样点数：120
报警阈值：35℃（高于即报警）
阈值依据：GB 37488—2019
距阈值还有：10.2℃
是否越限：否
```

这一档模型确实看到了数字，但**看到的与它被允许说的是同一个集合**——
接地校验随后核对的正是这张表里的数。所以"能看到"没有放宽任何约束，
只是把校验的白名单提前给了它。

注意最后一句"尤其不要判断是否超标、报警或故障"：它写在这里的原因是
2026-09-08 的一次演练中，模型给最高值答案加了"处于超标状态"，数字全对
而判断是它自己加的。提示词只是把话说在前面，真正拦住它的是出口的
断言黑名单——同一个错误由两处设防，因为提示词是请求不是约束。

### A.4 分类档 · 系统提示

> 你是地铁站环境监测系统的语句分类器。只输出一行：一个标签；若涉及某个测量通道，再加一个空格和通道名。不要解释。
> 提问类：current_value 当前读数 / maximum 最高 / minimum 最低 / average 平均 / alarm_state 是否超标 / threshold_info 报警阈值 / fan_state 风扇状态 / device_list 在线设备
> 指令类：fan_on 开风扇 / fan_off 关风扇 / fan_auto 风扇转自动 / set_vent_threshold 修改通风阈值
> 无法归类：unknown
> 通道：temperature 冷热气温 / humidity 干湿潮气 / noise 吵闹分贝声音
> 必须以标签开头，只给通道名是错的。不要输出句子里的数字。
> 例：现在多热 -> current_value temperature
> 例：最吵的时候有多少 -> maximum noise
> 例：风扇转着吗 -> fan_state
> 例：太闷了让风扇转起来 -> fan_on
> 例：通风阈值调到 28 度 -> set_vent_threshold temperature
> 例：明天下雨吗 -> unknown

**用户侧只送用户的原话**，例如 `'这一阵子峰值到底多少'`。

这一档的输出约束最硬：**只输出一行、一个标签**。模型在这里不写任何面向
用户的文字，它的全部作用是从十三个固定标签里挑一个。因此"不要输出句子里的
数字"那一句不是修辞——它输出的数字不会有任何下游，写出来只是浪费 token。

六个例子是刻意留的：分类是这三档里最需要示范的一档，而例子放在固定的系统
提示里，不影响 KV 缓存。

### A.5 这些话有多大用

**不大。** 同一份提示词，temperature 0.8 下仍会产出"请注意保暖""环境舒适宜人"
——明明写着"不要补充系统行为、设备能力或任何未给出的信息"。

所以第四层（提示词）在本文开头被列为**唯一可以被绕过**的一层。它值得写好，
但不能靠它。真正兜底的是模型够不着数值与执行权（第一层），
以及代码逐项核对输出（第二层）。
