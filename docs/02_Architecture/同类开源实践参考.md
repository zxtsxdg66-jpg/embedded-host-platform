## 一、与本项目结构直接同构的三条

### 1. Snips NLU：确定性解析器在前，概率解析器在后

`SnipsNLUEngine` 按顺序调用一串 `IntentParser`，取第一个有结果的：默认是
`DeterministicIntentParser`（正则，由训练语料展开成模式，保证训练集上 F1 = 1.0）
在前，`ProbabilisticIntentParser`（逻辑回归 + CRF）在后。官方文档给的理由是
"先用保守、精度高的解析器处理简单模式，再回落到能处理没见过的说法的机器学习解析器"。

**对本项目的意义**：这就是 `intent.recognise()` 在前、模型分类兜底的同一套调度顺序，
而且出自一个真正出货过的端侧产品（Snips Voice Platform 整套离线跑在树莓派 3 上，
论文见 arXiv 1805.10190）。第 4 章"规则优先"的写法因此不是本文的临时选择。

**差别**：Snips 的确定性解析器由训练语料自动展开成正则，本项目的规则是手写词表——
所以本项目会有"词表抢先"那一类错判（`Assistant_Design.md` §12.1 已登记），
它那种展开方式不会。**这是一处真实可改进的方向**，但改动面大，维护期不做。

- https://snips-nlu.readthedocs.io/en/latest/api.html
- https://arxiv.org/pdf/1805.10190

### 2. Rasa：`FallbackClassifier` 的两个阈值，与 Two-Stage Fallback

Rasa 的回落判定用两个阈值：`threshold`（最高意图的置信度下限，示例配 0.7）与
**`ambiguity_threshold`（前两名置信度之差的下限，示例配 0.1）**——差得太少即判为"歧义"。
配合 `RulePolicy` 的 Two-Stage Fallback：先请用户换种说法，换完仍然歧义，
再给出一张候选意图清单让用户挑，最后才转人工。

**对本项目的意义**：这是本次做的确认机制**最成熟的同类形态**，可以直接拿来对照：

| | Rasa | 本项目 |
| --- | --- | --- |
| 歧义信号 | 同一个分类器前两名的置信度之差 | **两个独立判定器（规则 / 模型）是否一致** |
| 不确定时 | 请用户换个说法 → 给候选清单 | 直接反问"你是想让我……吗" |
| 阈值 | 连续可调 | 二值，没有"多不一致"这个量 |

本项目没有连续置信度可用（规则是词表命中，非 0 即 1），所以用"两个来源是否一致"
代替"一个来源有多确定"。**代价是拿不到 Rasa 那种可调的松紧**：现在只能全拦或全不拦，
留出题库上误报约 8/148 这个数就没有旋钮可调。若阶段二（复核问题类）要做，
这是必须先想清楚的一处。

- https://legacy-docs-oss.rasa.com/docs/rasa/fallback-handoff/
- https://rasa.com/docs/rasa/reference/rasa/core/policies/two_stage_fallback/

### 3. Home Assistant Assist："优先本地处理" + 暴露实体白名单

Assist 的会话代理有一个 **Prefer handling commands locally** 开关：打开后先走内置意图引擎，
"关掉厨房的灯"这类命令**根本不会碰到 LLM**，只有内置引擎认不出的才转交给 LLM 代理。
另一侧是 **exposed entities**：LLM 只能看见、只能操作被显式暴露的实体。

**对本项目的意义**：两条都与本项目现有设计一一对应——前者对应规则优先（本项目更进一步，
指令方向上还让模型复核一次），后者对应 `control.CONTROL_KINDS` 四项白名单
（`LLM_Boundary.md` 第一层）。**白名单不是本文发明的谨慎，是这一类系统的通行做法**，
这一点值得在答辩时说。

- https://www.home-assistant.io/voice_control/assist_create_open_ai_personality/
- https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/

## 二、可借的机制，但本项目暂不采用

### 4. OVOS（Mycroft 后继）：按置信度分档的意图流水线

OVOS 把多个意图匹配器（Adapt 关键词、Padatious 例句、近期的 Model2Vec 语义匹配）
排成一条流水线，每个匹配器拆成 high / medium / low 三档
（默认 `conf_high: 0.7`、`conf_medium: 0.5`、`conf_low: 0.15`），
**按档位交错排列**而不是按匹配器排列——所有匹配器的 high 档先跑，再跑 medium 档。
社区文档里明确记着踩过的坑：流水线是 first-match-wins，
语义匹配器的高档若排在确定性引擎的高档之前，它会抢走本该被精确解析的句子。

**对本项目的意义**：这正是"规则与模型谁先"的一般化形态，比本项目的二值裁决更细。
本项目暂不采用，因为**规则侧给不出置信度**：词表命中是布尔的，分不出高低档。
真要往这个方向走，得先让规则输出一个分数（例如命中词的长度、是否整句匹配），
那是比本次改动大得多的一次重构。记在这里，等训练阶段若要提升模型分类准确率时一并考虑。

- https://tigregotico.pt/ovos-technical-manual/debugging-intent-matching/
- https://github.com/OpenVoiceOS/ovos-adapt-pipeline-plugin

### 5. LangGraph / LangChain 的 human-in-the-loop 工具批准

`interrupt()` 在工具调用前挂起图、把决定权交回调用方，人可以 approve / edit / reject / respond，
并且支持按工具参数决定要不要拦（predicate 收到 `ToolCallRequest`，返回 True 才中断）。

**对本项目的意义**：**方向恰好相反，这一点值得写进论文**。那一套批准的是
"模型发起的动作"——模型是动作的提出者，人是审核者；本项目批准的是
"规则发起、模型有异议的动作"——模型在这里是审核者，而且**没有发起权**。
本次实现里"规则认不出、只有模型判成指令 → 必须反问"那一行，就是不肯给它发起权的落点。
按参数决定是否拦截这一点倒是可借：本项目现在对四项指令一视同仁地复核，
若以后白名单变宽（例如真的开放报警阈值），应当按动作可逆与否分档处理。

- https://docs.langchain.com/oss/python/langchain/human-in-the-loop

## 三、评测方向上的一条（**建议引用**）

### 6. 智能家居语音助手的"该不该拒答"基准（arXiv 2512.10257）

面向中文智能家居场景的**首个开源查询拒识基准**：11,913 条人工标注的文本—语音对，
分 13 类（闲聊、非人声、ASR 错误、指代不清、有效指令等）。方法侧是 Qwen-2.5-3B 微调 +
个性化历史对话 + RAG 纠正历史误拒，准确率 96.75%；零样本 LLM 约 68~75%。
论文明确指出关键词匹配与简单语义规则在复杂家庭交互下明显落后。

**对本项目的意义**：本项目的"范围外应当拒绝"正是这件事，而留出题库里范围外只有 **14 句**，
其中规则误接 5 句（`baseline/README.md`）——样本太少，结论只能当量级参考。
这份基准给出了两样本项目缺的东西：**一个成体系的拒识分类**（13 类，本项目实际只区分了
"范围内/范围外"），以及**一个可比的数量级**。若后续要把"范围外拒绝"做成一项正经指标，
应当按它的分类重建题库，而不是继续在 14 句上打转。

- https://arxiv.org/html/2512.10257v1

## 四、同域但取向相反的一个（答辩素材）

### 7. xiaozhi-esp32：把模型放进控制链路

`78/xiaozhi-esp32`，基于 ESP32-S3 的开源 AI 语音助手，流式 ASR → LLM → TTS，
**通过 MCP（Model Context Protocol）让模型直接调用设备工具**实现双向控制；
端侧负责唤醒与音频流，重活在服务端，也支持接 Ollama 等本地推理。

**对本项目的意义**：它是同一时期、同一硬件量级、同一语言场景下的主流做法，
而**取向与本文相反**——它让模型成为动作的发起者，本文让模型够不着执行权
（`LLM_Boundary.md` 第一层）。这不是谁对谁错：它要的是开放式的能力覆盖，
本文要的是"错了也不会动错设备"。**答辩若被问"为什么不直接用大模型控制设备"，
这就是最具体的回答对象**：可以承认那条路能力更宽，再说明本文为什么不走。

- https://github.com/78/xiaozhi-esp32
