# 本地模型训练（training/）

> 2026-09-18 建立。此前"训练代码放哪里"是维护期三个开放问题之一
> （见 `docs/05_Test/Project_Status_Context.md`「维护期的开放问题」）。
> 本文件是那个问题的答案，以及配套的产物管理约定。
>
> **目前只有这份说明，还没有代码。** 训练工作启动时按下面的约定往里放。

## 为什么是顶级目录，而不是 `src/` 下的一个包

与 `firmware/stm32f407/` 和 `android/` 同一个理由，也是 `CLAUDE.md` 已经为固件写过的那条：
**它是一套独立的工具链，不与 `src/` 共用构建与测试流程。**

具体到训练：

- **依赖不同且重**。训练要装的东西（PyTorch 一类）与上位机平台毫无关系，
  而 `pyproject.toml` 现在声明的是一个能在普通机器上 `pip install` 起来的桌面程序。
  把训练依赖混进去，等于让每个只想跑界面的人先下几个 GB。
- **不进 `pytest` 与 `mypy src` 的范围**。三项质量检查是每个任务的收尾条件，
  一个跑一次要几小时、还需要 GPU 的流程不该挂在上面。
- **生命周期不同**。平台是长期运行的；训练是一次性的离线作业，跑完留下的是权重，
  不是一个会被 import 的模块。

**尤其不能放进 `src/llm/`。** 那是**运行期适配层**——按 `CLAUDE.md`，它只能由
`application`/`scripts` 创建、且不得被 `service` import，因为它接的是一个外部服务。
训练与运行期无关，塞进去会让一个本就受约束的适配层同时承担两种生命周期，
而那两种生命周期的约束正好互相矛盾。

## 依赖方向：单向，且只有一个方向

```
training/  ──读──>  docs/05_Test/baseline/   （题库与基线，看，不改）
training/  ──产出─>  训练好的模型（由 Ollama 加载）
                          ↑
                    src/llm/ 运行期连上去

src/  ──/──>  training/      从不 import
training/  ──/──>  src/      也不 import
```

**两边都不 import 对方。** 训练的产出是一个模型，交接面是 Ollama 的模型名，
不是 Python 符号。这条保证了训练怎么折腾都伤不到已经稳定的平台——
维护期的那条规矩（改一处就要问它是否值得让已稳定的部分重新承担风险）在这里是免费的。

需要复用评测逻辑时，**照抄而不是 import**：`scripts/assistant_benchmark.py` 是运行期
工具，它假定有一个活着的 `ApplicationRuntime`。

## 目录约定

| 路径 | 放什么 | 入库？ |
| --- | --- | --- |
| `training/README.md` | 本文件 | 是 |
| `training/*.py`、`*.ipynb` 等 | 训练与数据构造脚本 | 是 |
| `training/datasets/` | 训练集、评测集 | **否**（见下） |
| `training/runs/<日期>_<模型>_<轮次>/` | 每轮训练的权重、日志、配置快照 | **否** |

`datasets/` 与 `runs/` 已写进 `.gitignore`。理由与 `data/`、`exports/` 一样：
它们是数据产物，体量大、可重新生成，而且训练集里可能含真人问过的原话
（`logs/assistant/` 同理，那份也不入库）。

**`runs/` 一轮一个目录，不要覆盖。** 这是"训练产物怎么管"那个开放问题的落点：
第二轮把第一轮覆盖掉，就再也没有可比的基线了——而能不能比较，正是这件事唯一的判据。
目录名带日期与模型名，配置快照跟权重放在一起，否则半个月后没人说得清那一版是怎么训出来的。

## 怎么判断"训练有没有变好"

抓手是现成的，不必新造：

- **评测脚本**：`scripts/assistant_benchmark.py`
- **题库**：87 句拟合题库（脚本内 `BANK`）与 148 句留出题库
  （`docs/05_Test/baseline/heldout_set.json`）
- **基线**：`docs/05_Test/baseline/问答基线_20260910_qwen3.5-4b.txt`
  —— 84/87 = 96.6%，规则命中 87/87，改写采纳 49/87，中位 4.9 s。
  归档规则见同目录 `README.md`。

**两个题库必须都看，而且分开报。** 87 句那套是照着词表调出来的，
规则全部命中、模型分类一次都没被触发过，它的 96.6% 只说明规则没退化；
留出题库那 82.8% 才是泛化能力的量级参考。2026-09-14 正是搞混这两者才发现问题的。

**换模型之后有两件事必须重测**（`docs/02_Architecture/LLM_Boundary.md`）：
四层约束里①结构与②出口校验与模型无关，**③采样温度与④提示词与模型强相关**——
温度 0.3 这个取值、以及出口检查的触发率，都是在 qwen3.5:4b 上实测出来的结论。

## 不变的那条线

无论训练成什么样，这条不换：**数字永远由检索层产出，模型不得直接说出任何读数、
阈值或统计量。** 接地校验（`numbers_are_grounded`）与"控制指令的数值由代码从用户
原话正则提取"两条机制都建立在它上面，论文第 4 章的论证也是。
训练能改进的是模型对问题的理解与措辞的自然度，不是让它获得说出数字的资格。
